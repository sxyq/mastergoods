## 一、项目用途

**智慧记（Master-Goods / zhihuiji）** 是一套面向小微零售与批发商户的**进销存 + 财务 + AI 助手**多端系统，采用单一仓库承载全部端与工程资产。

### 1.1 业务能力

面向店主/店员的核心闭环：

- **档案**：商品（含价格等级、单位、分类、供应商关系）、客户、供应商
- **单据**：销售订单、采购订单、采购收货、采购退货、销售退货、收付款单
- **财务**：财务流水、账户与转账、资金与单据勾稽、应收应付
- **库存**：库存流水、库存快照、月度统计、安全库存预警
- **报表**：销售汇总、按商品、按客户、应收、库存报表
- **同步**：多端离线变更上传/拉取、变更日志、墓碑、冲突合并
- **AI Agent**：对话式助手（工具编排、上下文检查点、记忆、草稿确认、运行审计）
- **管理后台**：独立管理员端（用户、审计、配置、导出、留存策略、演示数据灌入）

### 1.3 架构特征

- **分层**：`api`（controller / dto / common）→ `application`（service）→ `domain`（entity）→ `infrastructure`（repository / config / security / storage / ai）
- **多租户**：无数据库 RLS，隔离在应用层实现——所有 Repository `@Query` 带 `ownerUserId` 参数 + `CurrentOwnerService.requireCurrentOwnerUserId()`
- **API 版本**：v1 与 v2 并行（v2 为演进版本，共 26 组控制器）
- **ID 策略**：`IdGenerator` 基于 `SecureRandom` 生成 63 位正整数（非雪花算法，随机不可排序）

### 7.1 P1（3 条）

#### ISSUE-001　销售订单核心金额使用 double（数据 / 精度）

- **路径**：`/Users/.../Code/backend/src/main/java/com/zhihuiji/backend/application/service/SaleOrderService.java`
- **类 / 函数**：`SaleOrderService` / `createForOwner`、`updateDraft`、`addPaymentForOwner`、`cancelForOwner`
- **行号**：68–130、218–241、255–290、362–391（关键：93、95、100、273、284、366）
- **触发条件**：任何下单、改价、收款、取消操作
- **当前行为**：销售订单服务中的金额字段（`subtotal` / `total` / `paid` / `discount` / `amount` / `balance`）使用 `double` 加减乘，并用 `0.000001` 容差判等值；这条结论针对该交易链路，不代表全项目所有金额实现都没有 `BigDecimal`
- **期望行为**：`BigDecimal` 或整数分定点计算
- **证据**：`第93行 entity.setAmount(item.quantity() * item.unitPrice())`；`第273行 Math.abs(paid-total) < 0.000001`；全项目扫描到的 `BigDecimal` 不仅出现在海报/积分域，还包括 `ProductService`、`ProductAdjustStockRequest`、`AnswerSynthesizer` 等文件；当前销售订单主链路仍未采用定点金额类型
- **影响**：订单金额与客户应收余额对不上、报表合计与明细不平、"是否付清"边界抖动
- **建议**：金额列与 DTO 迁移 `BigDecimal`（DB `numeric(18,4)`），或统一改 Long 分；同步改 Repository / Entity / DTO 与三端解析
- **可信度**：高｜**需运行时验证：是**｜需产品确认：否

#### ISSUE-002　验证码与邀请码实现混用（安全 / 认证）

- **路径**：`.../application/service/AuthService.java`
- **函数**：`issueVerifyCode` 135–149、`isVerifyCodeValid` 151–166、`register` 48–66
- **触发条件**：调用 `POST /v1/auth/verify-code` 后注册
- **当前行为**：① 配置 `auth.invite-code` 非空时，校验直接 `inviteCode.equals(verifyCode)`（153 行），同一个值可用于不同手机号和类型，且邀请码分支不消费记录；README.md:141 公开了 `021218`，但源码默认配置为空，无法仅凭仓库确认当前运行环境确实使用该值；② 配置为空时生成随机 6 位码只存入内存 `ConcurrentHashMap`，接口只返回 `{success, expireSeconds}`，仓库内没有下发或发送验证码的实现
- **期望行为**：验证码一次性、按手机号下发、限次；邀请码与短信验证码是两条独立机制
- **影响**：在邀请码配置已启用、且上游没有额外限流时，知晓配置值的人可用它尝试注册不同手机号；配置为空时，调用方无法从接口响应取得随机码，注册链路缺少可用的交付环节
- **建议**：拆两套机制；邀请码一次性核销；验证码接真实通道并限次限频；移除内存 Map 或改 Redis；禁止在文档公开生产邀请码
- **可信度**：高｜**需运行时验证：是**（确认生产 `AUTH_INVITE_CODE` 实际值）｜**需产品确认：是**（业务意图）

#### ISSUE-003　销售订单主表写入未加锁（并发 / 数据一致性）

- **路径**：`.../application/service/SaleOrderService.java`
- **函数**：`addPaymentForOwner` 248–291、`cancelForOwner` 342–392、`updateDraft` 210–241、`updateStatus` 293–328；v2 的 `V2SaleOrderService.updateDraft` 135–219、`confirm` 221–238 也直接读取订单主表
- **触发条件**：同一订单并发收款、并发取消，或收款与取消交叉
- **当前行为**：普通销售服务的四个写方法都用 `SaleOrderRepository.findByIdAndOwnerUserId`（第 19 行，无锁）读取后 read-modify-write；v2 的 `updateDraft` 和 `confirm` 同样未锁订单主表。仓库已提供 `@Lock(PESSIMISTIC_WRITE)` 的 `findByIdAndOwnerUserIdForUpdate`（第 21–26 行），当前明确使用它的是 `V2SyncService`；下单、取消和 v2 改草稿锁住的是商品库存行，不等同于锁住订单主表

- **影响**：并发收款可能产生重复收款记录与 `paidAmount` 丢失更新；并发取消可能重复回补库存、重复写入 `AUTO-REFUND`；收款与取消交叉时订单状态、付款记录和客户余额可能不一致
- **建议**：为所有实际写入口选择同一并发策略，覆盖普通与 v2 销售订单路径；若使用订单行锁，需要同时评估订单、商品和客户的加锁顺序，以及收款/退款幂等处理，不能只按方法名替换
- **可信度**：高｜**需运行时验证：是**｜需产品确认：否

## 十、修改建议

### 10.1 优先处理（P1）

1. **ISSUE-001 金额精度**：先确认后端实体、数据库列、Android `Double` 模型、Web `number` 接口类型和表单字符串之间的实际边界，再统一改为 `BigDecimal`（或 Long 分）。这是改造面最大的一项，建议先加金额对账测试，再同步数据库与迁移脚本。
2. **ISSUE-002 验证码**：先确认业务意图（产品），再决定是"邀请码一次性核销"还是"接短信通道"。无论哪种，都要加频率限制与失败计数，并移除内存 `ConcurrentHashMap`（或改 Redis）。同时把 README 中的 `021218` 从公开文档移除。

4. **ISSUE-004 + 005**：先分别覆盖 local 与非 local profile 的 `/v1/admin/**`、`/v2/admin/**` 和带注解业务接口，再决定是否收紧 local 放行、缺认证信息或依赖缺失时的拦截行为。当前只能确认存在风险分支，不能直接宣称已有组合绕过。
5. **ISSUE-006 Web 令牌**：改 httpOnly + Secure + SameSite Cookie；若短期无法改造，至少不持久化 `refreshToken`。
