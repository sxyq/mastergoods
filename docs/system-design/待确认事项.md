## 2.1 Grill 审核后新增确认（2026-09-28）

1. 商户侧账号不可转店：OWNER / STAFF 一旦建立 Merchant Membership，不允许同一 User 以后加入其他 Merchant。
2. STAFF 配额是累计注册配额：停用 / 离职不返还，SYSTEM_ADMIN 显式提高总额度才增加名额。
3. SYSTEM_ADMIN 可刷新某个邀请码，也可新建额外邀请码；多个邀请码共享同一 Merchant 注册配额，新建邀请码不重置额度。
4. 后台可查看邀请码状态、创建 / 刷新历史、绑定 Merchant、OWNER 使用、STAFF 累计使用与剩余额度。
5. Merchant 可按 `CLOSED → FROZEN → ACTIVE` 受控恢复，禁止 `CLOSED → ACTIVE`。
6. FROZEN 建立 `READ_ONLY` 会话；查看 / 导出允许，经营写入拒绝。
7. Step-up / 临时设备锁按 User + Device / Session 作用域；必须改密等全局事实仍属于 User。
8. 随机临时密码只有 Copy 成功且 Server Confirm 成功才激活；未 Copy、断网、闪退、确认失败均视为 Reset 未成功。
9. 正式改密前闪退可重新使用仍有效临时密码进入受限改密；正式密码提交成功后才标记 USED。
10. Token Rotation 使用 `token_version + CAS`。
11. EMAIL / PHONE 均是正式支持的身份渠道；PHONE 实际短信接入可因资质 / 备案后置。
12. 已有 RUNNING Task 且余额低于并发准入阈值时拒绝新 Agent Task；已准入 Task 继续。
13. Agent 结算以 Model Call Usage Log 为事实来源；失败进入 `SETTLEMENT_PENDING` 并可靠重试。
14. 同步采用 Session 状态 / Rotation 分离、配额耗尽派生化、Hard Rule + Weighted Risk、MerchantClosureGuard、Clock、SecureRandom、Ledger append-only、Decimal/fixed-point 禁止 float。

## 4. 当前明确规则

- P-03 已确定：一个 Merchant 一个 OWNER；替换 OWNER 只能通过店长交接。
- 单 Merchant Membership、STAFF 自助使用 MerchantInvitation 注册的规则保持不变。
- Agent 积分归 Merchant；Task 准入后可扣成负数，只阻止下一个 Task；禁止用固定预留积分代替最终实际用量结算。
- Email 首期验证基线、P-01、P-02、P-04—P-17 的建议方案均须按上表状态等待确认；不能因已写入汇总表就视为冻结。PHONE / SMS 仅保留扩展能力，首期禁用。

## 5. 推荐确认顺序

1. 先确认 P-01、P-04—P-10，确定架构、生命周期、身份及会话基础规则。
2. 再确认 P-11、P-12、P-14、P-15 的安全验证默认值和策略边界；P-13 参数通过部署 benchmark 决定。
3. 接着确认 P-16、P-17 的 STAFF 配额与报表需求。
4. 按 Roadmap 启动 P-18—P-21 对应的后续业务 / 专题设计。


## 6. 模块 02 — 出库与销售待确认项

> 本节使用 S 编号，与账户 / 平台 P-01～P-21 分开跟踪；不改变上方 P 系列统计口径。

~~~mermaid
flowchart TD
    A[02-01 创建出库与商品明细] --> B[S-01 服务端可恢复 SaleDraft]
    A --> C[S-02 临时商品]
    A --> D[S-03 他人 Draft 查看 / 接管]
    A --> E[S-04 多 ACTIVE Draft]
    A --> F[S-05 ACTIVE Draft 过期]
~~~

### S-01 服务端可恢复 SaleDraft

- **建议**：服务端持久化 ACTIVE Draft；
- **原因**：支持移动端闪退恢复、多客户端继续、Agent 与人工共享同一业务草稿；
- **状态**：待产品确认；
- **约束**：若采用服务端 Draft，打开卖货入口只查询，不自动创建空 Draft。

### S-02 临时商品

- **建议**：v1 不支持自由文本临时商品；
- **流程**：未找到商品 → 有商品新增权限则进入正式 Product 创建 → 创建成功后再加入 SaleDraft；
- **状态**：待产品确认；
- **约束**：确认前禁止用 product_id = NULL 偷渡临时商品。

### S-03 他人 Draft 查看 / 接管

- **建议**：STAFF 默认只自动恢复自己的 Draft；OWNER / 特殊权限是否能查看、接管其他人 Draft，在销售查询 / 权限子模块继续确认；
- **状态**：待产品确认；
- **约束**：Merchant 相同不等于任意 STAFF 可互相覆盖 Draft。

### S-04 同一用户是否允许多条 ACTIVE Draft

- **建议**：允许多条 ACTIVE Draft，进入卖货时列出可恢复草稿，由用户明确选择；
- **原因**：避免人工正在录入的销售被 Agent、新客户或另一设备的新业务覆盖；
- **备选**：极简产品可以限制每用户每 Merchant 仅一条 ACTIVE Draft；
- **状态**：待产品确认。

### S-05 ACTIVE Draft 是否自动过期

- **建议**：v1 不自动过期 ACTIVE Draft；
- **原因**：现有状态机只有 ACTIVE / CANCELLED / CONSUMED，静默删除 ACTIVE 会造成未完成经营工作的无提示丢失；
- **如果未来启用**：先定义 EXPIRED（或等价）状态、恢复规则、用户提示和 Agent 行为，再实现后台清理；
- **状态**：待产品确认。

## 7. 模块 02-02 — 数量、单位、价格与金额计算待确认项（2026-10-09）

### 7.1 决策前的使用方式

1. 后续 02-03～02-05 可以引用“推荐基线 + 明确假设”继续细化需求；不能把这些假设写成产品已批准事实。
2. 任一 S-06～S-13 被明确确认或否决后，同步修改 02-02、模块总览、待确认事项、交接文档及相关下游规则。
3. 02-09 收口人员权限 / 风险，02-10 收口行金额、订单金额、收款、欠款与库存的一次完成事务；在最终业务闭环与关键规则未确认前不进入 Schema / API / Coding。
4. S-01～S-05 与 S-06～S-13 合计 13 个销售待确认项，其中有些可以合并产品会议决策，但仍按编号逐项追踪。
