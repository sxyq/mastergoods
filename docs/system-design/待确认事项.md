## 2. 已冻结、无需重复确认的规则

以下内容在当前详细设计中已经明确，不应再次作为“待确认项”提出：

- 只有 `OWNER`、`STAFF`、`SYSTEM_ADMIN` 是系统账号；客户和供应商不是登录账号。
- 一个 `OWNER` 只能对应一个 Merchant；一个 Merchant 只有一个 `OWNER`，`STAFF` 可以有多个。
- `SYSTEM_ADMIN` 不属于 Merchant，负责全局配置、风险处理、积分下发和审计。
- iOS / Android 采用 30 天滑动 Session；允许多设备登录；修改密码后当前设备保留并轮换，其他设备失效。
- 登录和密码恢复不得暴露账号是否存在；高风险动作必须经过验证、审计和必要的 Step-up。
- 临时密码随机生成、只显示一次、只存 Hash、首次登录强制改密；密码和验证码明文不得进入日志或 Audit。
- Agent 积分归 Merchant；Task 准入后可扣成负数，负余额只阻止下一个 Task，充值自然抵消负余额。
- 模型定价和 USD → Points 比例必须版本化，历史消费引用原版本，不随新价格重算。
- 验证、Risk、Session、Provider、Points 的具体数值属于版本化配置，不改变已冻结的业务流程和领域边界。

## 3. 确认顺序建议

1. 先确认 P-01、P-06、P-07、P-08、P-10，避免工程实现和账户状态机反复返工。
2. 再发布 P-11 至 P-16 的安全、验证和计费配置版本。
3. 最后按 P-18 至 P-21 进入权限、供应商、Agent 运行时和销售等后续模块设计。
