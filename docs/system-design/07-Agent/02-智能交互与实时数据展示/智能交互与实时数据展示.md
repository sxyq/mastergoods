# 07-Agent / 02 — 智能交互与实时数据展示：完整需求与交互设计

> **状态：2026-11-01 第一版完整详细讨论稿，尚非所有交互选择已经由用户逐项确认。**  
> **优先级：Agent 最重要的直接用户界面专题。** 以现有《Agent模块.md》和 01《模型提供商与模型配置.md》的已确认规则为约束，本文负责详细定义对话界面、固定 Intelligent UI 组件、布局、交互、数据呈现与实时体验；其余 Agent 执行机制各由对应子模块负责。  
> **本文件不是代码实现报告。** 其中“推荐/建议/候选”表示待产品讨论的详细方案，不代表已开发或业务规则已冻结。

> **真实进销存定位：** 仓库为中心；商品、库存、销售出库、采购入库、客户供应商、往来/人工经营账目；无外部支付接口，不把销售等同收款。业务待定规则（销售 W/S 系列等）保持待定。

## 1. 目标、边界与产品定位

### 1.1 一句话定义

**一个类似 ChatGPT 的单一聊天窗口，能够以流式文字、计算好的数据表格、图表、业务卡片和受控交互组件来展示服务端 Agent 对真实进销存系统的查询、分析和操作结果。** 用户不需要理解 Task、Checkpoint、Model Call、Tool 参数或上下文压缩，也不需要进入独立的桌面工作台。

### 1.2 用户实际能做什么

1. 输入“帮我查矿泉水库存”“最近 30 天什么卖得好”“准备采购草稿”等自然语言请求。
2. 在聊天输入区仅选择**快速 / 标准 / 深入**三个模型档位；速度、能力和大致消耗倾向用简短文字解释，不泄露真实模型、价格及单次积分消耗。
3. 观看流式文字回复；在业务 Tool 获取真实查询结果后查看表格、图表、数字摘要、对象卡片等；同一条回复可混合文本与多个组件。
4. 在表格内排序/本地筛选、在图表间切换、展开业务详情、查看数据来源和统计范围。
5. 通过参数选择、数量编辑、表单补全、草稿预览和确认操作继续业务任务；正式数据写入通过既有业务 Application Service。
6. 对上一轮结果继续追问，例如“只看饮料”“把这个数量换成 15 箱”“打开刚才第一条”。
7. 查看历史对话及当时产生的结果；需要最新数据时主动刷新或再次提问。
8. 遇到上游模型故障时保留已显示内容，展示**“模型服务暂时不可用，请重试。”**及重试按钮；遵循 Agent 01 的失败请求不向用户扣积分规则。

### 1.3 不属于 02 的责任

- 不在前端进行模型调用、意图分类、工具规划、直接 SQL、库存扣减或定价结算。
- 不由模型在客户端生成任意可执行页面、任意 JS、任意 HTML，亦不复刻复杂 DIL 编译器 / iframe / Worker 沙箱。
- 不再设计一套 ERP 业务管理后台；复杂业务编辑跳转或打开已有领域页面。
- 不在本模块冻结销售、采购、库存入出库、单位与售价、客户和付款等尚未确认业务规则。
- 不做复杂的 AG-UI / MCP / Skills/多子 Agent 工程体系；可借鉴其有价值的消息和数据交互思想。
- 不建立持续的全量库存变化订阅。**实时流式回答 ≠ 数据每秒推送**；真实查询是当前业务快照，需要最新数据时可刷新。

### 1.4 已确定的上游规则（不得在本模块另行改变）

| 来源 | 已确认事实 | 02 具体表现 |
|---|---|---|
| Agent 01 | 对外三个固定档位：FAST / STANDARD / DEEP | 显示三个通俗中文选项，不列出真实模型名 |
| Agent 01 | 切档位不改变进行中的 Task，影响下一 Task | 选择器显示新选择，但正在进行的回答不立即换模型 |
| Agent 01 | 无状态模型请求；消息和会话由本系统管理 | UI 仅根据服务端会话与消息渲染 |
| Agent 01 | 上游模型错误直接中断，用户手动重试 | 保留已展示内容 + 统一错误 + 重试 |
| Agent 01 | 本次失败模型请求不扣用户积分 | 聊天页不显示模型成本或单次积分账单 |
| Agent 总览 | Agent Runtime/Tool/业务数据操作在 Go 后端 | 前端只展示结果并转发用户操作 |
| 账户模块 | Merchant 积分账本归账户模块 | 不在聊天卡片开发账务或支付逻辑 |
| 进销存领域 | 业务授权、真实库存销售采购规则由领域决定 | 用户看到按钮不代表越权拥有业务操作权 |

## 2. 同一产品的页面布局：桌面 Web、窄屏手机、微信小程序

### 2.1 布局原则

- **对话优先、内容优先、移动优先。** 用户打开后直接看到对话、输入框和最近的回答；复杂结果在消息内展开，不另建多窗口工作台。
- 每个回复可顺序显示一段文字、一个图、一张表、一个参数面板、另一段说明；布局由固定组件与内容类型决定，而非模型任意输出像素坐标。
- **聊天区纵向滚动**，局部表格可横向滚动；输入框稳定处于可输入区域，不遮挡系统软键盘和安全区域。
- 业务操作在聊天内先完成最常见的小动作；字段复杂、需大量校验或需要大屏编辑时打开已有 ERP 详情/编辑页面，保留返回会话的上下文。
- 不要求 Android、iOS、Web、小程序像素一致；只要求语义、数据来源、操作结果和用户能完成的任务一致。

- 大表默认展示 2～4 列关键字段，更多字段通过“查看详情”或横向滚动访问；不得把 12 列硬挤成不可阅读的小字。
- 图表显示简短标题、单位、范围与关键数值；细长图可展开；横轴标签多时适当缩略，点击数据点读出精确值。
- 顶部/底部系统安全区域、滚动惯性、返回手势、单手触达、可访问字体缩放采用平台现有原生组件行为。

### 2.4 微信小程序布局

与手机单列一致，但组件使用微信小程序现有容器、列表、Canvas 或已选图表能力；遇到复杂长表优先进入独立明细页。不得为小程序单独改变业务事件含义或单独发明 Agent 逻辑。连接限制与流式传输的实际适配由 12 模块确定。

### 2.5 不同页面状态

| 页面状态 | 顶部 | 内容区 | 底部 |
|---|---|---|---|
| 未开始的新对话 | Agent 助手/历史入口 | 简短介绍、适量示例提问，不加载复杂仪表盘 | 输入框 + 三档选择 |
| 正常历史对话 | 会话标题 | 既有消息和组件结果 | 输入框 |
| 任务运行中 | 保持标题与档位展示 | 进度行、文字流、按结果出现卡片 | 可继续输入的策略以 03/06 确定，不假设立即并发 |
| 数据需要补充 | 同上 | InputCard/选择卡/业务草稿预览 | 允许追问 |
| 上游模型故障 | 同上 | 已显示内容保持、统一错误、重试入口 | 输入区仍可交互 |
| 无查询结果 | 同上 | 空状态和可用的调整查询提示 | 输入区 |
| 权限不足 | 同上 | 简洁的权限说明，不展示越权数据 | 输入区 |
| 历史结果已过时 | 同上 | 显示查询时刻和“刷新数据”入口 | 输入区 |

### 2.6 滚动、焦点与输入体验

- **仅在用户位于底部附近时自动随流式内容滚动。** 用户上翻历史时停止强制滚动，并显示“回到最新”入口；点击后回底部。
- 新的 User Message 发出后在列表追加本地发送状态，由服务端 Message ID 确认后建立映射；重复点发送不应生成两条独立请求。
- 流式追加文本只更新当前 TextBlock，不能因为整条消息重绘而让输入框失焦、选择器归零或滑动位置跳变。
- 用户切换表格筛选/图表视图不应打断 Agent 回复；交互组件使用稳定组件 ID 来保留当前视图状态。
- 空消息不可发送；多行输入、复制粘贴、删除、发送/停止按钮应符合各端通用习惯。Web 的 Enter/Shift+Enter 组合可与现有产品输入规范一致。
- 模型档位只显示快速/标准/深入及相对速度与能力说明；不在聊天里逐字显示真实 Provider、Model 或 Token 账单。

## 4. 固定 Intelligent UI：基础渲染器少、业务表现形式足够丰富

### 4.1 设计选择

**避免“只有十种卡片不够用”，也避免“每个业务结果一个全新框架”。** 本文推荐分成两层：

- **基础渲染类型（12 类）**：文本、状态、通知、指标、表格、图表、列表、对象详情、表单、操作区、文件、错误。这是真正要在四端维护的一小组可复用渲染能力。
- **固定业务模板/变体（约 40 种候选）**：如商品卡、库存摘要、销量排行榜、销售单据卡、采购草稿、数据筛选条等。它们由上述渲染类型组合而成，大多数只是固定字段集合和有限交互规则，不是独立运行环境。

Agent 可以在已允许的组件类型和业务模板中选择展示方式，但由后端展示适配逻辑提供合法的结构化数据、字段单位和权限范围。**模型不能直接指定任意前端代码或伪造“成功创建业务单”。**

### 4.2 十二类基础渲染类型

| 基础类型 | 职责 | 常见内容 | 主要交互 |
|---|---|---|---|
| TextRenderer | 普通正文、标题、Markdown | 普通解释、结论、建议、引用提示 | 选择/复制、继续提问 |
| StatusRenderer | 一行简短任务状态 | 正在处理、正在查询、生成中、已中断 | 默认无需操作 |
| NoticeRenderer | 提示、无结果、注意项 | 无符合条件商品、时间范围说明 | 查看原因、调整条件 |
| MetricRenderer | 一个或一组汇总指标 | 库存量、销量、金额、商品数 | 查看明细 |
| TableRenderer | 列表式结构化记录 | 商品列表、出库记录、库存明细 | 排序、筛选、分页、行操作 |
| ChartRenderer | 图形统计及数据点 | 柱状、折线、饼/环、排名/趋势 | 切换视图、数据点查看 |
| ListRenderer | 紧凑信息、分类/分组清单 | 排名、待办、异常提醒、分组项目 | 展开分组、选择条目 |
| RecordRenderer | 单条业务对象详情 | 商品、客户、供应商、草稿、业务记录 | 查看原业务详情 |
| FormRenderer | 受控参数补全 | 选择商品/客户、数量、单位、日期 | 输入/选择/提交 |
| ActionRenderer | 有具体语义的操作入口 | 创建草稿、刷新、继续、确认 | 调用明确的后端动作 |
| FileRenderer | 文件/附件结果 | Excel、PDF、图片、导入预览 | 打开、下载、分享 |
| ErrorRenderer | 模型和业务错误的用户反馈 | 暂不可用、无权限、输入无效 | 重试、修改输入 |

**技术注解：** 渲染器是“共享组件机制”，不是强制新建 12 个微服务或安装 12 个依赖。Web、Android、iOS、小程序沿用各自现有组件体系组合实现。

### 4.5 每一类组件的必备通用状态

| 状态 | 呈现行为 |
|---|---|
| loading | 占位/简短加载文字，不伪造数值 |
| ready | 展示服务器返回的完整有效数据 |
| empty | “暂无符合条件的数据”，保留查询条件 |
| error | 组件级查询失败说明；模型层错误遵循统一固定文案 |
| disabled | 无权或暂不可操作时不显示虚假可用按钮 |
| stale | 历史查询快照，标记查询时间并提供刷新 |
| editing | 受控字段的本地编辑中状态，未经保存不视为业务事实 |
| submitted | 仅当后端返回实际业务成功结果才显示成功 |

**数据组件的显示要有单位、查询范围与数据时间。** 对权限敏感或缺失字段应根据服务端授权结果隐藏或标注不可查看，而不是填入虚假默认值。

## 5. 组件数据协议：固定类型 + 服务端真实数据 + 稳定 ID

### 5.1 为什么消息必须拆成有序内容块

纯 content 字符串不足以表达“说明 + 指标 + 图表 + 表格 + 采购草稿”。建议对一条 Assistant Message 使用有序 parts；parts 数据由后端 Agent 和结果展示适配层组织，前端只做固定组件选择与更新。

~~~json
{
  "message_id": "msg_102",
  "conversation_id": "conv_42",
  "role": "assistant",
  "status": "completed",
  "parts": [
    {
      "id": "part_text_1",
      "type": "text",
      "text": "以下是最近30天饮料销量的统计。"
    },
    {
      "id": "part_metrics_1",
      "type": "metric",
      "variant": "stat_grid",
      "data": {
        "items": [
          {"label": "销售数量", "value": "675", "unit": "瓶"},
          {"label": "商品数", "value": "3", "unit": "种"}
        ]
      }
    },
    {
      "id": "part_chart_1",
      "type": "chart",
      "variant": "bar",
      "data_ref": "sales_stats_203",
      "data": {
        "x_key": "product",
        "series": [{"key": "quantity", "label": "销量", "unit": "瓶"}],
        "rows": [
          {"product": "矿泉水", "quantity": 360},
          {"product": "绿茶", "quantity": 190},
          {"product": "橙汁", "quantity": 125}
        ]
      },
      "meta": {
        "scope": "已授权商户，最近30天",
        "queried_at": "示例时间",
        "is_snapshot": true
      }
    },
    {
      "id": "part_action_1",
      "type": "action",
      "variant": "follow_up",
      "actions": [
        {"id": "act_stock", "label": "继续查看库存", "kind": "ask_agent"}
      ]
    }
  ]
}
~~~

**示例说明：** 这是一份**用于讨论的概念协议**，数字为演示，非真实业务数据库结果，字段名可在 03/12 模块最终化。服务端保存 Conversation/Message/Task 的真实关联；组件状态与已完成业务动作不得仅从前端消息推断。

### 5.2 固定字段的推荐职责

| 字段 | 作用 |
|---|---|
| message_id / conversation_id | 后端消息和会话引用 |
| part.id | 稳定局部组件标识，用于增量更新、局部状态保留 |
| part.type | 选择 12 类预定义基础渲染器 |
| part.variant | 当前渲染器中的固定业务模板，例如 product/stock/sale |
| data | 少量可直接显示的结构化结果，不是任意可执行源码 |
| data_ref | 大量结果、长表格或数据分页的后端引用 |
| meta.scope / queried_at / unit | 说明数据来源范围、时间、单位，防止把历史快照当实时 |
| actions | 服务器授权的已知操作 ID、标签、必要参数（不得是任意可执行 JS） |
| status / revision | 支持流式/本地状态更新与稳定组件识别 |

### 5.3 结果生成责任

~~~mermaid
flowchart LR
    USER[用户自然语言] --> AGENT[Go Agent Runtime]
    AGENT --> TOOL[受控业务 Tool]
    TOOL --> BIZ[业务 Application Service]
    BIZ --> DATA[真实业务查询结果]
    DATA --> ADAPTER[Go 中的轻量展示适配函数]
    ADAPTER --> PARTS[Text / Table / Chart / Record / Form 等数据块]
    PARTS --> FRONT[四端固定渲染器]
~~~

**图示说明：** Agent 决定“用什么方式解释结果”，但真实数量、价格、业务状态来自业务服务的可靠数据。展示适配函数只负责结构，不重算库存或财务规则；也不要求新微服务。

### 5.4 组件更新的基本原则

- 同一 part.id 的更新只影响对应组件，不重建整条消息及所有输入控件。
- 已计算好的表格和图表可一次性发送完整数据；不强制“每个数据点流式出现”。
- 服务器正在处理时可先发 status 与加载占位；有真实数据后执行 upsert，将结果卡填满。
- 巨大表格使用 data_ref + 服务端分页，避免一次把全部仓库/客户业务数据塞进消息正文或模型上下文。
- 表格排序/已加载结果筛选属于前端显示操作；新条件需要重新统计或刷新真实库存时走服务端查询。
- 更新同一图表的 chart_type 时应复用 data_ref；图表切换不能偷偷改变统计口径。
- 未识别的 part.type 不执行未知代码，可使用普通“此结果需在新版客户端查看”提示；不显示不可信 JSON 源码给普通用户。

## 6. 流式消息、固定组件增量更新、生命周期

### 6.1 推荐事件集（概念协议，不冻结 12 模块最终字段）

| 事件 | 数据主体 | 客户端职责 |
|---|---|---|
| message.start | conversation_id、message_id、Task 引用 | 创建当前 Agent 回复 |
| status.update | 简短阶段名、显示文案 | 显示正在处理/查询/生成 |
| text.delta | part_id、追加文本 | 在现有文本块原位追加 |
| component.upsert | part_id、type、variant、data / data_ref | 创建或替换指定固定组件的数据 |
| component.patch | part_id、revision、变化字段 | 仅更新组件指定数据，不全屏重绘 |
| message.done | 最终状态、持久化消息引用 | 本轮回复完成 |
| message.error | 统一错误种类/是否允许用户重试 | 保留已见内容、显示固定提示 |
| action.result | 用户动作结果或返回的对象引用 | 更新相应输入卡/业务结果卡 |

**重要：** 对固定组件，首期用 upsert（整块替换）和 text.delta 已经足够；patch 只在确有高频/大量数据更新时使用，不先复制示例项目的全路径通用补丁引擎。

### 6.2 消息状态机

~~~mermaid
stateDiagram-v2
    [*] --> Created: 用户提交消息
    Created --> Processing: 后端开始
    Processing --> Streaming: 收到文字或组件增量
    Processing --> Failed: 上游异常
    Streaming --> Completed: 消息完成
    Streaming --> Failed: 上游异常
    Failed --> RetryReady: 展示固定错误和重试入口
    RetryReady --> Processing: 用户主动重试
    Completed --> [*]
~~~

**状态图说明：** 此处只是客户端**消息可见状态**，不是 Agent Task 的完整业务状态机；用户重试由服务端创建/恢复何种 Task 由 03/07 决定，不在 02 自行假设业务 Tool 可重做。

### 6.3 流式增量实现顺序（示例）

~~~mermaid
sequenceDiagram
    actor 用户
    participant UI as 四端消息界面
    participant API as Go Agent API
    participant BIZ as 进销存业务服务
    用户->>UI: 最近30天饮料销量是多少
    UI->>API: 发送用户消息与所选档位
    API-->>UI: message.start
    API-->>UI: status.update 正在处理
    API->>BIZ: 通过 Tool 获取真实销量统计
    BIZ-->>API: 销售统计结果与口径
    API-->>UI: text.delta 文字解释
    API-->>UI: component.upsert 摘要卡
    API-->>UI: component.upsert 图表卡
    API-->>UI: component.upsert 明细表
    API-->>UI: message.done
    UI-->>用户: 文字与组件保持在同一条回复中
~~~

**时序说明：** 前端不能先假设库存/销售数字再以“动画补齐”。只有真实业务服务返回后，才把算好的表格和图表放入消息。

### 6.4 断线与模型错误的区别

- 客户端**网络断开**不直接等于服务端模型故障；连接和消息恢复策略由 12 与 03/07 决定。UI 应显示连接状态，不擅自把网络故障计为上游模型失败。
- 明确收到**上游模型失败**时，遵循 Agent 01：停止当前流、保留已显示内容、显示“模型服务暂时不可用，请重试。”、用户主动点击重试；失败上游模型请求不向用户扣积分。
- 不实现主备模型输出无标识拼接；若以后后端重试了模型，也由后端给出清晰的新消息/新生成状态。
- 不默认向用户展示 Provider 实际错误、HTTP 状态码、Tool JSON、原始内部推理文本。

## 7. 交互动作：区分本地显示、重新查询、真实业务操作

| 动作类型 | 示例 | 客户端能否自行完成 | 是否需要重新调用模型 |
|---|---|---|---|
| display.local | 已加载表格排序、图/表切换、展开字段 | 可以 | 不需要 |
| query.refresh | 刷新库存、切换统计日期需新数据 | 不可以，调用后端查询 | 通常不需要单独的意图识别模型；按实际后端设计 |
| ask_agent | “把范围改成上个月”“解释销售变化” | 发送新用户需求 | 由 Agent 决定 |
| business.preview | 修改采购数量并预览表单 | 本地临时草稿可变化，服务器决定有效字段 | 是否调用模型取决于任务 |
| business.execute | 创建采购草稿、修改商品、确认出库 | **必须服务端执行** | 由 Agent/Tool 模块处理 |
| navigation.open | 打开本商户已有销售单据详情 | 前端导航到授权的 ERP 页面 | 不需要 |
| file.open/export | 打开报表或请求导出 | 有效文件可本地打开；新导出由服务端 | 不必每次调模型 |

### 7.1 表单与用户动作设计

- InputCard 只提供当前任务需要的字段，默认值来自服务端合法数据或显式用户输入，不能凭空编造客户、仓库、售价和付款状态。
- 选择商品/客户时，展示有足够辨识度的候选项（名称、SKU/联系信息中允许展示部分），并将**真实业务对象 ID**提交回后端，不用仅凭显示名称作最终引用。
- 数量编辑同时展示单位；商品存在多单位关系时以领域模块有效规则为准，不由 UI 自行设定箱/瓶换算。
- 真实业务动作必须有服务端成功结果才能显示“创建成功”“出库成功”，用户看到的预览未必已写入数据库。
- 客户端可保存临时视觉编辑状态，但**不承担最终业务规则校验或持久化真相**；后端重新核对授权、业务对象和必要字段。
- 复杂表单不必强行挤在消息内部；提供“打开现有业务编辑页”，操作完成后回到原会话并展示结果。

### 7.2 View State：只保留有意义的交互状态

示例仓库的 view-state 机制为动态 UI 回灌完整控件状态。我们可以精简为：part_id、当前选中项/筛选/数据分页、用户提交的必要参数和 action_id。**不要在每一次滑块拖动都调用 LLM**。客户端改变未提交的筛选条件可以先本地完成；只有涉及新业务信息/下一任务时才提交必要状态。

### 7.3 对组件动作的服务端确认

~~~mermaid
sequenceDiagram
    actor 用户
    participant UI as InputCard / DraftPreview
    participant AGENT as Go Agent API
    participant BIZ as 采购业务服务
    用户->>UI: 输入采购数量 15箱
    UI->>UI: 本地展示待提交的预览值
    用户->>UI: 点击准备或确认
    UI->>AGENT: action_id + 对象引用 + 15 + 单位
    AGENT->>BIZ: 按已有业务规则调用对应服务
    BIZ-->>AGENT: 返回已创建或拒绝的真实结果
    AGENT-->>UI: action.result + BusinessResultCard
    UI-->>用户: 根据服务端事实展示结果
~~~

**时序说明：** 采购量 15 箱只是交互示例，不确认采购业务是否具备该单位或该操作在什么状态合法；由采购领域决定。

| 用户动作 | 按钮/列表行、键盘快捷键 | 大触控热区、系统返回 | 触控热区、系统导航 |
| 文件 | 浏览器打开/下载 | 调用系统文件查看/分享 | 小程序支持的预览/下载 |
| 用户主动重试 | 原位重试入口 | 原位重试入口 | 原位重试入口 |
| 深色与浅色 | 跟随产品主题 | 跟随系统/产品主题 | 跟随小程序主题能力 |

### 8.1 表格移动端行为示例

“商品库存明细”Web 可显示商品、SKU、单位、库存、价格、查询时间等多列；手机默认只显示商品/库存/单位三项，点击行展开其他字段或进入商品详情。不要因为窄屏直接丢弃字段或让后端返回不同口径的数量。

### 8.2 图表移动端行为示例

对 30 天销售折线图：手机可以只显示少量轴刻度，点选/长按某日显示完整数值；用户从“折线”切“表格”直接读取同一个结果引用，不要重新统计一次生成两个不同结果。

### 8.3 软键盘与滚动规则

输入框在底部安全区内、键盘弹出时不覆盖当前编辑文本；用户上翻时不跟随新回复滚动；点“回到最新”才回底部；业务表单输入框获得焦点不应因流式增量而被无故重置。

## 9. 真实进销存业务场景（用例 / 交互 / 空状态 / 业务边界）

### 9.1 用例 U-01：查询一个商品当前库存

- **输入：** “矿泉水还有多少库存？”
- **服务端工作：** Agent 识别查询，调用商品与库存服务；必要时识别多个同名商品并要求用户选定。
- **UI 输出顺序：** StatusLine“正在查询库存” → TextBlock“查询结果如下” → StockCard（商品、单位、真实库存、查询范围、时间）→“查看明细” ActionCard。
- **响应场景：** 匹配 1 个商品时展示；匹配多个时显示 SingleSelect；没有结果时显示 EmptyResult；无法查看则显示权限提示，不伪造数量。
- **移动体验：** 当前库存数优先大字显示；商品/单位/范围可见；较多仓库字段放入展开区域。当前产品仓库规则仍以业务设计为准，不预设多仓。
- **业务边界：** 不因用户说“还剩多少”就将采购在途数、已售未出库数等自行混合为可用库存。

### 9.2 用例 U-02：查询销量并给出经营分析

- **输入：** “最近 30 天什么饮料卖得最好？”
- **服务端工作：** 使用销售服务确定范围、统计字段和合法单位；返回 Top N 结果和相应解释数据。
- **UI 输出顺序：** 文字说明 → StatGrid（销售件数等同口径摘要）→ RankingList 或 BarChart → DataTable → FollowUpSuggestions。
- **交互：** 用户切换图表/表格时本地完成；点某商品进入 ProductCard；用户更改为“上个月”时触发新服务端统计。
- **空数据：** “该范围没有销售记录”，允许修改范围，不制造趋势图。
- **边界：** 不将混合“瓶/箱/件”直接相加，不自动等同销售完成和已收款。

### 9.3 用例 U-03：生成采购草稿预览

- **输入：** “帮我准备矿泉水 10 箱的采购草稿。”
- **服务端工作：** 查商品、对应单位和可能必要字段；若缺少供应商/数量等则返回补充参数请求。
- **UI 输出顺序：** TextBlock → ProductCard/SingleSelect（如歧义）→ ParameterForm/QuantityEditor → DraftPreviewCard → ActionCard（受控动作）。
- **交互：** 把数量从 10 改成 15，先更新本地预览；用户明确提交后才根据业务模块校验并创建合法草稿。
- **边界：** 预览状态不等于已创建，不等于采购完成，不等于库存入库；是否存在采购草稿及其具体字段由采购模块最终确认。

### 9.4 用例 U-04：查看销售出库记录

- **输入：** “查一下昨天卖给老王的水。”
- **服务端工作：** 按客户、时间、商品和 Merchant 权限查询真实销售记录；有歧义时提供选择。
- **UI 输出：** DataTable/CompactTable + SaleRecordCard + 关联商品信息。
- **交互：** 点记录打开既有销售页面，或发送新的追问。
- **边界：** 不凭“卖”自动生成收款记录，不替销售模块确定历史补录、实际出库时间和客户账务 W/S 待决规则。

### 9.5 用例 U-05：多轮追问与数据视图切换

用户先问“近 30 天销量”，再点图表里的“矿泉水”，接着问“它的库存呢”。下一轮请求由 03/04/05 依据消息历史与业务对象引用理解；02 只把选中的对象 ID 与可用组件上下文交给服务端。前端本地切换图表/表格不需要调用模型，也不应该改变先前查询结果的原始时间范围。

### 9.6 用例 U-06：模型流式回复中断

~~~mermaid
flowchart TD
    A[用户发送请求] --> B[显示正在处理]
    B --> C{模型回复是否正常}
    C -->|正常| D[增量展示文字和业务组件]
    D --> E[完成本轮]
    C -->|上游异常| F[保留已经显示的内容]
    F --> G[固定显示模型服务暂时不可用 请重试]
    G --> H{用户主动点击重试}
    H -->|点击| I[再次向服务端发请求]
    H -->|不点击| J[保持中断状态]
~~~

**说明：** UI 不能将已经失败的请求标成成功、不能擅自扣用户积分，也不尝试拼接主备模型的半截回答。是否复用既有业务步骤/Task 属于 06/07，不在此重复设计。

### 9.7 用例 U-07：历史结果与刷新

- 历史卡片显示的是当时查询得到的真实结果快照；例如“昨天查询的库存为 120 瓶”，下次打开历史仍显示昨日结果且带查询时间。
- 点击“刷新当前库存”发起新的查询并显示新的结果或新消息；旧消息不应悄悄变成今天的数据而失去历史含义。
- 02 定义视觉行为，历史数据保存、Message 关联及跨端恢复由 03/12 明确。

### 9.8 用例 U-08：文件结果与附件

- 聊天中可通过 FileCard 展示“销售统计.xlsx”等已生成文件；上传图片、Excel、语音输入和导入预览依据 14 模块确定细节。
- 首期若尚未实现上传/语音，不保留无效按钮、占位完成提示或虚假的“已识别文件”行为。
- 02 只负责本端预览、状态和用户操作入口，不定义后端文件解析算法。

## 10. 更完整的时序与组件交互

### 10.1 受控业务动作的序列

~~~mermaid
sequenceDiagram
    actor 用户
    participant UI as 聊天窗口固定组件
    participant API as Go Agent Runtime
    participant TOOL as 内置业务 Tool
    participant BIZ as 业务 Application Service
    用户->>UI: 准备采购草稿
    UI->>API: 提交用户消息
    API->>TOOL: 查商品及必要数据
    TOOL->>BIZ: 查询真实数据
    BIZ-->>TOOL: 合法结果
    TOOL-->>API: Tool Result
    API-->>UI: InputCard 与 DraftPreviewCard
    用户->>UI: 补充数量和必要字段
    UI->>API: action_id + 业务参数
    API->>TOOL: 进行受控业务操作
    TOOL->>BIZ: 调用合法业务服务
    BIZ-->>TOOL: 成功或失败事实
    TOOL-->>API: 真实业务结果
    API-->>UI: BusinessResultCard 或错误信息
~~~

**时序说明：** UI 的“确认”是向服务端提交明确动作，不是把模型生成的文案当作交易结果。

### 10.2 用户切换同一结果图表形态

~~~mermaid
sequenceDiagram
    actor 用户
    participant UI as 固定图表/表格组件
    participant STATE as 客户端轻量 View State
    participant API as Go Agent API
    API-->>UI: chart + table 共用结果引用
    用户->>UI: 从柱状图切换表格
    UI->>STATE: 将当前视图改为 table
    STATE-->>UI: 使用已有数据重绘表格
    Note over UI,API: 本地展示切换 不发生新的模型调用
    用户->>UI: 切换日期为上个月
    UI->>API: 提交新的服务端统计请求
    API-->>UI: 新时间范围的真实数据
~~~

**时序说明：** 交互体验应接近 Intelligent UI 中“控件切换立即看到结果”，但不把每一次 UI 变化回灌为新的模型思考。

## 11. 前后端实现划分与推荐的最少技术结构

~~~text
Go 后端（现有 Agent/Business 逻辑内）
  Agent 会话与消息调用
  └─ 业务工具结果
     └─ UI Result Presenter（简单的结果→固定内容块适配函数）
        └─ 消息及流式组件事件（含 data_ref）

Web / Android / iOS / 微信小程序
  Conversation Screen（消息列表/历史/输入区/档位）
  ├─ MessagePartRenderer（按 type / variant）
  │  ├─ 基础文字/状态/通知/错误
  │  ├─ 指标/表格/图表/业务对象
  │  └─ 表单/动作/文件结果
  └─ ViewState（当前组件筛选/切换/编辑中的值）
~~~

- 不新增“通用 GenUI 编译器”或“动态 JS Runner”；已存在的 Web/原生组件是最终渲染目标。
- 适配层只做格式整理：把服务端合法结果映射成固定组件数据。销量/库存/采购业务算法仍在原有业务服务。
- Frontend 侧共享的是**消息/组件 JSON 语义**；Web React、Android Compose、iOS SwiftUI、小程序原生 TS 各自使用匹配的 UI 实现。
- 需要较多组件时优先通过复用基础 Renderer、业务字段模板、统一间距/字体/状态控制解决，不扩张新的跨端 UI 引擎。
- 现有前端技术栈若尚未正式选定，仅把这些框架作为项目既有候选，详细技术决议不在本文件擅自冻结。

## 12. 细节体验：组件标题、操作反馈与业务真实感

### 12.1 文案与内容层级

- 先一句话回答用户主要问题，再用卡片展示数据，必要时附“统计口径/查询范围”；避免为了展示功能一次塞满所有图表。
- 一个回复中尽量以 1～3 个核心数据块为主要内容，更多明细采用展开/分页；组件能力丰富不意味着每次全上屏。
- 状态文字是“正在查询库存”“正在整理销售统计”“正在处理”，不是“模型运行 Tool: search_stock(args={...})”。
- 表格列名必须直观，商品 SKU/批次/单位等细节视业务相关性展示；数值按对应业务单位，不使用模糊无单位数字。
- Agent 的建议与真实业务事实可通过“建议”“当前查询结果”文案明确区分，不凭建议直接展示“已采购”。

### 12.2 图表细节

| 图类型 | 用途 | 必需标识 | 手机默认策略 |
|---|---|---|---|
| 柱状图 | 单位一致的商品销量排名 | 统计区间、单位 | Top N，长标签省略后点击查看 |
| 折线图 | 按日/周/月趋势 | 时间轴、单位 | 简化时间刻度 |
| 饼/环图 | 分类占比 | 分类与分母总量 | 类目不宜太多，必要时合并其他 |
| 表格切换 | 数据点详情 | 原数据表与单位 | 使用同一 data_ref |
| 对比卡 | 两个时段或对象的比较 | 比较口径与日期 | 先指标，再可展开明细 |

### 12.3 用户动作反馈

- 操作按钮点击后应立即给出“正在处理”反馈，并阻止在结果未确认时重复触发同一动作。
- 正式业务完成返回实际业务对象链接及状态；业务拒绝则显示可理解原因（例如权限不足或字段有误），不显示虚假的成功。
- 权限不足时不展示未授权字段/记录。客户端隐藏按钮只是体验，服务端仍是权限事实来源。
- 空列表优先提供“调整条件/重新查询”，无须创造一套专门的错误恢复子系统。
- 后端数据变化可能让历史快照过期，刷新时新结果应与原历史可区分。

## 13. 产品首期与后续批次：以完整体验为目标，不以组件数量为目标

### 首期最完整的一条用户路径

**从文本提问 → 获得真实查询 → 一条回复内看到摘要+图+表 → 点选对象 → 填写缺少的参数 → 预览业务草稿 → 提交到正常业务服务 → 获得实际结果 → 可以继续追问。**

这一条路径覆盖：Text、Status、Metric、Table、Chart、Record、Form、Action、Error 八大基础类型及最常用 ERP 变体；它比先实现 49 个空壳组件更有价值。

### 后续结合领域逐步增加

- 商品与客户/供应商详情展示增强，进一步的排行、分组和趋势对比。
- 导入、导出、文件、语音和图像输入对应 14。
- 会话历史复用、跨端继续与状态补全对应 03/07/12。
- 复杂业务动作不在 02 实现新业务规则，而随对应采购/销售/库存模块成熟后增加相应模板。

## 14. 当前仍需用户确认的 02 交互选择（仅真实产品选择）

| 编号 | 产品选择 | 本文建议 | 状态 |
|---|---|---|---|

| UI-04 | 组件本地交互与业务提交如何划分 | 已加载数据的视图切换本地完成；新查询/写入走服务端 | 建议 |

| UI-06 | 手机窄屏表格形态 | 关键列 + 横向/明细展开，不强迫所有列同时显示 | 建议 |
| UI-07 | 文件与语音入口何时展示 | 功能真实可用时再展示；详细能力等 14 讨论 | 建议 |

**已明确且不必再次询问：** 四端同一 Agent 后端、普通用户三个档位、上游故障统一提示并手动重试、不显示内部模型费用、业务操作服务端执行、固定组件不用动态代码生成、不是重型桌面工作台。
