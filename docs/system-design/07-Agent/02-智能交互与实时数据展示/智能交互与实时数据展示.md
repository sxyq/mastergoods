## 1. 产品定位、使用目标与跨模块边界

### 1.1 一句话定义

**一个类似 ChatGPT 的单一聊天窗口，能够以流式文字、计算好的数据表格、图表、业务卡片和受控交互组件来展示服务端 Agent 对真实进销存系统的查询、分析和操作结果。** 用户不需要理解 Task、Checkpoint、Model Call、Tool 参数或上下文压缩，也不需要进入独立的桌面工作台。

### 1.2 用户实际能做什么

1. 输入“帮我查矿泉水库存”“最近 30 天什么卖得好”“准备采购草稿”等自然语言请求。
2. 在聊天输入区仅选择**快速 / 标准 / 深入**三个模型档位；速度、能力和大致消耗倾向用简短文字解释，不泄露真实模型、价格及单次积分消耗。
3. 观看流式文字回复；业务 Tool 返回真实事实后由模型结合上下文整理、计算并输出有结构的图表/表格数据，通过最少必要检查后显示在固定组件中；同一条回复可混合文本与多个组件。
4. 在表格内排序/本地筛选、在图表间切换、展开业务详情、查看数据来源和统计范围。
5. 通过参数选择、数量编辑、表单补全、草稿预览和确认操作继续业务任务；正式数据写入通过既有业务 Application Service。
6. 对上一轮结果继续追问，例如“只看饮料”“把这个数量换成 15 箱”“打开刚才第一条”。
7. 查看历史对话及当时产生的结果；需要最新数据时主动刷新或再次提问。
8. 遇到上游模型故障时保留已显示内容，展示**“模型服务暂时不可用，请重试。”**及重试按钮；遵循 Agent 01 的失败请求不向用户扣积分规则。

### 1.3 不属于 02 的责任

- 不在前端进行模型调用、意图分类、工具规划、直接 SQL、库存扣减或定价结算。
- 不由模型在客户端生成任意可执行页面、任意 JS、任意 HTML，亦不复刻复杂 DIL 编译器 / iframe / Worker 沙箱。
- 不再设计一套 ERP 业务管理后台；复杂业务编辑跳转或打开已有领域页面。
- 不在本模块冻结销售、采购、库存入出库、单位与售价、客户和付款等尚未确认业务规则。
- 不做复杂的 AG-UI / MCP / Skills/多子 Agent 工程体系；可借鉴其有价值的消息和数据交互思想。
- 不建立持续的全量库存变化订阅。**实时流式回答 ≠ 数据每秒推送**；真实查询是当前业务快照，需要最新数据时可刷新。

### 1.4 已确定的上游规则（不得在本模块另行改变）

| 来源 | 已确认事实 | 02 具体表现 |
|---|---|---|
| Agent 01 | 对外三个固定档位：FAST / STANDARD / DEEP | 显示三个通俗中文选项，不列出真实模型名 |
| Agent 01 | 切档位不改变进行中的 Task，影响下一 Task | 选择器显示新选择，但正在进行的回答不立即换模型 |
| Agent 01 | 无状态模型请求；消息和会话由本系统管理 | UI 仅根据服务端会话与消息渲染 |
| Agent 01 | 上游模型错误直接中断，用户手动重试 | 保留已展示内容 + 统一错误 + 重试 |
| Agent 01 | 本次失败模型请求不扣用户积分 | 聊天页不显示模型成本或单次积分账单 |
| Agent 总览 | Agent Runtime/Tool/业务数据操作在 Go 后端 | 前端只展示结果并转发用户操作 |
| 账户模块 | Merchant 积分账本归账户模块 | 不在聊天卡片开发账务或支付逻辑 |
| 进销存领域 | 业务授权、真实库存销售采购规则由领域决定 | 用户看到按钮不代表越权拥有业务操作权 |

## 2. 全局信息架构：默认主页、AI 居中、库存管理归一

### 2.1 已确认的产品行为

**用户已明确：** 打开 App 默认进入主页；不需要细分非采购、非销售的库存操作，一律由“库存管理”提供；AI 助手置于主底栏中间；不是蓝色主体设计。

此前五栏“商品｜采购｜AI 助手｜销售｜经营”没有主页标签。为保证主页能在导航内重复进入，**建议将第一栏由“商品”调整为“首页”**，原商品、库存查询、库存流水和商品库存维护进入首页的“库存管理”入口。用户确认的是“默认主页”，这个一级标签调整属于配套 IA 建议，不擅自写成用户已经明确批准。

### 2.2 当前推荐的五项主导航

| 主入口 | 二级内容 | 定位 |
|---|---|---|
| **首页（默认）** | 当前库存摘要、**库存管理**、商品资料及查询、常用采购/销售快捷入口、经营摘要 | 每次启动 App 默认进入 |
| **采购** | 采购进货、采购单、到货与实际收货入库、供应商关联 | 采购不等于已经入库 |
| **AI 助手（中间）** | 对话、三档、语音、真实工具日志、固定表图、业务操作 | 可直接完成经授权的业务动作 |
| **销售** | 销售出库、记录、草稿、客户关联 | 出库不等于已收款 |
| **经营** | 客户/供应商资料、往来账、人工账目和经营分析 | 不接外部支付网关 |

库存管理不额外拆出“其他入库”“其他出库”等一级入口；若有确实需要的日常盘点或库存操作，统一放在库存管理中，具体操作依库存领域已经确认的规则。

### 2.5 AI 允许实际业务办理

**用户已允许在 Agent 中完成业务操作，不限定只能选择商品或改数量。** 只要已有固定业务卡支持该业务所需字段、用户有权限、Go Tool 和领域服务可以合法执行，聊天中就能填写、修改、确认并完成采购、销售或库存相关操作。复杂表单可以选择跳转现有完整业务页面，但不是强制跳转；无论入口如何，服务端真实结果才代表正式写入成功。

### 2.6 导航和会话状态

打开 App **默认主页**，不再默认进入 AI 或自动恢复上一 Tab 作为首页策略。切到 AI 后，仍保留此前会话、已生成表图和未发送文本；用户从其他页面返回 AI 时继续查看。跨设备同步与正在运行 Task 的细节归 03/07/12。库存管理是正常业务页面，不额外复制 AI 专属商品/库存业务服务。


## 3. 聊天页面布局、手机四端适配与输入区

### 3.1 空白首页、有历史对话与运行中的区别

| 界面状态 | 主要内容 | 底部输入区 | 主业务底栏 |
|---|---|---|---|
| 空会话 | 简洁欢迎语、适量建议提问、最近使用提示 | 可输入、显示档位/语音 | 显示，AI 选中 |
| 已有消息 | 用户消息与 Agent 回答的混合内容流 | 可继续追问 | 显示 |
| Tool 执行中 | 可展开步骤链、当前转圈项、已到达的文本 | 发送位置可显示停止 | 显示 |
| 执行资源繁忙 | 原有聊天和本机未发送输入保持可见 | 发起新执行时提示“模型繁忙，请稍后重试。”，不透露任务名额或线程数量 | 显示 |
| 数据展示中 | 指标、可交互图表、表格/记录卡 | 可输入、支持继续追问 | 显示 |
| 业务信息补充 | 商品选择、数量编辑、业务信息预览 | 可输入 | 显示 |
| 模型故障 | 已输出内容+固定提示+用户重试 | 可输入 | 显示 |
| 打开历史列表 | 搜索、时间分组、会话管理 | 历史抽屉/页面遮挡输入区 | 按导航容器决定 |
| 软键盘出现 | 焦点处正常输入 | 随键盘上移 | 暂时隐藏或让位 |
| 业务详细编辑页 | 原 ERP 单据/表单 | 不显示 Agent 输入框 | 可根据保存按钮布局隐藏 |

### 3.2 顶栏、消息区、输入区分工

**顶栏**：页面标题、打开历史、开启新对话；不展示具体 Provider/Model 和内部 Token 数据。**消息区**：用户右侧气泡、Agent 正文式信息流、执行链和数据洞察容器；正文内容可跨多个有序组件。**输入区**：文字、多行编辑、附件入口、语音按钮、紧挨发送的档位、发送/停止；所有按钮只在能力实际可用时启用。

### 3.3 历史管理的完整入口

手机点左上角历史入口，打开抽屉或全屏历史页：支持新建、按时间分组、重命名及删除。历史搜索先分组呈现**会话标题命中**，再呈现**消息文字/回复摘要命中**，支持模糊匹配并可定位到原消息。执行期间的会话不提供删除；所有Task终结后才允许删除。历史中的图表和表格显示**当时查询快照**与时间，不自动变成最新库存；用户明确点刷新才重新查询。桌面可常驻可折叠历史列。

### 3.4 滚动与组件焦点

- 仅当用户位于列表末尾附近时跟随流式增量滚动，用户上翻时不强制拉回底部，并显示“回到最新”。
- 同一 part_id 局部更新不重新创建整个消息，不让正在编辑的数量、筛选条件、键盘焦点或图表切换被重置。
- 手机大表优先关键列、横向滚动和详情页；图表轴标签过多时缩略，用户点数据点可以读出完整值。
- 业务按钮点击后显示处理状态；正式结果只能由服务端工具成功返回后显示。
- 已发送消息应稳定关联服务端消息 ID，不因双击发送产生两条独立操作；并发/幂等详细语义由 03/06/10 负责。

## 5. 固定组件库：12 类基础渲染器与 49 个业务模板

### 5.1 设计选择

**避免“只有十种卡片不够用”，也避免“每个业务结果一个全新框架”。** 本文推荐分成两层：

- **基础渲染类型（12 类）**：文本、状态、通知、指标、表格、图表、列表、对象详情、表单、操作区、文件、错误。这是真正要在四端维护的一小组可复用渲染能力。
- **固定业务模板/变体（约 40 种候选）**：如商品卡、库存摘要、销量排行榜、销售单据卡、采购草稿、数据筛选条等。它们由上述渲染类型组合而成，大多数只是固定字段集合和有限交互规则，不是独立运行环境。

Agent 可以在已允许的组件类型和业务模板中选择展示方式，但由后端展示适配逻辑提供合法的结构化数据、字段单位和权限范围。**模型不能直接指定任意前端代码或伪造“成功创建业务单”。**

### 5.2 十二类基础渲染类型

| 基础类型 | 职责 | 常见内容 | 主要交互 |
|---|---|---|---|
| TextRenderer | 普通正文、标题、Markdown | 普通解释、结论、建议、引用提示 | 选择/复制、继续提问 |
| StatusRenderer | 一行简短任务状态 | 正在处理、正在查询、生成中、已中断 | 默认无需操作 |
| NoticeRenderer | 提示、无结果、注意项 | 无符合条件商品、时间范围说明 | 查看原因、调整条件 |
| MetricRenderer | 一个或一组汇总指标 | 库存量、销量、金额、商品数 | 查看明细 |
| TableRenderer | 列表式结构化记录 | 商品列表、出库记录、库存明细 | 排序、筛选、分页、行操作 |
| ChartRenderer | 图形统计及数据点 | 柱状、折线、饼/环、排名/趋势 | 切换视图、数据点查看 |
| ListRenderer | 紧凑信息、分类/分组清单 | 排名、待办、异常提醒、分组项目 | 展开分组、选择条目 |
| RecordRenderer | 单条业务对象详情 | 商品、客户、供应商、草稿、业务记录 | 查看原业务详情 |
| FormRenderer | 受控参数补全 | 选择商品/客户、数量、单位、日期 | 输入/选择/提交 |
| ActionRenderer | 有具体语义的操作入口 | 创建草稿、刷新、继续、确认 | 调用明确的后端动作 |

### 5.4 组件之间如何组合，而不是彼此孤立

~~~mermaid
flowchart TD
    MSG[一条 Agent 消息] --> TXT[TextBlock：解释]
    MSG --> S[StatGrid：摘要]
    MSG --> CH[ChartCard：统计图]
    MSG --> TB[DataTable：明细表]

    ACT --> NEXT[下一次聊天/业务动作]
~~~

**图示说明：** Agent 消息有序组合多个内容块。Chart 和 Table 可引用同一批服务端统计结果；用户本地切换“图/表”不必重复查询或重新调用模型。

### 5.5 每一类组件的必备通用状态

| 状态 | 呈现行为 |
|---|---|
| loading | 占位/简短加载文字，不伪造数值 |
| ready | 展示服务器返回的完整有效数据 |
| empty | “暂无符合条件的数据”，保留查询条件 |
| error | 组件级查询失败说明；模型层错误遵循统一固定文案 |
| disabled | 无权或暂不可操作时不显示虚假可用按钮 |
| stale | 历史查询快照，标记查询时间并提供刷新 |
| editing | 受控字段的本地编辑中状态，未经保存不视为业务事实 |
| submitted | 仅当后端返回实际业务成功结果才显示成功 |

**数据组件的显示要有单位、查询范围与数据时间。** 对权限敏感或缺失字段应根据服务端授权结果隐藏或标注不可查看，而不是填入虚假默认值。

## 7. 可展开的思考与真实 Tool 执行链

### 7.1 用户点击的精确交互

第一级：一句话进度，例如“正在整理近30天销售统计”。

第二级：时间线步骤，展示 **已完成 / 当前运行中 / 等待中 / 失败**。运行中的转圈图标本身和对应整行都可点击；不是一个不能操作的纯动画。

第三级：展开具体步骤后可以阅读真实工具状态、工具显示名称、输入参数摘要、结果摘要、运行用时和对应的结果入口。用户打开后，这个步骤继续运行，UI 的日志详情也跟随新事件更新，不必反复打开。

~~~text
┌──── 统计最近30天销量 ───────────────┐
│ ◌ 正在执行                   [收起]  │
│ 处理目的：统计指定商品近30天销量     │
│ 工具：销售统计查询                  │
│ 参数：商品 / 统计范围 / 汇总方式     │
│ 结果：正在等待真实查询完成          │
│ 用时：执行中                        │
└────────────────────────────────────┘
~~~

### 7.2 状态、来源和日志条目

| 类型 | 用户表现 | 必须来自哪里 |
|---|---|---|
| understanding | 理解需求：查询销售情况 | 可由模型提供对外的简要目标，不冒充已执行工具 |
| tool_waiting | 等待调用某项业务能力 | Agent Runtime 真实调度 |
| tool_running | 转圈、正在查询库存或销售 | Runtime/Tool 的实际开始事件 |
| tool_completed | 对勾、已得到结果摘要 | 真实工具返回 |
| tool_failed | 查询步骤未成功 | 真实工具失败结果 |
| composing | 正在整理文字与图表 | 模型输出阶段 |
| finished | 完成几项业务处理步骤 | Runtime 统计已完成步骤 |
| interrupted | 本轮中断 | 真实 Agent 错误状态 |

**绝不把“模型内部原始推理链”当作这张执行日志卡的内容。** 模型可以提供公开的任务理解/进度摘要，具体 Tool 开始/结束/结果/用时必须由 Go 运行时实际事件驱动；不出现原始 SQL、Provider Key、敏感字段、内部调用堆栈或模型的隐私思考内容。

### 7.3 Tool Log 与 Intelligent UI 容器关联

以最少字段关联 task_id、step_id、message_id、part_id、result_ref。模型基于某 Tool 结果生成图表容器时，part.source_refs 可关联相应结果；用户在执行时间线上点“查看结果”可滚动到对应数据容器。**这只是消息和展示引用，不是额外业务数据库体系。**

### 7.4 完成与失败的外观

- 运行中：展开展示当前真实步骤，用户可点转圈查看详情。
- **已确认**：运行中的真实步骤可点击转圈或整行展开实时日志；完成后默认收拢到“已完成 N 个步骤”的摘要，用户可以再次点击展开。用户正在查看某一步详情时，不因新事件强制关掉。最终文字和图表随后正常显示。
- 上游模型失败：保留已显示步骤与内容，原位呈现 **“模型服务暂时不可用，请重试。”**；用户主动重试，当前失败请求不扣用户积分。
- 业务工具自身拒绝/权限不足：展示与其真实结果相符的说明，不伪装为模型高峰。
- 运行中步骤的状态更新与最终图表生成是两个独立通道，不要求 Tool 结束就自动出现图表。

## 8. 统一 Data Insight Container：布局与数据表达

### 8.1 一个容器，多个视图

~~~text
┌───────── 近30天饮料销量 ──────────────┐
│ 查询范围：近30天    单位：瓶          │
│ [销售数量 675] [参与商品 3]           │
│ [图表] [表格] [排行]        [展开]    │
│ ┌───────────────────────────────┐   │
│ │     模型输出的固定视图数据     │   │
│ │ 图表/表格使用同一结果数据集    │   │
│ └───────────────────────────────┘   │
│ 真实统计来源/时间 [查看明细][继续追问]│
└───────────────────────────────────┘
~~~

**数据来自哪里：** Tool 产生的真实数据进入模型上下文，模型可聚合、分组、计算派生指标，并以受限字段调用 present_ui。Go 解析成该容器的数据内容。前端不在 Tool 返回时就无条件直绘，更不从自然语言字符串用正则猜图表数字。

### 8.2 选择哪一种图形

| 用户问题类型 | 推荐预置视图 | 常见替代 |
|---|---|---|
| 商品库存是多少 | metric + 商品卡 | 相关明细表 |
| 商品销量 Top N | horizontal_bar / ranking | bar、data_table |
| 每日销售趋势 | line | area、data_table |
| 类别销售构成 | donut / pie | ranking、stacked_bar |
| 两时间段对比 | grouped_bar / comparison | data_table |
| 库存增减组成 | waterfall（具备真实变动记录时） | 库存流水表 |
| 价格与销量 | scatter（两轴有单位） | data_table |
| 星期×日期统计 | heatmap（实际存在二维数据时） | data_table |
| 真实业务阶段统计 | funnel（仅真实存在阶段） | data_table |
| 已有目标完成情况 | progress_gauge（目标真实存在） | metric |
| 推导日均销量等 | calculation + metric | 数据表 |

模型可选择默认视图，但**每次响应不必强制绘图**。一条短问答仍应只显示文字。模型可提交多个合规 part；在窄屏优先摘要、主图和“查看完整明细”，避免一次塞满所有类型。

### 8.3 容器状态

waiting → renderable → completed 是最常见路径；此外有 empty、unsupported、error、historical。文字可以先到达；图表需要完整结构化块和必要检查后才能渲染，不能拿尚未结束的数字片段绘制。模型若输出新有效 revision，可原位更新指定 part，保留用户当前选择的图/表状态。


## 9. 模型可见的 present_ui：单一展示契约

### 9.1 最终推荐的一种实现方式

**统一使用一个模型可见、无业务副作用的 present_ui 展示工具**，而不是 21 个图表 Tool，也不是让模型生成可执行 DIL/JS。Go 业务 Tool 负责查商品、库存、销售、采购和真实写入；模型拿到 Tool Result 后决定解释、衍生计算、图形及 UI 数据；present_ui 将完整结构参数转成消息展示内容。已有 Provider 协议适配必须保证工具调用参数可解析；原生 API 差异由 Agent 01 Adapter 负责。

~~~mermaid
flowchart LR
    U[用户需求] --> INTENT[当前模型理解业务和展示意图]
    INTENT --> TOOL[真实业务Tool]
    TOOL --> FACT[真实Tool Result]
    FACT --> MODEL[模型整理并计算]
    MODEL --> V[present_ui 展示工具]
    V --> CHECK[Go 固定类型解析与必要检查]
    CHECK --> PART[标准消息 parts]
    PART --> UI[四端预置组件渲染]
    MODEL --> TEXT[自然语言解释]
    TEXT --> UI
~~~

### 9.2 模型可见的展示目录

present_ui 的 description 简短描述固定 view_type（第 6 节）与何时选表、图或卡。具体输入按 type/view_type 分支为固定字段，而不是开放的任意 data/HTML/JS。**提示词说明何时使用，Schema 说明能填什么字段。** 需要展示时可以调用，不需要图形时直接回答文字。

### 9.3 模型提示词摘要（可纳入 Agent System Prompt）

~~~text
你是仓库进销存 Agent。商品、库存、销售、采购和实际写入结果只能依据已执行的业务 Tool。
先理解用户业务目标，需要数据时调用合法工具；拿到结果后可整理、排序、分组、聚合与衍生计算。
如果最终回答需要指标、表格、图表、业务卡、交互表单或计算说明，使用 present_ui。
只使用已注册的 view_type 与规定数据字段，包含单位、范围、真实来源引用。
fact 表示查询事实，不得与真实 Tool Result 矛盾；derived/estimate 应注明来源和推导口径。
mutation_result 只能来自已经成功的业务写 Tool，不可凭 present_ui 声称修改成功。
不需要图形的问题正常文字回答；不生成任意 HTML、JavaScript、DIL 或原始内部推理。
~~~

### 9.4 与业务 Tool 不混淆

| 工具类别 | 负责的真实行为 | UI 与安全边界 |
|---|---|---|
| business_read | 查询授权商品、库存、经营记录 | 产生可追溯的业务查询事实 |
| business_write | 调用原有 Application Service 创建/修改业务 | 业务成功必须来自服务端返回 |
| **presentation: present_ui** | 把模型给定的数据对象变成结构化 UI 消息 part | **不查询或改写真实业务记录** |

对于 Tool Calling 和最终文字的具体先后顺序，不强求所有模型供应商支持相同输出顺序。一个 Task 可以多次模型请求与多次真实 Tool 调用；present_ui 只是其中的展示能力，不新建业务状态机。


## 10. 前后端统一数据结构与最低必要过滤

### 10.1 标准消息：有序 parts

一条 Agent Message 包含 message_id、conversation_id、status，以及按呈现顺序排列的 parts。所有 UI 块有稳定 part.id；文本 delta 追加指定文本 part；结构化组件使用 component.upsert 进行局部更新。**模型的 present_ui 调用参数和客户端存储的 MessagePart 是两个层次，但共用固定 view_type 和标准化 data 结构；Go 负责一次转换。**

### 10.2 唯一规范示例（模型调用 present_ui 的参数）

~~~json
{
  "title": "矿泉水库存与销量",
  "parts": [
    {
      "client_ref": "stock_sales",
      "kind": "insight",
      "view_type": "bar",
      "title": "库存与近30天销量",
      "origin": "derived",
      "source_refs": ["stock_tool_1", "sales_tool_2"],
      "scope": "当前商户，近30天",
      "metrics": [
        {"key":"stock", "label":"当前库存", "value":120, "unit":"瓶", "origin":"fact", "source_ref":"stock_tool_1"},
        {"key":"sales", "label":"30天销量", "value":360, "unit":"瓶", "origin":"fact", "source_ref":"sales_tool_2"},
        {"key":"daily", "label":"日均销量", "value":12, "unit":"瓶/天", "origin":"derived", "expression":"360/30"},
        {"key":"coverage", "label":"预计可售天数", "value":10, "unit":"天", "origin":"estimate", "expression":"120/(360/30)"}
      ],
      "data": {
        "category_key": "name",
        "series": [{"key":"qty","label":"数量","unit":"瓶"}],
        "rows": [
          {"name":"当前库存","qty":120},
          {"name":"30天销量","qty":360}
        ]
      }
    }
  ]
}
~~~

**解释：** 数据为示例，不对应真实商户。present_ui 是一次仅展示的调用；模型可以把 Tool 的库存 120、销量 360 生成日均和估算天数，但不能自行把真实库存改成 100。chart 的 data.rows 是单一标准化数据集，DataTable 切换使用同一数据引用或行，而不是让模型再复制一份可能冲突的表格值。源引用由服务端限定合法集合。

### 10.3 规范化后的前端事件

~~~json
{
  "event": "component.upsert",
  "message_id": "msg_102",
  "part": {
    "id": "part_insight_1",
    "type": "insight",
    "view_type": "bar",
    "revision": 1,
    "data_ref": "stock_sales",
    "title": "库存与近30天销量",
    "data": {
      "category_key": "name",
      "series": [{"key":"qty","label":"数量","unit":"瓶"}],
      "rows": [
        {"name":"当前库存","qty":120},
        {"name":"30天销量","qty":360}
      ]
    }
  }
}
~~~

客户端根据 type 和 view_type 查自己的固定渲染器；Android Compose、iOS SwiftUI、Web React 与小程序各自实现原生视觉，但数据语义相同。不能把模型提供的字符串当可执行 UI 程序。

### 10.4 约束：只保留防止明显错误的最低必要处理

| 规则 | 为什么需要 |
|---|---|
| view_type 属于固定枚举，字段符合对应数据体类型 | 未知类型不执行、图表不白屏 |
| 业务数值有效、有限；标题/行数/系列数有合理限制 | 避免残缺 JSON、过大内容冲垮手机 |
| 单位、时间范围和坐标口径一致 | 不把瓶和箱或元和件错误混加 |
| origin=fact 的关键库存/业务状态对应本次合法 Tool Result | 防止模型改写真值后伪装成业务事实 |
| origin=derived/estimate 标注计算依据与来源 | 允许模型计算新指标，但与真实库存区分 |
| mutation_result 必须有关联正式业务 Tool 的成功结果 | present_ui 成功不等于已经修改数据库 |
| action_id 必须是后端允许的操作 | 不按模型生成任意前端脚本执行写入 |
| 格式失败时局部降级 | 展示可靠文字和“该图表暂无法展示”，不重新执行已提交业务 |

**注意：** 格式正确不等于模型算得正确。用于展示的普通衍生指标可让模型计算并注明口径；财务金额与库存等需要当作权威事实显示时，必须以服务端真实业务结果和领域规则为准。避免额外建立一套独立图表审计或反复校验系统。

### 10.5 为什么不能从散文正则提取数据

“360 瓶销量，日均 12 瓶，现有 120 瓶，估计 10 天卖完”的四个数字分别是历史销量、派生率、现存库存和估计天数。单纯文本解析无法稳定区分来源、单位、口径与日期，必须以模型产出的受约束数据对象作为可视化输入。

### 10.6 Tool 业务数据变化与界面更新

- 原始 fact：Tool 查询结果；历史消息保留原快照。
- derived：模型生成的计算指标，可以换图、改分类、解释，但不能当数据库写入。
- mutation_result：真正业务写 Tool 返回的新事实，模型可以据此生成新业务结果卡和图表，旧查询卡不被悄悄篡改。
- 模型未结束的半截 UI 数据暂存；完整有效 part 才发布；出现合法更新用同一 part_id + revision 局部替换。


## 11. 消息流、Tool 执行事件和跨端交互

### 11.1 最小用户可见事件集合

| 事件概念 | 内容与效果 |
|---|---|
| message.start | 为当前 Agent 回复创建消息容器 |
| trace.step.start / trace.step.update / trace.step.done | 更新可展开的真实 Tool 步骤、参数摘要与结果 |
| status.update | 显示任务处理阶段与“正在整理回答”等状态 |
| text.delta | 向稳定 TextBlock 追加文本 |
| component.upsert | 将完整合法数据块填入固定 UI 组件 |
| message.done | 回复完成，工具链摘要可以收起 |
| message.error | 模型上游故障的固定提示与手动重试 |
| action.result | 返回真实业务动作/表单的处理结果 |

这些是 Agent 02 对显示语义的定义，不在这里强行冻结 Agent 12 最终 SSE/WebSocket 格式或不同端的 transport 实现。组件高频变化时可选择局部 revision，但首个版本不必复制第三方 DIL 的全路径通用 patch 编译引擎。

### 11.1.1 断网恢复的文字仍必须逐段浮现（与03/12统一）

**本轮已确认**：客户端恢复连接后，03先提供最新JSON会话快照及服务端真实Task状态，12从一致cursor接续新事件。对于断网期间产生、用户尚未看过的文字，**仍使用02原本的流式消息呈现组件逐段显示**，不能瞬间在页面铺满大段新内容。已见文字立即恢复、最近一轮未见文本进入显示队列、完整表格/图表按原顺序一次渲染。Task如果已经完成，状态仍显示已完成，不要为了文字动画伪装模型还在推理。长内容允许用户点击“立即显示全部”。

**并发是后台执行资源，不是前端额度**：同一账号最多同时运行三个独立会话的主Task，后台并行执行，同会话同时一个，各自有独立task_id；Tool调用次数不受该数字限制。用户界面不展示线程数、Task数量或并发名额，无法受理新执行时统一提示“模型繁忙，请稍后重试。”已加载内容优先本机恢复，另一设备自动从服务器下载；未读新增文字按原流式效果呈现。已发送消息不可编辑，输入框/卡片的未提交修改仅保存在当前设备。具体见03第5、6、10、11、13节，实际流传输由12负责。

### 11.2 真实流程时序（一次库存和销量分析）

~~~mermaid
sequenceDiagram
    actor 用户
    participant UI as 手机/Web对话界面
    participant AGENT as Go Agent Runtime
    participant TOOL as 真实进销存工具
    participant MODEL as 当前档位模型
    participant VIEW as present_ui
    用户->>UI: 库存能撑多久 最近30天卖得怎样
    UI->>AGENT: 新消息与当前档位
    AGENT-->>UI: message.start
    AGENT->>MODEL: 必要历史与业务Tool定义
    MODEL-->>AGENT: 请求查询库存及销售
    AGENT-->>UI: trace.step.start
    AGENT->>TOOL: 查询真实库存与销量
    TOOL-->>AGENT: 返回实际Tool Result
    AGENT-->>UI: trace.step.done
    AGENT->>MODEL: 加入Tool Result和可用展示组件
    MODEL-->>AGENT: text.delta 文字解释
    AGENT-->>UI: text.delta
    MODEL-->>AGENT: present_ui 结构化参数
    AGENT->>VIEW: 仅展示型调用及必要字段检查
    VIEW-->>UI: component.upsert
    AGENT-->>UI: message.done
~~~

**执行链实时事件与模型 UI 输出是两个独立过程。** Tool 完成后步骤可立即变为对勾，但最终统计图表仍要等待模型组织完完整合法数据块。用户点击转圈步骤可查看真实执行摘要，不能展示模型内部未公开思维链。

### 11.3 消息状态与故障

~~~mermaid
stateDiagram-v2
    [*] --> Created
    Created --> Processing
    Processing --> Streaming
    Processing --> Failed
    Streaming --> Completed
    Streaming --> Failed
    Failed --> RetryReady
    RetryReady --> Processing: 用户主动重试
    Completed --> [*]
~~~

- **模型上游故障**：停止本次流，保留已出现文字和执行步骤，统一文案“模型服务暂时不可用，请重试。”，用户手动重试，遵循 Agent 01 失败模型请求不扣用户积分规则。
- **组件数据格式失败**：该组件显示“图表暂不能展示”，其余可靠文字不必整轮报模型故障。
- **客户端网络暂时中断**：属于连接层状态，不能直接宣称上游模型失败；恢复和跨端状态按 03/07/12。
- **业务工具拒绝**：用普通用户可理解的业务失败反馈，不把权限不足伪装成“模型忙”。
- 对已提交的经营写操作，不允许 UI 一次重试就自行重复提交；真实工具执行和恢复规则留给 06/07/10。

### 11.4 任务执行期间切换页面

用户去货品或业务页再返回 AI，前端应恢复当前会话、已显示消息、表格当前视图和未发送的文本；服务端任务是否继续及重新订阅事件由后续会话/流式模块决定，不让 UI 重新提交已处理的任务来“刷新”页面。


## 12. 组件动作：本地交互、业务请求与正式结果

| 动作类型 | 示例 | 客户端能否自行完成 | 是否需要重新调用模型 |
|---|---|---|---|
| display.local | 已加载表格排序、图/表切换、展开字段 | 可以 | 不需要 |
| query.refresh | 刷新库存、切换统计日期需新数据 | 不可以，调用后端查询 | 通常不需要单独的意图识别模型；按实际后端设计 |
| ask_agent | “把范围改成上个月”“解释销售变化” | 发送新用户需求 | 由 Agent 决定 |
| business.preview | 修改采购数量并预览表单 | 本地临时草稿可变化，服务器决定有效字段 | 是否调用模型取决于任务 |
| business.execute | 创建采购草稿、修改商品、确认出库 | **必须服务端执行** | 由 Agent/Tool 模块处理 |
| navigation.open | 打开本商户已有销售单据详情 | 前端导航到授权的 ERP 页面 | 不需要 |
| file.open/export | 打开报表或请求导出 | 有效文件可本地打开；新导出由服务端 | 不必每次调模型 |

### 12.1 表单与用户动作设计

- InputCard 只提供当前任务需要的字段，默认值来自服务端合法数据或显式用户输入，不能凭空编造客户、仓库、售价和付款状态。
- 选择商品/客户时，展示有足够辨识度的候选项（名称、SKU/联系信息中允许展示部分），并将**真实业务对象 ID**提交回后端，不用仅凭显示名称作最终引用。
- 数量编辑同时展示单位；商品存在多单位关系时以领域模块有效规则为准，不由 UI 自行设定箱/瓶换算。
- 真实业务动作必须有服务端成功结果才能显示“创建成功”“出库成功”，用户看到的预览未必已写入数据库。
- 客户端可保存临时视觉编辑状态，但**不承担最终业务规则校验或持久化真相**；后端重新核对授权、业务对象和必要字段。
- **内部暂存不对用户暴露**：候选回复、内部准备数据、领域Draft与上下文采纳属于服务端处理；不显示“暂存区”“提交区”“草稿已持久化”等技术阶段。用户只看自然建议、业务预览、必要字段、必要的确认动作和最终真实结果；内部暂存不取消实际经营操作需要的确认。
- **已确认允许 AI 内直接业务办理**：固定业务组件只要覆盖当前所需字段与交互、获得用户许可/权限且真实业务 Tool 可处理，用户可以在聊天内完整填写、修改和确认。复杂表单**可以**进入现有业务编辑页，但不是必须跳转；无论哪种展示方式，最终成功必须来自领域服务的实际结果。

### 12.2 View State：只保留有意义的交互状态

示例仓库的 view-state 机制为动态 UI 回灌完整控件状态。我们可以精简为：part_id、当前选中项/筛选/数据分页、用户提交的必要参数和 action_id。**不要在每一次滑块拖动都调用 LLM**。客户端改变未提交的筛选条件可以先本地完成；只有涉及新业务信息/下一任务时才提交必要状态。

~~~mermaid
    UI->>UI: 本地展示待提交的预览值
    用户->>UI: 点击准备或确认
~~~

## 13. 进销存典型场景与业务用例（八种）

### 13.1 用例 U-01：查询一个商品当前库存

- **输入：** “矿泉水还有多少库存？”
- **服务端工作：** Agent 识别查询，调用商品与库存服务；必要时识别多个同名商品并要求用户选定。
- **UI 输出顺序：** StatusLine“正在查询库存” → TextBlock“查询结果如下” → StockCard（商品、单位、真实库存、查询范围、时间）→“查看明细” ActionCard。
- **响应场景：** 匹配 1 个商品时展示；匹配多个时显示 SingleSelect；没有结果时显示 EmptyResult；无法查看则显示权限提示，不伪造数量。
- **移动体验：** 当前库存数优先大字显示；商品/单位/范围可见；较多仓库字段放入展开区域。当前产品仓库规则仍以业务设计为准，不预设多仓。
- **业务边界：** 不因用户说“还剩多少”就将采购在途数、已售未出库数等自行混合为可用库存。

### 13.2 用例 U-02：查询销量并给出经营分析

- **输入：** “最近 30 天什么饮料卖得最好？”
- **服务端工作：** 使用销售服务确定范围、统计字段和合法单位；返回 Top N 结果和相应解释数据。
- **UI 输出顺序：** 文字说明 → StatGrid（销售件数等同口径摘要）→ RankingList 或 BarChart → DataTable → FollowUpSuggestions。
- **交互：** 用户切换图表/表格时本地完成；点某商品进入 ProductCard；用户更改为“上个月”时触发新服务端统计。
- **空数据：** “该范围没有销售记录”，允许修改范围，不制造趋势图。
- **边界：** 不将混合“瓶/箱/件”直接相加，不自动等同销售完成和已收款。

### 13.3 用例 U-03：生成采购草稿预览

- **输入：** “帮我准备矿泉水 10 箱的采购草稿。”
- **服务端工作：** 查商品、对应单位和可能必要字段；若缺少供应商/数量等则返回补充参数请求。
- **UI 输出顺序：** TextBlock → ProductCard/SingleSelect（如歧义）→ ParameterForm/QuantityEditor → DraftPreviewCard → ActionCard（受控动作）。
- **交互：** 把数量从 10 改成 15，先更新本地预览；用户明确提交后才根据业务模块校验并创建合法草稿。
- **边界：** 预览状态不等于已创建，不等于采购完成，不等于库存入库；是否存在采购草稿及其具体字段由采购模块最终确认。

### 13.4 用例 U-04：查看销售出库记录

- **输入：** “查一下昨天卖给老王的水。”
- **服务端工作：** 按客户、时间、商品和 Merchant 权限查询真实销售记录；有歧义时提供选择。
- **UI 输出：** DataTable/CompactTable + SaleRecordCard + 关联商品信息。
- **交互：** 点记录打开既有销售页面，或发送新的追问。
- **边界：** 不凭“卖”自动生成收款记录，不替销售模块确定历史补录、实际出库时间和客户账务 W/S 待决规则。

### 13.5 用例 U-05：多轮追问与数据视图切换

用户先问“近 30 天销量”，再点图表里的“矿泉水”，接着问“它的库存呢”。下一轮请求由 03/04/05 依据消息历史与业务对象引用理解；02 只把选中的对象 ID 与可用组件上下文交给服务端。前端本地切换图表/表格不需要调用模型，也不应该改变先前查询结果的原始时间范围。

### 13.6 用例 U-06：模型流式回复中断

~~~mermaid
flowchart TD
    A[用户发送请求] --> B[显示正在处理]
    B --> C{模型回复是否正常}
    C -->|正常| D[增量展示文字和业务组件]
    D --> E[完成本轮]
    C -->|上游异常| F[保留已经显示的内容]
    F --> G[固定显示模型服务暂时不可用 请重试]
    G --> H{用户主动点击重试}
    H -->|点击| I[再次向服务端发请求]
    H -->|不点击| J[保持中断状态]
~~~

**说明：** UI 不能将已经失败的请求标成成功、不能擅自扣用户积分，也不尝试拼接主备模型的半截回答。是否复用既有业务步骤/Task 属于 06/07，不在此重复设计。

### 13.7 用例 U-07：历史结果与刷新

- 历史卡片显示的是当时查询得到的真实结果快照；例如“昨天查询的库存为 120 瓶”，下次打开历史仍显示昨日结果且带查询时间。
- 点击“刷新当前库存”发起新的查询并显示新的结果或新消息；旧消息不应悄悄变成今天的数据而失去历史含义。
- 02 定义视觉行为，历史数据保存、Message 关联及跨端恢复由 03/12 明确。

### 13.8 用例 U-08：文件结果与附件

- 聊天中可通过 FileCard 展示“销售统计.xlsx”等已生成文件；上传图片、Excel、语音输入和导入预览依据 14 模块确定细节。
- 首期若尚未实现上传/语音，不保留无效按钮、占位完成提示或虚假的“已识别文件”行为。
- 02 只负责本端预览、状态和用户操作入口，不定义后端文件解析算法。

## 14. 视觉语言、关键帧与第三方实现参考

### 14.1 统一设计语言（主色不使用蓝色；墨绿也不再优先）

**用户已明确不采用蓝色主体，后来又反馈此前绿色主色不理想。** 历史 Android 品牌蓝、此前星穹蓝以及上一版深墨绿都不是当前确定的品牌色，不应继续在正式设计中称之为已经选择。

现阶段优先建议采用**石墨陶土**作为下一轮视觉探索基准（**未获用户最终确认**）：主文字石墨黑 #282624、暖白底 #F8F5F0、白色业务卡 #FFFFFF、重点交互陶土色 #B25C45、次要文字 #77716B、浅边框 #E9E5DF。陶土色只用于选中导航、发送按钮、少量重点动作，不让数据表/图表大面积着色。也可以对照黑金商务或低饱和梅紫，但不同时引入多个主色。

| 层级 | 当前视觉建议 | 说明 |
|---|---|---|
| 页面背景 | 暖白 #F8F5F0 | 长时间查看经营数据的低刺激背景 |
| 卡片表面 | 白色 #FFFFFF | 库存/业务表单/图表/表格 |
| 主标题与正文 | 石墨 #282624 | 保持清晰、自然对比 |
| 重点交互 | 陶土 #B25C45 | AI 中央入口、发送、选中操作 |
| 次要文字 | #77716B | 时间、单位、来源说明 |
| 反馈色 | 成功/警示/错误语义独立 | 不能用品牌色替代业务状态判断 |

正文约 15～16px、说明 12～13px，按 4/8/12/16/24px 间距组织，卡片约 14～16px 圆角。最终品牌色需以后续用户看到的视觉关键帧确认，不能把这份 PRD 的推荐色值当作已冻结品牌资产。

## 15. 与 Agent 01、03～17 和真实业务模块的职责边界

| 模块 | 02 所需的接口与分工 |
|---|---|

| Agent 06 Agent Loop | 多次模型请求、真实 Tool 调用和阶段事件 |

| Agent 08 上下文 | 向模型提供必要对话历史与合法 Tool Result |
| Agent 10/11 业务工具/草稿 | 领域业务写入、草稿、确认和授权 |
