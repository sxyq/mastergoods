# 07-Agent / 06 — Agent 循环与任务执行

> **设计阶段：已确认的执行规则与下一轮详细讨论入口（2026-11-11）。** 本文件是 Agent 主执行流程的归属文档，不把 02 的 UI、03 的消息存储、07 的停止恢复、08 的上下文和 11 的业务提交再次实现一遍。尚未确认的运行时细节明确标为建议；当前仓库未实现生产 Agent Runtime。

## 1. 本模块负责什么

### 1.1 目标

在 Go 模块化单体中，接收已经受理的用户任务，组织模型请求、合法 Tool 调用与结果回填，按服务端真实事实记录每一步，支持执行期间用户继续发送新消息、默认插话和可选排队。模型请求、Tool 执行、UI 文字动画与经营数据库事务是不同层次。

### 1.2 责任分工

| 对象/模块 | 本模块职责 | 其他模块职责 |
|---|---|---|
| Task | 每轮独立 task_id、执行循环、步骤关联和调度 | 03 保存消息/Task 引用；07 定义取消和终态恢复 |
| 模型请求 | 发起前的准入/等待、真实在途数、结果进入下一轮 | 01 维护模型/Provider/价目及 Model Call 用量计费 |
| Tool | 选择可调用的合法工具、执行、接入实际结果 | 05 定义 Tool 契约；业务 Application Service 持有正式业务事实 |
| 用户新指令 | 识别发送模式，按排队或插话调整后续执行 | 02 提供简单选择；03 保存已发送消息与任务关系 |
| 上下文 | 在发起模型请求前索取有权限的上下文 | 04/08 识别对象、澄清歧义、组装消息与压缩 |
| 流式与管理记录 | 产出真实 Task/Step 事件、关联输入与输出 | 12 传输增量；17 提供管理员受控查看 |
| 经营变更 | 调用原业务命令并记录真实结果 | 11 处理业务确认；销售/采购/库存服务决定事务是否成立 |

## 2. 核心身份：Task、模型请求、Model Call、Tool Call

- **Task**：用户发出的一个工作指令对应一个独立身份，可有多轮模型调用、多个 Tool 步骤、等待用户或等待模型资源。**Task 数量不受“3”限制**；相同会话也可以有多个关联 Task，消息和结果不得混写。
- **在途模型请求**：当前确实已向上游发出、尚未结束的模型请求。**每个用户同时最多 3 个**，超过时待发请求服务端排队，有名额后继续原 Task，不需要用户重发。
- **Model Call**：沿用 01 的实际调用和 Usage 记录单位，**累计调用次数不设 3 个上限**。本文件不更改积分结算算法，也不按 Tool 调用次数收费。
- **Tool Call**：一个 Task 内可能有零次或多次，模型的一次响应可以提出多个 Tool 调用。Tool 执行时没有在途模型请求，则不占上游模型请求名额；但 Tool 的实际业务权限、版本、幂等仍必须由对应业务服务执行。
- **waiting_user**：正在等待用户真实确认的 Task，没有在途模型请求时不占模型请求名额；但仍未终结，所在会话暂不能删除。

~~~mermaid
flowchart TD
    A[已受理Task] --> B[组装当前合法上下文]
    B --> C{需要新的模型请求?}
    C -->|是| D{当前用户在途模型请求少于3?}
    D -->|否| E[待发模型请求排队]
    E --> D
    D -->|是| F[实际发送模型请求 占一个名额]
    F --> G[模型请求结束 释放名额]
    G --> H{模型要求执行Tool?}
    H -->|是| I[调用合法Tool并保存真实结果]
    I --> B
    H -->|否| J[保存回答或进入等待用户]
    C -->|否| I
~~~

**排队类型必须区分**：模型请求名额不足产生的是全局模型请求队列；用户选择“排队发送”产生的是同一会话中对前序工作的顺序依赖。两者都不是模型失败，也不要求用户重复发送。

## 3. 执行中发送新消息：默认插话，可选排队

### 3.1 统一产品行为

**已确认：同一会话存在正在执行的任务时，新消息默认采用「插话」，用户可在发送前切换「排队」。** 正常发送不额外弹确认窗口；02 仅提供发送旁的轻量切换。没有正在执行的相关任务时直接正常发送，不必展示模式选择。用户不会看到后台三个模型请求名额或内部草稿阶段。

| 模式 | 已确认的用户意图 | 本模块执行含义 |
|---|---|---|
| **插话（默认）** | 立即优先处理刚才输入的新要求 | 保留新消息，创建独立新 Task，通知旧 Task 不再继续无必要的后续生成/未发步骤；以新要求继续 |
| **排队（可选）** | 让相关旧任务先完成，再执行新要求 | 立即保存新消息及新 Task，保留前序依赖；旧任务完成/进入可继续状态后解除依赖并执行 |
| 模型请求资源排队 | 与用户选择无关 | 已具备执行条件但上游在途请求已满，等待名额后继续，不要求再发送 |

**插话不等于删除旧任务、篡改历史消息或回滚经营数据库。** 新 Task 要有新 task_id，保留它与被插话旧 Task 的关联；旧 Task 已生成的安全文本及实际 Tool 结果留在 03 会话历史中，其真实终态由 07 决定。

### 3.2 插话最小处理流程

~~~mermaid
sequenceDiagram
    actor U as 用户
    participant UI as 02输入区
    participant C as 03会话服务
    participant R as 06执行循环
    participant S as 07停止与恢复
    participant B as 原业务服务
    participant M as 上游模型
    U->>UI: 在执行中输入新要求并直接发送 默认插话
    UI->>C: 新消息及mode=interrupt
    C-->>R: 已受理消息和新task_id
    R->>S: 对关联旧Task请求停止后续工作
    alt 旧Task仅模型生成或待发Tool
        S-->>R: 旧Task可停止/替代
    else 旧Task有正在执行且结果未知的业务命令
        S->>B: 查询原业务请求的真实结果
        B-->>S: 已成功/失败/仍处理中
        S-->>R: 结果确定后允许有序继续
    end
    R->>R: 为新Task组织最新合法上下文
    R->>M: 有模型名额时发送新请求 无名额则排队
    M-->>R: 返回新回复
    R->>C: 保存新Task的消息和结果
~~~

处理原则：

1. 新用户消息**立即受理并持久保存**；新旧 Task 均有不同 ID，03 只记录关联关系。不要把旧的 UserMessage 改写成新问题。
2. 向旧 Task 请求停止**后续尚未执行的步骤**；已发送的模型请求若不能真正停止，在途名额须持续计算到实际结束，不能为插话制造第 4 个并发请求。
3. 已成功的只读查询可以复用合法结果；已经成立的采购、销售、库存事实不回滚。旧业务写命令**结果未知**时先查明，避免新旧命令同时作用于同一业务对象。
4. 新 Task 的上下文由 08 根据新指令、旧任务的已完成事实和未完成标记重新组装；涉及商品、订单等对象不明确时由 04/08 提问，不猜测。
5. **具体取消协议与停止完成条件归 07**；06 只发起并响应真实状态，不编造“旧任务已取消”。

### 3.3 排队最小处理流程

1. 用户发送时选「排队」，03 立即保存不可编辑的新消息并关联新 Task。
2. 06 记录新 Task 对正在处理的相关前序任务的顺序依赖；前序任务正常结束后，再组装新 Task 上下文。**不能先用未完成的回答冒充已产生的结果。**
3. 前序任务如果失败/被停止，08 根据可用的历史事实决定是否需要澄清，不能虚构成功；是否继续后续任务由实际指令与用户授权决定。
4. 新 Task 真正需要发起模型请求时，仍遵守每用户最多3个在途模型请求，资源不足继续排队；这与用户选的「排队发送」不是同一层队列。

### 3.4 同一会话有多个 Task 时的关联

- 同一 Conversation 可以先后或在可独立执行时关联多个 Task，**不新增“同会话只能一个Task”的隐藏限制**。
- 02 展示时把每个回复按稳定 message_id、task_id、part_id 更新，不因完成顺序不同而混合结果。
- 插话优先针对**当前消息正在对应的活跃工作**；多个任务并存时须按被插话的 message_id/task_id 精确关联，不默认取消其他无关会话或任务。
- 多个 Task 同时写同一会话 JSON 时，由 03 按版本顺序合并，不让最后一个写入覆盖其他任务。

## 4. 经营业务安全边界

插话、排队、停止和重新生成都不是对正式业务数据库的通用回滚操作。真正经营写操作只由采购、销售、库存等原 Application Service 按其权限、版本、事务及幂等规则执行。**已成功写入不能因插话自动撤销；结果未知不能直接再次写入。** 用户提出“改成10箱”属于新意图，11和原领域规则决定是更新尚未正式提交的业务准备数据，还是执行明确且合法的更正命令；不能让06自定义一套库存冲销规则。
