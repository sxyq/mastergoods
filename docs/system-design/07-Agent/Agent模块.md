# 07 — Agent 模块总览与详细设计路线

> 状态：**总览及子模块目录已建立；01 模型配置已有详细设计；02 智能交互已有统一现行详细设计；**03 会话消息与多端历史已有完整 PRD（2026-11-05）**；04 意图理解和 05 工具契约已加入与 UI 相关的专题第一版，其余专题待继续讨论。**
>
> 产品定位：**ChatGPT 式自然语言对话入口 + 可操作真实进销存业务数据的完整 Agent 执行能力**。不将桌面式多面板工作台作为产品前提。
>
> 目标客户端：微信小程序、Android App、iOS App、Web；共用同一后端 Agent 任务事实，客户端呈现适配其平台。
>
> 边界：本专题只设计 Agent 的理解、执行、工具、上下文、交互、恢复、扩展和模型用量事实，不重写商品、库存、销售、采购、往来或 Merchant 积分的领域规则。

## 1. 产品需求与非目标

### 1.1 用户看到的产品

- 用户打开类似 ChatGPT 的消息列表、历史会话和输入框，即可提出复杂经营任务。
- 在聊天消息中展示文字、工具执行进度、库存/销售/采购表格、图表、操作草稿与结果。
- 工具过程可展开查看，但不强迫普通商户理解工具实现或进入开发者工作台。
- 可以追问“刚才那件商品”、修改任务目标、补充信息、查看已经执行过的动作、恢复先前任务。
- 业务数据来自有权限的真实业务服务，不能把模型文本生成当成数据库查询事实。
- 用户切换手机/小程序/Web 后可以继续查看会话、任务状态和可恢复的待处理操作。
- 采用现有跨端组件体系进行 UI 呈现，Agent 组合受控结果组件，不让模型自行生成不可控页面代码。

### 1.2 不做什么

- 不复制 Codex / Claude Code 的 IDE、文件树、Terminal 和桌面三栏工作区作为默认产品。
- 不开放任意 SQL、Shell 或不受约束的数据库写入给经营用户。
- 不接入外部支付网关或把收款回调作为销售出库前提。
- 不在首期引入多仓/电商/POS 专用业务语义。
- 不首期搭建多个常驻专职子 Agent；只规划未来可扩展的专项 Agent 调用方式。
- 不用新的 Agent 技术讨论擅自批准销售模块 S/W 待确认事项。

## 3. 核心概念的候选语义（尚未冻结）

| 概念 | 推荐含义 | 主要区别 |
|---|---|---|
| Conversation / Session | 一组连续对话与消息历史 | 不等于一次执行任务 |
| Message | 用户/Agent 的消息及关联结果 | 不等于已执行业务动作 |
| Task / Run | 一次经准入的完整 Agent 执行单位 | 可包含多次 Model Call 与 Tool Call；积分规则与模块 01 一致 |
| Step / Tool Call | Task 内某个模型/工具执行动作 | 可追踪结果，超时不能直接当成失败并重复写入 |
| Tool | 可被 Agent 选择和调用的受控能力 | 需要明确业务语义，不能向模型开放任意数据库写入 |
| Business Draft | 商品/销售/采购等业务模块自身的草稿 | 不等于 Agent 的待执行计划 |
| Context | 发送给某次模型调用的必要信息 | 不等于数据库中的完整对话历史 |
| Checkpoint / Task State | 用于恢复未完成 Task 的状态事实 | 不能只依靠语言摘要重建已提交动作 |
| Memory / Knowledge | 跨轮可检索的资料和偏好 | 不等于实时库存/欠款 |
| UI Result / Artifact | 对话中的表格/图表/文件/表单结果 | 可区分生成时快照和重新查询的数据 |

以上概念只为避免后续混用名词，不代表字段或状态名最终定稿。

## 4. Agent 全链路功能主路径

~~~mermaid
flowchart TD
    A[用户输入自然语言需求] --> B[读取会话与当前任务上下文]
    B --> C[理解意图与识别业务实体]
    C --> D{需要查询或操作真实数据吗}
    D -->|不需要| E[生成直接回答]
    D -->|需要| F[选择相关工具]
    F --> G[通过业务服务读取或操作]
    G --> H{对象唯一且参数充足吗}
    H -->|否| I[在对话中补充信息或澄清]
    I --> B
    H -->|是| J{任务是否完成}
    J -->|未完成| F
    J -->|完成| K[输出结构化结果和后续操作入口]
    E --> L[保存消息及结果]
    K --> L
~~~

**解释：** 意图识别、业务对象解析和工具执行可以在一个动态循环内进行；简单问答不必强制独立分类模型；涉及正式写入必须调用既有业务服务，执行结果只能依据工具返回的正式事实宣称完成。工具、会话与任务的细节分别进入 04～12 专题讨论。

### 4.1 贯穿讨论的真实场景

> “看最近 30 天饮料销量，结合库存建议补货，给我准备采购草稿；先把第二个商品的建议量改成 20 箱。”

候选能力链：理解经营意图 → 查找商品分类 → 查询销售汇总 → 获取实时库存 → 形成可调整补货表格 → 用户修改候选数量 → 创建采购草稿 → 返回真实草稿标识。**补货建议不等于采购已完成，采购草稿也不等于实际入库。**

贯穿异常：商品多匹配、单位换算不确定、查询期间库存更新、用户中途修改目标、模型上下文超长、应用断网、工具调用结果未知、任务等待用户、异设备继续。

## 6. 需要在对应模块落实的关键问题

### 6.1 意图与工具

- 复合意图、上下文指代、同名商品/客户、单位和时间解析；无法唯一识别时如何澄清。
- Tool Registry 与业务 Tool Catalog 分离：前者负责发现/调用描述，后者定义商品、库存、销售、采购等真实操作。
- Tool 细化 Search / Read / List / Query / Create / Update / Draft / Confirm / Correct / Import / Export，不能把通用 Update 当作绕过领域动作的入口。
- 工具执行结果需可供后续模型调用使用，错误区分参数错误、权限不足、冲突、暂不可用、结果未知。
- 大量工具按需发现而不是每次向模型注入所有描述。
- 模型可参与任务规划，但工具权限与实际业务规则不由自然语言自行发明。

### 6.2 会话、任务、恢复与上下文（Agent 03 现行摘要）

详细业务和数据边界唯一依据：**03《会话消息与多端历史》现行统一 PRD**，不在总览复制其图表和接口示例。

- **创建与隔离**：首次发送被服务端受理时创建Conversation；聊天历史仅创建人可访问，同商户其他STAFF/OWNER不共享。员工离开商户后服务端拒绝访问，本地按权限变化清理缓存。
- **并发**：**每个用户跨多个会话最多3个同时执行的主Agent Task，同一会话同时最多1个主Task**；每轮task_id独立，Tool步骤和子代理不自动另占用户会话任务名额。实际准入与运行状态归06/07。
- **任务与网络分离**：断线时服务器端已准入Task继续执行，客户端从会话快照及一致cursor恢复后再接真实事件；本机已看文字即时出现、未读新增文字按02已有的流式方式渐进呈现；另一设备自动读取服务器历史。12负责传输和重连。
- **存储**：**每个Conversation一份服务器JSON会话文件**存正文/固定UI快照；PostgreSQL存会话索引、搜索投影、Task真实状态和管理员执行记录。单文件修改顺序合并，业务写入用领域数据库事务，不将聊天文件当经营真值。
- **消息和上下文**：已发送用户消息不可编辑；停止后的原指令/安全部分输出应保存，下轮08组装上下文时携带正确的未完成标记。对象引用有歧义时由04/08向用户提问，不猜测。
- **暂存与重新生成**：未发送文字和卡片字段本机保存；生成的回复候选立即持久化，下一轮可选择采纳进入上下文。未提交领域Draft可按业务规则调整；已提交采购、销售、库存变更不能通过重新生成或恢复JSON自动回滚，需走领域更正/撤销。
- **删除与搜索**：未终结Task的会话**禁止删除**；终结后可删除、用户立即不可恢复、服务器JSON7天后清理，正式经营数据不删。历史搜索先标题后消息/回复摘要分组并支持模糊匹配。
- **长会话**：建议结合用户轮数、JSON体积和实际模型上下文预算提示新开会话；阈值在03第11章列为建议，尚未定稿。

### 6.3 UI、流式与实时数据

- ChatGPT 式对话入口：普通气泡、工具执行状态、结果卡片、展开的表格、可选操作表单、历史会话。
- 共享 Agent 事件语义，但 Web/Android/iOS/微信小程序根据原生体验选择不同的结果组件呈现。
- 流式涵盖消息文字、工具开始/结果、Task 状态、需要用户操作、结果更新、任务完成/异常；不仅是文字分段。
- 区分生成时静态快照与可重新查询/刷新数据，不把大表格全部塞给模型。
- UI 表格筛选排序及结果明细优先调用业务数据服务，模型负责决定呈现什么和接下来做什么。
- 技术候选：Go 后端 + SSE + 任务状态查询/事件续传；WebSocket/AG-UI/A2UI 是否采用之后评估，不提前强制依赖。

### 6.4 子 Agent

- 第一阶段：单主 Agent + 受控 Tool/Skill 体系。
- 未来允许专项 Agent 作为 Tool 被调用，但不首期引入多 Agent 协商、并行协调系统。
- 后续必须讨论上下文隔离、Merchant/权限继承、Task 与子运行归属、费用汇总、错误传播和用户取消语义。

## 8. Agent 专题现行决定与尚待细化的范围

### 8.1 已由正式专题明确的事项

## 10. 2026-10-15 — 服务端 Agent 架构与 Skills/MCP 首期范围决策

> 用户本轮明确产品架构方向：Agent 作为后台服务端能力，前端采用 ChatGPT 式对话并接收流式综合结果。继续沿用本文件 17 个子模块，不添加新工程模块。

### 10.1 职责与交互方式

- **Go 服务端 Agent Runtime**：对话/任务状态、上下文装配与压缩、意图识别、模型调用、工具发现和执行循环、Checkpoint/任务恢复、历史结果、用量事实、流式事件的产生与持久化。首期作为现有后端中的逻辑模块，并不要求新部署一个 Agent 服务。
- **Go 业务 Application Service**：商品、库存、销售、采购、客户、经营账务等真实查询与写入的唯一正常业务入口；Merchant/用户权限和已冻结业务语义继续生效。Agent 不直接执行任意 SQL 或绕开领域规则。
- **四端前端**：ChatGPT 式会话列表和输入、文件/语音等本端输入控件（能力按后续讨论确定）、SSE 流接收、文本/表格/图表/表单渲染、展开与筛选、本地临时显示状态、用户确认及继续追问；不在前端执行模型决策、私存 API Key 或直接写数据库。
- **用户界面展示真实 Tool 执行链，可点击运行中的步骤展开参数与结果摘要**，完成后默认折叠成单行摘要并允许重新展开。不能对外展示模型内部私有推理、敏感 Tool JSON 或数据库语句。
- **任务与连接解耦**：App 切后台、页面退出或 SSE 断线不直接意味着 Task 被取消。恢复时先读取服务端事实与已产生的事件；已提交的业务动作不得重复执行。
- **流式展示应分阶段提供反馈**：任务开始/简短进度/文字增量/结构化结果/需要用户输入/任务结束或错误。并非所有工具内部结果都要流式暴露，也不能只在长任务全结束后才告诉用户正在执行。

    U[四端 ChatGPT 式对话] -->|用户消息与操作| A[Go Agent Runtime]
    A -->|安全的任务事件与结果| U
    A --> M[模型调用与意图理解]
    A --> C[会话状态、上下文压缩与任务恢复]
    A --> T[工具发现与执行循环]

    B --> DB[(PostgreSQL 真实业务数据)]
~~~

## 11. 2026-10-31 — 模型 01 统一简化后的最新规则

> 本节取代先前自动无感主备切换、必须同时配置主备、USD→CNY 外汇换算、单次模型故障仍向用户扣积分等旧表达。详见现行 `01-模型提供商与模型配置.md`。

- 普通用户只有 **快速 FAST / 标准 STANDARD / 深入 DEEP** 三个档位；后台 SYSTEM_ADMIN 配置各档主模型、**可选**备用、多个 Provider/Model、Reasoning、Context/Output、支持的协议及价格。
- 模型请求采用服务端 Agent 的**按次无状态调用**，对话信息由本地服务端维护，Provider 不承担持久远程会话职责；一轮 Task 内可多次模型调用并由工具模块执行多个 Tool Calls。
- 管理员按实际 Provider 支持情况配置 300K/400K 等统一上下文请求上限；上下文压缩和 Tool Call 部分成功/失败均为其它 Agent 专题，不在 01 中过度讨论。
- 上游故障**停止当前流式回答**，界面统一显示“模型服务暂时不可用，请重试。”并提供用户点击重试；可选备用模型由下一次重试调用使用，不拼接已中断文字。
- **失败的模型请求不扣用户积分**，供应商真实模型成本独立记账；成功模型请求按其实际输入、输出、缓存用量计算。
- 国外模型从 OpenRouter 获取模型价目，例如 OpenRouter 标价 USD 2 / 百万 Token，本平台直接记作人民币 2 元 / 百万 Token；不引入外汇汇率。国内模型直接使用人民币官方价目。**1 积分 = 1 元人民币**。
- 计费支持微小数值，目标为六位小数；内部不在每个 Token 上提前舍入，不给普通聊天用户展示逐次计分或真实模型细节。
- 活跃 Task 正在使用的模型配置不可被管理员修改或停用，后台提示“请待任务结束后操作”；其它配置可正常管理。
- Task 积分准入、Merchant 余额/流水、负余额、幂等最终结算继续沿用模块 01 已确定规则；工具部分成功/失败归 Agent 05/06/07/10/11。

## 12. Agent 02 统一现行设计摘要（2026-11-01）

> **详细依据只有一份**：docs/system-design/07-Agent/02-智能交互与实时数据展示/智能交互与实时数据展示.md。02 原先不断增补的版本已合并成 16 章，旧的章节号、过时导航及分期图表列表不再引用。以下仅概述模块协作与现行状态，不重复全文。

### 12.1 确定的功能与边界

- ChatGPT 式单一 Agent 对话：多轮追问、历史对话、流式文字、固定组件、业务对象卡、语音入口；iOS/Android/小程序/移动 Web 使用同一页面布局原则。
- 三档模型选择（快速/标准/深入）只位于发送按钮旁；真实 Provider、模型名和单次积分消耗不展示给普通用户。
- **可点击的 Tool 执行链**：开始、运行、完成、失败来自 Runtime 的真实工具事件；点击转圈/整行查看工具名、参数与结果摘要和用时，不展示模型私有推理文本。
- **模型驱动 Intelligent UI**：真实 Tool Result 与会话上下文进入模型，模型可以重组、计算衍生指标并调用单一展示工具 **present_ui**；Go 解析固定结构并核对必要数据事实，四端渲染预置组件；不把 Tool JSON 直接无条件画成最终模型图表。
- **组件全集**：12 类可复用基础渲染器、49 个业务模板候选及 21 个固定 view_type（包含指标、表格、视图切换，并非 21 个独立图形框架），全部纳入完整设计目标，不再把部分图表列为默认后置。
- 库存等原始事实和正式业务写入以 Application Service/Tool Result 为准，模型计算属于 derived/estimate，不可伪装成数据库真实修改。
- Agent 01 的上游故障固定提示/手动重试规则不变；历史数据保留查询快照，不自动修改旧业务事实。

### 12.2 当前推荐导航，不是已确定的最终产品标签
