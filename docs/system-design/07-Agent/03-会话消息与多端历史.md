# 07-Agent / 03 — 会话消息、个人历史与跨端恢复（现行详细 PRD）

> 更新：2026-11-09。**本文为单一现行设计**，直接修订旧规则，不叠加“以最新章节为准”的历史补丁。
>
> 已确认：首次发送受理才创建会话；同商户员工不共享各自的聊天；**同一用户最多同时执行三个不同会话的主 Agent Task**，且**同一会话同时最多一个主 Task**；每次 Task ID 唯一；已发送消息不得编辑；管理员在专门的运行记录界面查看有权限的实际输入、输出和 Tool 步骤；**执行中的会话不能删除**；每会话一份服务器 JSON 文件，PostgreSQL 保存索引、任务状态与搜索投影；设备本地缓存已下载内容；重连保留既有流式浮现；用户删除后不可恢复，服务端 JSON 保留7天后清理；已成立经营事实不随聊天删除。
>
> **需区分**：聊天回复候选的暂存/上下文采纳、服务端保存消息、领域业务草稿与正式数据库事务是不同层次；不能通过点击重新生成直接回滚已提交的库存、销售或采购。

## 1. 产品目标、角色与模块边界

### 1.1 用户目标

从首页进入底栏中间的 AI，可以第一次发送时创建会话、查看个人历史、查询库存/销量、处理业务卡、跨设备接续。客户端断线时服务端已准入的任务继续执行；返回同一设备时已看过的文字立即呈现、未看过的增量按既有流式效果浮现；另一设备自动下载会话。真实业务结果来自领域服务，不来自聊天文件。

### 1.2 业务场景

同一用户在 Android 会话 A 查询库存，在 Web 会话 B 分析销售，在另一会话 C 准备采购草稿，三者各自有独立 Task ID，可同时执行；第四个会话的新执行请求提示超额。另一用户 STAFF 的会话不因处于相同 Merchant 而共享。用户对“刚才那个商品”指代不明时，必须询问目标商品，不能由模型选择不确定记录进行写入。

### 1.3 模块分工

| 模块 | 本模块依赖的事实 | 03 负责 |
|---|---|---|
| 02 | 聊天消息、固定图表/卡片、文字渐进呈现 | 保存及返回标准 MessagePart |
| 06/07 | Task 执行、停止、真实状态、每用户并发上限 | 会话与 Task ID 关联、可恢复内容 |
| 08/04 | 上下文选择、业务对象解析与澄清 | 提供原指令、部分回答与业务引用 |
| 11 和采购/销售/库存领域 | 草稿状态、正式写入、版本/权限和更正 | 保留消息/业务引用，不自行改数据库 |
| 12 | 增量流、事件重连与游标 | 返回与增量衔接的可靠快照 |
| 14/17 | 附件、管理员 Task 输入输出与用量记录 | 提供会话归属及必要关联索引 |

架构沿用现有 Go + PostgreSQL + Modular Monolith：会话生命周期与隔离约束在 Domain；发送、历史、搜索、删除在 Application；JSON 文件、数据库索引、本地缓存同步合同在 Infrastructure。03 不再造第二套任务执行器或经营服务。

## 2. 核心数据对象和三层存储

### 2.1 领域对象

| 对象 | 职责 | 不得混淆 |

| Conversation | 一个创建人、一个 Merchant、长期多轮对话及历史消息 | 不等于一个 Task 或一个模型请求 |
| Message | 一条用户/助手消息，保存发送/生成时刻、顺序及状态 | 已发送用户消息不可就地编辑 |

### 2.2 三种持久化边界

- **服务端单会话标准 JSON 文件**：保存完整消息、规范化图表/业务卡快照、可见 Tool 摘要、原始用户指令、候选回答与版本；聊天历史的内容依据，不是正式业务数据库。
- **PostgreSQL**：保存会话 ID、创建人、商户、标题、文件位置与版本、搜索文字投影、Task 状态/关联、管理员运行输入输出及业务正式数据（在各领域表）；不需要把每个 token 又保存为另一份聊天全文。
- **本机缓存**：已下载会话内容、已见文字位置、未发送的输入框文字和未提交卡片字段；不同设备各自缓存，同账号新设备从服务端自动取得。

不同会话文件可并行读写；**同一个会话 JSON 文件的更新应由会话仓储顺序合并**，使用完整临时文件和原子替换，避免半截 JSON。PostgreSQL 本身依事务处理并发，不能理解成所有用户的业务数据库写入必须全局串行。

## 3. 创建会话、消息不可编辑与生命周期

### 3.1 第一次消息被服务端受理才创建

点“新对话”只显示本机空白会话；首次正式发送时服务端核验 user_id / Merchant 和稳定的 client_request_id，并创建 conversation_id、UserMessage、独立 Task ID、服务器 JSON 文件与数据库索引。若服务端已受理但网络丢失回执，使用同一个 client_request_id 恢复既有 ID；不得重复创建会话/Task。

### 3.2 已发送、已停止与未发送的区别

- **未发送**：输入框、语音转写和卡片上尚未点提交的修改，只存本机；切页面可恢复，但不算 Task，也不写入正式业务。
- **已发送**：用户指令已经成为会话不可编辑的 Message；可复制、引用、另发一条修改指令，不提供直接编辑原消息按钮。
- **执行中断/被用户停止**：已经发出的原指令和实际已产生的安全回复部分仍保存在服务端，下次构建上下文应考虑这些历史，但明确状态未完成，不能伪称业务已经提交。
- **生成的回答**：先保存到服务器 JSON 供恢复，再决定候选版本如何被下一轮上下文采纳；保存/采纳不是业务 commit。

### 3.3 会话生命周期

### 4.2 对话与任务关系

Conversation可以有很多已经完成的历史Task，但同一时刻最多执行一个主Task；同一账号可以同时在三个不同会话中运行三个主Task。模型内部多次请求或工具调用不会额外占用用户的三个名额。正式业务工具是否成功执行只由领域Application Service确认，不能根据展示动画判断。

## 5. 用户级三任务并发与上下文归属

### 5.1 并发单位：User而非Conversation

**已确认**：同一个user_id最多同时运行三个会话级主Agent Task；一个Conversation同时只能执行一个主Task，每次新执行都创建独立task_id。Task内部可以调用多个Tool、模型或受控子代理，不把它们算成不同的用户主任务。

| 场景 | 产品处理 | 执行责任 |
|---|---|---|
| A/B/C三个会话各有一项运行中Task | 三个任务都可工作、结果独立 | 06/07 |
| 再从D发起第四项 | 提示已有3项任务在处理 | 06/07准入 |
| 会话A未终结时继续发新的Agent指令 | 告知本会话忙，不能在同会话交错执行两个主Task | 06/07 |
| A完成，B/C仍运行 | 释放一个用户任务名额 | 06/07 |
| Task等待用户确认 | 建议暂停占用执行名额；恢复时重新准入 | 07待细化 |
| 不同会话写同一商品/草稿 | JSON相互独立，正式业务事务按领域规则处理冲突 | 领域服务 |
| Task完成顺序与消息创建顺序不同 | 各自消息按原创建顺序显示，不交叉拼接 | 03/02 |

服务端应按user_id与真实Task状态统计和准入，不能靠某设备显示多少按钮。等待确认状态是否释放执行名额由07详细定义，目前建议释放但不将其误判为已经完成。

### 5.2 上下文歧义必须询问用户

用户在不同会话查询矿泉水和绿茶，随后说“帮我采购刚才那个商品”，不能自动跨会话取最近完成的Task，也不能猜测同名SKU。04/08应优先依据当前会话的明确业务对象ID定位；仍有两个合理候选时直接询问用户“你指矿泉水还是绿茶？”，等待明确选择。正式经营写Tool在指代不明确时不得调用。

用户停止某个Task后，已发送指令和安全的部分输出仍存会话历史。08后续组装上下文应可选取这些内容，但必须保留其未完成状态，不得当作已经提交的业务事实。

### 5.3 管理员任务输入输出

每个task_id保存真实执行所属user_id、merchant_id、conversation_id、ToolStep的输入/输出摘要及执行时间。管理员通过独立运行记录页查看获授权内容，不等于员工个人会话在商户内共享。管理员详情权限与保留策略由17细化，03提供正确关联。

## 6. 断网续跑、最新快照与流式浮现

### 6.1 断线只改变连接状态

客户端断网、锁屏、切后台或离开AI页只中断事件接收，已准入的服务端Task继续执行。真正失败、用户显式停止或等待用户业务确认仍可能发生。断网不能把Task标记为failed，也不能为了恢复重新发起原Task。

### 6.2 同设备与跨设备恢复行为

| 场景 | 立即呈现 | 接着处理 |
|---|---|---|
| 同一手机前次看到前200字 | 本机缓存的200字立即显示 | 未见新增文字通过02流式组件逐段呈现 |
| 同一手机有有效图表缓存 | 先原位显示 | 向服务端核对版本，有差异再更新 |
| 另一台设备首次打开 | 自动下载服务器保存的完整历史 | 直接展示旧内容，不用点击加载或从头动画回放 |
| 服务器已经完成 | 立即标记真实Task已完成 | 未读文字仍可渐进出现，允许立即显示全部 |
| 服务器仍在运行 | 显示真实执行状态 | 快照之后继续接收真实事件 |
| 多轮历史Task | 按消息顺序显示 | 不把不同Task的回答混为一条 |

**设备已看到多少字**属于本地DisplayCursor，不是服务端消息保存位置。恢复后的动画是视觉体验，不能伪装模型还在运行。

### 6.3 一致快照和后续事件

03返回完整消息/Part快照以及对应snapshot_cursor，12从该位置之后接收真实新事件；同一part_id/revision的事件不重复应用。增量不可回放时重新获取最新快照，绝不重做已完成Tool或正式业务写入。

### 6.4 连接、Task和业务结果各自独立

| 可见情况 | 正确判断 |
|---|---|
| 最后一段文字出现，Tool仍运行 | Task未完成 |
| 图表已出现，模型继续工作 | 组件已可读，Task仍真实运行 |
| SSE断开，服务器正在执行 | 显示网络重连，不显示模型失败 |
| 真正模型上游失败 | 按Agent 01固定错误文案并保留可靠内容 |
| 写Tool请求结果未知 | 查原请求的执行结果，不重新提交 |
| 需要用户确认 | 保留等待确认，不自动执行业务 |
| 点击立即显示全部 | 只停止本机文字动画 |

### 6.5 历史数据与当前业务数据

历史中昨日库存120瓶保持原时间和数值，今日实际库存可能是80瓶。打开历史不自动查询业务；用户点击刷新或确认旧业务卡时，才依据当前领域真值进行新查询或业务核对。

## 7. 本轮确认 C：历史业务卡必须按当前业务事实重新判定

### 7.1 为什么创建时间必须有，但不能单凭时间做决定

历史卡应当保留 generated_at（卡片生成时间）、数据来自什么 source_refs、对应哪个业务草稿/商品/用户/商户，以及生成时所基于的版本或业务引用。时间允许用户理解“这是此前的建议”，也帮助服务端确定这不是一个新生成动作。

**但时间老不一定不可用，时间新也不一定安全。**

例如 3 小时前生成的采购卡，其供应商、商品、价格和草稿如果仍处于可执行状态，并且现有业务领域允许，就可能继续合法执行；反过来，1 秒前的销售卡也可能因为另一设备已经完成该销售、商品停用或权限撤销而失效。

因此最终允许操作应看**当前业务事实 + 权限 + 版本/状态 + 原本要求的用户确认 + 是否已执行**，而不是设一个未经产品确认的“超过多少分钟就禁止”规则。对于真实 SaleDraft，如果领域采用 revision/CAS，应按其现有规范执行；采购草稿若尚未确认对应状态机和过期策略，03 不得自行规定 24 小时失效。

### 7.2 历史业务卡打开与点击的职责

- **打开历史消息**：03 读取并展示原卡片快照，标明生成时间和可能需要重新确认；不自动修改真实业务记录。
- **用户点击“确认/完成”**：将 action_id、业务引用、用户已确认的参数和服务端动作请求关联信息发往合法业务命令入口。
- **业务服务当前判定**：重新检查 Merchant/用户权限、草稿状态与 revision、商品与单位、当前领域业务事实、已执行结果和必要规则。
- **结果返回**：可以执行则真实提交，并把结果关联到原 MessagePart；已执行就返回原有结果；发生变化则提示用户查看变化，必要时重新确认；拒绝则保留原历史卡但标记“该操作不可继续”。
- **防重复**：历史卡可重复点击、断网后再次点击、两台设备同时点击都不得让同一个正式业务动作重复成立。

### 7.3 从历史卡到真实业务执行的完整时序

~~~mermaid
sequenceDiagram
    autonumber
    actor U as 用户
    participant UI as 历史业务卡
    participant C as 03会话消息
    participant API as 受控业务命令入口
    participant B as 真实业务服务
    participant DB as 业务数据库

    U->>UI: 打开几小时前的采购/销售卡
    UI->>C: 读取历史消息及卡片快照
    C-->>UI: 原卡数据、生成时间和业务引用
    UI-->>U: 展示原建议、时间与当前按钮
    U->>UI: 点击确认或提交
    UI->>API: action_id 业务引用 期望版本 请求幂等标识
    API->>B: 验证当前操作者、商户和合法权限
    B->>DB: 查询当前业务草稿/商品及已执行事实
    DB-->>B: 当前状态 版本 相关业务值
    alt 先前请求已经成功
        B-->>API: 返回原真实业务结果
        API-->>UI: 显示已完成及原单据入口
    else 当前状态与提交条件一致

        B->>DB: 原子保存正式业务事实
        DB-->>B: 返回当前真实结果
        B-->>API: 成功记录和最新业务版本

        C-->>UI: 更新卡片成功态
    else 当前数据发生影响用户决定的变化

    else 当前操作失效或无权

**时序说明**：03 只负责保存消息和业务引用；真正判断并提交的是现有 Application Service。再次点击旧卡时要进行当前事实核对，不能让前端根据消息里的 generated_at 或 AI 文本决定正式经营写入成功。

### 7.4 业务卡提交前的边界核对表（本轮确认需要此表）

以下表格区分**必须遵循的执行原则**与**由具体业务模块定义的政策细节**。不增加独立审核服务，不对所有查询图表做写前检查；只在真正需要执行经营命令时走正常领域检查。

| 编号 | 边界场景 | 需要读取或判断什么 | 应当如何处理 | 责任归属 |
|---|---|---|---|---|
| B01 | 历史卡创建很久，但业务数据未变化 | generated_at、当前对象状态/版本 | 不仅因为旧就禁止；若其他条件合法可继续 | 03展示，业务服务判定 |
| B02 | 卡片刚生成，但关联草稿已被修改 | expected_revision 与当前 revision | 返回版本冲突和新内容，重新确认后再操作 | 业务草稿领域 |
| B03 | 草稿已完成/已消费 | 正式状态、已存在的业务单据 | 不再新建第二笔，返回已经完成的记录 | 采购/销售领域 |
| B04 | 草稿已取消/业务已关闭 | 当前状态 | 不允许从旧卡直接继续，展示已失效 | 采购/销售领域 |
| B05 | 草稿明确存在过期状态 | 领域实际 expiry 状态和有效时间 | 若业务有正式过期规则则按其处理；无该规则不可擅自过期 | 领域定义，03展示 |
| B06 | 商品已停用或被删除/隐藏 | 当前合法商品状态与引用 | 按领域当前可用性判定，提示用户更新选择 | 商品/库存领域 |
| B07 | 商品名称相同但 ID 已变 | 原商品 ID 与当前选择 | 不悄悄改成同名另一商品，要求重新选择 | 商品领域 |
| B08 | 商品单位/规格/换算变化 | 单位 ID、换算规则和数量 | 若影响数量或金额，要求用户核对并确认 | 商品/采购/销售领域 |
| B09 | 商品价格或成交价规则变化 | 当前商品价、旧草稿价格快照、授权范围 | 不静默覆盖原草稿价；依据相应业务规则比较并提示 | 商品及销售价格规则 |
| B10 | 当前库存改变 | 当前库存与交易所需数量/业务策略 | 重新计算可执行性；库存不足时依据领域规则处理 | 库存/销售领域 |
| B11 | 供应商/客户状态变更 | 相关实体状态和启用规则 | 当前业务服务决定可否关联；无权时不继续 | 采购/销售/往来领域 |
| B12 | USER 或 STAFF 权限被撤销 | 当前 User、Membership、Merchant、权限 | 拒绝未授权写入；不沿用生成卡时的旧权限 | 身份/权限与领域服务 |
| B13 | Merchant 冻结/只读/关闭 | 当前商户状态与可写范围 | 遵循已有 Merchant 状态规则，禁止未授权写入 | 账户身份领域 |
| B14 | 卡片来自其他商户/其他人的私人会话 | 当前会话、Merchant 和业务对象归属 | 禁止跨商户访问；共享规则未定前不默认接管 | 03 + 身份/领域 |
| B15 | 一张卡被同一用户重复点击 | 相同动作请求身份、已有提交结果 | 命中已执行请求时返回原结果，不能重复写 | 业务命令幂等 |
| B16 | 两台设备同时点击同一张卡 | 相同目标动作、版本、状态竞争 | 仅按实际 CAS/事务结果允许一笔成立，其他设备拿到当前结果或冲突 | 业务服务 |
| B17 | 用户点击后客户端立刻掉线 | 该业务请求的真实执行状态 | 重新上线先查请求结果；不能因没有响应就重发成另一笔 | 业务服务 + 03/12 |
| B18 | 服务端请求超时、结果不确定 | 原请求标识和业务执行事实 | 显示处理中/结果待确认，查询原请求；不直接重新执行 | 业务服务 + 07/10 |
| B19 | 原卡数据源已过时 | source_refs、快照时刻及实际当前事实 | 历史卡保持旧内容；点击执行时用当前业务事实判断 | 03 + 业务服务 |
| B20 | 用户改变卡片数量或金额 | 变更字段、单位、当前版本、应授权字段 | 新提交参数走正常字段校验和领域命令，不以旧显示值为准 | 业务服务 |
| B21 | 旧卡关联的业务单已更正或撤销 | 当前正式记录及其更正关系 | 展示实际后续状态，不能凭旧卡再次完成原动作 | 业务领域 |
| B22 | 用户删除了原会话后业务仍已成立 | BusinessRecord ID、原真实结果 | 正式业务事实保留；后续在原业务页面管理，不靠聊天恢复 | 03 + 业务领域 |
| B23 | 业务服务暂不可用 | 当前事实无法可靠取得 | 暂不执行写操作，显示无法确认业务状态；允许稍后再试 | 业务服务/前端 |
| B24 | 旧卡试图重放未经允许的操作 | action_id 是否仍在受控允许集合 | 不执行未知动作或模型输出的自由指令 | Agent 05/11 + 领域 |
| B25 | 历史业务卡是“建议草稿”而非已保存草稿 | 是否存在真实业务 draft_id | 先明确创建/保存路径；不能把模型文本当已持久草稿 | 03/11/业务领域 |
| B26 | 采购单尚未实际入库 | 采购业务状态与入库记录 | 只展示真实采购状态，不能自动声称库存增加 | 采购/库存领域 |
| B27 | 销售单生成但未完成出库 | 销售/出库真实状态 | 不能显示已扣库存或已收款，按真实业务执行阶段展示 | 销售/库存/经营领域 |

**解释**：真正“确认”的是**操作时以当前真实事实与原请求的执行结果为准**。表格中某些政策尚未冻结，例如采购草稿是否到期、库存不足时能否继续某种流程、售价变化后的确认规则，必须沿用原业务模块未决状态，不由 Agent 03 替用户决定。

### 7.5 推荐的最少提交信息

为了正确关联当前业务请求与历史卡，提交参数至少要让服务端识别：

~~~json
{
  "conversation_id": "conv_123",
  "message_id": "msg_456",
  "part_id": "part_789",
  "action_id": "confirm_business_draft",
  "business_ref": {
    "type": "sale_draft",
    "id": "draft_001"
  },
  "expected_revision": 5,
  "request_key": "client_generated_stable_key",
  "input": {
    "quantity": "20",
    "unit": "箱"
  }
}
~~~

**示例说明**：这一结构是逻辑上的输入需求，不是已经冻结的 API 或现有业务字段。身份、Merchant 权限由当前认证上下文获取，不能相信客户端上传的所属商户；request_key 表示本次用户意图的稳定提交身份，网络重试应使用相同值。expected_revision 只在目标业务草稿采用版本控制时生效；与真实 SaleDraft 已有的 CAS 规则保持一致。不让模型自行指定后端正式记录 ID 或“修改成功”状态。

### 7.6 冲突后的 UI 呈现

<text>
原卡片：“采购矿泉水 20 箱，生成于 10:15”。
现在该商品信息或相关业务状态已经发生变化。
</text>

推荐采用以下交互：

1. **保留旧卡的原始内容**，在原位显示“业务信息已变化，需重新确认”，不可直接覆盖旧文字/数值。
2. 展示安全且当前用户有权查看的**变更前/当前**字段对比，例如数量、单位、当前价、草稿状态；不足以自动比较时展示“请查看最新业务信息”。
3. 用户重新选择/编辑并确认后，向业务服务发送合法的新操作；若草稿已终态或权限已经撤销，按钮禁用并说明原因。
4. 真实业务操作成功才显示新单据/库存结果。若后台收到成功结果而客户端未收到，重连后显示该已成功状态，不再显示“请重复提交”。
5. 两个不同业务表单对同一商品的并行操作，应继续依真实业务服务的当前版本及领域规则处理；03 不建立自己的商品库存版本系统。

**这里不需要一套新“卡片审批中心”或永久审计台。** 只是让已有业务写入口在执行前读取自己必需的当前事实，保证历史 UI 不会绕过真实领域约束。

## 8. 历史消息与数据快照、业务现值必须分开

### 8.1 三种时间

| 时间 | 含义 | 是否决定可执行 |
|---|---|---|
| generated_at | 模型生成这张 UI 卡/组件的时刻 | 不独立决定 |
| queried_at / source_at | 真实业务工具查询基础数据的时刻 | 说明快照新旧 |
| submitted_at / committed_at | 用户确认/业务服务真正提交执行的时刻 | 由领域正式结果决定 |

模型生成时间并不保证所有源数据都在同一时刻查询。若工具返回的是不同时间的查询快照，应以具体 data_source 的查询时间解释，不能用生成时刻冒充所有业务数据同时最新。

### 8.2 历史图表的显示与刷新

- 历史库存/销量卡保存模型输出的**规范化结果及当时数据引用、查询范围和时间**；打开时不自动用最新库存改写原有图表。
- 点击“更新到最新”应该触发一个新的受控查询/Agent Task，产生新的消息或清晰的新版本结果；旧结果仍可回看，避免对经营历史造成误导。
- 普通图表切换、排序已加载的数据不需要重新调用模型；涉及最新库存、日期范围或重新计算则发起新查询。
- 图表不能被当作经营记录原始事实的唯一来源，正式当前值始终从业务服务取得。

### 8.3 历史表单与可执行动作的不同生命周期

同一个 MessagePart 的**展示快照**应保持可恢复；但其**动作权限/当前可执行性**应基于每次操作时的实时业务状态。卡片的“原来显示可确认”只说明当时的 UI，不是无限期可使用的执行授权。

~~~mermaid
flowchart TD
    OPEN[打开历史会话] --> SNAP[读取保存的MessagePart]
    SNAP --> SHOW[显示原内容和生成时间]
    SHOW --> CHOOSE{用户只查看还是点击业务动作}
    CHOOSE -->|只查看| END[不执行业务查询或写入]
    CHOOSE -->|确认/修改| NOW[读取当前业务状态和权限]
    NOW --> IDEM{此前相同动作已成功吗}
    IDEM -->|是| RESULT[返回原真实结果]
    IDEM -->|否| VALID{当前合法且用户确认有效吗}
    VALID -->|是| WRITE[通过原领域Service提交]
    VALID -->|否| CHANGED[提示冲突/失效/无权]
    WRITE --> RESULT
~~~

**图示说明**：显示历史与执行历史卡是两件不同的操作。业务卡是否能点、点下去执行什么不能从历史 MessagePart 快照自行决定。

## 9. 会话删除：用户不可恢复，服务器JSON保留七天

### 9.1 已确认的删除结果

用户确认删除后，该会话立即从历史列表移除，不能通过旧ID、历史搜索或其他设备重新访问，不提供回收站或恢复。服务端会话JSON文件标记 deleted_at、purge_after=deleted_at+7天；达到清理时点后自动清除对应文件和可删除索引。这里明确区分用户侧立即不可恢复与服务端七天后物理清理。采购单、销售单、库存流水及正式经营账仍在原业务系统中。

### 9.2 已完成会话的提示

**标题：删除这段对话？**

**正文：删除后无法恢复。服务端将在7天后清理这段会话的数据文件。已经成立的采购、销售和库存记录不会被删除。**

按钮：[取消] [删除对话]。点击删除后服务端先标记删除，才向客户端返回成功并移除会话。

### 9.3 运行中会话的专用提示

**标题：这段对话还有任务正在执行**

**正文：当前有N个任务在服务器运行。删除后将无法查看或恢复这段对话，已发生的经营操作不会撤销。删除聊天不等于停止任务，后台任务可能继续执行。如需停止，请先返回会话使用“停止任务”。**

建议按钮：[返回查看任务] [仍然删除]。**用户明确要求采用与普通会话不同的提示；删除时是否自动停止仍需后续确定。** 当前建议不隐式取消已准入Task；删除也不能自动确认WAITING_USER的业务卡。任务停止以07真实状态为准。

### 9.4 删除流程时序图

~~~mermaid
sequenceDiagram
    actor U as 用户
    participant UI as 历史界面
    participant C as 会话服务
    participant R as Task服务
    participant F as JSON存储与索引
    participant B as 业务服务
    U->>UI: 点击删除
    UI->>C: 获取会话状态
    C->>R: 读取活动Task数
    R-->>C: 返回N
    alt N大于0
        C-->>UI: 显示运行中专用提示
    else N等于0
        C-->>UI: 显示普通删除提示
    end
    U->>UI: 明确确认删除
    UI->>C: 提交删除请求
    C->>F: 标记deleted_at和七天清理时间
    C-->>UI: 立即不可访问
    Note over R,B: 已完成经营记录不撤回
    Note over F: 七天后自动清除会话JSON
~~~

### 9.5 必要边界

| 情形 | 规则 |
|---|---|
| 另一设备仍打开删除的会话 | 同账号也不得继续读写或接收该会话流 |
| 提交删除时Task仍在运行 | 单独提示；Task真实状态归07，不能由UI猜 |
| 删除时存在待确认卡 | 无权再操作旧卡，不得自动确认或重复业务写入 |
| 删除后用户尝试恢复 | 不提供恢复入口，服务端拒绝该会话访问 |
| 本地未发送文字或卡片修改 | 删除对应本地草稿，不上传云端 |
| 七天后文件清理 | 清理服务器端JSON和关联缓存，不影响独立业务事实 |
| 清理时任务仍未结束 | 07处理必要终止/状态收尾，禁止重新生成已删会话文件 |

### 9.6 业务和会话绝不能级联删除

删除聊天仅改变会话历史生命周期。任何已成立的采购、销售、库存与经营记账记录均保留在相应的Application Service和领域数据中，不由会话JSON承担正式业务事实存储。

## 10. 新消息、失败重试、重复提交和并发任务

### 10.1 首次发送消息的因果顺序

理想情况下，用户发消息时客户端产生一个稳定的 client_request_id，Go Agent API 先确定当前用户、Merchant、Conversation，再让服务端保存 UserMessage 和 Task 关联；服务端返回确定的 message_id 与 task_id 后，客户端可将临时气泡与正式消息关联。客户端等待很久未收到响应，不能立刻另开一条新任务：先查询该请求是否已被受理，或者使用相同的请求身份安全地重新提交。

对于只读统计，这可以减少重复生成回答；对于会引发正式经营写入的任务，更要由真正执行 Tool 的领域服务保证**同一业务动作不重复成立**。03 消息提交的请求身份不能取代业务写命令自身的幂等机制。

### 10.2 首次发送时断网/重复点击时序

~~~mermaid
sequenceDiagram
    autonumber
    actor U as 用户
    participant UI as 客户端
    participant API as Agent API
    participant C as 03消息服务
    participant R as 06/07 Runtime

    U->>UI: 点击发送
    UI->>API: client_request_id和用户消息
    API->>C: 查询是否已经保存该请求
    alt 第一次被服务端受理
        C->>C: 保存消息并关联Task
        C-->>API: message_id task_id
        API->>R: 启动已准入Task
    else 相同请求此前已经受理
        C-->>API: 返回已有message_id和task_id
    end
    Note over UI,API: 响应可能在传输途中丢失
    U->>UI: 看到网络未连接后点击重试
    UI->>API: 使用相同client_request_id查询/重试
    API->>C: 检查已受理事实
    C-->>UI: 返回既有消息和当前Task状态
    UI-->>U: 展示现有消息 不产生新的重复任务
~~~

**原则**：用户主动重新提出一条不同问题属于新的请求；网络重连/重复点击同一次“发送”不应创建第二轮任务。同一动作的幂等身份应有明确作用范围（用户/商户/业务动作），避免不同用户之间错误复用。

### 10.3 Task 失败与用户手动重试

- 客户端离线：不触发用户“模型失败”提示；重连后读取真实 Task 状态。
- 真正模型上游失败：沿用 Agent 01 固定文案**“模型服务暂时不可用，请重试。”**，保留此前文字、工具步骤和已完成结构化块；是否创建新 Task/新模型请求由 06/07/01 统筹。
- UI 结构化图表损坏：可只将该 part 标为不可展示，不把整轮标为上游模型故障。
- 工具实际失败：保存业务可读的真实执行结果，不伪造成功。
- 用户点击“重新生成”：不直接复用上一次有副作用的 Tool 请求序列。若先前经营写入已经成功，服务端必须知道该事实，不能在新 Task 中自动再执行一次采购或销售。

### 10.4 同一个Conversation允许最多3个并发Agent Task（已确认）

**Task是一次Agent执行，而非一条Tool调用。** 用户查询销量、生成分析报告、创建/修改受控采购草稿，都可以构成Task；每轮Task内部允许多个Model Call、Tool Call及present_ui。用户仅在输入框改文字或修改尚未发送的卡片字段，**不构成Task**。

- 当前一个Conversation允许最多 **3个同时处于占用执行槽的Task**；该上限由服务端准入检查，不靠客户端按钮禁用。
- 推荐计数：已受理且准备执行、正在运行、正在调用模型/Tool的Task占槽；completed、failed、cancelled退出计数。WAITING_USER虽然未结束，但建议暂停时不占执行槽；用户确认后再次进入运行阶段必须取得可用槽位，这条属于实现细化，尚未被用户指定。
- 第4个同时执行请求返回明确提示：**当前会话已有3个任务正在执行，请等待其中一个完成后再发送。** 推荐不自动排队，不悄悄取消已有Task。
- 同一会话最多3个运行Task与会话累计可有任意轮消息不矛盾；不同会话之间按系统原有资源策略，不在03自造全局限制。
- 每个Task有独立UserMessage/AssistantMessage/ToolStep和流状态。结果按原消息位置展示，允许三个任务交错产生事件，但**不能把不同Task的文字、图表和Tool步骤拼在一起**。
- 采购、销售或同一草稿的写操作即便处于不同Task，仍应由对应业务Application Service的版本/CAS、授权与幂等保护。并发3不是允许同一单据被三次写入。
- 对“刚才那件商品”的指代，多个任务并行时必须由08/04基于明确消息及业务引用解析；不能随意挑最后完成的Task作为上下文。

~~~mermaid
flowchart TD
    SEND[当前会话接收新请求] --> COUNT[服务器检查活跃Task数]
    COUNT --> LIMIT{少于3个?}
    LIMIT -->|是| ACCEPT[建立新Task及消息关联]
    LIMIT -->|否| REJECT[提示本会话最多3个并发任务]
    ACCEPT --> RUN[模型及业务Tool运行]
    RUN --> DONE[完成或失败后释放执行槽]
    RUN --> WAIT[等待用户确认 具体占槽语义由07落实]
    WAIT --> RESUME[用户确认后再次申请运行槽]

### 10.5 消息更新与本地 UI 状态

- 新文本 delta 到来，不重建整个聊天消息组件。
- 同一个 part_id、revision 重复收到时不重复插入；版本更高时才更新对应块。
- 图表的图/表切换可以是本地状态，不需要更新服务端统计事实。
- 用户正在编辑业务卡时若服务器报告该卡业务版本变化，不应静默覆盖输入；应提示变化和重新确认。
- 用户点击“停止”只是在客户端发出真实任务控制请求，是否已停止以服务器 07 的状态为准。

## 11. 历史会话管理与手机/桌面用户操作

### 11.1 历史列表的页面能力

沿用 02 已有的 ChatGPT 风格历史入口，移动端从顶部历史图标进入抽屉/全屏列表，桌面可用折叠侧栏。建议列表内容：

| UI 信息 | 依据 | 交互 |
|---|---|---|
| 会话标题 | 用户命名或系统生成标题 | 点击打开；长按/更多可重命名 |
| 最近更新时间 | 服务端 last_message_at 等有效字段 | 按最新会话优先排序 |
| 近况摘要 | 最近一次可见内容的简短摘要 | 不含私密 Tool JSON |
| 任务状态（若仍活动） | 当前 Task 真值 | “运行中/等待确认”等，不以网络连接推断 |
| 搜索输入 | 用户有权查询的会话元数据/内容 | 只展示授权范围内的搜索结果 |
| 时间分组 | 今天、昨天、此前等 | 根据用户界面时区显示 |
| 删除入口 | 会话授权与产品删除策略 | 影响聊天历史，不删除正式经营事实 |

移动端列表应有明确的“新建会话”入口；用户打开旧会话时，读取服务端可恢复的标准消息和内容块。切换会话时，未发送文字与未提交卡片字段按已确认规则保存在当前设备，返回时还原，不跨设备同步。

### 11.2 新对话只在首次发送时创建（已确认）

点击“新对话”仅在本地新开一个空视图，不创建云端文件或空会话记录。首次请求真正被服务端受理后，才创建会话JSON并写入第1条用户Message。首次发送如果因网络异常不知道是否已受理，以同一个client_request_id查询或恢复，不能重复创建。

### 11.3 重新打开会话的用户路径

    B --> C[选择已有会话]

### 11.4 重命名、搜索和删除的区别

- **重命名**只是更新 Conversation 标题，不能修改任何 Agent 已说过的话或经营数据。
- **搜索**只返回用户有权访问的历史，不因为同 Merchant 就直接让全员检索其他人会话。
- **删除**确认后立即从用户历史移除且不可恢复，服务端JSON文件7天后自动清理；不执行经营业务撤销。
- **打开旧内容**只读取历史快照；点击刷新/执行才可能产生新的 Tool 请求。
- **删除政策已确认**：用户侧删除后立即不可访问且没有恢复入口；服务端单会话JSON文件保留7天后自动清理。

### 11.5 未发送文字及卡片编辑内容只保存在当前设备（已确认）

- 输入框中没有点击发送的文字、尚未发送给模型的语音转写文本、在固定业务卡里修改但**尚未提交服务器**的数量/对象/说明字段，在当前设备本地暂存。
- 暂存内容按照当前账号、Merchant、conversation_id（空对话可用本地临时ID）、卡片part_id分开，不能跨用户账号或不同Merchant恢复到另一人界面。
- 切页面、软键盘关闭或短时离线再回来，保持这些输入原样；另一个设备不进行这部分未提交编辑的云端同步。
- 本机正式点击发送或成功提交业务字段后，清除相应未发送本地草稿，开始采用服务端Message/BusinessDraft真实状态。**这里说的本地草稿不是已在服务端保存的正式SaleDraft/PurchaseDraft**。
- 用户主动删除整段聊天时同步丢弃本机与该会话相关的未提交草稿；退出登录后不能把上一账号的草稿暴露给新账号。
- 本地保存只保留必要用户输入，不存用户Token、真实业务执行凭据或未经授权的敏感工具原文。

### 11.6 两类看似相同但性质不同的卡片

| 类型 | 是否发送/提交服务器 | 放在哪里 | 重新进入如何处理 |
|---|---|---|---|
| 用户尚未点提交的卡片字段编辑 | 没有 | 当前设备本地 | 还原未发送字段；不算业务已修改 |
| Agent已经调用业务Tool保存的正式业务草稿 | 已提交 | 真实业务服务 | 依据最新服务端草稿ID、状态与revision恢复并核对 |
| 模型生成的建议卡 | 是展示内容，未必已建业务草稿 | 会话JSON里的MessagePart | 历史可读；点击动作时仍校验是否存在真实Draft |

## 12. 会话权限、Merchant 范围与业务对象可见性

### 12.1 员工会话严格个人隔离；访问与业务权限是两回事

**已确认：同一Merchant内部的员工聊天互不共享。** 每一条会话绑定创建人User ID及原Merchant，只有该账号在有效授权范围内能够读取、搜索、重命名或删除。OWNER不能仅凭商户归属阅读任意STAFF私聊；STAFF也不能读取其他STAFF或OWNER的聊天。账号在本人另一台设备登录可以查看其个人会话。即使用户有权阅读自己以前的旧卡，也不代表今天仍有权限执行采购或销售；每次实际业务写入仍依目标领域的当前授权。

不提供员工之间的共享会话入口，不以商户成员身份推断聊天内容公开。业务工具正常授权访问商户经营数据，不等于能读取别人私人聊天文字。

### 12.2 重要情形

| 情形 | 推荐处理 | 不能做的事 |
|---|---|---|
| 同账号在 Android 和 Web 打开会话 | 在当前授权范围内读取相同消息事实 | 两设备各自重启原 Task |
| 同商户 A 用户和 B 用户 | **已确认不共享**，各自只能访问本人会话 | 因同 Merchant 自动读取任意私聊 |
| STAFF 权限被收回 | 仍按当前可读范围访问历史；新业务写受当前权限限制 | 用历史卡里旧的 STAFF 权限执行 |
| Merchant 进入 FROZEN/READ_ONLY | 按身份模块已确认规则允许的查看/导出；拒绝不允许的经营写入 | 以旧会话状态绕过商户只读 |
| 商户已关闭 | 按账户模块真实关闭语义处理历史访问 | 随意创建新经营记录 |
| 用户退出登录 | 不再展示需要认证的服务器私密数据 | 依旧用旧访问 Token 执行 Tool |
| 用户切换有效 Merchant 上下文 | 当前会话/对象始终保持其原 Merchant 绑定 | 把商户 A 的草稿应用到商户 B |
| 管理员处理系统问题 | 仅按已确定的管理权限与可见范围 | 因系统管理员身份直接读取所有员工私聊 |
| 模型生成非法业务记录引用 | 拒绝或剔除无授权引用 | 根据模型字段直接访问任何记录 |
| 历史业务卡被复制到其他会话 | 服务端验证原 action 和归属关系 | 仅因参数相同就重用别人的动作权限 |

### 12.3 错误反馈语义

- 会话不存在或用户无访问权限：返回普通授权/不存在结果，不泄露其他商户是否拥有某条会话。
- 用户无权执行旧卡动作：显示无法继续，保留有权查看的历史内容。
- Merchant 只读：保留合法阅读能力，但不能将旧卡作为写入豁免。
- 客户端网络错误：提示连接状态，不伪装为商户被禁用或模型失败。

### 12.4 归属字段的作用范围

Conversation 归属以 merchant_id 和 owner_user_id 共同控制，且**不支持员工间共享会话**；Message 与 MessagePart 继承 Conversation 的归属，不在每条 part 里让模型自由指定商户。Task 原始准入与具体业务 Tool 的授权由服务端掌握，尤其不能把旧 session Token 的权限当作永恒有效的业务授权。

### 13.3 图表与可恢复文本的最小字段

| 字段 | 作用 | 是否由模型直接决定 |
|---|---|---|
| conversation_id / message_id | 稳定归属与消息顺序 | 不应由模型决定 |
| task_id / step_id | 关联真实执行事实 | 服务端产生 |
| part_id | UI 组件稳定身份 | 服务端/解析器管理 |
| type / view_type | 固定内容类型与图形类型 | 模型可通过 present_ui 选择合法类型，服务端规范化 |
| revision | UI 块的局部更新顺序 | 服务端管理，不能由模型随意增减 |
| content / data_ref | 可恢复的完整内容或引用 | 模型提供展示数据，服务端保存规范化结果 |
| generated_at / queried_at | 组件生成和数据源时刻 | 以服务端时钟与真实 Tool 来源为准 |
| source_refs | 合法 Tool 结果引用 | 模型可声明，但服务器限定有效集合 |
| business_ref | 相关真实业务对象引用 | 只认现有授权业务 ID，不由自然语言猜测 |
| action_ref | 卡片可执行动作引用 | 服务端授权映射，不允许任意脚本 |
| snapshot_cursor | 恢复位置/一致性边界 | 服务端生成，12 用于订阅 |

### 13.4 不做的事情

- 不把整套业务数据库行、敏感成本或客户未授权字段复制进 Agent 历史。
- 不把单个 ToolStep 的全部原始凭据、SQL 和内部模型推理存为普通用户可见消息内容。
- 不把所有模型 Token 分段都保存成独立永久 Message；可保存可恢复文本和必要的事件位置/更新。
- 不把客户端自动生成的 chart 配置当成可执行脚本。
- 不为消息历史引入新的外部会话 Provider 依赖；模型 API 可以无状态，请求上下文由本系统按 08 组装。

### 13.5 哪些字段在真正实现时才定型

比如 PostgreSQL 的表名和索引、文本分段保存频率、SSE 的事件 ID 具体编码方式、消息保留时限、超大图表 data_ref 的加载方式，这些是实现细节；PRD 先冻结用户看到的**一致快照、增量不丢、历史可读、业务写入不重复**的语义，避免为了先验数据库形状增加形式化流程。

### 13.6 会话正文按Conversation保存一个服务端JSON文件（已确认）

**存储目标：每段会话在服务器上拥有一份JSON文件**，保存有序的User/Assistant消息、完整MessagePart文本/图表/业务卡、可见Tool步骤、来源时间及一致快照版本。它不是手机本地文件，也不是由模型供应商保存的远程会话。

建议利用原有Go+PostgreSQL：**JSON文件承载会话内容**；PostgreSQL保留轻量会话索引（conversation_id、owner_user_id、merchant_id、标题、文件位置、最近更新时间、删除标记）、真实Task关联和当前状态。采购/销售/库存正式事实依旧在各领域业务表，不复制成“会话真实订单”。

~~~mermaid
flowchart LR
    UI[各端客户端] --> API[Go Agent API]
    API --> INDEX[(会话索引和Task状态)]
    API --> JSON[(每会话JSON文件)]
    JSON --> PART[消息 文字 图表 Tool摘要]
    API --> STREAM[12实时事件]
    API --> BIZ[(原有进销存业务服务)]
~~~

### 13.7 三个Task同时写一个JSON文件（必要的防丢失规则）

不能让三个Task各自读取旧文件后整份覆盖，否则会丢失另外两个Task的内容。推荐由现有Go会话模块为同一Conversation**串行合并文件变更**：各Task按task_id、message_id、part_id定位内容块，file_revision逐次递增；写临时完整JSON后原子替换，普通高频文本增量可以小批量合并，完整图表与Task关键状态及时保存。多个进程时复用已有数据库版本/CAS协调，不引入新微服务。

重连读取到的文件快照必须和snapshot_cursor相对应。订阅窗口已失效时直接再取最新JSON快照；文字展示仍交02的流式浮现组件，不能通过重新请求模型达到视觉效果。

### 13.8 删除后的文件状态

删除当下将deleted_at和purge_after=deleted_at+7天写入服务端索引及该会话文件元数据；从此禁止用户读取和恢复。到期清理文件、缓存和可清理索引，正式业务数据不随之删除。后台Task在删除后不能再通过普通会话接口向用户展示，也不能在文件清理后重新创建已删JSON。

## 14. 重要状态图、恢复判断与可视化交互状态

### 14.1 服务端 Task 与客户端连接不是同一个状态机

~~~mermaid
stateDiagram-v2
    state "客户端连接" as Connection {
        [*] --> Connected
        Connected --> Disconnected: 断网或退出页面
        Disconnected --> Reconnecting: 网络恢复/回到会话
        Reconnecting --> Connected: 获取快照并成功订阅
        Reconnecting --> Disconnected: 仍无法连接
    }
    state "Task真实执行" as TaskState {
        [*] --> Running: 准入并开始
        Running --> WaitingUser: 需要用户确认
        WaitingUser --> Running: 合法用户确认后继续
        Running --> Completed: 完成
        Running --> Failed: 真实失败
        Running --> Cancelled: 有效取消
        WaitingUser --> Cancelled: 有效取消
    }
~~~

**状态图说明**：左右两组状态互不直接驱动。用户手机进入 Disconnected 时，不会引发 Task 从 Running 转成 Failed；需要确认时可能转入 WaitingUser，等待用户回到会话操作。正式 Task 状态以 07 实际定义为准，图中的英文状态仅为产品逻辑示例。

### 14.2 历史业务卡的显示状态与执行状态

~~~mermaid
stateDiagram-v2
    [*] --> Historical: 从服务端恢复卡片
    Historical --> Reviewing: 用户点确认
    Reviewing --> AlreadyDone: 原请求已提交成功
    Reviewing --> CanExecute: 当前事实合法
    Reviewing --> NeedUpdate: 版本/相关条件变化
    Reviewing --> Unavailable: 过期/取消/权限不足
    CanExecute --> Submitting: 用户提交有效确认
    Submitting --> Done: 业务服务正式成功
    Submitting --> Unknown: 未知执行结果
    Unknown --> Done: 查明原请求成功
    Unknown --> Reviewing: 查明未执行并允许继续
    NeedUpdate --> Reviewing: 用户重新核对
    AlreadyDone --> [*]
    Done --> [*]
    Unavailable --> [*]
~~~

**状态图说明**：Historical 卡本身代表保存过的展示快照；后面的 Reviewing、CanExecute、Submitting 代表新一次业务动作处理状态。即使卡的图文还保留，用户执行能力也可能因为当前权限和领域状态改变而被拒绝。

### 14.3 把当前运行状态展示成用户能理解的语言

| 服务器事实 | 用户看到的建议文案 | 是否能主动重试 |
|---|---|---|
| 正常运行、连接正常 | 正在查询/分析，可展开具体步骤 | 不应重复发相同任务 |
| 运行中但连接断开 | 网络已断开，任务仍由服务器处理，恢复连接后继续查看 | 先重新连接，不重新提交 |
| 运行中且重连成功 | 已恢复到最新进度，继续接收处理结果 | 无需 |
| 等待用户确认 | 请查看并确认业务内容 | 可以确认/取消，需当前事实核对 |
| 已完成 | 已完成，可查看完整回答及结果卡 | 无需 |
| 模型上游实际失败 | 模型服务暂时不可用，请重试。 | 按 01/07 允许手动重试 |
| 业务动作结果未知 | 正在确认本次操作结果，请勿重复提交 | 先查原动作状态 |
| 当前卡数据冲突 | 信息已更新，请核对变化后再次确认 | 编辑/重新确认而非盲重试 |
| 无权限/已失效 | 该操作当前无法继续 | 不提供绕过权限的重试 |
| 用户删除聊天历史 | 立即不可访问、不支持恢复；服务器7天后清理JSON | 不影响正式经营记录 |

“任务仍由服务器处理”文案只有在服务端确认 Task 已准入并仍处于 running/waiting_user 等有效状态时才能显示；如果服务端已经失败或停止，不能继续承诺必然完成。

### 14.4 对话与实际业务卡联动的边界流程

~~~mermaid
flowchart TD
    START[用户恢复历史会话] --> SNAP[03恢复消息和part快照]
    SNAP --> INTENT{用户当前想做什么}
    INTENT -->|只阅读| READ[显示当时快照和时间]
    INTENT -->|继续提问| NEWTASK[保存新消息并创建新Task]
    INTENT -->|确认旧卡| ACTION[提交受控action引用]
    ACTION --> LIVE[业务服务读取当前真实状态]
    LIVE --> CHECK{已提交成功或当前是否合法}
    CHECK -->|已成功| ORIGINAL[返回已有真实结果]
    CHECK -->|当前合法| SUBMIT[按业务服务规则提交]
    CHECK -->|数据改变| CONFLICT[提示变化并要求重新确认]
    CHECK -->|无权或失效| REJECT[解释不可执行]
    SUBMIT --> RESULT[保存正式业务事实]
    RESULT --> LINK[03关联最终结果到消息]
    ORIGINAL --> LINK
    LINK --> PRESENT[02更新原卡片显示]
~~~

**流程说明**：读历史与确认经营动作是两条分支；显示数据不等于立即执行。模型建议、MessagePart 卡片、真实业务 Service 各司其职，能避免“AI 建议已存在就视为采购成功”。

## 15. 详细经营案例：采购建议卡跨天继续

### 15.1 场景与前提

11月4日，用户查询矿泉水销量，模型整理后给出“建议采购 20 箱”的**建议卡**。如果该建议卡只是用于分析，它不是已经创建的采购草稿；如果 Agent 已调用合法工具创建了正式采购草稿，就应存有真实业务草稿引用。11月5日用户从历史中打开原卡决定执行。期间商品单价、库存或供应商可能变化，也可能有另一设备已经执行过该动作。

以上“20 箱”和日期用于解释流程，不代表真实商户数据；采购草稿是否支持状态、版本以及到货策略最终以采购模块已确认业务设计为准。

### 15.2 用户行为和系统行为

| 步骤 | 用户界面 | 03/12 消息与流行为 | 真实业务与权限行为 |
|---|---|---|---|
| 1 | 11月4日显示建议卡 | 保存文字/卡片/来源/生成时间 | 只能称为采购建议，除非真实 Draft 已创建 |
| 2 | 用户切到销售页面或断网 | 03 保留会话、12 连接断开 | 已准入 Task 按 06/07 继续或等待用户 |
| 3 | 11月5日打开旧会话 | 03 恢复完整图文快照 | 不因为打开历史就查库或创建新单 |
| 4 | 用户看到“生成于11月4日” | 原内容和时间不被静默改写 | 时间只是判断可能过时的信号 |
| 5 | 用户点击确认 | 客户端发受控 action 引用与本次输入 | 业务服务按当前身份查询草稿/商品/供应商 |
| 6A | 仍可执行 | 页面允许按当前参数提交 | 业务服务合法提交并返回真实结果 |
| 6B | 商品单位/单价发生变化 | 展示哪些字段不同 | 用户重新选择/核对；领域服务决定何时要求新确认 |
| 6C | 原草稿已被他人或另一设备完成 | 显示原完成记录 | 返回已有业务单据，绝不创建第二笔 |
| 6D | 用户权限已变化 | 显示不可操作 | 当前权限不足则拒绝 |
| 7 | 成功后展示“已办理” | 原消息关联真实业务引用/结果 | 销售或采购事实只由业务服务写入 |
| 8 | 删除 Agent 会话 | 会话从历史移除 | 正式采购记录依旧存在 |

### 15.3 对“旧卡是否应自动变成最新数据”的最终判断

**不自动改旧卡。** 原建议卡仍然说明当时模型基于什么数据给出建议；用户主动确认时，以最新业务事实处理动作；如果需要将旧建议改为新建议，应通过**新查询/新模型整理结果**生成清晰的新内容，不用客户端悄悄修改历史推导。一个业务操作成功后可以在旧消息旁显示“该操作已完成”的**状态投影**，这并不等于把旧模型分析数字全部改成当前值。

### 15.4 当用户发完“帮我采购20箱”就离线

应区分四种真实服务端结果：

| 真实结果 | 离线期间服务器行为 | 用户再次进入后 |
|---|---|---|
| Agent 仅生成采购建议 | 保存建议卡并完成 Task | 看见建议，不显示“采购成功” |
| Agent 创建了可恢复业务草稿 | 保存草稿的真实 ID 并可能进入等待确认 | 看见草稿和必要确认操作 |
| 已按确认规则执行正式采购 | 保存已成立经营记录及关联结果 | 直接显示成功结果，不让用户再点一次提交 |
| 业务请求超时结果未知 | 保留请求关联并由领域服务确认最终结果 | 显示结果待确认，不自动重新执行 |

不能因为用户离线而把“等待用户确认”误当成任务失败，也不能为了让整个任务“完成”而跳过用户本来需要做的正式确认。

### 17.2 实施路径（不另建新体系）

- 在现有Go服务端每会话以一个JSON文件保存Messages/Parts/图表快照，数据库仅保留会话索引、Task真实状态及其他必要事实；同会话3个并发Task必须串行合并文件更新，正式业务写入依旧走原Application Service。
- 03 对外提供“首次发送创建/读取/删除会话、恢复JSON消息”的能力；12管理增量事件与文字浮现数据衔接，07负责真实Task运行与恢复，单会话最大并发3个Task。
- 对历史业务卡，点击动作直接调用正常业务服务，继承领域 CAS、幂等、权限和当前值判断；不新增“对话采购系统”或单独的库存影子表。
- 对普通图表/表格，保存模型通过 02/05 规范化的展示数据与查询时间，恢复时直接渲染原内容。
- 只做防止重复提交、消息漏传、越权访问和正式经营数据损坏的必要处理，不扩大为额外的审计系统、反复复核或工程门禁。

### 17.3 典型异常与最终责任

| 现象 | 真实含义 | 应当归属 |
|---|---|---|
| 设备掉线但模型继续生成 | 连接断开、Task 未终止 | 03/07/12 |
| 重新上线缺一半图表 | 快照/事件恢复边界不一致 | 03 快照合同 + 12 补流 |
