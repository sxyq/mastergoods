## 1. 产品目标、使用场景与边界

### 1.1 一句话定义

把用户与 Agent 之间的一段多轮经营对话，保存为可长期查看、可跨设备打开、可继续追问，并能关联工具运行、图表快照、业务草稿和真实经营结果的**服务端会话事实**。客户端只是该事实的观察和操作入口，用户退出 AI 页面不意味着服务端已准入的任务终止。

### 1.2 用户需要得到的体验

1. 从首页进入AI、点新对话仅显示空白视图；**首次真正发送且服务端受理消息时创建会话**，然后收到流式文字、工具步骤、图表与表格。
2. 提问后切到商品或采购页面、手机锁屏、网络切断，**任务仍在 Go 服务端按真实状态继续**；客户端不会仅因失去连接而把任务标记成失败。
3. 网络恢复后取得服务端最新消息快照；断线期间新增的文字使用已有流式文本组件**逐段浮现**而非瞬间整屏跳出，再无缝接续实时增量；显示上区分「恢复呈现」与服务端Task真实运行状态。
4. 历史图表显示原来查询的范围、数值和时间；重新需要真实库存或销量时主动发起新的查询，不悄悄改写旧回答。
5. Agent 在聊天中生成采购/销售/库存业务卡片，用户离开后从历史重新打开，点击“确认”之前服务端获取**当前真实业务数据**，判断旧卡片是否仍可执行，而不是直接相信几小时前的表单数据。
6. 删除会话不等于取消或删除真实采购、销售或库存事实；经营记录仍可通过正常业务页面查询和管理。

### 1.3 不属于 03 的事情

- 不运行模型、不决定意图、不修改业务数据库、不决定积分计费。
- 不重造 Task 的执行/恢复引擎（06/07）或 SSE/WebSocket 的具体传输机制（12）。
- 不用数据库历史信息直接生成最终模型图表；由 02/05 的 present_ui 组织并解析，然后 03 保存标准化 MessagePart。
- 不额外发明“草稿 24 小时自动过期”“缺货即禁止所有采购”等尚未由业务领域确认的规则。
- 不把会话删除当作对业务 Application Service 的取消命令。
- 不因客户端读取失败或设备断线就自动重做已成功的采购/销售写 Tool。

### 1.4 需求状态标记

| 状态 | 含义 |
|---|---|
| 已确认 | 本轮用户已明确表述，或已经在 02/01 等模块确认且可继承 |
| 推荐实现 | 为实现已确认体验所需的轻量设计建议，可能依现有 Go/PostgreSQL 架构调整 |
| 待产品决定 | 用户尚未选择的体验分支，不得当成最终产品规则 |
| 归其他领域 | 库存、销售草稿、采购草稿、权限等已有模块决定；03 引用其事实，不自行冻结 |

## 2. 核心对象与职责关系

### 2.1 Conversation、Message、Task、MessagePart 和 ToolStep

| 对象 | 定义 | 保存的核心事实 | 与其他对象关系 |
|---|---|---|---|
| Conversation | 一个用户连续多轮交谈的会话 | 会话 ID、Merchant 范围、创建人、标题、创建/更新时间、可见状态 | 包含多条 Message，可关联多个 Task |
| Message | 对话中的一条用户/Agent 可见消息 | message_id、顺序、role、状态、产生时间 | 属于 Conversation；Agent 消息可关联 Task |
| Task | 一次经准入的 Agent 执行单位 | task_id、关联消息、执行状态、模型档位（仅服务端）、终态 | 一轮 Task 可多次模型调用和多个 Tool Call |
| MessagePart | 一条 Agent 消息里有序的文字、指标、图表、表格或表单 | part_id、type、view_type、内容/引用、revision、快照时刻 | 属于 Message；由 02 固定渲染器展示 |
| ToolStep | 真实执行阶段或 Tool 调用 | step_id、task_id、状态、可展示输入/输出摘要、真实来源 | 属于 Task，执行链可展开 |
| BusinessRecordRef | 会话关联到正式经营记录的**引用** | 业务对象种类、Merchant 范围、后端业务 ID、可见权限 | 不复制记录本身，也不赋予新的业务权限 |
| UIActionRef | 某张卡片上可点击的受控动作引用 | action_id、所在 part、目标业务引用、模型建议的参数、服务端状态 | 不是已经执行成功的证明 |

**逻辑关系不要求每个对象单独建一张表。** 依据现有 Go 模块化后端和 PostgreSQL 实施，优先复用已有业务草稿与状态字段，避免复制业务数据。

### 2.2 服务端持久化与客户端临时状态

| 数据 | 以谁为准 | 原则 |
|---|---|---|
| Conversation 及消息顺序 | 服务端 | 客户端本地 ID 只是提交前临时标识 |
| Task 最终状态 | 06/07 服务端 | 断线不修改状态 |
| 业务单据/库存/金额 | 领域 Application Service | 聊天显示不能篡改真实业务 |
| 文字与完整图表快照 | 03 消息服务 | 旧会话能按原样渲染 |
| Tool 步骤状态及摘要 | 运行时产生，03 提供关联/可恢复读取 | 不泄露内部凭据/私有思维链 |
| 输入框未发送草稿 | 建议当前设备本地暂存 | 跨设备草稿同步尚未确认 |
| 图表当前展开/切换 | 客户端 UI 状态，可选择保存必要视图偏好 | 不能覆盖原始数据快照 |
| 正式动作是否执行过 | 领域业务服务及其幂等记录 | 不能从卡片的视觉状态推断 |

### 2.3 为什么不能把模型返回的一段文字直接当 Message 的全部内容

Agent 02 的模型可以输出普通文字及 present_ui 结构化数据。03 至少应保存**可恢复的标准 MessagePart**，含类型、稳定 ID、数据体/引用、来源、当时查询时刻与版本。仅存自然语言文本不能恢复固定图表和交互卡，更无法关联原始业务操作事实。

## 3. 会话与消息生命周期

### 3.1 首次发送时创建 Conversation（已确认）

- 从首页点AI或点击“新对话”只是本机空白视图，不创建服务端 Conversation 或JSON会话文件。
- 用户第一次点击发送，服务端在身份/商户合法和请求准入后，以稳定 client_request_id 识别本次发送；首次受理时建立 conversation_id、第一条 UserMessage 和关联 Task，同时初始化服务端会话JSON文件。
- 如果服务端已经受理但客户端未收到回执，恢复后先查询或重发**同一请求标识**以取回原 conversation_id/task_id，不创建第二个会话和重复任务。
- 未发送输入仅保留本机；不产生空会话历史。

### 3.2 会话生命周期（七天后清理，不提供恢复）

~~~mermaid
stateDiagram-v2
    [*] --> LocalEmpty: 打开新对话
    LocalEmpty --> Active: 首次发送已受理
    Active --> Active: 继续提问和执行Task
    Active --> DeleteConfirm: 点击删除
    DeleteConfirm --> Active: 取消
    DeleteConfirm --> Deleted: 用户确认删除
    Deleted --> Purged: 满7天自动清理JSON文件
    Purged --> [*]
~~~

- LocalEmpty 为本机空页面，不是云端持久会话。
- Active 只对创建人账号在该Merchant授权范围内可见；其他员工无权访问和共享。
- Deleted 表示用户确认后**立即从历史列表消失、禁止通过API打开且不提供恢复**；服务器将JSON文件标记 deleted_at 与 purge_after（删除时刻加7天）。
- Purged 表示到达清理时间由服务器自动清理该会话JSON文件和相应缓存、索引数据。**用户侧不可恢复是立即生效，物理文件删除是在7天后；不能把两者写成同一动作。**
- 删除会话不会连带删除已经成立的采购、销售、库存和人工经营账事实。

### 3.3 消息与任务状态不能合并

建议把消息至少区分发送受理、生成中、已完成、失败或被中止的显示状态；实际 Task 的 running、waiting_user、completed、failed、cancelled 等终态/中间态归 07 设计并对 03 提供投影。**message.done 由服务端最终 Task/回复事实发出；客户端接收到最后一个文字片段不代表 Task 已完成。**

### 3.4 主要操作和权限入口

- 创建会话、读取当前用户可访问的会话列表、打开某一会话、分页获取消息。
- 重命名、删除聊天历史入口、搜索、按更新时间排序和时间分组。
- 重新打开时获取当前 Task 状态、已持久化完整内容块及工具摘要。
- 继续追问引用已保存的消息和业务对象，实际上下文选择归 08。
- **已确认不共享**：会话只能由创建账号在原Merchant范围内访问；其他STAFF/OWNER不能因同商户而读取、搜索、接管或接收该会话流事件。

## 5. 本轮确认 A：客户端断线不取消服务器 Task

### 5.1 已确认产品语义

**用户确认：客户端断线时服务端仍按既有任务生命周期执行整个任务。** 手机断网、进入后台、切换页面、关闭前端窗口、SSE 断连，都只改变连接状态，不改变**已准入 Task**的业务运行状态。

必要例外：任务自身真实失败、用户发出有效停止指令、需要用户确认而进入 waiting_user、运行时遭受不可恢复错误时，Task 不可能无条件继续到完成。如何在服务器崩溃或进程重启后恢复归 07；**客户端离线后继续 ≠ 保证任何情况下永不失败**。

### 5.2 断线仍执行的完整时序

**重点**：客户端只负责显示，真正的执行和持久化必须存活于服务端任务生命周期。用户返回时不要重新创建同一 Task，不应为了补齐消息重做任何已经执行过的业务 Tool。

### 5.3 明确区分四个状态

| 事实 | 可能状态 | 用户端如何理解 |
|---|---|---|
| 网络/事件连接 | connected / disconnected / reconnecting | 只描述是否收到事件 |
| Task 运行 | queued / running / waiting_user / completed / failed / cancelled（建议映射） | 描述服务端真实处理情况 |
| 消息内容 | partial / complete / error | 描述目前可显示的文字和组件 |
| 业务动作 | not_submitted / submitted / succeeded / rejected / unknown | 描述是否实际改变经营记录 |

断网不等于 Task failed；消息已完成不等于业务提交成功；业务请求超时 unknown 不等于安全地再次提交。产品界面需要区别对待。

## 6. 本轮确认 B：重连读取最新消息、补齐流式更新且不重启任务

### 6.1 重连时到底应该读取什么

**用户确认：客户端重新上线以后，应收到最新消息和流式处理结果。** 这一产品要求分成两个动作才不会丢消息：

**第一步：获取服务端当前完整快照。** 含 conversation_id、当前可见的消息/内容块、关联 Task 真正状态、可查看的 Tool 运行步骤，以及该快照对应的事件位置 snapshot_cursor。

**第二步：从该快照对应的位置订阅后续增量。** 已经包含在快照中的事件不再重复应用；快照之后发生的事件继续追加或按 part_id/upsert 更新。同一个会话在 iOS、Android、小程序、Web 上行为一致。

为什么不能只“继续监听 SSE”？因为用户断网期间很可能已产生文字、工具结果和图表；如果仅监听未来，离线阶段的内容会缺失。为什么也不能只“读最新快照”？因为读完以后 Task 可能又执行新步骤，单次读取无法同步进行中的后续增量。

### 6.2 一致性位置与补流约定（轻量实现建议）

- 03 为当前会话/任务提供**可恢复的服务端内容快照与 snapshot_cursor**；12 负责怎样通过 SSE 或其他连接协议从该位置继续收到后续流事件。
- 同一个消息 part 以 part_id 和 revision 唯一定位其版本；客户端收到相同版本直接忽略，只有更高 revision 才覆盖。普通文本增量要有可识别的片段/范围或由服务端保存后的完整文本 revision 取代，不能盲目重复拼接。
- snapshot_cursor 必须与快照内容**语义一致**：快照覆盖到哪个事件位置，后续订阅就从那个位置之后继续。不能先读一个旧快照，再取得一个更靠后的 cursor，造成中间更新不可见。
- **优先**将本次已产生的标准 MessagePart 更新、任务状态及其事件序号在现有持久化路径中协调保存，再向客户端发布；不要求新增独立微服务。
- 若实际传输层支持某段事件重放，客户端可以请求 cursor 之后的增量；如果历史事件窗口已不可用，直接**重新取得最新消息快照并接着订阅**。无论采用哪条路，界面必须收敛到相同服务端最新事实。
- 快照中已完成的业务 Tool 步骤/业务结果只用于恢复**可见状态**，不自动触发服务端业务 Tool 再次执行。

上面是达到用户体验要求所需的最小一致性语义，具体 event_id 格式、事件保留时长及 SSE 重连头由 12 定义。

### 6.4 只收到最后事件，是否就算完成？

不算。必须根据服务器实际 Task 状态和消息状态显示：

| 客户端已收到 | 服务端真实情况 | 正确表现 |
|---|---|---|
| 最后一段文本 | Task 仍在整理 present_ui | 显示已有文字，继续等待图表或真实 Task 状态 |
| 工具完成对勾 | 模型还在计算图表 | 工具步骤完成，但 Agent 仍在整理回复 |
| 图表已显示 | 后续模型/业务步骤仍在运行 | 图表可以先展示，但 Task 不能提前标记 completed |
| 连接被关闭 | Task running | 显示网络已断，重新连接读取最新状态 |
| 已收到 message.done | 服务端 Task completed | 显示完整完成态，执行链按 02 折叠 |
| 模型实际失败 | Task failed | 显示 Agent 01 的固定错误文案，保留已产生内容 |
| 需要用户确认 | Task waiting_user | 显示已保存业务卡和待用户动作，不假装已经采购成功 |

### 6.5 断线期间可能有新的真实经营数据

注意两条独立时间轴：

1. **Agent 查询产生的结果快照**，例如当天上午查询库存 120 瓶，必须继续在历史消息中以当时查询时间展示。
2. **业务数据库当前库存**，如果下午已经降为 80 瓶，应在**新查询或确认业务动作时**使用当前数据。

消息恢复应忠实显示生成时快照；执行历史卡则必须重新依据当前业务状态判断，两者不能互相覆盖。打开旧对话无需为了展示历史数据而自动查最新仓库。

### 6.6 跨两台设备同时打开同一会话

两个客户端都可以从 03 读取同一消息快照；正在运行的 Task 只有**服务端一份**。客户端 A、B 各自订阅后续事件，无需分别创建 Task。某个设备掉线不会影响另一个设备实时接收，也不会触发两次模型计费或两次经营写入。若两个设备同时尝试提交**同一张业务卡动作**，由业务服务的状态、revision 和幂等语义决定只能按真实规则成功，不靠“前端按钮先变灰”保证安全。

### 6.7 断线内容必须沿用已有流式文字浮现效果（已确认）

**数据恢复方式与视觉显示方式分开：** 03从服务端JSON持久化的消息取得最新可靠全文/规范化组件；02沿用已经开发或规划的流式文字展示组件，将**用户上次实际看到的位置之后**新增的文本以有节奏的增量逐段显示，而不是在一次接口响应中把整段新内容瞬间铺开；12负责真正的新事件订阅。绝不通过重新请求模型来制造文字动画。

| 内容来源 | 如何显示 | 真实状态 |
|---|---|---|
| 断线前已经显示的旧文字 | 原位立即恢复，不重播 | 保持原MessagePart |
| 断线期间服务端生成但用户未见的文字 | 输入现有流式文字浮现队列，按短句/文本片段节奏递进 | 标注“恢复最新回复”，不伪装模型仍在生成 |
| 断线期间产生的新图表、业务卡 | 对应前面的文字呈现到关联位置后，完整插入固定组件，不逐位动画修改数值 | 以服务端保存的完整合法Part为准 |
| 恢复后服务端继续产生新文字 | 同一输出队列按Task及MessagePart原顺序接续 | Task确实running时才显示“正在生成” |
| 服务端Task已经完成 | 文本仍可按体验逐段展开，但状态显示“已完成 · 正在呈现回复” | 不把动画结束当Task完成 |
| 用户有大量未读历史或主动快速浏览 | 只对最近一轮未见输出采用浮现；允许“立即显示全部” | 不因长动画阻塞查看内容或业务操作 |

推荐使用轻微分段和节奏限制，不做固定伪造的token/s计数，不需要逐字模拟模型真实打字时间。**旧历史的每条消息不从头演一遍，只有本次断线未见的内容逐段呈现**；消息/图表体量很大时可以直接展示结构化大表，避免花数分钟“播完历史”。

### 6.9 并发三个Task时的文本展示规则

每个Task必须有独立的task_id、UserMessage、AssistantMessage和ToolStep归属。**同一会话最多三个并发活跃Task并不会产生一条交叉拼接的“万能回答”**。文字浮现队列按所属AssistantMessage分别追加和显示；界面可以同时看到最多三条回复各自运行状态，不能把任务A的文字插入任务B的图表。历史显示顺序由服务端Message顺序决定，不按照事件哪条先到就随意交换消息。未完成任务的“刚才那个”对象引用及跨任务上下文选择归08/06进一步定义。

## 7. 本轮确认 C：历史业务卡必须按当前业务事实重新判定

### 7.1 为什么创建时间必须有，但不能单凭时间做决定

历史卡应当保留 generated_at（卡片生成时间）、数据来自什么 source_refs、对应哪个业务草稿/商品/用户/商户，以及生成时所基于的版本或业务引用。时间允许用户理解“这是此前的建议”，也帮助服务端确定这不是一个新生成动作。

**但时间老不一定不可用，时间新也不一定安全。**

例如 3 小时前生成的采购卡，其供应商、商品、价格和草稿如果仍处于可执行状态，并且现有业务领域允许，就可能继续合法执行；反过来，1 秒前的销售卡也可能因为另一设备已经完成该销售、商品停用或权限撤销而失效。

因此最终允许操作应看**当前业务事实 + 权限 + 版本/状态 + 原本要求的用户确认 + 是否已执行**，而不是设一个未经产品确认的“超过多少分钟就禁止”规则。对于真实 SaleDraft，如果领域采用 revision/CAS，应按其现有规范执行；采购草稿若尚未确认对应状态机和过期策略，03 不得自行规定 24 小时失效。

### 7.2 历史业务卡打开与点击的职责

- **打开历史消息**：03 读取并展示原卡片快照，标明生成时间和可能需要重新确认；不自动修改真实业务记录。
- **用户点击“确认/完成”**：将 action_id、业务引用、用户已确认的参数和服务端动作请求关联信息发往合法业务命令入口。
- **业务服务当前判定**：重新检查 Merchant/用户权限、草稿状态与 revision、商品与单位、当前领域业务事实、已执行结果和必要规则。
- **结果返回**：可以执行则真实提交，并把结果关联到原 MessagePart；已执行就返回原有结果；发生变化则提示用户查看变化，必要时重新确认；拒绝则保留原历史卡但标记“该操作不可继续”。
- **防重复**：历史卡可重复点击、断网后再次点击、两台设备同时点击都不得让同一个正式业务动作重复成立。

### 7.4 业务卡提交前的边界核对表（本轮确认需要此表）

以下表格区分**必须遵循的执行原则**与**由具体业务模块定义的政策细节**。不增加独立审核服务，不对所有查询图表做写前检查；只在真正需要执行经营命令时走正常领域检查。

| 编号 | 边界场景 | 需要读取或判断什么 | 应当如何处理 | 责任归属 |
|---|---|---|---|---|
| B01 | 历史卡创建很久，但业务数据未变化 | generated_at、当前对象状态/版本 | 不仅因为旧就禁止；若其他条件合法可继续 | 03展示，业务服务判定 |
| B02 | 卡片刚生成，但关联草稿已被修改 | expected_revision 与当前 revision | 返回版本冲突和新内容，重新确认后再操作 | 业务草稿领域 |

| B18 | 服务端请求超时、结果不确定 | 原请求标识和业务执行事实 | 显示处理中/结果待确认，查询原请求；不直接重新执行 | 业务服务 + 07/10 |
| B19 | 原卡数据源已过时 | source_refs、快照时刻及实际当前事实 | 历史卡保持旧内容；点击执行时用当前业务事实判断 | 03 + 业务服务 |
| B20 | 用户改变卡片数量或金额 | 变更字段、单位、当前版本、应授权字段 | 新提交参数走正常字段校验和领域命令，不以旧显示值为准 | 业务服务 |
| B21 | 旧卡关联的业务单已更正或撤销 | 当前正式记录及其更正关系 | 展示实际后续状态，不能凭旧卡再次完成原动作 | 业务领域 |
| B22 | 用户删除了原会话后业务仍已成立 | BusinessRecord ID、原真实结果 | 正式业务事实保留；后续在原业务页面管理，不靠聊天恢复 | 03 + 业务领域 |
| B23 | 业务服务暂不可用 | 当前事实无法可靠取得 | 暂不执行写操作，显示无法确认业务状态；允许稍后再试 | 业务服务/前端 |
| B24 | 旧卡试图重放未经允许的操作 | action_id 是否仍在受控允许集合 | 不执行未知动作或模型输出的自由指令 | Agent 05/11 + 领域 |
| B25 | 历史业务卡是“建议草稿”而非已保存草稿 | 是否存在真实业务 draft_id | 先明确创建/保存路径；不能把模型文本当已持久草稿 | 03/11/业务领域 |
| B26 | 采购单尚未实际入库 | 采购业务状态与入库记录 | 只展示真实采购状态，不能自动声称库存增加 | 采购/库存领域 |
| B27 | 销售单生成但未完成出库 | 销售/出库真实状态 | 不能显示已扣库存或已收款，按真实业务执行阶段展示 | 销售/库存/经营领域 |

**解释**：真正“确认”的是**操作时以当前真实事实与原请求的执行结果为准**。表格中某些政策尚未冻结，例如采购草稿是否到期、库存不足时能否继续某种流程、售价变化后的确认规则，必须沿用原业务模块未决状态，不由 Agent 03 替用户决定。

### 7.5 推荐的最少提交信息

为了正确关联当前业务请求与历史卡，提交参数至少要让服务端识别：

~~~json
{
  "conversation_id": "conv_123",
  "message_id": "msg_456",
  "part_id": "part_789",
  "action_id": "confirm_business_draft",
  "business_ref": {
    "type": "sale_draft",
    "id": "draft_001"
  },
  "expected_revision": 5,
  "request_key": "client_generated_stable_key",
  "input": {
    "quantity": "20",
    "unit": "箱"
  }
}
~~~

**示例说明**：这一结构是逻辑上的输入需求，不是已经冻结的 API 或现有业务字段。身份、Merchant 权限由当前认证上下文获取，不能相信客户端上传的所属商户；request_key 表示本次用户意图的稳定提交身份，网络重试应使用相同值。expected_revision 只在目标业务草稿采用版本控制时生效；与真实 SaleDraft 已有的 CAS 规则保持一致。不让模型自行指定后端正式记录 ID 或“修改成功”状态。

### 7.6 冲突后的 UI 呈现

<text>
原卡片：“采购矿泉水 20 箱，生成于 10:15”。
现在该商品信息或相关业务状态已经发生变化。
</text>

推荐采用以下交互：

1. **保留旧卡的原始内容**，在原位显示“业务信息已变化，需重新确认”，不可直接覆盖旧文字/数值。
2. 展示安全且当前用户有权查看的**变更前/当前**字段对比，例如数量、单位、当前价、草稿状态；不足以自动比较时展示“请查看最新业务信息”。
3. 用户重新选择/编辑并确认后，向业务服务发送合法的新操作；若草稿已终态或权限已经撤销，按钮禁用并说明原因。
4. 真实业务操作成功才显示新单据/库存结果。若后台收到成功结果而客户端未收到，重连后显示该已成功状态，不再显示“请重复提交”。
5. 两个不同业务表单对同一商品的并行操作，应继续依真实业务服务的当前版本及领域规则处理；03 不建立自己的商品库存版本系统。

**这里不需要一套新“卡片审批中心”或永久审计台。** 只是让已有业务写入口在执行前读取自己必需的当前事实，保证历史 UI 不会绕过真实领域约束。

## 8. 历史消息与数据快照、业务现值必须分开

### 8.1 三种时间

| 时间 | 含义 | 是否决定可执行 |
|---|---|---|
| generated_at | 模型生成这张 UI 卡/组件的时刻 | 不独立决定 |
| queried_at / source_at | 真实业务工具查询基础数据的时刻 | 说明快照新旧 |
| submitted_at / committed_at | 用户确认/业务服务真正提交执行的时刻 | 由领域正式结果决定 |

模型生成时间并不保证所有源数据都在同一时刻查询。若工具返回的是不同时间的查询快照，应以具体 data_source 的查询时间解释，不能用生成时刻冒充所有业务数据同时最新。

### 8.2 历史图表的显示与刷新

- 历史库存/销量卡保存模型输出的**规范化结果及当时数据引用、查询范围和时间**；打开时不自动用最新库存改写原有图表。
- 点击“更新到最新”应该触发一个新的受控查询/Agent Task，产生新的消息或清晰的新版本结果；旧结果仍可回看，避免对经营历史造成误导。
- 普通图表切换、排序已加载的数据不需要重新调用模型；涉及最新库存、日期范围或重新计算则发起新查询。
- 图表不能被当作经营记录原始事实的唯一来源，正式当前值始终从业务服务取得。

### 8.3 历史表单与可执行动作的不同生命周期

同一个 MessagePart 的**展示快照**应保持可恢复；但其**动作权限/当前可执行性**应基于每次操作时的实时业务状态。卡片的“原来显示可确认”只说明当时的 UI，不是无限期可使用的执行授权。

~~~mermaid
flowchart TD
    OPEN[打开历史会话] --> SNAP[读取保存的MessagePart]
    SNAP --> SHOW[显示原内容和生成时间]
    SHOW --> CHOOSE{用户只查看还是点击业务动作}
    CHOOSE -->|只查看| END[不执行业务查询或写入]
    CHOOSE -->|确认/修改| NOW[读取当前业务状态和权限]
    NOW --> IDEM{此前相同动作已成功吗}
    IDEM -->|是| RESULT[返回原真实结果]
    IDEM -->|否| VALID{当前合法且用户确认有效吗}
    VALID -->|是| WRITE[通过原领域Service提交]
    VALID -->|否| CHANGED[提示冲突/失效/无权]
    WRITE --> RESULT
~~~

**图示说明**：显示历史与执行历史卡是两件不同的操作。业务卡是否能点、点下去执行什么不能从历史 MessagePart 快照自行决定。

## 9. 本轮确认 D：删除会话不删除正式经营记录

### 9.1 规则与用户预期

**已确认**：删除 Agent 会话不能删除或撤销已经正式发生的采购、销售、库存变动、客户往来和真实记账记录。这些经营事实只能由对应业务模块按权限执行合法更正、取消或撤销操作。

删除历史会话的**产品显示行为**可以选择“从本人会话列表隐藏并按既有数据政策处理”；是否有撤回入口、保留多久、是否物理删除聊天正文尚需单独决定。03 不得把**业务不被删除**扩张成“用户删除聊天后系统永远留存其私聊”的默认规则。

### 9.2 删除历史与经营事实并存的时序

~~~mermaid
sequenceDiagram
    autonumber
    actor U as 用户
    participant UI as 历史会话页面
    participant C as 03会话服务
    participant DB as 会话消息存储
    participant B as 进销存业务服务

    U->>UI: 删除某段历史会话
    UI->>C: 请求删除或隐藏会话
    C->>C: 验证当前用户和会话权限
    C->>DB: 处理会话可见性/聊天数据生命周期
    DB-->>C: 返回会话操作结果
    C-->>UI: 历史列表已移除
    Note over B: 已提交经营记录完全不受会话删除影响
    U->>UI: 打开采购或销售业务页面
    UI->>B: 查询实际经营记录
    B-->>UI: 返回仍有权访问的正式单据
~~~

**图示说明**：从聊天历史列表移除的只是会话对象的显示/管理；不能联动删除业务单、库存流水或经营往来记录。

### 9.3 删除时如果还有运行中 Task？

这是仍需明确的**产品选择**，不应从“删除聊天不删除经营记录”推导为“删除时必然停止所有执行”。推荐：当会话存在 running 或 waiting_user 的真实 Task，删除入口明确提示当前情况；如需要停止，用户先走**显式取消任务**的真实规则（归 07），而不是将删除历史等同取消。

已经完成的经营写操作无论如何都不能因会话删除而被静默回滚。若服务端收到删除请求时仍有业务工具处于结果未知状态，应以真实业务服务结果为准，不能通过删除动作掩盖业务是否提交。

### 9.4 删除/隐藏与可恢复草稿

未发送文本草稿属于客户端输入状态；正式 SaleDraft/PurchaseDraft（如果领域实际支持）属于业务聚合。删除聊天不能代替用户取消业务草稿，也不决定草稿是否过期。若卡片已关联正式业务对象，其访问能力仍由对应业务页面和授权决定，删除历史后不要求保留该卡作为唯一操作入口。

## 10. 新消息、失败重试、重复提交和并发任务

### 10.1 首次发送消息的因果顺序

理想情况下，用户发消息时客户端产生一个稳定的 client_request_id，Go Agent API 先确定当前用户、Merchant、Conversation，再让服务端保存 UserMessage 和 Task 关联；服务端返回确定的 message_id 与 task_id 后，客户端可将临时气泡与正式消息关联。客户端等待很久未收到响应，不能立刻另开一条新任务：先查询该请求是否已被受理，或者使用相同的请求身份安全地重新提交。

对于只读统计，这可以减少重复生成回答；对于会引发正式经营写入的任务，更要由真正执行 Tool 的领域服务保证**同一业务动作不重复成立**。03 消息提交的请求身份不能取代业务写命令自身的幂等机制。

### 10.2 首次发送时断网/重复点击时序

~~~mermaid
sequenceDiagram
    autonumber
    actor U as 用户
    participant UI as 客户端
    participant API as Agent API
    participant C as 03消息服务
    participant R as 06/07 Runtime

    U->>UI: 点击发送
    UI->>API: client_request_id和用户消息
    API->>C: 查询是否已经保存该请求
    alt 第一次被服务端受理
        C->>C: 保存消息并关联Task
        C-->>API: message_id task_id
        API->>R: 启动已准入Task
    else 相同请求此前已经受理
        C-->>API: 返回已有message_id和task_id
    end
    Note over UI,API: 响应可能在传输途中丢失
    U->>UI: 看到网络未连接后点击重试
    UI->>API: 使用相同client_request_id查询/重试
    API->>C: 检查已受理事实
    C-->>UI: 返回既有消息和当前Task状态
    UI-->>U: 展示现有消息 不产生新的重复任务
~~~

**原则**：用户主动重新提出一条不同问题属于新的请求；网络重连/重复点击同一次“发送”不应创建第二轮任务。同一动作的幂等身份应有明确作用范围（用户/商户/业务动作），避免不同用户之间错误复用。

### 10.3 Task 失败与用户手动重试

- 客户端离线：不触发用户“模型失败”提示；重连后读取真实 Task 状态。
- 真正模型上游失败：沿用 Agent 01 固定文案**“模型服务暂时不可用，请重试。”**，保留此前文字、工具步骤和已完成结构化块；是否创建新 Task/新模型请求由 06/07/01 统筹。
- UI 结构化图表损坏：可只将该 part 标为不可展示，不把整轮标为上游模型故障。
- 工具实际失败：保存业务可读的真实执行结果，不伪造成功。
- 用户点击“重新生成”：不直接复用上一次有副作用的 Tool 请求序列。若先前经营写入已经成功，服务端必须知道该事实，不能在新 Task 中自动再执行一次采购或销售。

### 10.4 同一会话内的并发任务（尚待决定）

当前**建议**同一个 Conversation 只允许一个活动前台用户任务进入 Agent 主循环，用户在 waiting_user 状态下的后续业务动作应由 07/11 协调。不同会话可各自运行任务。这样可以让“刚才那个”“上一轮图表”的上下文顺序更清晰，但用户并未确认这一并发限制。03 不直接定义或实现任务队列；若采用该建议，冲突时应返回可理解状态，而不是让第二个客户端悄悄创建一条交错回复。

### 10.5 消息更新与本地 UI 状态

- 新文本 delta 到来，不重建整个聊天消息组件。
- 同一个 part_id、revision 重复收到时不重复插入；版本更高时才更新对应块。
- 图表的图/表切换可以是本地状态，不需要更新服务端统计事实。
- 用户正在编辑业务卡时若服务器报告该卡业务版本变化，不应静默覆盖输入；应提示变化和重新确认。
- 用户点击“停止”只是在客户端发出真实任务控制请求，是否已停止以服务器 07 的状态为准。

## 11. 历史会话管理与手机/桌面用户操作

### 11.1 历史列表的页面能力

沿用 02 已有的 ChatGPT 风格历史入口，移动端从顶部历史图标进入抽屉/全屏列表，桌面可用折叠侧栏。建议列表内容：

| UI 信息 | 依据 | 交互 |
|---|---|---|
| 会话标题 | 用户命名或系统生成标题 | 点击打开；长按/更多可重命名 |
| 最近更新时间 | 服务端 last_message_at 等有效字段 | 按最新会话优先排序 |
| 近况摘要 | 最近一次可见内容的简短摘要 | 不含私密 Tool JSON |
| 任务状态（若仍活动） | 当前 Task 真值 | “运行中/等待确认”等，不以网络连接推断 |
| 搜索输入 | 用户有权查询的会话元数据/内容 | 只展示授权范围内的搜索结果 |
| 时间分组 | 今天、昨天、此前等 | 根据用户界面时区显示 |
| 删除入口 | 会话授权与产品删除策略 | 影响聊天历史，不删除正式经营事实 |

移动端列表应有明确的“新建会话”入口；用户打开旧会话时，读取服务端可恢复的标准消息和内容块。若本机有未发送文本，切换会话时应按尚未确认的草稿保存规则处理，不在前端静默丢弃。

### 11.2 新会话创建行为（推荐，尚未确认）

空白页可以先只存在客户端，第一次成功提交消息后再正式建立 Conversation。用户切换到历史页面又返回时，不应凭空产生大量无内容会话。若用户确实要求“打开 AI 自动创建一条空会话”，那是另一种产品方向，需要另行确认；目前不冻结。

### 11.4 重命名、搜索和删除的区别

- **重命名**只是更新 Conversation 标题，不能修改任何 Agent 已说过的话或经营数据。
- **搜索**只返回用户有权访问的历史，不因为同 Merchant 就直接让全员检索其他人会话。
- **删除**只作用于会话历史和其可见性/聊天数据生命周期，不执行经营业务撤销。
- **打开旧内容**只读取历史快照；点击刷新/执行才可能产生新的 Tool 请求。
- **会话隐藏和物理删除**需要单独确定数据保留政策；不能在 PRD 写出尚未决定的硬性保留天数。

### 11.5 表单输入、语音转写与未发送草稿

已发送的消息及合法业务结果属于服务器事实。未发送文本和刚转写出的语音文字在正式发送前是输入草稿；推荐先由设备本地保存，避免跨端草稿同步冲突。**这只是建议，不是用户已确认“必须只保留本机”的产品策略**。涉及真正 SaleDraft 的数据则按原业务草稿服务端事实，不得被本地未发送文字替代。

## 12. 会话权限、Merchant 范围与业务对象可见性

### 12.1 访问会话与操作业务是两种权限

即使用户能够看到某条旧消息，也不代表今天仍有权限执行里面的采购或销售动作。会话读取依据当前登录用户、当前 Merchant Membership 和产品的会话可见规则；具体业务写入再依据目标业务服务的当前授权。

同样，拥有经营统计查看权限不意味着可以看到 Agent 历史中其他员工写下的私人问题，除非产品明确定义了共享会话模式并授权。

### 12.2 重要情形

| 情形 | 推荐处理 | 不能做的事 |
|---|---|---|
| 同账号在 Android 和 Web 打开会话 | 在当前授权范围内读取相同消息事实 | 两设备各自重启原 Task |
| 同商户 A 用户和 B 用户 | 建议默认个人会话；共享另行确认 | 因同 Merchant 自动读取任意私聊 |
| STAFF 权限被收回 | 仍按当前可读范围访问历史；新业务写受当前权限限制 | 用历史卡里旧的 STAFF 权限执行 |
| Merchant 进入 FROZEN/READ_ONLY | 按身份模块已确认规则允许的查看/导出；拒绝不允许的经营写入 | 以旧会话状态绕过商户只读 |
| 商户已关闭 | 按账户模块真实关闭语义处理历史访问 | 随意创建新经营记录 |
| 用户退出登录 | 不再展示需要认证的服务器私密数据 | 依旧用旧访问 Token 执行 Tool |
| 用户切换有效 Merchant 上下文 | 当前会话/对象始终保持其原 Merchant 绑定 | 把商户 A 的草稿应用到商户 B |
| 管理员处理系统问题 | 仅按已确定的管理权限与可见范围 | 因系统管理员身份直接读取所有员工私聊 |
| 模型生成非法业务记录引用 | 拒绝或剔除无授权引用 | 根据模型字段直接访问任何记录 |
| 历史业务卡被复制到其他会话 | 服务端验证原 action 和归属关系 | 仅因参数相同就重用别人的动作权限 |

### 12.3 错误反馈语义

- 会话不存在或用户无访问权限：返回普通授权/不存在结果，不泄露其他商户是否拥有某条会话。
- 用户无权执行旧卡动作：显示无法继续，保留有权查看的历史内容。
- Merchant 只读：保留合法阅读能力，但不能将旧卡作为写入豁免。
- 客户端网络错误：提示连接状态，不伪装为商户被禁用或模型失败。

### 12.4 归属字段的作用范围

Conversation 归属以 merchant_id 和当前个人/共享可见策略控制；Message 与 MessagePart 继承 Conversation 的归属，不在每条 part 里让模型自由指定商户。Task 原始准入与具体业务 Tool 的授权由服务端掌握，尤其不能把旧 session Token 的权限当作永恒有效的业务授权。

| 字段 | 作用 | 是否由模型直接决定 |
|---|---|---|
| conversation_id / message_id | 稳定归属与消息顺序 | 不应由模型决定 |

| part_id | UI 组件稳定身份 | 服务端/解析器管理 |
| type / view_type | 固定内容类型与图形类型 | 模型可通过 present_ui 选择合法类型，服务端规范化 |
| revision | UI 块的局部更新顺序 | 服务端管理，不能由模型随意增减 |
| content / data_ref | 可恢复的完整内容或引用 | 模型提供展示数据，服务端保存规范化结果 |
| generated_at / queried_at | 组件生成和数据源时刻 | 以服务端时钟与真实 Tool 来源为准 |
| source_refs | 合法 Tool 结果引用 | 模型可声明，但服务器限定有效集合 |
| business_ref | 相关真实业务对象引用 | 只认现有授权业务 ID，不由自然语言猜测 |
| action_ref | 卡片可执行动作引用 | 服务端授权映射，不允许任意脚本 |
| snapshot_cursor | 恢复位置/一致性边界 | 服务端生成，12 用于订阅 |

### 13.4 不做的事情

- 不把整套业务数据库行、敏感成本或客户未授权字段复制进 Agent 历史。
- 不把单个 ToolStep 的全部原始凭据、SQL 和内部模型推理存为普通用户可见消息内容。
- 不把所有模型 Token 分段都保存成独立永久 Message；可保存可恢复文本和必要的事件位置/更新。
- 不把客户端自动生成的 chart 配置当成可执行脚本。
- 不为消息历史引入新的外部会话 Provider 依赖；模型 API 可以无状态，请求上下文由本系统按 08 组装。

### 13.5 哪些字段在真正实现时才定型

比如 PostgreSQL 的表名和索引、文本分段保存频率、SSE 的事件 ID 具体编码方式、消息保留时限、超大图表 data_ref 的加载方式，这些是实现细节；PRD 先冻结用户看到的**一致快照、增量不丢、历史可读、业务写入不重复**的语义，避免为了先验数据库形状增加形式化流程。

## 14. 重要状态图、恢复判断与可视化交互状态

### 14.1 服务端 Task 与客户端连接不是同一个状态机

~~~mermaid
stateDiagram-v2
    state "客户端连接" as Connection {
        [*] --> Connected
        Connected --> Disconnected: 断网或退出页面
        Disconnected --> Reconnecting: 网络恢复/回到会话
        Reconnecting --> Connected: 获取快照并成功订阅
        Reconnecting --> Disconnected: 仍无法连接
    }
    state "Task真实执行" as TaskState {
        [*] --> Running: 准入并开始
        Running --> WaitingUser: 需要用户确认
        WaitingUser --> Running: 合法用户确认后继续
        Running --> Completed: 完成
        Running --> Failed: 真实失败
        Running --> Cancelled: 有效取消
        WaitingUser --> Cancelled: 有效取消
    }
~~~

**状态图说明**：左右两组状态互不直接驱动。用户手机进入 Disconnected 时，不会引发 Task 从 Running 转成 Failed；需要确认时可能转入 WaitingUser，等待用户回到会话操作。正式 Task 状态以 07 实际定义为准，图中的英文状态仅为产品逻辑示例。

### 14.2 历史业务卡的显示状态与执行状态

~~~mermaid
stateDiagram-v2
    [*] --> Historical: 从服务端恢复卡片
    Historical --> Reviewing: 用户点确认
    Reviewing --> AlreadyDone: 原请求已提交成功
    Reviewing --> CanExecute: 当前事实合法
    Reviewing --> NeedUpdate: 版本/相关条件变化
    Reviewing --> Unavailable: 过期/取消/权限不足
    CanExecute --> Submitting: 用户提交有效确认
    Submitting --> Done: 业务服务正式成功
    Submitting --> Unknown: 未知执行结果
    Unknown --> Done: 查明原请求成功
    Unknown --> Reviewing: 查明未执行并允许继续
    NeedUpdate --> Reviewing: 用户重新核对
    AlreadyDone --> [*]
    Done --> [*]
    Unavailable --> [*]
~~~

**状态图说明**：Historical 卡本身代表保存过的展示快照；后面的 Reviewing、CanExecute、Submitting 代表新一次业务动作处理状态。即使卡的图文还保留，用户执行能力也可能因为当前权限和领域状态改变而被拒绝。

### 14.3 把当前运行状态展示成用户能理解的语言

| 服务器事实 | 用户看到的建议文案 | 是否能主动重试 |
|---|---|---|
| 正常运行、连接正常 | 正在查询/分析，可展开具体步骤 | 不应重复发相同任务 |
| 运行中但连接断开 | 网络已断开，任务仍由服务器处理，恢复连接后继续查看 | 先重新连接，不重新提交 |
| 运行中且重连成功 | 已恢复到最新进度，继续接收处理结果 | 无需 |
| 等待用户确认 | 请查看并确认业务内容 | 可以确认/取消，需当前事实核对 |
| 已完成 | 已完成，可查看完整回答及结果卡 | 无需 |
| 模型上游实际失败 | 模型服务暂时不可用，请重试。 | 按 01/07 允许手动重试 |
| 业务动作结果未知 | 正在确认本次操作结果，请勿重复提交 | 先查原动作状态 |
| 当前卡数据冲突 | 信息已更新，请核对变化后再次确认 | 编辑/重新确认而非盲重试 |
| 无权限/已失效 | 该操作当前无法继续 | 不提供绕过权限的重试 |
| 用户删除聊天历史 | 会话已从历史中移除 | 不影响真实经营记录 |

“任务仍由服务器处理”文案只有在服务端确认 Task 已准入并仍处于 running/waiting_user 等有效状态时才能显示；如果服务端已经失败或停止，不能继续承诺必然完成。

### 14.4 对话与实际业务卡联动的边界流程

~~~mermaid
flowchart TD
    START[用户恢复历史会话] --> SNAP[03恢复消息和part快照]
    SNAP --> INTENT{用户当前想做什么}
    INTENT -->|只阅读| READ[显示当时快照和时间]
    INTENT -->|继续提问| NEWTASK[保存新消息并创建新Task]
    INTENT -->|确认旧卡| ACTION[提交受控action引用]
    ACTION --> LIVE[业务服务读取当前真实状态]
    LIVE --> CHECK{已提交成功或当前是否合法}
    CHECK -->|已成功| ORIGINAL[返回已有真实结果]
    CHECK -->|当前合法| SUBMIT[按业务服务规则提交]
    CHECK -->|数据改变| CONFLICT[提示变化并要求重新确认]
    CHECK -->|无权或失效| REJECT[解释不可执行]
    SUBMIT --> RESULT[保存正式业务事实]
    RESULT --> LINK[03关联最终结果到消息]
    ORIGINAL --> LINK
    LINK --> PRESENT[02更新原卡片显示]
~~~

**流程说明**：读历史与确认经营动作是两条分支；显示数据不等于立即执行。模型建议、MessagePart 卡片、真实业务 Service 各司其职，能避免“AI 建议已存在就视为采购成功”。

## 15. 详细经营案例：采购建议卡跨天继续

### 15.1 场景与前提

11月4日，用户查询矿泉水销量，模型整理后给出“建议采购 20 箱”的**建议卡**。如果该建议卡只是用于分析，它不是已经创建的采购草稿；如果 Agent 已调用合法工具创建了正式采购草稿，就应存有真实业务草稿引用。11月5日用户从历史中打开原卡决定执行。期间商品单价、库存或供应商可能变化，也可能有另一设备已经执行过该动作。

以上“20 箱”和日期用于解释流程，不代表真实商户数据；采购草稿是否支持状态、版本以及到货策略最终以采购模块已确认业务设计为准。

### 15.2 用户行为和系统行为

| 步骤 | 用户界面 | 03/12 消息与流行为 | 真实业务与权限行为 |
|---|---|---|---|
| 1 | 11月4日显示建议卡 | 保存文字/卡片/来源/生成时间 | 只能称为采购建议，除非真实 Draft 已创建 |
| 2 | 用户切到销售页面或断网 | 03 保留会话、12 连接断开 | 已准入 Task 按 06/07 继续或等待用户 |
| 3 | 11月5日打开旧会话 | 03 恢复完整图文快照 | 不因为打开历史就查库或创建新单 |
| 4 | 用户看到“生成于11月4日” | 原内容和时间不被静默改写 | 时间只是判断可能过时的信号 |
| 5 | 用户点击确认 | 客户端发受控 action 引用与本次输入 | 业务服务按当前身份查询草稿/商品/供应商 |
| 6A | 仍可执行 | 页面允许按当前参数提交 | 业务服务合法提交并返回真实结果 |
| 6B | 商品单位/单价发生变化 | 展示哪些字段不同 | 用户重新选择/核对；领域服务决定何时要求新确认 |
| 6C | 原草稿已被他人或另一设备完成 | 显示原完成记录 | 返回已有业务单据，绝不创建第二笔 |
| 6D | 用户权限已变化 | 显示不可操作 | 当前权限不足则拒绝 |
| 7 | 成功后展示“已办理” | 原消息关联真实业务引用/结果 | 销售或采购事实只由业务服务写入 |
| 8 | 删除 Agent 会话 | 会话从历史移除 | 正式采购记录依旧存在 |

### 15.3 对“旧卡是否应自动变成最新数据”的最终判断

**不自动改旧卡。** 原建议卡仍然说明当时模型基于什么数据给出建议；用户主动确认时，以最新业务事实处理动作；如果需要将旧建议改为新建议，应通过**新查询/新模型整理结果**生成清晰的新内容，不用客户端悄悄修改历史推导。一个业务操作成功后可以在旧消息旁显示“该操作已完成”的**状态投影**，这并不等于把旧模型分析数字全部改成当前值。

### 15.4 当用户发完“帮我采购20箱”就离线

应区分四种真实服务端结果：

| 真实结果 | 离线期间服务器行为 | 用户再次进入后 |
|---|---|---|
| Agent 仅生成采购建议 | 保存建议卡并完成 Task | 看见建议，不显示“采购成功” |
| Agent 创建了可恢复业务草稿 | 保存草稿的真实 ID 并可能进入等待确认 | 看见草稿和必要确认操作 |
| 已按确认规则执行正式采购 | 保存已成立经营记录及关联结果 | 直接显示成功结果，不让用户再点一次提交 |
| 业务请求超时结果未知 | 保留请求关联并由领域服务确认最终结果 | 显示结果待确认，不自动重新执行 |

不能因为用户离线而把“等待用户确认”误当成任务失败，也不能为了让整个任务“完成”而跳过用户本来需要做的正式确认。

### 16.2 能直接作为实现建议、不必再扩展成多轮审批的问题

| 建议项 | 推荐做法 | 原因 |
|---|---|---|
| 补流和断线恢复 | 先读取与 snapshot_cursor 一致的服务端快照，再接收较新事件；不支持回放则重新取快照 | 不丢、不错乱 |
| 事件更新 | 稳定 message_id/part_id、revision，重复事件忽略 | 防止重复追加文字或图表 |
| 已成功业务动作 | 同一请求返回原结果；不重做已执行的写 Tool | 防止重复业务 |
| 历史卡数据核对 | 仅在真正经营写命令执行时由已有业务服务获取当前事实 | 不为普通历史阅读增加不必要查询 |
| 跨设备打开 | 多端共享同一会话/Task 服务端事实，各自订阅实时更新 | 不重复建立任务 |
| 表格/图表快照 | 保存规范化 MessagePart 与必要 source refs 和时间；不存任意可执行 UI 代码 | 与 02 present_ui 一致 |
| 身份权限 | 会话读取权限和业务写入权限各自依据当前合法身份判断 | 防止旧权限绕过 |

### 16.3 还需要产品选择的真正未决项

### 17.2 实施路径（不另建新体系）

- 在现有 Go 服务端的 Agent 模块中，将 Conversation、Message、Part 与 Task 引用按既有数据库习惯保存；真正业务写入走原 Application Service。
- 03 对外只提供“创建/读取/管理会话与可恢复消息”的能力；12 接收已有事件并负责增量流，07 保证真实任务执行与恢复语义。
- 对历史业务卡，点击动作直接调用正常业务服务，继承领域 CAS、幂等、权限和当前值判断；不新增“对话采购系统”或单独的库存影子表。
- 对普通图表/表格，保存模型通过 02/05 规范化的展示数据与查询时间，恢复时直接渲染原内容。
- 只做防止重复提交、消息漏传、越权访问和正式经营数据损坏的必要处理，不扩大为额外的审计系统、反复复核或工程门禁。
