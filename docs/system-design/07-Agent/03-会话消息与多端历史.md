# 07-Agent / 03 — 会话消息、个人历史与跨端恢复（现行详细 PRD）

> 更新：2026-11-09。**本文为单一现行设计**，直接修订旧规则，不叠加“以最新章节为准”的历史补丁。
>
> 已确认：首次发送受理才创建会话；同商户员工不共享各自的聊天；**同一用户最多同时执行三个不同会话的主 Agent Task**，且**同一会话同时最多一个主 Task**；每次 Task ID 唯一；已发送消息不得编辑；管理员在专门的运行记录界面查看有权限的实际输入、输出和 Tool 步骤；**执行中的会话不能删除**；每会话一份服务器 JSON 文件，PostgreSQL 保存索引、任务状态与搜索投影；设备本地缓存已下载内容；重连保留既有流式浮现；用户删除后不可恢复，服务端 JSON 保留7天后清理；已成立经营事实不随聊天删除。
>
> **需区分**：聊天回复候选的暂存/上下文采纳、服务端保存消息、领域业务草稿与正式数据库事务是不同层次；不能通过点击重新生成直接回滚已提交的库存、销售或采购。

## 1. 产品目标、角色与模块边界

### 1.1 用户目标

从首页进入底栏中间的 AI，可以第一次发送时创建会话、查看个人历史、查询库存/销量、处理业务卡、跨设备接续。客户端断线时服务端已准入的任务继续执行；返回同一设备时已看过的文字立即呈现、未看过的增量按既有流式效果浮现；另一设备自动下载会话。真实业务结果来自领域服务，不来自聊天文件。

### 1.2 业务场景

同一用户在 Android 会话 A 查询库存，在 Web 会话 B 分析销售，在另一会话 C 准备采购草稿，三者各自有独立 Task ID，可并行执行；第四个会话如果暂时无法准入，普通界面只提示“模型繁忙，请稍后重试。”，不暴露内部工作槽的数量。另一用户 STAFF 的会话不因处于相同 Merchant 而共享。用户对“刚才那个商品”指代不明时，必须询问目标商品，不能由模型选择不确定记录进行写入。

### 1.3 模块分工

| 模块 | 本模块依赖的事实 | 03 负责 |
|---|---|---|
| 02 | 聊天消息、固定图表/卡片、文字渐进呈现 | 保存及返回标准 MessagePart |
| 06/07 | Task 执行、停止、真实状态、每用户并发上限 | 会话与 Task ID 关联、可恢复内容 |
| 08/04 | 上下文选择、业务对象解析与澄清 | 提供原指令、部分回答与业务引用 |
| 11 和采购/销售/库存领域 | 草稿状态、正式写入、版本/权限和更正 | 保留消息/业务引用，不自行改数据库 |
| 12 | 增量流、事件重连与游标 | 返回与增量衔接的可靠快照 |
| 14/17 | 附件、管理员 Task 输入输出与用量记录 | 提供会话归属及必要关联索引 |

架构沿用现有 Go + PostgreSQL + Modular Monolith：会话生命周期与隔离约束在 Domain；发送、历史、搜索、删除在 Application；JSON 文件、数据库索引、本地缓存同步合同在 Infrastructure。03 不再造第二套任务执行器或经营服务。

## 2. 核心数据对象和三层存储

### 2.1 领域对象

| 对象 | 职责 | 不得混淆 |
|---|---|---|
| Conversation | 一个创建人、一个 Merchant、长期多轮对话及历史消息 | 不等于一个 Task 或一个模型请求 |
| Message | 一条用户/助手消息，保存发送/生成时刻、顺序及状态 | 已发送用户消息不可就地编辑 |
| MessagePart | 文本、固定图表、表格、业务卡及来源时间/版本 | 不等于实际库存/正式采购记录 |

### 2.2 三种持久化边界

- **服务端单会话标准 JSON 文件**：保存完整消息、规范化图表/业务卡快照、可见 Tool 摘要、原始用户指令、候选回答与版本；聊天历史的内容依据，不是正式业务数据库。
- **PostgreSQL**：保存会话 ID、创建人、商户、标题、文件位置与版本、搜索文字投影、Task 状态/关联、管理员运行输入输出及业务正式数据（在各领域表）；不需要把每个 token 又保存为另一份聊天全文。
- **本机缓存**：已下载会话内容、已见文字位置、未发送的输入框文字和未提交卡片字段；不同设备各自缓存，同账号新设备从服务端自动取得。

不同会话文件可并行读写；**同一个会话 JSON 文件的更新应由会话仓储顺序合并**，使用完整临时文件和原子替换，避免半截 JSON。PostgreSQL 本身依事务处理并发，不能理解成所有用户的业务数据库写入必须全局串行。

## 3. 创建会话、消息不可编辑与生命周期

### 3.1 第一次消息被服务端受理才创建

点“新对话”只显示本机空白会话；首次正式发送时服务端核验 user_id / Merchant 和稳定的 client_request_id，并创建 conversation_id、UserMessage、独立 Task ID、服务器 JSON 文件与数据库索引。若服务端已受理但网络丢失回执，使用同一个 client_request_id 恢复既有 ID；不得重复创建会话/Task。

### 3.2 已发送、已停止与未发送的区别

- **未发送**：输入框、语音转写和卡片上尚未点提交的修改，只存本机；切页面可恢复，但不算 Task，也不写入正式业务。
- **已发送**：用户指令已经成为会话不可编辑的 Message；可复制、引用、另发一条修改指令，不提供直接编辑原消息按钮。
- **执行中断/被用户停止**：已经发出的原指令和实际已产生的安全回复部分仍保存在服务端，下次构建上下文应考虑这些历史，但明确状态未完成，不能伪称业务已经提交。
- **生成的回答**：先保存到服务器 JSON 供恢复，再决定候选版本如何被下一轮上下文采纳；保存/采纳不是业务 commit。

### 4.2 对话与任务关系

Conversation可以有很多已经完成的历史Task，但同一时刻最多执行一个主Task；同一账号可以同时在三个不同会话中运行三个主Task。模型内部多次请求或工具调用不会额外占用用户的三个名额。正式业务工具是否成功执行只由领域Application Service确认，不能根据展示动画判断。

## 5. 用户级三任务并发与上下文归属

> **产品显示约束**：三个主Task是服务端可并行运行的执行工作槽，不限制一个模型请求内发出几个Tool调用，也不对用户提供“3个线程/3个任务额度”的可见计数。用户端只在无法准入时显示统一的“模型繁忙，请稍后重试。”。真实Task身份、步骤及输入输出供授权系统管理员查看。


### 5.1 并发单位：User而非Conversation

**已确认**：同一个user_id最多同时运行三个会话级主Agent Task；一个Conversation同时只能执行一个主Task，每次新执行都创建独立task_id。Task内部可以调用多个Tool、模型或受控子代理，不把它们算成不同的用户主任务。

| 场景 | 产品处理 | 执行责任 |
|---|---|---|
| A/B/C三个会话各有一项运行中Task | 三个任务都可工作、结果独立 | 06/07 |
| 再从D发起第四项 | 用户仅看到“模型繁忙，请稍后重试。”，不透露数值和资源状态 | 06/07准入 |
| 会话A未终结时继续发新的Agent指令 | 用户同样看到“模型繁忙，请稍后重试。”，内部不交错执行两个主Task | 06/07 |
| A完成，B/C仍运行 | 释放一个用户任务名额 | 06/07 |
| Task等待用户确认 | 建议暂停占用执行名额；恢复时重新准入 | 07待细化 |
| 不同会话写同一商品/草稿 | JSON相互独立，正式业务事务按领域规则处理冲突 | 领域服务 |
| Task完成顺序与消息创建顺序不同 | 各自消息按原创建顺序显示，不交叉拼接 | 03/02 |

后台以user_id和真实Task状态控制最多3个可并行运行的主Task执行槽，属于运行线程/工作单元的上限，**不限制 Tool Call 数、Model Call 数或单个 Task 的工具步骤数量**，且不在用户端展示上限、线程数和Task ID。服务端应按真实状态准入，不能靠某设备显示多少按钮。等待确认状态是否释放执行名额由07详细定义，目前建议释放但不将其误判为已经完成。

### 5.2 上下文歧义必须询问用户

用户在不同会话查询矿泉水和绿茶，随后说“帮我采购刚才那个商品”，不能自动跨会话取最近完成的Task，也不能猜测同名SKU。04/08应优先依据当前会话的明确业务对象ID定位；仍有两个合理候选时直接询问用户“你指矿泉水还是绿茶？”，等待明确选择。正式经营写Tool在指代不明确时不得调用。

用户停止某个Task后，已发送指令和安全的部分输出仍存会话历史。08后续组装上下文应可选取这些内容，但必须保留其未完成状态，不得当作已经提交的业务事实。

### 5.3 管理员任务输入输出

每个task_id保存真实执行所属user_id、merchant_id、conversation_id、ToolStep的输入/输出摘要及执行时间。管理员通过独立运行记录页查看获授权内容，不等于员工个人会话在商户内共享。管理员详情权限与保留策略由17细化，03提供正确关联。

## 6. 断网续跑、最新快照与流式浮现

### 6.1 断线只改变连接状态

客户端断网、锁屏、切后台或离开AI页只中断事件接收，已准入的服务端Task继续执行。真正失败、用户显式停止或等待用户业务确认仍可能发生。断网不能把Task标记为failed，也不能为了恢复重新发起原Task。

### 6.2 同设备与跨设备恢复行为

| 场景 | 立即呈现 | 接着处理 |
|---|---|---|
| 同一手机前次看到前200字 | 本机缓存的200字立即显示 | 未见新增文字通过02流式组件逐段呈现 |
| 同一手机有有效图表缓存 | 先原位显示 | 向服务端核对版本，有差异再更新 |
| 另一台设备首次打开 | 自动下载服务器保存的完整历史 | 直接展示旧内容，不用点击加载或从头动画回放 |
| 服务器已经完成 | 立即标记真实Task已完成 | 未读文字仍可渐进出现，允许立即显示全部 |
| 服务器仍在运行 | 显示真实执行状态 | 快照之后继续接收真实事件 |
| 多轮历史Task | 按消息顺序显示 | 不把不同Task的回答混为一条 |

**设备已看到多少字**属于本地DisplayCursor，不是服务端消息保存位置。恢复后的动画是视觉体验，不能伪装模型还在运行。

### 6.3 一致快照和后续事件

03返回完整消息/Part快照以及对应snapshot_cursor，12从该位置之后接收真实新事件；同一part_id/revision的事件不重复应用。增量不可回放时重新获取最新快照，绝不重做已完成Tool或正式业务写入。

### 6.4 连接、Task和业务结果各自独立

| 可见情况 | 正确判断 |
|---|---|
| 最后一段文字出现，Tool仍运行 | Task未完成 |
| 图表已出现，模型继续工作 | 组件已可读，Task仍真实运行 |
| SSE断开，服务器正在执行 | 显示网络重连，不显示模型失败 |
| 真正模型上游失败 | 按Agent 01固定错误文案并保留可靠内容 |
| 写Tool请求结果未知 | 查原请求的执行结果，不重新提交 |
| 需要用户确认 | 保留等待确认，不自动执行业务 |
| 点击立即显示全部 | 只停止本机文字动画 |

### 6.5 历史数据与当前业务数据

历史中昨日库存120瓶保持原时间和数值，今日实际库存可能是80瓶。打开历史不自动查询业务；用户点击刷新或确认旧业务卡时，才依据当前领域真值进行新查询或业务核对。

## 7. 本轮确认 C：历史业务卡必须按当前业务事实重新判定

### 7.1 为什么创建时间必须有，但不能单凭时间做决定

历史卡应当保留 generated_at（卡片生成时间）、数据来自什么 source_refs、对应哪个业务草稿/商品/用户/商户，以及生成时所基于的版本或业务引用。时间允许用户理解“这是此前的建议”，也帮助服务端确定这不是一个新生成动作。

**但时间老不一定不可用，时间新也不一定安全。**

例如 3 小时前生成的采购卡，其供应商、商品、价格和草稿如果仍处于可执行状态，并且现有业务领域允许，就可能继续合法执行；反过来，1 秒前的销售卡也可能因为另一设备已经完成该销售、商品停用或权限撤销而失效。

因此最终允许操作应看**当前业务事实 + 权限 + 版本/状态 + 原本要求的用户确认 + 是否已执行**，而不是设一个未经产品确认的“超过多少分钟就禁止”规则。对于真实 SaleDraft，如果领域采用 revision/CAS，应按其现有规范执行；采购草稿若尚未确认对应状态机和过期策略，03 不得自行规定 24 小时失效。

### 7.2 历史业务卡打开与点击的职责

- **打开历史消息**：03 读取并展示原卡片快照，标明生成时间和可能需要重新确认；不自动修改真实业务记录。
- **用户点击“确认/完成”**：将 action_id、业务引用、用户已确认的参数和服务端动作请求关联信息发往合法业务命令入口。
- **业务服务当前判定**：重新检查 Merchant/用户权限、草稿状态与 revision、商品与单位、当前领域业务事实、已执行结果和必要规则。
- **结果返回**：可以执行则真实提交，并把结果关联到原 MessagePart；已执行就返回原有结果；发生变化则提示用户查看变化，必要时重新确认；拒绝则保留原历史卡但标记“该操作不可继续”。
- **防重复**：历史卡可重复点击、断网后再次点击、两台设备同时点击都不得让同一个正式业务动作重复成立。

### 7.3 从历史卡到真实业务执行的完整时序

### 7.4 业务卡提交前的边界核对表（本轮确认需要此表）

以下表格区分**必须遵循的执行原则**与**由具体业务模块定义的政策细节**。不增加独立审核服务，不对所有查询图表做写前检查；只在真正需要执行经营命令时走正常领域检查。

| 编号 | 边界场景 | 需要读取或判断什么 | 应当如何处理 | 责任归属 |
|---|---|---|---|---|
| B01 | 历史卡创建很久，但业务数据未变化 | generated_at、当前对象状态/版本 | 不仅因为旧就禁止；若其他条件合法可继续 | 03展示，业务服务判定 |
| B02 | 卡片刚生成，但关联草稿已被修改 | expected_revision 与当前 revision | 返回版本冲突和新内容，重新确认后再操作 | 业务草稿领域 |
| B03 | 草稿已完成/已消费 | 正式状态、已存在的业务单据 | 不再新建第二笔，返回已经完成的记录 | 采购/销售领域 |
| B04 | 草稿已取消/业务已关闭 | 当前状态 | 不允许从旧卡直接继续，展示已失效 | 采购/销售领域 |
| B05 | 草稿明确存在过期状态 | 领域实际 expiry 状态和有效时间 | 若业务有正式过期规则则按其处理；无该规则不可擅自过期 | 领域定义，03展示 |
| B06 | 商品已停用或被删除/隐藏 | 当前合法商品状态与引用 | 按领域当前可用性判定，提示用户更新选择 | 商品/库存领域 |
| B07 | 商品名称相同但 ID 已变 | 原商品 ID 与当前选择 | 不悄悄改成同名另一商品，要求重新选择 | 商品领域 |
| B08 | 商品单位/规格/换算变化 | 单位 ID、换算规则和数量 | 若影响数量或金额，要求用户核对并确认 | 商品/采购/销售领域 |
| B09 | 商品价格或成交价规则变化 | 当前商品价、旧草稿价格快照、授权范围 | 不静默覆盖原草稿价；依据相应业务规则比较并提示 | 商品及销售价格规则 |
| B10 | 当前库存改变 | 当前库存与交易所需数量/业务策略 | 重新计算可执行性；库存不足时依据领域规则处理 | 库存/销售领域 |
| B11 | 供应商/客户状态变更 | 相关实体状态和启用规则 | 当前业务服务决定可否关联；无权时不继续 | 采购/销售/往来领域 |
| B12 | USER 或 STAFF 权限被撤销 | 当前 User、Membership、Merchant、权限 | 拒绝未授权写入；不沿用生成卡时的旧权限 | 身份/权限与领域服务 |
| B13 | Merchant 冻结/只读/关闭 | 当前商户状态与可写范围 | 遵循已有 Merchant 状态规则，禁止未授权写入 | 账户身份领域 |
| B14 | 卡片来自其他商户/其他人的私人会话 | 当前会话、Merchant 和业务对象归属 | 禁止跨商户访问；员工会话明确不共享且需核对归属 | 03 + 身份/领域 |
| B15 | 一张卡被同一用户重复点击 | 相同动作请求身份、已有提交结果 | 命中已执行请求时返回原结果，不能重复写 | 业务命令幂等 |
| B16 | 两台设备同时点击同一张卡 | 相同目标动作、版本、状态竞争 | 仅按实际 CAS/事务结果允许一笔成立，其他设备拿到当前结果或冲突 | 业务服务 |
| B17 | 用户点击后客户端立刻掉线 | 该业务请求的真实执行状态 | 重新上线先查请求结果；不能因没有响应就重发成另一笔 | 业务服务 + 03/12 |
| B18 | 服务端请求超时、结果不确定 | 原请求标识和业务执行事实 | 显示处理中/结果待确认，查询原请求；不直接重新执行 | 业务服务 + 07/10 |
| B19 | 原卡数据源已过时 | source_refs、快照时刻及实际当前事实 | 历史卡保持旧内容；点击执行时用当前业务事实判断 | 03 + 业务服务 |
| B20 | 用户改变卡片数量或金额 | 变更字段、单位、当前版本、应授权字段 | 新提交参数走正常字段校验和领域命令，不以旧显示值为准 | 业务服务 |
| B21 | 旧卡关联的业务单已更正或撤销 | 当前正式记录及其更正关系 | 展示实际后续状态，不能凭旧卡再次完成原动作 | 业务领域 |
| B22 | 用户删除了原会话后业务仍已成立 | BusinessRecord ID、原真实结果 | 正式业务事实保留；后续在原业务页面管理，不靠聊天恢复 | 03 + 业务领域 |
| B23 | 业务服务暂不可用 | 当前事实无法可靠取得 | 暂不执行写操作，显示无法确认业务状态；允许稍后再试 | 业务服务/前端 |
| B24 | 旧卡试图重放未经允许的操作 | action_id 是否仍在受控允许集合 | 不执行未知动作或模型输出的自由指令 | Agent 05/11 + 领域 |
| B25 | 历史业务卡是“建议草稿”而非已保存草稿 | 是否存在真实业务 draft_id | 先明确创建/保存路径；不能把模型文本当已持久草稿 | 03/11/业务领域 |
| B26 | 采购单尚未实际入库 | 采购业务状态与入库记录 | 只展示真实采购状态，不能自动声称库存增加 | 采购/库存领域 |
| B27 | 销售单生成但未完成出库 | 销售/出库真实状态 | 不能显示已扣库存或已收款，按真实业务执行阶段展示 | 销售/库存/经营领域 |

**解释**：真正“确认”的是**操作时以当前真实事实与原请求的执行结果为准**。表格中某些政策尚未冻结，例如采购草稿是否到期、库存不足时能否继续某种流程、售价变化后的确认规则，必须沿用原业务模块未决状态，不由 Agent 03 替用户决定。

### 7.5 推荐的最少提交信息

为了正确关联当前业务请求与历史卡，提交参数至少要让服务端识别：

~~~json
{
  "conversation_id": "conv_123",
  "message_id": "msg_456",
  "part_id": "part_789",
  "action_id": "confirm_business_draft",
  "business_ref": {
    "type": "sale_draft",
    "id": "draft_001"
  },
  "expected_revision": 5,
  "request_key": "client_generated_stable_key",
  "input": {
    "quantity": "20",
    "unit": "箱"
  }
}
~~~

**示例说明**：这一结构是逻辑上的输入需求，不是已经冻结的 API 或现有业务字段。身份、Merchant 权限由当前认证上下文获取，不能相信客户端上传的所属商户；request_key 表示本次用户意图的稳定提交身份，网络重试应使用相同值。expected_revision 只在目标业务草稿采用版本控制时生效；与真实 SaleDraft 已有的 CAS 规则保持一致。不让模型自行指定后端正式记录 ID 或“修改成功”状态。

### 7.6 冲突后的 UI 呈现

<text>
原卡片：“采购矿泉水 20 箱，生成于 10:15”。
现在该商品信息或相关业务状态已经发生变化。
</text>

推荐采用以下交互：

1. **保留旧卡的原始内容**，在原位显示“业务信息已变化，需重新确认”，不可直接覆盖旧文字/数值。
2. 展示安全且当前用户有权查看的**变更前/当前**字段对比，例如数量、单位、当前价、草稿状态；不足以自动比较时展示“请查看最新业务信息”。
3. 用户重新选择/编辑并确认后，向业务服务发送合法的新操作；若草稿已终态或权限已经撤销，按钮禁用并说明原因。
4. 真实业务操作成功才显示新单据/库存结果。若后台收到成功结果而客户端未收到，重连后显示该已成功状态，不再显示“请重复提交”。
5. 两个不同业务表单对同一商品的并行操作，应继续依真实业务服务的当前版本及领域规则处理；03 不建立自己的商品库存版本系统。

**这里不需要一套新“卡片审批中心”或永久审计台。** 只是让已有业务写入口在执行前读取自己必需的当前事实，保证历史 UI 不会绕过真实领域约束。

## 8. 历史消息与数据快照、业务现值必须分开

### 8.1 三种时间

| 时间 | 含义 | 是否决定可执行 |
|---|---|---|
| generated_at | 模型生成这张 UI 卡/组件的时刻 | 不独立决定 |
| queried_at / source_at | 真实业务工具查询基础数据的时刻 | 说明快照新旧 |
| submitted_at / committed_at | 用户确认/业务服务真正提交执行的时刻 | 由领域正式结果决定 |

模型生成时间并不保证所有源数据都在同一时刻查询。若工具返回的是不同时间的查询快照，应以具体 data_source 的查询时间解释，不能用生成时刻冒充所有业务数据同时最新。

### 8.2 历史图表的显示与刷新

- 历史库存/销量卡保存模型输出的**规范化结果及当时数据引用、查询范围和时间**；打开时不自动用最新库存改写原有图表。
- 点击“更新到最新”应该触发一个新的受控查询/Agent Task，产生新的消息或清晰的新版本结果；旧结果仍可回看，避免对经营历史造成误导。
- 普通图表切换、排序已加载的数据不需要重新调用模型；涉及最新库存、日期范围或重新计算则发起新查询。
- 图表不能被当作经营记录原始事实的唯一来源，正式当前值始终从业务服务取得。

### 8.3 历史表单与可执行动作的不同生命周期

同一个 MessagePart 的**展示快照**应保持可恢复；但其**动作权限/当前可执行性**应基于每次操作时的实时业务状态。卡片的“原来显示可确认”只说明当时的 UI，不是无限期可使用的执行授权。

~~~mermaid
flowchart TD
    OPEN[打开历史会话] --> SNAP[读取保存的MessagePart]
    SNAP --> SHOW[显示原内容和生成时间]
    SHOW --> CHOOSE{用户只查看还是点击业务动作}
    CHOOSE -->|只查看| END[不执行业务查询或写入]
    CHOOSE -->|确认/修改| NOW[读取当前业务状态和权限]
    NOW --> IDEM{此前相同动作已成功吗}
    IDEM -->|是| RESULT[返回原真实结果]
    IDEM -->|否| VALID{当前合法且用户确认有效吗}
    VALID -->|是| WRITE[通过原领域Service提交]
    VALID -->|否| CHANGED[提示冲突/失效/无权]
    WRITE --> RESULT
~~~

**图示说明**：显示历史与执行历史卡是两件不同的操作。业务卡是否能点、点下去执行什么不能从历史 MessagePart 快照自行决定。

## 9. 运行中禁止删除、删除后不可恢复及七天清理

### 9.1 删除准入的最终规则

**已确认：执行期间不可删除会话。** 只要会话有任何尚未进入真实终态的主Task（含正在执行、已发停止请求但未停止成功、Tool结果未知、waiting_user尚未终结），UI删除入口不可用；服务端删除API也必须核实状态并拒绝，不能仅禁用按钮。用户可以查看Task或显式请求停止，**等服务端确定完成/失败/取消后，才允许删除**。

### 9.2 两类用户界面

| 会话状态 | 页面提示 | 可执行动作 |
|---|---|---|
| 仍有非终态Task | “当前对话有任务正在处理，执行期间无法删除。请等待完成，或先停止任务。” | 查看任务 / 请求停止；**无强制删除** |
| 全部Task均已终结 | “删除后这段对话将立即从历史中移除，无法恢复。服务端7天后清理会话文件；已成立的采购、销售和库存记录不会删除。” | 取消 / 确认删除 |

停止请求不等于已经停止；如果业务写命令已经提交，停止也不能暗中回滚。若真正结果不确定，需等07/业务服务确定任务状态后才允许删除。已停止的用户消息和安全的部分回复仍保留在会话历史中，直到用户正式删除。

### 9.3 删除后的实际数据生命周期

1. 用户确认删除后服务端立即将会话标记为Deleted，禁止列表、搜索、详情、旧卡执行、重新订阅和其他设备访问，不提供恢复按钮或回收站。
2. 会话索引记录deleted_at以及purge_after=deleted_at+7天，JSON文件临时保留于服务端，**这并不构成用户可恢复的保留期**。
3. 到期清理JSON文件及其私人缓存/检索投影和可删索引；正式采购、销售、库存、经营账和独立业务审计记录不随聊天文件删除。
4. 若另一设备恰好打开该会话，收到删除状态后立即关闭该聊天并清理本机关联缓存；服务端再次授权时拒绝旧请求。员工离开商户也必须清理该商户本机会话缓存并隔离服务端访问。
5. 删除和新Task准入必须检查同一会话当前状态，避免“检查空闲后另一设备启动了任务，同时删除”的竞态；不需要额外创建一个业务审批系统。


## 10. 已发送消息、停止后上下文、暂存与重新生成

### 10.1 不允许编辑已发送消息

用户可以复制、引用、继续追问和重新提出一个更正指令；**已经发送并保存的 UserMessage 原文不允许编辑、覆盖或伪造之前的发送时间**。例如用户先说“采购20箱”，后来说“改成10箱”，第二条属于新 UserMessage，必须有新的消息身份；领域草稿则按其原版本规则更新，不能直接改写历史问题让执行事实失去依据。

### 10.2 停止Task后的上下文

用户指令已发出但模型任务被停止，**原用户消息和已经生成的真实部分内容必须保存**。后续08组装上下文时可以把这些内容带给模型，但带有cancelled/partial标记，不能声称任务已完成，不能把当时模型想要调用但未成功的业务Tool当作已执行。上下文组织不要求再运行原任务。

### 10.3 回复暂存与下一轮上下文采纳：**仅服务端内部状态**

**最新确认：普通用户完全不需要感知“暂存/采纳/提交区”的内部机制。** 用户看到的是正常的 Agent 消息、必要的经营信息和最终结果，不出现“回复已暂存”“是否提交暂存区”“草稿已保存”等技术状态；管理员运行详情可以按授权查看执行步骤。

- **可靠保存**：本轮生成的文字、组件及中间可信结果需要立即保存到服务器 JSON，断网或换设备时能够恢复；不能等下一条消息才首次持久化。
- **内部候选**：当前回复可在内部标记为 candidate，重新生成形成独立候选；用户无需看到 candidate/adopted 的状态名字或任何内部提交按钮。
- **下一轮采纳**：下一条正式用户消息被受理时，08依据本轮已经保存的消息、停止状态和回复版本构建上下文，内部选定合法候选并记录采纳关系；不能无视用户纠正要求。
- **经营事实**：内部回复暂存与业务 Service 真实 Draft/正式经营事务是两种不同状态。不能因用户发送任意下一条消息就自动把上一轮采购、销售写入数据库，也不能把已成立经营记录隐藏当作可撤销缓存。
- **必要经营确认依旧可见**：当实际领域操作需要用户核对商品、数量或明确确认时，UI 以自然的“请确认这笔采购/销售”呈现，不展示后台是否创建了什么暂存对象。

这里的 candidate/adopted 仅是 03/08 的内部实现语义，不新增独立的用户功能入口。

### 10.4 重新生成：按是否实际改动业务分类

| 上轮实际执行内容 | 重新生成时应做什么 | 禁止行为 |
|---|---|---|
| 纯文字/只读查询/图表推导 | 允许生成新回答候选或新查询说明，保留Task关联与查询时间 | 不覆盖用户原问题或旧经营事实 |
| 未提交的模型建议 | 可以丢弃或替换候选建议 | 不虚称原建议是正式采购单 |
| 已在真实业务Service保存但未正式提交的草稿 | 根据当前草稿状态/revision修改、取消或重新准备 | 不跳过领域权限与版本检查 |
| 正式销售、采购或库存变更已提交成功 | 提示正式业务已生效；可以重新生成解释或分析 | **不得从聊天JSON快照直接回滚已提交的数据库事务** |
| 已提交请求但结果未知 | 先查询原请求及幂等记录，再决定可做的下一步 | 不能再次提交同一笔业务试探是否成功 |

### 10.5 对“Git暂存区—提交”的合理借鉴

**推荐**：Agent准备业务建议/真正领域Draft（prepare），由用户在对话中确认或新一条明确允许执行的指令触发领域Commit，成功后返回真实业务记录ID。下一条消息如果是“取消”“重新生成”“改成10箱”，不能仅因为“发了下一条”就自动把旧的20箱正式入库；应先识别指令目的。

对于已提交的经营变更，所谓“回退”只能通过**领域实际支持的撤销、更正、冲销等合法操作**实现：先查询当前状态、检查权限、依领域规则执行并保留相反交易事实。不是把旧JSON还原为较早版本就能回滚数据库；销售库存可能已被其他用户或后续单据依赖。

~~~mermaid
flowchart TD
    I[用户发出业务指令] --> P[形成建议或领域Draft]
    P --> R{用户下一步}
    R -->|重新生成| E[更新候选或合法草稿]
    R -->|取消| D[取消可撤销草稿]
    R -->|明确确认/继续办理| C[校验当前业务事实与权限]
    C --> W[正式领域事务提交]
    W --> ID[返回真实单据或库存变更结果]
    ID --> RE{再次请求重新生成?}
    RE -->|是| EX[可重生成解释 不自动撤销记录]
    EX --> COMP[确需撤销则另发合法领域更正命令]
~~~

### 10.6 重新生成前的提示

如果上一轮已经产生正式业务写入，界面提示：“本轮已执行经营操作。重新生成回答不会自动撤销已提交记录；需要撤销或更正请使用相应业务功能。” 对纯文本分析不必额外增加确认。真实记录是否允许撤销、如何修正仍由采购、销售、库存领域PRD确定。

### 10.7 重试与请求身份

客户端发送时使用稳定client_request_id，若回执丢失，查原会话/Task是否已受理。重新生成是明确的新Task，不能在新Task中自动重复旧Task已成功的业务Tool。正式业务写命令需要自己的幂等身份、当前版本及事务规则，不以聊天层的“重新生成”按钮保障业务正确性。

## 11. 个人历史、分类搜索、本机缓存与会话长度

### 11.1 历史列表与新会话

历史只列当前账号在有效 Merchant 权限下自己创建且未删除的 Conversation。手机使用02的历史抽屉/页面，桌面使用折叠侧栏；按今天、昨天和较早时间分组。列表显示会话标题、最近摘要、更新时间、真实Task状态；支持重命名、打开和删除（删除准入依第9节）。点“新对话”只是本机空白页，第一次发送才创建服务器端会话。

### 11.2 标题和消息正文分组的模糊搜索（已确认）

用户已明确：搜索不仅覆盖会话标题，还覆盖消息文本与回复摘要，按**两类结果分区展示**，并支持合理的模糊/相似匹配，不只依靠完全一致的关键词。

| 结果分组 | 匹配对象 | 返回字段与展示 | 点击后 |
|---|---|---|---|
| **第一组：会话标题** | 用户自定义标题或自动生成的标题 | 标题、关键词高亮、最近时间、匹配程度 | 打开对应会话 |
| **第二组：消息文字** | 用户原问题和助手可搜索的文字/回复摘要 | 会话标题、匹配的短文本片段、时间、消息位置 | 打开会话并定位该message_id |
| 无结果 | 当前账号授权范围内均未命中 | “未找到相关会话或消息” | 保留搜索条件供调整 |

PostgreSQL可以保存用于搜索的**文本投影/摘要和索引**，完整消息仍在服务器JSON文件中。中文模糊匹配可结合拆词、字符相似度、标题前缀和必要的索引实现；早期不需要单独引入全文搜索服务。排序建议先标题完整/前缀匹配，再标题模糊匹配，然后按正文相关度和时间列出第二组。检索必须排除其他员工、无权限商户、已删除会话、未发送本机草稿、私密Tool原始参数及敏感凭据。

~~~mermaid
flowchart TD
    Q[输入模糊搜索词] --> S[按当前user_id和Merchant过滤]
    S --> T[标题完整/前缀/相似匹配]
    S --> M[用户及助手文字摘要匹配]
    T --> G1[第一组 标题命中]
    M --> G2[第二组 消息正文命中]
    G1 --> R[展示分组结果]
    G2 --> R
    R --> OPEN[点击恢复会话并定位消息]
~~~

### 11.3 本机缓存和跨设备加载（已确认）

- **同设备**：本机已有授权缓存，打开时先立即显示已加载内容；后台取服务端版本/后续事件并更新，本机未读新增文字按02既有浮现方式展示，不能瞬间整屏铺开。
- **另一设备**：无本机缓存时自动从服务器获取消息和图表，打开就加载，不需另外点按钮；默认直接渲染旧历史，只有实际新回复参与实时流式更新。
- **未发送状态**：输入框文字、语音转写和未提交卡片字段按当前 user_id、merchant_id、conversation_id 本地暂存，不与另一设备同步；一旦正式发出/提交，再以服务器消息或领域Draft为准。
- **会话被删除或用户离开商户**：清除此设备对应会话的缓存及未发送编辑，停止订阅；服务器端必须按当前权限拒绝读取。完全断网设备无法瞬间接收远程撤权，必须利用本机有效身份保护缓存，并在重新联网/切账号时清理。
- **历史图表**：默认显示原查询时间与数据快照，点击刷新产生新受控查询，不覆盖旧内容。

### 11.4 会话过长时建议用户开新对话

限制必须分别考虑：**模型上下文Token**（归08，决定单次请求携带哪些历史）、**累计对话轮数**（决定对话继续使用体验）、**会话JSON大小**（决定读写/加载代价）。不能仅凭文件字节数计算模型能否继续，也不能因为上下文压缩就删除完整历史。

| 维度 | 当前建议的提醒阈值 | 当前建议的限制动作 | 决策状态 |
|---|---|---|---|
| 用户发送轮数 | 达到100轮，提示当前会话较长 | 200轮不再准入新的主Task，建议开启新对话；旧历史可查看 | **推荐数值，尚未最终确认** |
| 规范化JSON体积 | 达到8 MiB先提示和分离大图表引用 | 超过16 MiB时限制新增内容，保留旧数据与必要导出/查看 | **推荐数值，尚未最终确认** |
| 模型上下文占用 | 接近实际可用预算80% | 08先摘要/压缩历史，仍不适用才提示新会话 | **实现建议，非固定产品轮数** |

实际大型附件/明细表应作为安全引用按需读取；不把整个附件数据内嵌进JSON。限制提示可使用“当前对话内容较长，建议新建对话。已有历史仍可查看。” 如果用户希望延续话题，新会话可以经08组织经授权的相关业务对象和简短摘要，不能直接复制旧会话所有消息或借此绕过用户/商户隔离。**200轮/16 MiB是当前推荐，不是ChatGPT官方固定上限，也未获用户最终定数。**

### 11.5 长历史显示与稳定消息身份

历史按有序message_id/sequence返回，客户端可分页或视窗渲染，避免上千条消息同时占满内存。每个结构化Part使用稳定part_id、revision；若服务器更新某张业务卡的已提交状态，用同一Part局部替换视图，不覆盖用户旧的分析结论或旧查询时间。不同Task完成顺序不影响历史消息顺序。

## 12. 用户个人隔离、商户权限与管理员边界

### 12.1 私人会话只属于创建账号

**已确认**：同一Merchant中的OWNER、STAFF不可相互访问私人AI会话。服务端按会话的owner_user_id、merchant_id及当前身份/Membership做授权；不能从普通历史列表、搜索、会话ID、重连cursor、Tool调用或缓存路径访问别人聊天。一个账号在自己有权限的另一设备可以查看自己的历史。

### 12.2 员工离开商户与切换账号

- 用户失去Merchant有效关系后，服务器拒绝读取或继续执行该商户私人会话的操作，不允许旧业务卡保留以前的授权。
- 客户端接收到成员关系变更时删除该商户本地缓存与未发送编辑；退出登录或换账号时，不向新账号暴露前一个人的任何历史缓存。
- 已经正式产生的采购、销售和库存记录属于原商户真实业务事实，用户离开或删除聊天不自动删除经营记录。
- 管理员需要查看任务真实输入输出时，使用**独立的系统运行记录权限**而不是普通员工共享会话；见13.5。

### 12.3 当前权限与旧消息必须分开

| 场景 | 必须处理 |
|---|---|
| STAFF离开Merchant后点击旧历史URL | 拒绝访问，会话正文不向无权主体返回 |
| OWNER试图查询STAFF私聊 | 不因OWNER身份自动开放 |
| 同账号Web和Android同时打开 | 依据服务器同一会话数据，各自本地缓存 |
| 另一个Merchant使用同名商品 | 不能利用旧会话对象引用进行跨商户读写 |
| 登录权限变更时仍有活动Task | 06/07/身份模块决定实际任务状态，写Tool必须按当前权限重查 |
| SYSTEM_ADMIN查询某Task运行详情 | 依平台授权获取必要脱敏输入输出；不允许任意员工访问 |
| 旧卡已显示可确认，但用户现已无写权限 | 执行时拒绝，不允许借历史状态绕过权限 |

## 13. JSON 文件、PostgreSQL 索引、管理记录与接口契约

### 13.1 一段会话一份服务器JSON文件（已确认）

此选择参考部分Coding Agent的文件式历史，但以项目现有架构为准：**每Conversation一份标准JSON文件**，服务器保存完整用户消息、Agent回复、标准化图表表格、业务卡引用、可见步骤摘要、来源及版本。它不是移动端本机JSON，也不是将所有消息正文再复制到PostgreSQL JSONB。

推荐内部结构（实际文件位置不得作为公共链接）：

~~~text
conversation-store/
  <merchant-id>/
    <owner-user-id>/
      <conversation-id>/
        conversation.json
~~~

### 13.2 PostgreSQL保存会话索引与真实运行状态

| 逻辑记录/表 | 必要字段与用途 | 权威内容 |
|---|---|---|
| agent_conversations | conversation_id、owner_user_id、merchant_id、标题、最后更新时间、文件位置/版本、删除时间/清理时间 | 会话归属、检索与可见性 |
| agent_tasks | 全局唯一task_id、user_id、conversation_id、状态、开始/完成时间、重试关联 | 06/07的真实任务状态及用户并发上限 |
| agent_run_records / steps | 运行输入输出、模型/Tool步骤、耗时、脱敏参数和结果、错误、必要用量 | 管理员Task运行详情，归17 |
| agent_message_search | 会话ID、消息ID、可搜索文本摘要、相关度索引 | 标题/正文模糊搜索的轻量投影 |
| 领域业务表 | 商品、库存流水、采购、销售、往来、必要业务幂等/更正记录 | **唯一正式经营事实** |

这里是逻辑分工，表名和索引实现可按已有PostgreSQL/Repository约定调整；不建立专门的“聊天数据库微服务”。

~~~mermaid
flowchart LR

    APP --> JSON[(按Conversation存储JSON文件)]
    APP --> PG[(PostgreSQL索引与Task)]
    APP --> SEARCH[个人历史搜索]
    SEARCH --> PG
~~~

### 13.3 JSON安全写入与数据库索引一致性

即使同一会话一次只有一个主Task，也可能有Task流式写入、设备读取、业务卡结果更新和清理动作竞争：**同一Conversation的文件更新必须串行合并**。推荐在现有Go仓储中使用文件修订号file_revision，保存完整临时JSON后原子替换正式文件，避免进程重启留下半截文件；高频文字片段小批量合并，完整组件、状态及关键结果及时保存。

**跨介质边界**：服务器JSON存内容、PostgreSQL存索引与真实Task。两者不是一个天然ACID事务；如果JSON写完后索引更新失败，下次读取/启动时应按有效文件版本和Task状态修复索引，不能反过来让索引覆盖较新的完整正文，也不能据此重新执行已成功的业务Tool。不同会话可以并行更新文件，不应人为把整个PostgreSQL数据库改为串行写。

| 展示结果 | 已生成的可见回复、指标/图表/业务卡摘要与来源 | 与已保存MessagePart对应 |
| 正式业务动作 | 真实单据ID、操作类型、成功/失败与关联领域结果 | 与原领域业务状态一致 |
| 重新生成/重试 | 原Task ID和新Task ID、回复候选版本、是否已有业务写入 | 不把重新生成当作业务已撤销 |

管理员运行记录应由系统已有权限体系控制，既不开放员工之间共享私聊，也不依赖于可被用户7天后清理的唯一会话JSON副本。具体运行记录保留和导出归17与平台管理模块，不在03额外创造不必要的审核流程。

### 13.6 API与接口语义（概念层）

| 操作 | 主要请求 | 结果 |
|---|---|---|
| send_message | 文本、稳定client_request_id、可选conversation_id、档位 | 内部返回新会话/消息/唯一task_id，或资源不可用状态；用户只显示“模型繁忙，请稍后重试。” |
| list_conversations | 当前认证、分页、关键词 | 本人有权访问的标题、摘要、时间和任务状态 |
| search_history | 关键词、分页 | 标题分组 + 消息正文分组，支持模糊匹配 |
| get_conversation | 会话ID、客户端已有版本 | 有序消息/Part快照、真实Task状态与一致cursor |
| subscribe_updates | 会话ID与cursor | 12负责后续增量及重连语义 |
| regenerate_response | 原消息/回复候选引用和新请求标识 | 新task_id或明确经营写入风险提示 |
| stop_task | task_id | 请求停止及真实任务状态 |
| execute_card_action | 合法action/业务引用、预期版本、幂等身份与字段 | 正式业务结果/冲突/拒绝 |

上述是应用语义，不要求创建十个独立服务或固定这些英文名作为最终HTTP路径。

## 14. 状态图、关键分支与异常反馈

### 14.1 连接状态与真实Task状态不可混用

~~~mermaid
stateDiagram-v2
    state "客户端连接" as Conn {
        [*] --> Connected
        Connected --> Disconnected: 断网/离开页面
        Disconnected --> Reconnecting: 网络恢复
        Reconnecting --> Connected: 读取快照并继续订阅
        Reconnecting --> Disconnected: 网络仍不可用
    }
    state "主Task状态" as TaskState {
        [*] --> Running: 服务端准入
        Running --> WaitingUser: 等待确认
        WaitingUser --> Running: 合法确认与重新准入
        Running --> Completed: 完成
        Running --> Failed: 真实失败
        Running --> Cancelled: 有效停止
        WaitingUser --> Cancelled: 取消
    }
~~~

说明：进入Disconnected不驱动Task失败；Task未终结时会话不能删除。WaitingUser是否占用户的三个活动执行槽是07需要明确的实现规则，不能让UI猜测。

### 14.2 历史业务卡的展示与动作状态

~~~mermaid
stateDiagram-v2
    [*] --> Historical: 恢复原卡片快照
    Historical --> Checking: 用户点击受控确认
    Checking --> AlreadyDone: 相同业务动作已经成功
    Checking --> Available: 当前状态和权限合法
    Checking --> Conflict: 当前版本或业务条件变化
    Checking --> Rejected: 已结束/失效/无权
    Available --> Submitted: 按领域Service提交
    Submitted --> Done: 真实成功
    Submitted --> Unknown: 请求结果未知
    Unknown --> Done: 查明原请求成功
    Unknown --> Rejected: 查明没有执行且当前已失效
    Conflict --> Checking: 用户核对并重新确认
~~~

**显示旧卡不查新库存；执行旧卡时必须查当前真实数据。** 原草稿已提交则返回已有业务结果，不另新建销售/采购；被删除会话的卡片不再提供访问和操作入口。

## 15. 详细业务用例：跨天采购、重新生成和删除

### 15.1 案例：旧采购建议与当前商品数据

11月4日，用户查询矿泉水近30天销量，Agent生成“建议采购20箱”卡片。如果仅有模型建议，它仍不是正式采购单；如果实际保存了领域Draft，需有真实draft_id与对应revision。11月5日用户在另一设备打开：从服务器下载旧消息，保留当时查询时间，不自动把旧数值改成今天的库存。用户点确认时，业务Service重新检查当前供应商/商品单位/价格/状态及权限，已完成的草稿返回已有记录，发生版本冲突则明确显示差异。整个执行以领域真实结果为准。

| 步骤 | 用户界面 | 03和12 | 业务领域 |
|---|---|---|---|
| 11月4日生成建议 | 显示“建议采购20箱”与查询时间 | 保存JSON展示快照和来源 | 仅建议不等于已建草稿 |
| 用户离开页面 | UI失去连接 | 保存最新消息、真实Task仍运行 | 无须因掉线重做Tool |
| 11月5日另设备打开 | 自动下载显示原卡片 | 核对用户/商户权限后读取JSON | 不自动改写订单 |
| 用户点击确认 | 显示处理中 | 记录动作关联 | 查询当前状态、版本、库存、单价与授权 |
| 数据无冲突、允许执行 | 显示真实结果 | 关联正式业务ID | 领域事务正式提交 |
| 数据已变化或被其他设备完成 | 显示变化或原成功记录 | 不再新建同一动作 | 领域幂等/CAS决定 |
| 任务终结后用户删除聊天 | 删除后不可见 | 七天后清理JSON | 已成立业务仍在 |

### 15.2 案例：重新生成涉及正式业务写入

~~~mermaid
sequenceDiagram
    actor U as 用户
    participant UI as Agent聊天
    participant A as 03消息与上下文
    participant D as 11领域草稿
    participant B as 采购销售Application
    U->>UI: 帮我办理采购
    UI->>A: 保存不允许编辑的用户指令
    A->>D: 准备建议或领域Draft
    D-->>UI: 预览卡片
    U->>UI: 重新生成建议
    UI->>A: 创建新Task及新候选
    A->>D: 可修改未提交草稿
    D-->>UI: 新的候选/草稿版本
    U->>UI: 正式确认办理
    UI->>B: 当前版本和幂等身份
    B-->>UI: 正式业务记录ID
    U->>UI: 再次点重新生成
~~~

**提醒**：如果用户明确要求“回退刚才这笔正式出库”，只有原领域实际支持的合法更正/冲销/撤销命令才可能改变经营事实，且须在当前权限/状态下执行；03不提供把数据库恢复成模型旧回答时刻的泛用回滚。

### 15.3 案例：断线、停止与上下文

用户发出“分析上季度销售”，Task产生部分分析后用户点停止。03保存原指令及已生成的合法部分，Task状态标记已停止；用户下一条说“继续，但只看矿泉水”，08可以利用之前的指令和部分结果，但必须知道前轮未完成，必要时重新查询实际销量，不允许把半截模型分析当作已经完成的权威统计。新Task获得不同task_id，与旧Task明确关联，不在会话 JSON 里篡改已发送原消息。
