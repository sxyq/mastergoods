# 07-Agent / 04 — 意图理解、业务对象解析与 UI 展示意图

> **2026-11-01 首轮详细设计草稿。** 本文与 02《智能交互与实时数据展示》以及 05《工具目录发现与调用契约》衔接。业务意图和展示意图要同时考虑，但**不建立独立的二级模型、多个专门分类 Agent 或新的模型路由服务**。本模块尚未覆盖所有未来实体语义细节；商品、采购、出库、库存领域尚未确认的规则保持原状态。

## 1. 为什么在意图理解中讨论 UI

同一句“最近 30 天矿泉水卖得怎么样”，实际至少有两类决定：

1. **业务意图：** 应查询销量及可能的库存、时间、商品信息；找准 Merchant 范围和真实业务对象。
2. **展示意图：** 是否适合显示统计卡、趋势折线、商品排行、明细表或计算说明；需要几种视图及用户能做什么操作。

但**展示意图不能代替真实数据**：模型看见业务 Tool Result 后，才确定最终图表数据并调用 02 的 present_ui。请求初始阶段只是“偏好/候选”，不是强制直接绘图。

## 2. 业务意图与展示意图关系

~~~mermaid

    M --> B{业务意图}

    B --> A[统计分析]
    B --> W[草稿或实际业务修改]
    B --> N[页面导航或业务详情]

    Q --> T[必要业务Tool]
    A --> T
    W --> T
    T --> R[真实Tool Result]
    R --> S[模型组织最终回答和展示意图]
    S --> X{需要结构化UI吗}
    X -->|需要| P[present_ui]
    X -->|不需要| TEXT[正常文字回复]
~~~

**图示说明：** 不需要先让一个 LLM 做分类，再让第二个 LLM 做意图识别，再让第三个生成图表。用当前 Agent Loop 的模型理解当前任务，在必要的业务 Tool 完成后决定最终展示；多个 Tool/多轮模型调用由 06 处理。

## 3. 业务意图分类：面向真实进销存

| business_intent | 典型输入 | 目标 | 是否需要业务 Tool |
|---|---|---|---|
| general_question | “你能帮我什么” | 简短解释和示例 | 不一定 |
| product_lookup | “找矿泉水/这个条码的商品” | 解析商品或候选项 | 有真实商品事实时需要 |
| stock_query | “矿泉水还剩多少瓶” | 查询当前库存 | 需要 |
| stock_movement_query | “这周为什么少了那么多货” | 查询出入库记录 | 需要 |
| sales_query | “昨天卖给谁了” | 查询销售/出库单据 | 需要 |
| sales_analysis | “近30天什么卖得最好” | 聚合销售数据 | 需要 |
| procurement_query | “最近有哪些采购” | 查询采购单与入库记录 | 需要 |
| create_draft | “帮我准备采购草稿” | 解析商品、数量、单据必要字段 | 需要 |
| business_mutation | “修改这个商品默认售价” | 由领域权限决定合法写操作 | 需要 |
| business_navigation | “打开刚才那张销售单” | 定位有效业务对象/页面 | 可直接后端引用 |
| follow_up | “只看饮料”“第二个呢” | 利用当前会话及相关对象引用继续 | 视前一个任务而定 |
| explanation | “为什么库存变少了” | 解释真实查询结果 | 通常需要 |
| file_export | “给我导出 Excel” | 生成实际文件结果 | 交给 14/业务模块 |

这张表是**意图类别草案**，可允许一条用户请求组合多个类别，不因分类命名而冻结新的销售/采购业务规则。

## 4. 展示意图分类：决定给模型提示什么视图

| presentation_intent | 推荐视图 | 对应场景 | 数据前提 |
|---|---|---|---|
| plain_text | TextBlock | 普通问答、简单解释 | 无结构化数据也可 |
| single_metric | metric / metric_grid | 库存件数、单据数量 | 有明确单位与事实 |
| record_list | data_table / compact_table | 商品、销售、采购记录 | 真实行和对象引用 |
| ranking | ranking / bar / horizontal_bar | 商品销量排行 | 同口径可比较值 |
| time_series | line / area | 按日期的销量趋势 | 连续且有序时间轴 |
| composition | pie / donut / stacked_bar | 分类占比、结构组成 | 非负、统一总量 |
| comparison | comparison / grouped_bar | 同比/环比/两组比较 | 比较双方口径一致 |
| distribution | scatter | 价格与销量分布 | 明确 x/y 单位 |
| cross_dimension | heatmap | 按周、日期、品类的二维统计 | 行列数值矩阵 |
| movement_explanation | waterfall | 期初库存 + 入出变动 = 期末 | 真实库存变动事实 |
| process_stages | funnel | 有真实业务状态的流程统计 | 有序且真实存在的阶段 |
| progress | progress_gauge | 既有目标与完成率 | 目标/分母确实存在 |
| derived_calculation | calculation | 日均销量、库存估算天数 | 原始输入与衍生公式 |
| data_view_switch | chart_table_toggle | 需要同时看图与明细 | 两视图共用相同数据引用 |
| object_detail | record | 商品、客户、采购单详情 | 真实业务对象引用 |
| missing_fields | form / action | 商品歧义、草稿补充数量 | 已授权且有合法字段 |
| file_result | file | 已生成的业务文件 | 真实文件引用 |
| no_visualization | 不调用 present_ui | 一句回答或纯文本 | 不为了好看强制画图 |

**与模块 02 的全量范围一致：** 所有此前列出的图形/数据视图均纳入本轮完整设计，不再当成必须等到后续期才能使用；没有合适数据时可以只显示文字/表格，不杜撰统计图。

## 5. 关键业务对象解析

| 对象类型 | 最少可用引用 | 常见歧义 | 处理方式 |
|---|---|---|---|
| 商品 | Product ID；SKU/条码用于候选查询 | 同名、不同规格/单位 | 显示候选 Select/RecordCard |
| 库存 | 商品 ID 与当前合法仓库/经营范围 | 是现存还是可用库存 | 由已确定库存领域字段决定，不能随意猜 |
| 客户 | Customer ID | “老王”多个同名 | 候选列表，等待用户选定 |
| 供应商 | Supplier ID | 名称相似、历史不同主体 | 候选列表 |
| 销售/出库 | Sale/Outbound Record ID | 昨天多笔单据 | 日期/客户/商品/真实 ID |
| 采购 | Purchase Record ID | 同类多笔进货 | 状态、日期、供应商和真实 ID |
| 时间范围 | 起止日期 + 所属时区/口径 | “上个月”“最近30天” | 后端统一解释，不把不同区间混为一谈 |
| 数量/单价 | 数字 + 单位/币种 + 业务字段 | 箱/瓶、默认价/本次成交价 | 依业务领域事实，无法确认则询问 |

解析出的对象和条件随着任务传递，不要求客户端重新识别意图。若用户点了一张真实商品卡，优先携带后端已授权的 Product ID，而不是在新消息中只传“这个”。

## 6. 模型推理结果、Tool 事实与业务写入事实的边界

模型允许：
- 选择表/图/卡、排序、分组、归纳、做衍生计算与预测；
- 输出解释性文字和合法的 present_ui 展示参数；
- 依据真实的 Tool Result 分析销量趋势和补货建议。

模型不得：
- 把库存 Tool 返回的 120 瓶擅自声称成当前真实库存 100 瓶；
- 在真实业务 Tool 没成功时向用户报“出库成功/入库成功”；
- 仅凭自然语言按“已经买过”推断现实中采购/收款已完成；
- 输出未经授权的商户外数据或修改任意数据库字段。

衍生指标如 360 瓶 / 30 天 = 12 瓶/天可以显示为 derived；按当前库存 120 瓶估算 10 天可以显示 estimate。二者不是正式库存值，也不自动写入商品/采购记录。

## 7. 建议给模型的精简提示

~~~text
理解用户的经营目标，并关联当前会话中已经确定的商品、客户、采购或销售对象。
若需要真实经营数据，选择已有合法业务 Tool。不得编造商品、库存和正式业务执行结果。
对 Tool Result 可以统计、分组、排序、衍生计算和解释；保留原始事实的单位与来源。
业务目标确定后，同时选择适合的展示意图。需要图表、表格、指标、业务卡或计算说明时，
按本 Task 可用的组件目录调用 present_ui，选择支持的 view_type 和正确的数据形状。
纯文字问题不强制生成图表；模糊商品要先询问或展示候选；业务写入必须经过领域 Tool。
不暴露私有内部推理、真实模型、凭据、跨商户数据和原始日志秘密。
~~~

这是**Prompt 引导**；真正能选哪些业务 Tool、哪些固定组件及参数形状由受控的工具目录与 Schema 提供，不能只依赖提示词。

## 8. 意图与展示输出的概念结构

~~~json
{
  "business_intents": ["sales_analysis", "stock_query"],
  "entities": [
    {"kind": "product", "ref": "product_123"},
    {"kind": "time_range", "value": "recent_30_days"}
  ],
  "presentation_hints": ["metric_grid", "line", "data_table", "calculation"],
  "requires_business_tool": true,
  "needs_user_clarification": false
}
~~~

**重要：** 以上是 Agent 内部逻辑的**示例**，不是要求先增加一个必须持久化的分类数据表，也不代表模型在业务 Tool 之前就有最终图表数据。Tool 返回后模型可以改变展示选择，只要真实数据和合法 Schema 支持。

## 9. 用例与时序

~~~mermaid
sequenceDiagram
    actor 用户
    participant Agent as Go Agent
    participant Tool as 业务Tool
    participant UI as present_ui
    participant Client as 四端固定组件
    用户->>Agent: 哪些饮料卖得好 按近30天统计
    Agent->>Agent: 理解销售分析意图 时间和商品范围
    Agent->>Tool: 查询合法销售数据
    Tool-->>Agent: 实际统计/记录
    Agent->>Agent: 选择排行与可视化并推导摘要
    Agent->>UI: 提交模型生成的结构化数据与图表类型
    UI-->>Client: 渲染排名图和表格
    Agent-->>Client: 文字解释与可继续提问的入口
~~~
