# 07-Agent / 05 — 工具目录发现与调用契约：经营 Tool 与展示 Tool

> **2026-11-01 专题第一版：与 02 Intelligent UI、04 意图理解直接相关的工具契约。** 其他 Tool 安全性、执行循环、业务写入与恢复细节留给本模块的后续领域专题和 06/07/10；本轮不引入 MCP/Skills/多子 Agent，也不为 UI 建立新服务。

## 1. 一个 Registry，明确区分工具作用

| tool kind | 例子 | 作用 | 能否修改经营数据 |
|---|---|---|---|
| business_read | query_product、query_stock、query_sales | 调用现有业务服务查询数据 | 否 |
| business_write | create_purchase_draft、update_product_price 等已有授权能力 | 通过 Application Service 执行真正业务操作 | 可能；依领域权限 |
| presentation | **present_ui** | 模型将文字之外的数据组织成固定 UI 组件 | **绝不能** |
| task_context | 必要的已有上下文读写能力 | 为 Agent 完成当前任务提供上下文 | 不得绕过经营业务授权 |

**关键产品决定：** 只注册一个模型可见的 presentation 工具 present_ui，内含多个可选择的固定图表/表格/指标/对象模板。不是给 21 个图形种类注册 21 个真正业务 Tool；也不让模型通过任意 UI JavaScript 执行后台业务。

### 调用结构

~~~mermaid
flowchart TD
    MODEL[Agent Model] --> C{工具名}
    C -->|真实经营工具| R[Tool Registry 业务调用分支]
    R --> APP[已有 Application Service]
    APP --> RESULT[Tool Result]
    RESULT --> MODEL
    C -->|present_ui| V[展示 Tool 解析器]
    V --> UI[02 Fixed UI Message Parts]
    UI --> CLIENT[Web Android iOS 小程序]
~~~

同一个 Task 可以先查询多个业务工具，再把结果提供给模型，最后由模型调用 present_ui 填入预置图表数据；若只需要文字则无需调用 present_ui。

## 2. present_ui 的必要契约

| 字段 | 含义 | 限制 |
|---|---|---|
| parts[].type | metric、chart、table、ranking、calculation、record、form、action 等 | 固定 enum |
| parts[].view_type | 02 第 24 节定义的图表/数据视图 | 只能使用已注册枚举 |
| parts[].title | 组件标题 | 有限长度、可读 |
| parts[].source_refs | 相关 Tool Result ID 引用 | 只能引用本次合法结果 |
| parts[].origin | fact / derived / estimate / mutation_result | 依类型约束真假值 |
| parts[].unit | 真实单位与币种 | 显示口径清晰 |
| parts[].data | 固定类型的数据行、series、轴、指标等 | 符合具体 view_type 的结构 |
| parts[].actions | 经后端许可的动作 ID | 不能提交自由 JS、SQL、URL 脚本 |
| parts[].revision | 同一展示块新版本 | 必要时原位更新、保留视图状态 |

Go 后端依据 type/view_type 解析成固定的 typed struct（或等价明确字段结构），不接受任意 HTML、DIL、JS。OpenAI Function Calling 的 strict 模式须正确提供 required 和 additionalProperties 等字段；各 Provider 的协议适配由 Agent 01 处理，不强行把所有协议当 OpenAI Responses。

## 3. 工具执行与 UI 展示的顺序

~~~mermaid
sequenceDiagram
    actor 用户
    participant UI as 聊天页
    participant AGENT as Agent Runtime
    participant READ as 真实业务Tool
    participant MODEL as 模型
    participant VIS as present_ui
    用户->>AGENT: 查近30天销量并画图
    AGENT->>MODEL: 用户问题和可用工具
    MODEL-->>AGENT: 请求真实销售查询Tool
    AGENT-->>UI: trace.step.start
    AGENT->>READ: 查询销售统计
    READ-->>AGENT: Tool Result
    AGENT-->>UI: trace.step.done
    AGENT->>MODEL: 真实Tool Result和必要上下文
    MODEL-->>AGENT: 组织结果 调用present_ui
    AGENT->>VIS: 结构化图表参数
    VIS-->>AGENT: UI Part或明确格式错误
~~~

实际模型响应中工具调用与文字先后顺序可因模型原生协议而异，上图仅说明必要因果：**业务事实先取得，模型才有依据生成最终图表；工具日志来自真实 Runtime，图表内容来自模型 present_ui 参数。**

## 4. present_ui 与 Business Tool 的成功含义不同

- present_ui 只表示**UI 数据格式可接受并已创建消息展示块**，**不等于**库存修改或采购单写入成功。
- 真实写操作只有业务 Application Service 回报成功，才能生成 mutation_result 类的已成功记录卡。
- 模型允许衍生计算、排序、分类和解释，但 fact 的库存、单据状态和金额事实必须对应真实 Tool Result。
- 展示失败不清空已经发给用户的可靠文字；对图表显示局部不可展示提示。不可在展示工具错误时重做已成功业务写 Tool。
- UI 展示 Tool 的原始调用细节对普通用户可折叠为“整理数据视图”；实际业务 Tool 逐步运行日志可按 02 要求点击展开，不暴露凭据和私有推理。

## 5. 模型工具描述与 UI 展示分类

无需为每个图表注册单独 Tool。Prompt 和工具 description 提供简洁说明：

~~~text
present_ui 负责将已经查询或计算出的经营数据呈现成固定的图表、数据表、指标卡或交互组件。
可选图形包括 metric、table、ranking、bar、horizontal_bar、line、pie、donut、grouped_bar、
stacked_bar、area、scatter、heatmap、waterfall、funnel、progress_gauge、comparison、
calculation，以及 metric_grid、compact_table、chart_table_toggle 等组合视图。
必须填写真实数据单位、源引用、视图专用字段；不能改写真实库存和业务成功状态；
无需可视化时直接回复文字。
~~~

与 04 双向衔接：用户的 business_intent 选择真实经营业务工具，presentation_intent 帮助模型选择一项或多项固定视图；模型可以在收到业务 Tool Result 后调整展示选择，不预先生成空图表。

## 6. 前端固定渲染器不是一个 Tool Runtime

前端只认识 UI Message Parts，不需要理解业务 Tool 的原生参数。Go 转出 component.upsert 等消息事件，Web/Android/iOS/小程序实例化自己已有的固定组件。图表与表格的本地切换不回调 Model；涉及新的统计范围或业务写入才调用真实后端任务或受控动作。

本文件现阶段只设计与 UI 直接相关的 Tool 目录契约，不表示 05 其他工具发现和跨模块业务用例已经全部讨论完成。具体 UI 组件列表与全局底部导航详见 02，意图分类详见 04。
