# 1. 定位、范围和需求溯源

## 1.1 用户任务

用户希望通过卖货操作：选商品 → 输入数量和单位 → 查看默认售价 → 必要时修改成交价 → 得到可理解、可复核的明细金额与整单金额 → 再关联客户、填写收款并完成销售。

现行正式需求已明确 OWNER 卖货可修改数量和成交价；STAFF 可卖货，但“修改成交价”应可独立授权。正式需求没有冻结数量精度、单位换算、优惠、金额舍入算法等细则。本子模块不得把未确认项伪装为已冻结。

需求上游：
- docs/rewrite/产品角色与一级用例需求.md：卖货属于商户经营记录而非支付清算；
- docs/rewrite/二级功能用例需求.md：OWNER 卖货流程、STAFF 销售与独立改价权限；
- 02-01：Sales Draft 商品行、入口、新增和更新、跨 Merchant 校验、状态/版本/幂等；
- docs/system-design/待确认事项.md：P-18 权限码应由业务用例最终推导，不提前拍定编码。

## 1.2 本文件负责

1. 有效的销售数量、销售单位与单位换算对“金额”和后续“库存数量”的影响；
2. 默认售价、成交价、人工改价和权限；
3. 商品行身份、重复选择/扫码、合并与拆行边界；
4. 行金额与整单金额计算，舍入和异常输入；
5. 草稿更新、价目变更、并发编辑、重新计算与价格快照；
6. 向 03/04/05 输出一致的金额与标准库存数量候选事实。

## 1.3 本文件不越界决定

- 商品档案本身支持的单位体系、销售单位集合与参考价维护生命周期：模块 04；
- 客户必填、赊销条件、欠款何时产生：02-03；
- 实收、超额收款、找零、收款账户和结算：02-04；
- 负库存、出库提交库存账与最终库存精度：02-05 / 模块 04；
- Sale / Outbound 正式聚合结构与完成事务：02-10；
- 销售退货、退款、原单改错：02-08 或之后独立专题；
- Schema、API 字段、具体权限码、UI 技术实现：后续阶段。

# 2. 已继承且不得重新发散的不变量

1. 销售创建 / 编辑阶段与显式完成阶段分离；Draft 只描述经营意图，不形成正式库存、收款或欠款事实。
2. OWNER 在同 Merchant ACTIVE 且身份 / Membership 可用时可发起销售；STAFF 需要销售权限，额外敏感能力另验。
3. Merchant FROZEN 为 READ_ONLY，CLOSED 禁止经营写入；从页面进入时通过校验不意味着后续写入免检。
4. Agent 通过同一 Application Service 和同一权限 / 业务判定入口执行；不得绕过人工应遵守的规则。
5. 商品必须属于当前 Merchant，新增商品行前重新验证可销售；最终完成时仍须验证商品有效性。
6. 不允许没有业务差异、系统无法解释的重复商品行；技术重试与真实多次扫码须区分。
7. Draft 写入采用 expected_revision + status CAS；幂等命中先于普通版本冲突判定。
8. 只有服务端已提交 revision 才代表修改成功；发生并发冲突不能静默覆盖。
9. Cancel / Complete / Edit 竞态只能有一个合法落地状态；终态不得继续修改。
10. 真正 Complete Sale 前不得出现部分正式经营事实；一次完成涉及明细金额、欠款 / 收款和库存的整体一致性。
11. 销售选品接口不能因销售权限暴露采购参考价、成本、利润等非必要敏感字段。
12. 经营金额禁止用二进制浮点数做事实计算；使用 Decimal 或定点精确表示（继承已有全局设计约束）。

# 3. Actor、权限与数据暴露

| Actor / 场景 | 行为 | 业务判断 |
|---|---|---|
| OWNER | 选择单位、数量，录入成交价并查看本次金额 | 在同 Merchant ACTIVE 与可用会话下允许；金额风险仍有统一规则 |
| STAFF：有卖货权限 | 选商品、输入数量、查看适用默认售价 | 允许，但查看不应暴露采购成本、利润 |
| STAFF：无改价权限 | 自行输入 / 导入不同于系统认可参考成交价的单价 | 拒绝“人工改价”；不允许通过 Agent、换客户端或直接调用命令绕过 |
| STAFF：有额外改价权限 | 手工修改成交价 | 通过能力授权、数值有效性与风险 Policy；具体权限码到 09 |
| SYSTEM_ADMIN | 普通经营界面替代 OWNER/STAFF 卖货 | 不作为日常销售操作者；纠错走受控专用命令和完整审计 |
| Agent | 建议、编辑数量 / 单价 | 在关联用户身份下同权校验；高风险确认交由 09/07 决定 |

“STAFF 是否拥有卖货权限”不能推导出“STAFF 可修改成交价”。字段未显式改变，也需防止客户端通过伪造 price_source 绕过改价授权。

# 4. 领域概念与事实来源

## 4.1 SaleLineDraft 的概念字段（非 Schema）

| 概念 | 含义 | 约束 / 来源 |
|---|---|---|
| line_id | 草稿商品行标识 | 02-01 负责身份与增删 |
| product_id | 已存在且同 Merchant 的商品 | 02-01 Product 校验 |
| selected_sale_unit | 用户选择的销售单位 | 必须在当前可售单位策略中可识别 |
| quantity_decimal | 按销售单位输入的数量 | 正确解析、合法性与精度校验 |
| unit_conversion_snapshot | 选定时的销售单位→库存基础单位换算候选 | 有多单位时保存来源 / 版本，完成前复核 |
| default_unit_price_snapshot | 当前选定单位对应的默认销售单价快照 | Product 的有效价目 / 策略提供；不得依赖客户端自报 |
| agreed_unit_price | 当前拟成交单价 | 可能由默认价带入，也可能经授权人为修改 |
| price_origin | 参考价/手工修改/其他批准的定价原因 | 用于权限、来源与 Audit，不可由无权客户端随意声明 |
| amount_exact | quantity × agreed_unit_price 的精确中间值 | 不能用 JS Number / float 做事实 |
| line_amount | 经确认的金额规则归一化后的该行金额 | 货币精度 / 舍入策略暂待 S-12 |
| price_context / line_identity | 可解释不合并的业务差异 | 如单位、不同成交单价、合法的其他定价上下文 |
| draft_revision | SaleDraft 级别的 CAS 版本 | 多端、Agent 所有改动共享 |

字段名是业务概念名称，具体表结构 / DTO / API 等冻结后再定。商品名称、单位标签、价目来源版本可用于显示快照和追溯，必须保留交易时用户看到的关键依据，但字段组成尚待实现设计。

## 4.2 不同量纲不得混用

- Sale quantity：用户按销售单位录入的正数，如 2 箱。
- Stock base quantity：换算为库存基础单位的数量，如 2 箱 × 12 件/箱 = 24 件。
- Unit sale price：按**所选销售单位**计价，如每箱 120.00 元，而不是每件 120.00 元。
- Line amount：按销售单位数量乘所选单位成交单价计算，如 2 箱 × 120.00 元/箱 = 240.00 元。
- 同商品多单位时金额不得混用不同单位对应的单价；库存统一映射到基础量纲，但库存不足判定属于 05。

### 数值示例（说明量纲，不代表冻结多单位产品能力）

~~~text
Product：饮料，库存基础单位 = 瓶
销售单位：箱，转换系数 = 12 瓶/箱
数量 = 2 箱
单位成交价 = 30.00 元/箱
库存标准数量候选 = 2 × 12 = 24 瓶
行金额 = 2 × 30.00 = 60.00 元
~~~

# 5. 数量与单位 Policy

## 5.1 数量正负与空值

**设计基线（建议确认 S-06）**：
- 正常销售行数量必须严格大于 0；0 / 负数不能作为完整可成交销售行。
- 正常退货、撤销和冲销不能靠负销售数量伪装，应由对应业务处理。
- 新选商品时可先带入默认数量 1，但未实际确认的输入框空值可以是“未完成编辑”，不能被当成 0 正式提交。
- 删除商品请使用 RemoveLine，而非提交 quantity=0 偷渡删除。
- 若发生超限、数量缺失、格式无效、精度非法，则草稿可继续保留其它已提交行，但该命令不得产生半条新行或覆盖上次有效数量。

## 5.2 数量精度

不可一刀切要求每种商品 3 位小数或所有商品只能整数：
- 计件：通常要求整数；
- 重量 / 散装：可允许有限小数；
- 多销售单位：销售单位的数量小数位与映射后的库存基础数量精度**分别**校验；
- 超出单位支持精度的输入**拒绝**，不能静默四舍五入数量后成交；
- 具体 unit.quantity_scale、stock.quantity_scale、单行上限及商品是否允许拆分为小数须由模块 04 及产品共同确认（S-06/S-07）。

正数、格式校验和单位精度校验发生在 Domain 层；客户端输入校验只是即时提示。

## 5.3 多单位与换算

**条件性方案，等待 S-07**：
1. v1 若只支持每个 Product 一个销售单位，则 quantity 仍可有商品 / 单位精度差异，未启用的换算界面不得假装支持箱 / 件。
2. 若允许多销售单位，Product 需定义有方向、确定、正值、可追溯的“销售单位→基础库存单位”转换关系；不可由客户端临时填任意换算率。
3. 只有已配置且当前可销售的单位可选；不识别、已停用、跨 Merchant 的单位定义不能用于新行。
4. Qty × factor 应使用精确十进制或有理数表示，最终库存精度能否容纳该结果须在提交前拒绝或由明确转换策略处理，不静默截断。
5. 换算配置改变后，已有 Draft 不静默重写历史输入；重新编辑或完成时判断配置版本是否还适用，必要时要求用户明确刷新 / 重选单位。
6. 不允许“只改销售单位但保持数字和单价不变”造成用户未察觉的数量 / 金额突变。切单位应作为显式复核操作，重新确定数量、单价和库存等效量。

# 6. 价格来源与改价边界

## 6.1 默认单价

**设计基线（待确认 S-08）**：
- 默认销售价来自本 Merchant 商品当前有效的销售价格信息 / Price Policy，由服务端获取；不能相信客户端请求中随带的“商品售价”。
- 选定销售单位后，必须确认价格的量纲也是此单位。例如每箱价与每件价不等价。
- 有默认价时，AddProduct 可以使用服务端识别的默认单价生成候选行。
- 无默认价、缺失对应单位价目，是否允许手动输入、是否要求拥有改价能力，是产品选择；在确认前不自动以 0 作为合法价。
- Product 参考销售价后来发生变化，不自动覆盖用户正在编辑的 Draft 成交价。Draft 当前价格与来源应可见；再次显式“采用最新默认价”需要权限 / 价格变动校验，完成时的价格快照与新价偏差如何处理仍在 S-08。

这样可避免用户录到一半后台改价，最终金额在无提示情况下变化。

## 6.2 人工成交价和权限

**建议独立改价能力（待确认 S-09，继承 STAFF 可独立授权的上游要求）**：
- OWNER 可按业务需要调整成交价；STAFF 改价需要独立授权。
- 若 STAFF 原先按系统参考价录入，而 Product 默认价随后被调整，不自动认为其草稿变成“未经授权改价”，但完成环节是否要求复核最新价由 S-08 决定。
- “改价”检测以服务端记录的 price_origin、原单价、最新合法参考值和本次命令意图判定，不允许只比客户端前后字符串。
- 如果 STAFF 原有改价能力后来被撤销，已经保存的 Draft 不得被无痕覆盖；下一次改价命令必须拒绝。最终 Complete 是否允许带着已保存的人工价完成，也必须由 09 的风险策略显式判定，不能默认允许。
- 人工改价要记录操作者、前后值、原因（如产品要求）和动作来源；无须把每次光标输入都写成业务 Audit。

## 6.3 零价、负价与优惠

- **负单价：建议一律拒绝**，不把折让 / 退货 / 赔付藏在负售价中（S-11）。
- **零价销售：待产品确认**。赠送、样品、搭售可能有真实需求，不能擅自以“0 就是无效”否决一切，也不能默认普通 STAFF 都可做。
- **折扣 / 整单优惠：待产品确认 S-11**。v1 推荐先以“逐行最终成交单价”为清晰核心，不隐式生成整单折扣字段；若真实业务必须按比例或整单减免，另行定义分摊、税费（若有）、舍入和授权，不能临时代入公式。
- 负数量、负单价、负行金额不作为“反向销售”方案；撤销 / 退回 / 纠错进入独立流程。

# 7. 商品行识别、合并与拆行

02-01 已冻结“没有业务差异的完全重复商品行不得无解释出现”，但没有冻结“同商品只能一行”。

**建议 S-10**：

- 业务相同：同 Product + 同销售单位 + 同被认可的成交单价 / 定价上下文，且操作者选择了合并意图 → 可增加该行数量并重新计算。
- 业务不同：同 Product 但销售单位、成交价或其他定价上下文明显不同 → 保留独立行，不能强制合并；例如同一商品 2 件原价、1 件特别价。
- 技术请求重试：相同 Idempotency Key + 相同 fingerprint 必须返回原结果，不是“再加一次数量”。
- 客户实际连续扫码两次：两个不同的用户动作，即使商品相同也不能被幂等机制吞掉；依业务合并规则累加数量一次。
- 同单位同价格但用户明确要求保留两组明细的理由与允许条件尚未定义；不得以隐藏的客户端行序号制造无业务区别的重复行。
- 当价目、单位或优惠条件被人工修改后，必须复查 LineIdentityKey；不能将两行不同成交价折叠成一行再丢失原本的成交价或数量。
- 一次 UpdateLine 必须原子校验、合并 / 拆分、总额重算和 revision+1；失败保持旧版。

# 8. 金额计算与舍入

## 8.1 输入类型

- 不使用 float / double / JavaScript Number 承载权威金额计算。
- Decimal（定点或任意精度）从规范十进制字符串 / 可信精确存储值解析。
- 拒绝 NaN、Infinity、科学计数法、空白字符串、负号隐藏、非十进制字形、非法千位分隔、货币符号夹杂、精度与量级超限；UI 可友好做本地格式化，但服务端只接受无歧义的规范数值。
- 货币单位和 scale 必须一致。当前如以人民币记账为 v1 方案，可建议货币最小记账精度 0.01 元，但**本轮不擅自冻结全系统货币类型、币种与舍入模式**（S-12）。
- 高精度 unit_price 允许多少位，与最终可记账 line_amount 保留多少位是两个问题，不能混为一个配置。

## 8.2 计算公式（不含尚未定义的折扣、税或额外费用）

~~~text
Q_i          = 第 i 行按销售单位计量的 Decimal 数量
P_i          = 第 i 行该销售单位的 Decimal 成交单价
E_i          = Q_i × P_i                         // 高精度中间值
A_i          = MoneyRound(E_i, money_scale, rounding_mode)
SaleTotal    = Sum(A_i), i = 1..n
BaseQty_i    = Q_i × exact_unit_conversion_i       // 库存标准数量候选
~~~

**建议基线 S-12**：一行先以统一金额策略舍入为可记账的行金额，再求和为整单商品金额。不允许“显示每行两位，实际合计却先累加各行未舍入值再舍入”导致肉眼看不到的差额。

- 所有行金额与 SaleTotal 的单位一致；
- 空 Draft 不能 Complete；
- 某行数量 / 单价 / 单位未通过校验则不能 Complete；
- 修改某行金额必须推导出新的 SaleTotal，不允许用户随意写入一个与行金额不匹配的合计；
- 如后续引入订单级优惠、税费、运费或调整项目，必须扩展为可追溯的金额构成公式，不直接篡改上述商品行求和事实；
- 最终完整应收基线交由 02-03/04 确认，不能把“商品合计”直接等同已冻结的“最终欠款”。

## 8.3 有条件的金额示例

以下只演示 **假设人民币 2 位小数 + ROUND_HALF_UP + 逐行舍入** 的效果；规则本身仍是 S-12 待确认：

| 数量 Q | 单价 P | 精确乘积 E | 行金额 A |
|---:|---:|---:|---:|
| 2 | 12.50 | 25.00 | 25.00 |
| 0.333 | 2.00 | 0.66600 | 0.67 |
| 1 | 1.005 | 1.005 | 1.01 |
| 3 | 0.335 | 1.005 | 1.01 |

同单据的行金额 0.67 与 1.01 合计须是 1.68，而非对未舍入乘积 0.666 + 1.005 = 1.671 再重新舍入的 1.67。若最终选择其他舍入策略，应将整套文档、算法与测试联动更换。

## 8.4 零金额与极端情况

- 正常 quantity > 0 不保证 line_amount > 0（例如极低单价舍入到 0.00）。
- 允许为 0 的行金额 / 总额、单价的小数精度、最小非零金额和免费销售权，应统一由 S-11/S-12 决定，不能只在 UI 强制。
- 使用精确算术仍需防止乘法和合计的资源耗尽：数值位数、最大行数量、请求体和计算复杂度须技术约束（S-13），不可静默截断。
- 大数输入和正值校验须在做乘法前拒绝，避免 DoS / 溢出。
- 显示层千分位格式化不得再参加权威金额计算。

### 10.1 页面上存在未提交编辑

客户端键入中的 1.25 不等于服务端已保存的 1.25。网络断开、提交失败或 revision 冲突时，页面必须明确标注未保存状态；刷新后以服务端 committed Draft 为准，不能用本地未提交内容覆盖服务器状态。客户端可以暂存输入帮助恢复，但不改变权威性。

### 10.2 当前单价变更

用户编辑中 Product 默认售价从 10.00 改为 12.00：
- 已存 Draft 成交价 10.00 暂保持原事实，不静默跳 12.00；
- 新增该商品行时取服务端当时有效默认价；
- 选择“更新为最新参考价”是显式业务动作；
- 完成是否允许沿用旧价、是否作为改价纳入额外授权，待 S-08/S-09 确认；
- 业务上同商品不同成交价可保留分行，受 S-10 决策。

# 11. 状态与事务边界

本子模块不增加 Draft 生命周期状态。沿用 02-01：
- ACTIVE：可在权限与 revision 均合法时更新明细数量、单位和成交价。
- CANCELLED / CONSUMED：拒绝任何 Draft 金额改动。
- 任何单行编辑成功都使 Draft revision +1；保存行与整单派生总额在同一逻辑事务中生效。
- 查询预览不会写 Draft、不会增加 revision。
- Complete 与 UpdateQuantity/ChangePrice 的竞态采用 status + revision CAS；只有获胜者能提交。若 Complete 先成功，晚到修改不得重写正式销售；若修改先成功，旧 expected_revision 的 Complete 必须拒绝并重新确认金额。

~~~mermaid
stateDiagram-v2
    [*] --> ACTIVE: 创建 Draft
    ACTIVE --> ACTIVE: 合法修改数量/单位/成交价，revision+1
    ACTIVE --> CANCELLED: Cancel
    ACTIVE --> CONSUMED: Complete成功
    CANCELLED --> [*]
    CONSUMED --> [*]
~~~

**图示说明**：循环修改只发生在 ACTIVE；失败不改变 revision；终态不可恢复为 ACTIVE。S-05 如果将来引入 EXPIRED，必须先统一升级 02-01 状态机，此处不擅自加状态。

在同一 PostgreSQL 下，以本地事务 / Unit of Work 原子完成 Draft 修改、派生合计及幂等成功结果；若 Activity 与主事实要保持原子，则同事务写入必要记录或 Outbox。最终正式销售提交属于 10，不在此处自行定义跨模块 Saga。

# 12. 定价/数量判断伪代码

~~~text
UpdateSaleLine(ctx, draft_id, line_id, input, expected_revision, idempotency_key):
  prior = Idempotency.Find(scope(ctx, command), idempotency_key)
  if prior.exists:
    if prior.fingerprint != Fingerprint(input + target + expected_revision):
      return IDEMPOTENCY_KEY_REUSED
    return prior.first_committed_result

  AssertAuthenticatedAndWritable(ctx)           // User, Membership, Merchant
  AssertSaleCapability(ctx)
  draft = LoadDraftWithMerchantScope(draft_id, ctx.merchant)
  Require(draft.status == ACTIVE)
  Require(draft.revision == expected_revision)

  line = draft.RequireLine(line_id)
  product = ProductPolicy.RequireCurrentSaleable(line.product_id, ctx.merchant)
  saleUnit = UnitPolicy.Resolve(product, input.sale_unit)
  quantity = Decimal.ParseStrict(input.quantity)
  Require(quantity > 0)
  Require(UnitPolicy.QuantityFits(quantity, saleUnit))
  baseQuantity = UnitPolicy.ConvertExactly(quantity, saleUnit)
  Require(UnitPolicy.BasePrecisionFits(baseQuantity, product))

  price = ResolvePriceFromTrustedSourceOrManualInput(input, product, saleUnit)
  Require(PricePolicy.Valid(price))
  if PricePolicy.IsManualChange(input, line, product):
    Require(Authorization.CanChangeSalePrice(ctx))
    RiskPolicy.CheckPriceChange(ctx, line, price)

  revisedLines = LinePolicy.EditMergeOrSplit(draft.lines, line, quantity, saleUnit, price)
  foreach item in revisedLines:
    item.amount = MoneyPolicy.Round(item.quantity * item.unit_price)
  newTotal = MoneyPolicy.SumPostedLineAmounts(revisedLines)
  Require(MoneyPolicy.TotalValid(newTotal))

  // 02-03 / 04 以后定义此标记的具体客户、收款重新校验行为。
  revisedDraft = draft.WithLinesAndTotal(revisedLines, newTotal)
  revisedDraft.MarkSettlementInputsForRevalidationIfNeeded()

  CommitAtomic(
    CAS(expected_revision, ACTIVE),
    revisedDraft,
    Idempotency.StoreSuccess(result),
    RequiredActivityOrOutbox
  )
  return result(newTotal, lineAmounts, draft.revision + 1)
~~~

**算法约束**：
- ResolvePrice 不可信任客户端传来的 origin/status；所有价格引用必须有服务端可核验凭据。
- 失败码来自最先成立的安全与业务规则；最终前置安全校验顺序应由 09/10 统一校准。
- 自动行合并只能在 S-10 已确认时执行；未确认阶段由 LinePolicy 标注待决策，不能当成开发默认行为。
- 以上是领域伪代码，不是最终 API、事务 SQL 或权限码。

# 13. Audit、Risk、安全与性能

## 13.1 Audit / Activity

- 记录 Draft 的 creator、最后修改人、动作来源（人工 / Agent）、revision、编辑时间。
- 成交价变化至少在重要业务活动中可追溯：原价、新价、价目依据、Actor、来源及必要原因；敏感或违规尝试记录必要安全事件。
- 数量改变属于常见业务编辑，默认不要求每次输入字符创建全量不可变审计记录；是否保留逐次商品行修改轨迹由 09 与保留策略确定。
- 完成正式交易后应保存足以还原当时数量、单位、换算、成交价、金额的快照；之后默认价变动不允许改写历史销售金额。
- SYSTEM_ADMIN 特殊纠错使用专用记录 Before/After 和原因，不得无痕改价。

## 13.2 风险与越权

- 未授权 STAFF 发送更低单价，即使客户端隐藏改价按钮也必须由服务端拒绝。
- 明显异常折价、零价、量纲切换、巨大数量和极端单价可触发风险策略；阈值 / 二次确认 / OWNER 审批不能在本子模块擅自设为固定产品语义（S-09/S-11/S-13）。
- 禁止 Agent 编造单价、默认价来源和单位换算，Tool 输入仍需服务端重新验证。
- 价格、数量更新请求必须带 Draft revision 与 Idempotency Key；源于相同 key 的不同 payload 必须拒绝。
- 查询返回经营所需价格 / 数量 / 合计，不额外透出商品成本、参考进价、利润。

## 13.3 性能、索引与读模型

- Draft + 行应支持按 draft_id / merchant_id 定位；按 product_id 和 line identity 找到业务相同行。这里只是索引需求，不指定 SQL DDL。
- 避免按每次输入键击逐一读库或审计；关键保存动作落在业务事务内，客户端可做本地预览。
- 对行数、数量精度、数值位数及复杂单位换算设置可观测技术资源保护，不将经验值（比如 100 行）写成未经确认的业务上限。
- 服务端每次修改可采用只重新计算受影响行，再精确更新整单派生值；提交前保证整体一致与并发隔离，不得因增量缓存过期造成总价漂移。
- 报表 / 历史系统不得因 Product 当前售价或单位配置改变而重算已有完成单据金额。

# 14. 失败语义与用户提示

| 场景 | 语义错误（建议名称） | 用户处理 |
|---|---|---|

# 16. 已冻结、设计基线、待确认严格分层

## 16.1 已冻结 / 继承冻结（无需重新讨论）

- 系统是经营记账而非收单/支付清算。
- 三系统角色、Merchant 归属、STAFF 授权、FROZEN READ_ONLY。
- SaleDraft 创建阶段与正式业务事实完成阶段分离。
- 商品行同 Merchant、商品状态重验、失效行不静默改写。
- 防无解释重复行、CAS、Idempotency、幂等优先、最终完成原子性。
- 不用二进制浮点数做权威金额事实。
- 不能无痕篡改历史完成销售；Agent 不可绕过业务服务。

## 16.2 第一轮推荐基线（暂不等于产品已确认）

- 正常销售数量必须严格正数；小数精度由单位能力定义。
- 选品默认 Q=1；不以 Q=0 代表删除。
- 若支持多单位则在金额与库存两个量纲精确转换。
- 默认价取服务端，Draft 不因 Product 改价而静默变价。
- STAFF 手工改价独立能力授权。
- 同商品不同成交单价 / 销售单位保持可辨行；完全相同且业务明确合并才累加。
- 负价不可作退货；零价与优惠需要显式产品策略。
- Decimal 运算，建议逐行舍入再求和；具体货币舍入仍待确认。
- 更改金额会使此前客户/收款输入进入待复核，不静默产生或调整资金/欠款。

## 16.3 新增待确认项（S-06～S-13）

| 编号 | 必须由产品确认的语义 | 本轮建议 |
|---|---|---|
| S-06 | 销售数量有效范围、默认数量、各单位 quantity_scale | Q>0，选品默认 1；精度按单位，计件可限制整数 |
| S-07 | v1 是否多销售单位、销售单位与库存单位换算及精度 | 有配置才支持；转换正值、精确、可追溯；禁止客户端自填 |
| S-08 | 默认售价来源、无报价时怎么办、Draft 价格快照、价目变更后能否按旧价完成 | 服务端参考价；不静默覆盖 Draft；完成时要求明示复核策略 |
| S-09 | STAFF 改价权限、权限撤销后的存量人工价、风险阈值 / 审批 | 独立授权；无权不能新增改价；完成前高风险再校验 |
| S-10 | 相同 Product 多次选择时如何合并 / 拆行 | 单位 + 成交价 + 定价上下文有差异即分行，重复业务可显式合并 |
| S-11 | 零价赠送、负价、折扣 / 整单优惠、对零金额授权 | 负价拒绝；零价与优惠必须先明确需求；v1 不暗藏整单优惠 |
| S-12 | 货币类型、单价精度、金额 scale、舍入模式、舍入层级 | 建议 Decimal，示例为 RMB 2 位、HALF_UP、逐行舍入求和 |
| S-13 | 商品行 / 单笔数量 / 数值长度的业务上限与技术安全阈值 | 先做技术保护；确有业务上限再由产品明确 |

**S-06～S-13 均未获得用户最终确认。** 可以据此继续 03～05 的详细需求设计，但在最终 Schema / API / Coding 前必须决策并把选择同步到本文件、待确认事项、顶层模块和交接文档。
