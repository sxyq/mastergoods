# 02 — 出库 / 销售模块

> 状态：**模块 02 第二轮需求定位校准进行中（2026-10-11）**；既有 01/02 仅为局部设计，模块整体不可冻结
> 当前进度：02-01 两轮边界审查、02-02 第一轮详细设计已完成；**当前优先任务是模块 02 的第二轮仓库进销存业务边界校准，02-03 暂不视为立即开工项**；S-01～S-13 及新设 W-01～W-07 待产品/业务复核

> 设计体系：9 个业务子模块 + 1 个最终收口子模块

## 1. 模块定位

本系统面向**单仓经营场景的进销存管理与经营记账**，围绕一个仓库/经营场所的商品、采购、销售、库存、往来和资金记录组织业务；不按电商 / POS 的“订单—支付—退款”模型设计，也不在没有实际需求时引入多仓价目或连锁定价。单仓是业务场景，不是提前确定永久数据库结构。

**2026-10-11 用户再次明确：系统以仓库进销存业务为核心，不对外提供支付接口，不接微信/支付宝/银行卡支付网关，也不处理真实付款回调。** 本模块首先关注真实货物出入库、数量与库存账，再视实际经营事实记录销售金额、客户往来与已发生的收款。**不得设计为“先支付成功才能出库”。**

本模块原先围绕一次“销售出库 / 卖货记录”的完整生命周期展开：

~~~text
确认这次是销售出库（普通领用/报损/其他出库是否分型待 W-01）
→ 选择商品 / 数量 / 单位 / 关联商品售价
→ 形成销售出库业务记录（草稿阶段不生效）
→ 用户确认业务发生，按库存策略扣减仓库库存并形成可追溯流水
→ 保存销售金额及必要客户信息
→ 如本次确有已发生收款/未收事实，再由人工记账与客户往来规则记录
→ 查询销售出库、库存变化、历史经营账目

无在线支付入口、无支付二维码/支付接口/支付回调、无真实退款接口；不能以支付状态驱动库存状态。
~~~

当前不把“客户退货 / 退款”作为标准销售子模块。若后续确认真实业务确有该场景，再单独判断应建模为入库、原出库冲销，还是独立退回业务。

## 4. 模块边界

- **01 账户与身份**：提供当前用户、Merchant、角色与权限上下文。
- **04 商品与库存**：拥有商品与通用库存生命周期；本模块只定义一次销售出库造成的库存变化。
- **05 往来与资金**：拥有外部往来对象、通用往来余额、记账账户和后续收付款；本模块只记录本次销售关联的客户及**现实中已发生的收款**、未收款等经营事实，不调用支付接口；正式客户往来余额与记账账户由 05 统一管理。
- **06 经营分析**：消费出库 / 销售记录形成统计与分析。
- **07 Agent**：通过同一业务服务查询、生成草稿与确认执行，不复制出库规则。
- **08 平台管理与数据迁移**：SYSTEM_ADMIN 通过受控业务服务纠错和审计，Legacy 数据按迁移规则进入新模型。

## 5. 01 子模块当前形成的跨模块不变量

从 01《创建出库与商品明细》继承以下设计基线：

1. 销售创建阶段与正式完成阶段分离；
2. 草稿阶段不产生正式库存、收款、欠款经营副作用；
3. OWNER 可以在本 Merchant 正常经营状态下创建销售；
4. STAFF 必须具备销售业务授权；
5. Merchant FROZEN / CLOSED 禁止销售写入；
6. Agent 必须复用正常销售 Application Service；
7. 商品必须属于同一 Merchant；
8. 当前禁止销售的商品不能新加入 Draft，完成时还需再次校验；
9. 不允许出现没有业务差异、系统无法解释的完全重复商品行；
10. Draft 使用 revision 乐观并发控制；
11. 销售写命令需要幂等；
12. Complete Sale 成功前不允许出现“部分正式业务事实已生效”的半完成销售。

其中 1～12 可继续作为后续子模块的设计约束。

第二轮边界审查又补充以下一致性不变量：

13. 打开卖货入口只查询可恢复 Draft，不自动创建持久化空 Draft；
14. 恢复 Draft 时重新校验当前 User / Membership / Merchant / Permission；
15. 搜索 / 扫码多匹配时必须由用户明确选择，禁止默认取第一条；
16. AddProduct 写入前重新校验 Product 当前状态，客户端搜索结果不是写入授权；
17. Draft 中失效商品行不得静默删除、替换或改写 product_id；
18. 幂等命中判定必须先于正常 revision 冲突判定；
19. Cancel / Complete / Edit 通过 status + revision CAS 防止终态竞争；
20. 只有服务端已提交 revision 才表示草稿修改已经保存；
21. 销售商品选择器不得因为卖货权限泄露参考进价、成本、利润等非必要敏感字段。

## 6. 01 子模块待确认项

当前共有五个产品确认项：

- **S-01 服务端可恢复 SaleDraft**：建议服务端持久化 ACTIVE Draft，以支持闪退恢复、多客户端和 Agent；
- **S-02 临时商品**：建议 v1 不支持自由文本临时商品，未建档商品先创建 Product；
- **S-03 草稿可见 / 编辑范围**：建议 STAFF 默认只自动恢复自己的 Draft；OWNER / 特殊权限是否可接管他人 Draft 在 07 / 09 确认；
- **S-04 多 ACTIVE Draft**：建议允许同一用户存在多条 ACTIVE Draft，由入口显式选择恢复哪一条，避免人工 / Agent / 多客户业务互相覆盖；
- **S-05 ACTIVE Draft 过期**：建议 v1 不自动过期 ACTIVE Draft；若未来需要过期，先引入显式 EXPIRED 生命周期再做后台清理。

未确认前：

- 可以继续做 02～10 的业务设计；
- 不进入最终 Schema / API / Coding；
- Coding Agent 不得自行选择相反语义。

## 7. 跨子模块事务原则

模块 02 最终必须保证：

> 一笔销售只有在全部正式业务事实能够一致提交时才算完成。

后续 02～05 需要逐步明确最终事务参与者，包括：

- 正式销售记录；
- 正式商品明细；
- 金额事实；
- 客户应收 / 欠款（如有）；
- 当次收款记账（如有）；
- 库存出库流水。

如果这些事实都位于同一 PostgreSQL，优先使用本地事务 / Unit of Work，不为了形式引入分布式 Saga。

外部通知、异步统计等事务后副作用使用 Outbox。

## 7.1 02 数量、单位、价格与金额的第一轮设计基线（2026-10-09）

详细定义见：docs/system-design/02-出库与销售/02-数量单位价格与金额计算.md。

以下是现行设计约束以及**待确认的建议基线**，不能混作已冻结产品决定：

- 数量与售价按所选销售单位计量，库存基础数量通过可追溯换算关系得到；若 v1 不支持多单位，则不得假设存在箱/件换算。
- 正常销售建议 quantity > 0，不用负数量表达退货；单位精度和多单位能力待 S-06/S-07 确认。
- **已确认**：商品默认售价由本 Merchant 的 OWNER 或获商品售价维护授权的 STAFF 设置；STAFF 修改后 OWNER 可查看最新价与修改轨迹。服务端只负责可信保存/读取商户设置的商品价格，不是自动定价主体。Product 价目变化不应静默覆盖旧 Draft；无默认价与旧 Draft 完成时复核仍属 S-08 未决部分。
- **须区分** STAFF 修改商品默认售价（Product 资料维护，店长可见）与 STAFF 在某笔 SaleDraft 临时修改成交价（本单授权与风险由 09/S-09 收口），二者不能互相冒充。
- 同商品的单位 / 成交单价 / 定价上下文不同，不应失去行级区分；合法合并细节待 S-10 确认。
- 负价建议禁止；零价、折扣、整单优惠的真实产品需求待 S-11 确认。
- 金额事实采用 Decimal/定点，不用 float；建议逐行按统一货币规则舍入后求和，币种、scale、rounding mode 待 S-12 确认。
- 行数、数量、数字长度与风险阈值需明确区分技术安全限额和产品业务限额（S-13）。
- Draft 每次有效修改须以 expected_revision + status CAS 原子保存行与合计；变更金额不直接创建正式欠款 / 收款 / 库存账，也不得静默重写已经填写的收款金额。
- 03 客户关联与欠款、04 当次收款、05 出库与库存，需要消费同一有效 Draft revision 与其一致金额/库存候选值；正式事务在 10 统一闭环。

新增 S-06～S-13 均属**待产品确认**；不阻塞后续 03～05 需求设计，但不允许开发阶段擅自拍定计算规则。

## 9. 用户更正后的商品售价与单仓业务定位（2026-10-11）

- 顶层场景：一个仓库/经营场所的进货—存货—卖货—往来—记账。与传统复杂 WMS、连锁仓多价目、电商支付模型区分。
- 商品默认售价：**由店长设置，店员也可以在商户商品维护授权范围内设置**；必须能够让店长在商品视图查看店员调整后的最新售价和修改历史。
- “STAFF 能设置 Product 默认售价”已经确定；“STAFF 对一笔销售做任意临时成交价修改”的单独能力规则仍在 S-09 继续细化，不得把前者错误限制成后者。
- PRODUCT_PRICE_CHANGE：商品当前价格与变更事实可靠一致，Product 版本/CAS；SALE_LINE_PRICE_CHANGE：按 SaleDraft revision/CAS，不能更新 Product 主档。
- 默认价读取的事实来源：本商户人员设置且服务端已提交的 Product 当前价；用户在销售中引用时保留快照。店员改 Product 价后 OWNER 可查最新价与历史，不追溯篡改已完成销售或旧草稿。
- 未确认：STAFF 商品维护能力默认开关、是否向 OWNER 主动推送、缺失默认价时是否开放本单临时报价；已确认的是 OWNER 可见，不是必须审批或必须推送。
- 现有 Roadmap 不变：02-01、02-02 已做第一轮/边界审查，下一项仍是 **02-03 客户关联与欠款**；随后 02-04 当次收款、02-05 库存出库，再完成 02-06～02-10。
- 跨业务后续设计：模块 04 继续详细定义 Product 创建、默认价/单位/库存生命周期；模块 03 负责采购入库；模块 05 负责客户/供应商与往来资金；不把 Product 价格维护的归属重新搬回销售模块。

# 10. 2026-10-11 第二轮整体需求校准：仓库进销存优先、非支付化

> **状态：范围审查已启动，关键业务语义未收口，不得称模块 02 整体已完成第二轮详细设计。** 用户明确指出此前的流程叙述和需求理解存在偏差。02-01 既有技术/安全边界审查与 02-02 数量金额第一轮设计保留，但它们不能替代“实际仓库如何卖货、何时出库、何时记账”的业务确认。

## 10.1 已明确、不得再误读的产品定位

1. 主产品是**围绕一个仓库实际经营的进销存系统**，核心账目是商品、入库、出库、库存数量和业务历史。
2. 系统**不对外提供真实支付接口**，也不是收银 POS。禁止在产品业务架构中假设微信支付/支付宝/银行卡 SDK、统一下单、支付二维码、支付回调、支付订单号、清算、自动退款、支付成功事件。
3. 已有一级/二级功能用例明确需要“收款/付款的业务记账”“记账账户”和“客户/供应商欠款”。此类**手工录入现实中已发生的交易事实**不代表系统触碰外部资金：记账账户是经营账本维度，不是可发起真实银行转账的接口。
4. 销售出库的关键事实是**真实商品从库存中减少并留下可追溯销售记录**。不能写成“支付成功 → 出库”；能否在本单不填实收时就完成销售，以及欠款和客户条件，需通过 W-03/W-04 的业务决策而非支付状态机决定。
5. “仓库出库”未必等于“卖货”。报损、领用、赠送、退货、调拨是否存在以及属于何种单据类型，**用户尚未明确**；不能将所有库存减少强行做成销售、自动计入收入或客户欠款。
6. 不得因为产品是单仓场景而创造多仓调拨/仓储物流/配送/收银支付的完整工作流；真实仓库内部的盘点、损耗、手工调整由商品与库存模块承接，销售只负责销售出库的合法业务事件。

## 10.2 两条相互关联但独立的事实轴

~~~mermaid
flowchart TD
    A[仓库发生一笔销售] --> B[选择商品与出库数量]
    B --> C[记录本次销售金额]
    C --> D[用户确认销售出库]
    D --> E[正式销售记录 + 库存出库流水]
    E --> F[库存余额变动]
    C --> G{现实中是否有要记录的收款/欠款事实?}
    G -->|有| H[人工录入已收/未收及必要客户关联]
    G -->|无或暂未录入| I[按待确认规则处理未知/零收款]
    H --> J[经营记账与客户往来]
    I --> J
    D -.不等待.-> P[外部支付网关]
~~~

**图示说明**：业务主轴为库存销售出库；金额是销售记录的必要核算维度，**实收是否必填及何时录入尚待决定**。如选择在完成销售时同时登记已发生收款/欠款，则这些正式本地经营事实应按最终事务策略一致提交；不是去调用任何外部网关。图中的外部网关节点仅用于标示业务**排除项**，没有实际调用关系。

## 10.3 关键概念纠偏

| 旧式误读（禁止） | 进销存应表达的业务事实 |
|---|---|
| 商品卖货 → 收银 → 等支付成功 → 出库 | 记录销售出库事实，按业务确认与库存规则落账；不依赖支付服务 |
| 支付订单 / 三方交易号 | 本系统自己生成的销售出库单据编号/业务标识 |
| 付款失败 / 退款失败（网关状态） | 本地记账写入失败、数据冲突、取消/更正、经营收支差错 |
| 微信/支付宝“收款渠道” | 若用户真实需要，可仅作为已经收款的**记账账户或备注**；不代表调用第三方 |
| 实收必填且默认“已付清” | 实收字段与全额/未收/未录的关系尚待用户确认，**不得自行填充** |
| 价格变动自动调整已经收款 | 不重写现实收款事实，需展示差异并要求用户复核 |
| 所有出库都产生销售收入 | 出库类型需明确：非销售消耗/报损等不可直接算收入 |

## 10.4 建议的业务职责优先顺序（不是最终 UI 顺序）

1. 销售出库定位：业务类型、仓库场景、用户是谁、操作发生在货物实际离库之前还是之后；
2. 实际卖货过程：找货/扫码、数量、单位、成交价（商品默认价按 OWNER/STAFF 维护规则）、客户信息是否必要；
3. **确认出库**：依据真实库存状态、数量、商品可售性确定库存影响；
4. **销售业务金额记录**：行金额、整单金额、历史价格快照；
5. **可选或待确定的手工经营记账**：客户往来、已发生收款、未收余额、记账账户；具体是否必填、是否能晚于出库登记，以 W-03/W-04/W-05 决策为准；
6. **查询和更正**：谁、何时、卖了什么、库存怎样变化、有没有对应已收/未收事实、如何纠正错录，保持审计；
7. 汇总为 02-09/10 权限、状态、幂等、并发与同一本地数据库中的一致性事务。

## 10.5 第二轮重点业务待确认：W-01～W-07（范围级问题）

| 编号 | 真实仓库场景要明确什么 | 本轮不可擅自冻结的分支 | 影响 |
|---|---|---|---|
| W-01 | **销售出库与普通出库是否同类？** 是否有领用、报损、赠品、调拨、退货出库 | 建议只有真实销售才生成销售金额；其他出库若存在另设类型并归属库存调整等模块 | 销售与库存模块边界、统计口径 |
| W-02 | **出库发生时点**：先实际把货给人再补录，还是系统确认即视为库存已出库？能否补录昨天的业务？ | 区分业务发生时间和系统记录时间；完成状态与库存生效时点不能仅从 UI 推断 | 库存历史、倒序录入、并发、报表 |
| W-03 | **销售只记卖货时能否不填实收？** “没收款”“未填”“已收0元”是否不同 | 不自动把空值当作已收 0 / 已全额结清；未知值如何保存待明确 | 可操作性、错误欠款、记账 |
| W-04 | **客户是否必须关联，哪种销售才产生正式欠款？** | 无客户、匿名成交、部分/全额赊账、零收款的处理需要业务确认 | 02-03/05 往来 |
| W-05 | **记账和出库是否必须同一步？** 现实已收款先记/后记、本次无记录如何处理 | 可考虑销售出库主流程与独立的真实收款记录联动，但时序和事务范围未决定 | 02-04、02-10 |
| W-06 | **库存不足与负库存**：仓库实物已经出库但系统库存不足怎么办？ | 严格阻止出库/允许补录/负库存哪条路径需要业务决定，不自动采用收银/电商策略 | 02-05、模块 04 |
| W-07 | **错误出库如何修正**：撤销、补录、误选商品、单位错、实物退回是否区分？ | 不能把所有业务恢复成在线退款；应围绕货物和台账的修正/冲销 | 02-08、审计 |

## 10.6 这一轮为什么不能直接宣告 02-01/02-02 整体可冻结

- 02-01 在技术安全上做过两轮审查，但未校验不同仓库业务实际操作顺序、补录销售与纯库存出库之间边界。
- 02-02 商品数量/金额在数学/技术上可行，但尚未确定销售成本、商品售价维护、业务发生日期及出库用途对交易事实的影响。
- 02-03/04 还只有骨架；必须先决定**是否存在真实要记录的客户/收款事实及是否为必填**，不能由“支付网关结算”的思维反向决定卖货状态机。
- 02-05 虽未开始，但库存是进销存的主轴，业务边界需要和 02-01/02-02 同步梳理，不宜排到“收款成功之后”才考虑。
- 因此当前阶段的下一项是**W-01～W-07 仓库业务场景需求澄清 / 模块 02 第二轮范围设计**，澄清后再继续 02-03、02-04、02-05 的正式详细设计。

## 10.7 非支付边界的系统测试清单

| 需求测试 | 预期 |
|---|---|
| 店员正常录入销售出库，但没有连接任何支付平台 | 不因缺失支付 SDK/网关无法使用卖货功能 |
| 微信/现金已在现实中收到钱，用户需要记账 | 只记录实际金额和账户/备注，不向微信或银行发起扣款 |
| 客户还没付款 | 不进入“等待第三方支付回调”；按确认的客户/未收规则处理 |
| 现场有货离库，但系统记录时间晚一天 | 按 W-02 的业务发生时间和权限策略留痕，不自动声称“线上订单已完成支付” |
| 商品出库后发现误选商品 | 按库存/销售错录更正设计，而非调用退款接口 |
| 商品售价更改 | OWNER/STAFF 在授权范围内维护默认价，店长可查历史；旧出库历史不回写 |
| 店员无商品售价维护权限 | 本店商品价不能越权改；但这与商品已设置的默认售价能否用于销售是独立判断 |
| 所有用户均不配置支付 Provider | 模块 02 核心商品、库存、销售历史与内部记账能力仍可运行 |
| 手工记录的实收字段为空 | 不无提示地当作已付清或已收0元；按 W-03 明确策略提示/阻止/允许后补 |
| 同一销售重复提交 | 销售记录、库存流水、本地账本（如有）幂等，不重复扣库存 |
