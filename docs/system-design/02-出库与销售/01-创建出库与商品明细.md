# 01 — 创建出库与商品明细

> 状态：第一轮详细设计完成（DESIGN BASELINE v1，部分产品语义待确认）
> 所属模块：02 出库 / 销售
> 当前边界：只定义“如何开始一笔销售出库、如何形成和维护商品明细”；价格、客户、收款、库存扣减的最终规则分别进入后续子模块。

---

# 1. 设计目标

本子模块回答以下问题：

1. 一次销售 / 出库从什么业务动作开始；
2. 谁可以发起；
3. 商品如何被搜索、扫码、选择并形成商品行；
4. 商品行如何新增、删除、修改；
5. 同一商品重复加入时如何处理；
6. 停用商品、跨 Merchant 商品、临时商品如何处理；
7. 用户中途退出后是否存在可恢复草稿；
8. 创建和编辑过程中失败后系统留下什么；
9. 哪些动作属于低风险草稿编辑，哪些必须推迟到“完成销售”时统一校验；
10. 创建阶段如何处理权限、幂等、并发和 Audit。

本文件不提前冻结：

- 数量精度、单位换算；
- 默认销售价、成交价修改；
- 客户是否必填；
- 欠款；
- 实收金额；
- 记账账户；
- 库存扣减；
- 完成后的更正、撤销、作废。

这些分别进入 02～10 子模块。

---

# 2. 继承的已冻结规则

以下不是本轮重新讨论的结论，而是直接继承上游正式需求与账户模块：

- 系统账号只有 SYSTEM_ADMIN、OWNER、STAFF；
- OWNER 是本 Merchant 的经营负责人；
- STAFF 采用“STAFF + 业务权限集合”；
- STAFF 是否可卖货必须由 OWNER 授权；
- Agent 不能绕过当前用户、Merchant、权限和业务规则，只能调用正常 Application Service；
- Merchant FROZEN 只能 READ_ONLY，禁止经营写入；
- Merchant CLOSED 不允许普通经营写入；
- master-goods 是经营记录 / 记账系统，不是实际支付清算系统；
- 客户不是系统账号；
- Permission Catalog 必须从真实销售用例反推，当前不提前把权限码写死成数据库常量；
- SYSTEM_ADMIN 的业务纠错必须走专用受控服务并写 Audit，不能伪装成普通 OWNER / STAFF 直接创建日常销售。

# 3. 业务动作定义

## 3.1 一次“创建销售”是什么

本模块把一次卖货设计为：

~~~text
创建一个 Merchant 范围内的可编辑销售草稿
→ 逐步加入商品明细
→ 后续补齐数量 / 单位 / 成交价 / 客户 / 收款等信息
→ 用户显式执行“完成销售”
→ 系统才形成正式、可追溯的销售 / 出库业务事实
~~~

因此：

- “创建草稿”不是“销售已经发生”；
- “加入商品”不是“库存已经扣减”；
- “修改商品行”不是“修改历史销售”；
- 只有后续 Complete Sale 成功，才允许正式业务事实生效。

这是为了避免多步骤录入过程中出现：

~~~text
商品行已保存
但金额未完成
或客户未完成
或库存只扣了一半
或收款记录已写而销售未完成
~~~

创建阶段必须保持“无正式经营副作用”。

## 3.2 SaleDraft 与正式销售记录

本子模块引入 SaleDraft 作为创建期业务聚合。

SaleDraft 的职责：

- 保存当前 Merchant；
- 保存创建人；
- 保存商品明细；
- 保存创建来源；
- 保存当前 revision；
- 承载后续子模块逐步补齐的字段；
- 在最终完成前保持可编辑。

SaleDraft 不是历史销售记录。

最终 Complete Sale 成功后：

- SaleDraft 不再可编辑；
- 后续由模块 10 决定是“同一聚合状态转为完成”还是“消费 Draft 形成正式 Sale / Outbound Record”；
- 无论最终实现形式如何，业务上都必须满足“完成后不可继续按草稿方式覆盖历史事实”。

Sale 与 Outbound 最终是否是一个领域实体或两个紧密关联概念，仍留到模块 10 收口，不在本文件提前锁死。

# 4. 角色与权限

## 4.1 OWNER

OWNER 在以下条件全部满足时可以创建和编辑本 Merchant 销售草稿：

- User 可用；
- Membership 可用；
- Merchant = ACTIVE；
- 当前 Session 允许经营写入。

OWNER 不需要额外 STAFF 业务授权。

## 4.2 STAFF

STAFF 需要同时满足：

- User 可用；
- Membership 可用；
- Merchant = ACTIVE；
- 当前 Session 允许经营写入；
- 拥有“创建 / 编辑销售”对应业务能力。

当前只冻结能力语义，不提前冻结最终 permission code 字符串。

例如后续 Permission Catalog 可能形成：

~~~text
销售创建
销售价格修改
赊销
收款账户修改
销售撤销
~~~

但具体 code 由模块 09 统一收口。

## 4.3 SYSTEM_ADMIN

SYSTEM_ADMIN：

- 可以查看和治理销售数据；
- 可以执行有原因、有 Audit 的纠错命令；
- 不通过普通“新建销售”入口替某 Merchant 日常记一单；
- 不因为拥有平台权限就绕过 Merchant 业务不变量。

## 4.4 Agent

Agent 可以：

- 在当前用户身份下创建 SaleDraft；
- 修改 SaleDraft；
- 解释当前草稿；
- 请求用户确认后执行后续高风险完成动作。

Agent 不可以：

- 直接写数据库；
- 绕过 STAFF 权限；
- 绕过 Merchant ACTIVE / FROZEN / CLOSED；
- 绕过商品有效性；
- 在用户未满足最终确认策略时直接把草稿变成正式销售。

# 5. SaleDraft 聚合

## 5.1 建议结构

概念结构：

~~~text
SaleDraft
├── draft_id
├── merchant_id
├── created_by_user_id
├── source
├── status
├── revision
├── created_at
├── updated_at
└── lines[]

SaleLineDraft
├── line_id
├── product_id
├── product_snapshot_ref
├── quantity-related fields      ← 由 02 子模块定义
├── unit-related fields          ← 由 02 子模块定义
├── price-related fields         ← 由 02 子模块定义
└── line_revision / ordering
~~~

这里的结构是领域概念，不是数据库 Schema。

## 5.2 Draft 状态

本子模块只需要三个创建期状态：

~~~text
ACTIVE
CANCELLED
CONSUMED
~~~

含义：

- ACTIVE：可继续编辑；
- CANCELLED：用户主动放弃，不再用于完成销售；
- CONSUMED：已经被成功的 Complete Sale 消费，不再允许草稿编辑。

最终正式销售自己的状态机由模块 10 决定。

~~~mermaid
stateDiagram-v2
    [*] --> ACTIVE: 创建销售草稿
    ACTIVE --> CANCELLED: 用户取消
    ACTIVE --> CONSUMED: 完成销售成功
    CANCELLED --> [*]
    CONSUMED --> [*]
~~~

规则：

- CANCELLED 不恢复为 ACTIVE；
- CONSUMED 不恢复为 ACTIVE；
- 用户需要继续业务时新建草稿；
- 不用“删除正式销售”来模拟取消草稿。

# 6. 商品选择与商品行

## 6.1 商品来源

商品可以通过以下入口被选择：

- 商品搜索；
- 商品列表；
- 条码 / 编码扫码；
- 最近使用 / 常用商品等 UI 快捷入口。

这些只是“如何找到 Product”的客户端方式。

进入 Domain / Application Service 后必须统一变成：

~~~text
SelectProduct(product_id)
~~~

或等价命令。

搜索和扫码不能形成两套业务规则。

## 6.2 商品合法性

加入 SaleDraft 前必须至少检查：

1. Product 存在；
2. Product 属于当前 Merchant；
3. Product 当前允许用于销售；
4. Product 没有被停用到“禁止新业务引用”的状态；
5. Draft 仍是 ACTIVE；
6. 当前操作者仍有编辑该 Draft 的权限。

跨 Merchant product_id 必须拒绝，不允许通过猜测 ID 访问。

## 6.3 停用商品

当前设计基线：

- 已停用商品不能新加入 SaleDraft；
- 商品加入 Draft 后、完成销售前如果被停用，最终 Complete Sale 必须重新校验；
- 不能因为“草稿里曾经选过”就永久绕过商品状态。

这样可以防止：

~~~text
A 设备打开旧草稿
→ 管理员停用商品
→ A 设备几小时后仍按旧状态完成销售
~~~

最终完成时必须以当时有效业务状态为准。

## 6.4 临时商品

v1 不引入“只存在于某一销售行、没有 Product 主数据”的临时商品。

如果现实中要卖未建档商品：

~~~text
先创建 Product
→ 再加入 SaleDraft
~~~

原因：

- 库存必须有稳定商品身份；
- 销售历史必须可按商品查询；
- 后续退货 / 更正 / 经营分析需要稳定引用；
- 临时自由文本商品会把商品主数据、库存和销售历史拆成两套模型。

如果后续真实业务证明必须支持临时商品，应作为明确产品能力单独设计，不通过允许 product_id = NULL 偷渡实现。

# 7. 同一商品重复添加

## 7.1 默认行为

同一商品重复选择时，系统不默认创建“完全相同的重复行”。

当前推荐算法：

~~~text
根据 LineIdentityKey 查找现有商品行
→ 如果是同一业务行：更新现有行
→ 如果因为单位 / 价格上下文不同而必须拆行：创建新行
~~~

在 01 子模块阶段：

~~~text
LineIdentityKey 至少包含 product_id
~~~

最终是否扩展为：

~~~text
product_id + unit + price_context
~~~

由 02 数量 / 单位 / 价格设计确定。

因此本文件冻结的是：

> 不允许产生语义完全相同、系统无法解释其差异原因的重复商品行。

不是冻结“一个商品在任何情况下永远只能一行”。

## 7.2 为什么不简单允许任意重复行

任意重复行会导致：

- 总数量计算复杂；
- 修改价格时不清楚改哪一行；
- 扫码连扫容易制造多行噪声；
- 用户容易误以为重复记账；
- Agent 修改草稿时难以稳定引用目标行。

所以重复行必须由明确业务差异产生，而不是由重复点击产生。

# 8. 商品行新增、修改、删除

## 8.1 新增

新增商品行：

~~~text
校验 Draft
→ 校验操作者
→ 校验 Product
→ 计算 LineIdentityKey
→ 新建或合并商品行
→ revision + 1
→ 返回最新 Draft
~~~

## 8.2 修改

当前子模块允许修改“商品行的可编辑属性”，但属性本身由后续模块定义。

任何修改都必须：

- 指定 draft_id；
- 指定 line_id；
- 携带预期 revision；
- 通过权限和 Draft 状态检查；
- 只作用于当前 Merchant。

## 8.3 删除

ACTIVE Draft 中可以删除商品行。

规则：

- 删除只是删除草稿中的意图；
- 不产生库存回补；
- 不产生资金冲销；
- 不产生客户欠款调整；
- 因为这些正式业务事实在草稿阶段根本还没有发生。

删除最后一个商品行后，Draft 可以暂时保持空草稿，但不能进入 Complete Sale。

# 9. 草稿保存、退出与恢复

## 9.1 推荐基线：服务端可恢复草稿

本轮建议采用服务端 SaleDraft，而不是仅客户端本地临时状态。

原因：

- 四个正式客户端共用同一后端契约；
- 移动端可能闪退、切后台、断网；
- Agent 需要创建和修改业务草稿；
- 同一个用户可能在不同设备继续；
- 不能把关键经营录入完全依赖单一客户端内存。

行为：

~~~text
用户创建 / 首次加入商品
→ 服务端持久化 ACTIVE Draft
→ 每次有效修改保存新 revision
→ 中途退出
→ 下次进入卖货入口时可查询自己的未完成草稿
~~~

## 9.2 草稿可见范围

默认业务基线：

- 普通 STAFF 自动恢复自己的草稿；
- 不自动把其他 STAFF 草稿塞给当前 STAFF；
- OWNER 是否可查看 / 接管其他人草稿，进入 07 查询历史与 09 权限审计统一设计；
- Agent 只能访问当前用户和权限允许的 Draft。

这里区分：

~~~text
“草稿属于 Merchant”
与
“谁默认可以继续编辑这个草稿”
~~~

不能因为 Merchant 相同就允许任何 STAFF 相互覆盖。

## 9.3 草稿自动清理

ACTIVE Draft 的自动过期 / 清理周期属于实现与运营配置，不影响正式经营账。

如果后续配置自动清理：

- 只能清理长期未完成 Draft；
- 不能清理已完成销售；
- 不能把清理 Draft 当成业务撤销。

# 10. 主时序

~~~mermaid
sequenceDiagram
    actor U as OWNER / 已授权 STAFF
    participant C as 客户端
    participant S as 销售应用服务
    participant A as 授权与 Merchant Policy
    participant P as 商品查询服务
    participant D as SaleDraft 聚合
    participant DB as PostgreSQL
    participant AU as Audit / Activity

    U->>C: 进入卖货
    C->>S: 创建或恢复销售草稿
    S->>A: 校验 User / Membership / Merchant / Permission
    A-->>S: 允许经营写入
    S->>DB: 创建或读取 ACTIVE Draft
    DB-->>S: Draft + revision
    S-->>C: 草稿

    U->>C: 搜索 / 扫码选择商品
    C->>S: AddProduct(draft_id, product_id, expected_revision)
    S->>A: 再校验当前权限与 Merchant
    S->>P: 查询并校验商品
    P-->>S: Product 可用于销售
    S->>D: 计算 LineIdentityKey 并新增 / 合并
    D->>DB: 原子保存 Draft 新 revision
    DB-->>D: 成功
    S->>AU: 记录必要的 Draft Activity
    S-->>C: 返回最新商品行和 revision
~~~

说明：

- 权限不能只在“进入页面”时检查一次；
- 每个写命令都必须重新验证；
- Product 合法性在服务端判断；
- revision 防止并发覆盖。

# 11. 关键分支

## 11.1 Merchant 已被冻结

~~~text
用户打开旧页面
→ Merchant 后续变为 FROZEN
→ 用户尝试继续加商品
→ 服务端拒绝经营写入
→ 原 Draft 保留
~~~

FROZEN 不允许继续编辑销售草稿。

## 11.2 Product 已停用

~~~text
草稿中已有商品 A
→ 商品 A 被停用
→ 用户继续编辑其他行可以按策略继续
→ 最终完成前再次校验 A
→ 若 A 当前不允许销售，则 Complete Sale 拒绝
~~~

是否在商品被停用时立即把整张 Draft 标红属于 UI / 查询表现，不改变最终服务端校验。

## 11.3 网络重试

~~~text
客户端发送 AddProduct
→ 服务端已成功
→ 响应丢失
→ 客户端用同一 idempotency_key 重试
→ 服务端返回第一次结果
→ 不重复加行 / 不重复增加数量
~~~

## 11.4 并发编辑冲突

~~~text
设备 A revision = 8
设备 B revision = 8

A 修改成功
→ revision = 9

B 仍提交 expected_revision = 8
→ CAS 失败
→ 返回 VERSION_CONFLICT
→ 客户端拉取 revision = 9 后重新展示
~~~

禁止最后写入者无提示覆盖前一个修改。

# 12. 事务边界

## 12.1 Draft 编辑事务

每个 Draft 写命令至少包含：

~~~text
校验当前 Draft revision
→ 修改行
→ 更新 Draft revision
→ 写必要的 Draft Activity
~~~

这些必须作为单个本地事务完成。

失败时：

- Draft 保持调用前状态；
- 不留下半条商品行；
- 不递增成功 revision；
- 不产生正式库存 / 收款 / 欠款事实。

## 12.2 完成销售事务

本子模块冻结跨模块原则：

> 一笔销售只有在 Complete Sale 的全部正式业务事实能够一致提交时，才算完成。

因此后续 02～05 设计完成后，模块 10 必须把：

- 正式销售记录；
- 正式商品明细；
- 最终金额事实；
- 客户应收 / 欠款事实（如有）；
- 当次收款记账事实（如有）；
- 销售出库库存流水；

纳入明确的一致性边界。

如果最终都在同一 PostgreSQL 中，优先本地事务 / Unit of Work，不使用无必要的分布式 Saga。

事务提交后的外部通知、异步统计等通过 Outbox。

# 13. 幂等

需要幂等的命令至少包括：

- CreateSaleDraft；
- AddProduct；
- RemoveSaleLine；
- UpdateSaleLine；
- CancelSaleDraft；
- 后续 CompleteSale。

建议幂等作用域：

~~~text
merchant_id
+ actor_user_id
+ command_type
+ idempotency_key
~~~

幂等结果需要能返回：

- 已完成的 draft_id；
- 最新 revision；
- 对应 line_id / 删除结果；
- 原始业务结果。

不能只存“请求来过”，否则客户端重试后无法恢复 UI。

# 14. 并发控制

SaleDraft 使用乐观并发控制。

核心字段：

~~~text
revision: integer
~~~

更新形式：

~~~text
UPDATE draft
SET ..., revision = revision + 1
WHERE draft_id = ?
  AND revision = expected_revision
  AND status = ACTIVE
~~~

受影响行数为 0：

- Draft 不存在；
- Draft 已不是 ACTIVE；
- revision 冲突；

需要进一步读取并映射成不同失败语义。

不建议对用户编辑全过程持有数据库悲观锁。

# 15. Audit 与来源追踪

Draft 阶段不需要把每一次输入框敲字都写成高成本全局 Audit。

至少保留：

- created_by_user_id；
- last_modified_by_user_id；
- source（WEB / MINI_PROGRAM / ANDROID / IOS / AGENT 等来源语义）；
- created_at / updated_at；
- revision；
- Create / Cancel / Agent 自动修改等关键 Activity；
- SYSTEM_ADMIN 任何介入必须单独记录完整 Audit。

最终 Complete Sale 必须保存正式操作者和完成来源。

Agent 修改 Draft 时需要能区分：

~~~text
human initiated
agent proposed
human confirmed
agent executed
~~~

具体确认事件在 07 Agent / 09 权限风险 / 10 事务收口继续设计。

---

# 16. Risk

创建空 Draft、搜索商品、增加普通商品行本身属于低风险经营准备动作。

高风险判断后置到真实风险产生的子模块，例如：

- 修改成交价；
- 赊销；
- 超额收款；
- 负库存；
- 撤销 / 作废；
- SYSTEM_ADMIN 纠错。

因此本子模块不引入“每次加商品都 Step-up”的过度安全设计。

但以下是 Hard Reject，不属于 Risk Score：

- Merchant 非 ACTIVE；
- User / Membership 不可用；
- STAFF 无销售编辑能力；
- Draft 非 ACTIVE；
- Product 不属于当前 Merchant；
- Product 当前禁止用于新销售。

---

# 17. 设计模式

## 17.1 Aggregate

SaleDraft 作为创建期 Aggregate Root：

- 统一控制商品行；
- 统一维护 revision；
- 统一保证 Draft 状态；
- 不允许客户端直接独立写 SaleLineDraft。

## 17.2 Command

写操作使用显式命令：

~~~text
CreateSaleDraft
AddProductToSaleDraft
UpdateSaleLine
RemoveSaleLine
CancelSaleDraft
~~~

便于权限、幂等、Audit 和 Agent Tool 复用。

## 17.3 Policy / Specification

建议至少有：

~~~text
CanEditSaleDraftPolicy
ProductEligibleForSaleSpecification
SaleDraftStatePolicy
~~~

把“是否允许”集中表达，不散落在 Controller。

## 17.4 Optimistic Concurrency Control

revision + CAS 解决：

- 多设备编辑；
- Agent 与人工同时编辑；
- 网络延迟导致旧请求覆盖新请求。

## 17.5 Idempotency

防止移动网络重试和 Agent Tool Retry 重复新增商品。

# 18. 判断算法

## 18.1 CanEditSaleDraft

~~~text
if user unavailable:
    reject

if membership unavailable:
    reject

if merchant != draft.merchant:
    reject

if merchant.status != ACTIVE:
    reject

if role == OWNER:
    allow

if role == STAFF and has sale-edit capability:
    allow

otherwise:
    reject
~~~

## 18.2 AddProduct

~~~text
load ACTIVE Draft
check expected revision
authorize actor
load Product within same Merchant
check Product eligible for sale

key = LineIdentityKey(product, current unit/price context)

if existing line with same key:
    merge according to quantity policy
else:
    append new line

revision += 1
commit atomically
return latest Draft
~~~

02 子模块完成前，quantity policy 仍是接口，不在此处偷偷实现整数 +1 的永久规则。

# 19. 性能与索引原则

正式 Schema 后续再定，但实现时至少考虑以下查询路径：

- Merchant + Draft Status + Created By 查询未完成草稿；
- draft_id + merchant_id 精确读取；
- Product 按 Merchant + 状态 + 名称 / 编码 / 条码搜索；
- SaleLine 按 draft_id 排序读取；
- 幂等键按 Merchant + Actor + Command + Key 唯一查询。

条码搜索的唯一性规则属于商品模块，不在销售模块私自定义。

SaleDraft 不应无限累积；长期未完成 Draft 的清理策略进入配置与运维设计。

# 20. 失败语义

建议使用稳定业务错误，而不是把所有失败都映射成 500：

| 场景 | 语义 |
|---|---|
| Merchant 非 ACTIVE | MERCHANT_NOT_WRITABLE |
| STAFF 无销售能力 | SALE_PERMISSION_DENIED |
| Draft 不存在 / 跨 Merchant | SALE_DRAFT_NOT_FOUND |
| Draft 已取消 / 已消费 | SALE_DRAFT_NOT_EDITABLE |
| revision 冲突 | SALE_DRAFT_VERSION_CONFLICT |
| Product 不存在 / 跨 Merchant | PRODUCT_NOT_FOUND |
| Product 已停用 | PRODUCT_NOT_SALEABLE |
| 幂等请求已成功 | 返回原成功结果 |
| 数据库事务失败 | 本次命令失败，Draft 保持原状态 |

错误 code 最终命名可在 API 设计阶段统一规范，但业务语义必须保留。

# 21. 边界测试矩阵

| 场景 | 预期 |
|---|---|
| OWNER 在 ACTIVE Merchant 创建 Draft | 允许 |
| STAFF 有销售能力创建 Draft | 允许 |
| STAFF 无销售能力创建 Draft | 拒绝 |
| FROZEN Merchant 从旧页面继续加商品 | 拒绝写入 |
| CLOSED Merchant 创建 Draft | 拒绝 |
| 加入本 Merchant 正常商品 | 允许 |
| 加入其他 Merchant 商品 ID | 拒绝 |
| 加入已停用商品 | 拒绝 |
| 商品加入后再被停用 | Draft 可保留，完成时必须重新校验 |
| 同一商品重复扫码 | 命中 LineIdentityKey；不产生无法解释的完全重复行 |
| 删除最后一行 | Draft 可为空，但不能完成 |
| 两设备同 revision 修改 | 只有一个 CAS 成功，另一方冲突 |
| AddProduct 响应丢失后同 key 重试 | 返回原结果，不重复 |
| 用户取消 Draft | 进入 CANCELLED，不产生库存 / 金额影响 |
| Agent 创建 Draft | 继承当前用户权限 |
| SYSTEM_ADMIN 通过普通商户入口代创建销售 | 不作为标准流程 |

# 22. 本轮已冻结 / 继承冻结

以下可以直接作为 Coding Agent 的业务不变量：

1. 销售创建阶段与正式完成阶段分离；
2. 草稿阶段不产生正式库存、收款、欠款经营副作用；
3. OWNER 可在本 Merchant 正常经营状态下创建销售；
4. STAFF 必须有销售业务授权；
5. Merchant FROZEN / CLOSED 禁止销售写入；
6. Agent 只能复用正常销售 Application Service；
7. 商品必须属于同一 Merchant；
8. 当前禁止销售的商品不能新加入 Draft；
9. 完成销售时必须重新校验商品有效性；
10. 不允许无业务差异的完全重复商品行；
11. Draft 写入使用 revision 乐观并发控制；
12. 写命令必须支持幂等；
13. 删除 Draft 行不产生库存或资金冲销；
14. Complete Sale 成功前不允许出现“部分正式业务事实已生效”的半完成销售。

# 23. 本轮新增待确认项

以下是本轮形成的推荐设计，但仍应由产品负责人显式确认后再标记为最终冻结：

## S-01 服务端可恢复 SaleDraft

建议：

- 使用服务端持久化 ACTIVE Draft；
- 支持用户中途退出后恢复；
- 支持 Agent 和多客户端共用。

如果否决，则需要明确哪些客户端只保留本地草稿，以及 Agent 如何与人工共享未完成业务。

## S-02 临时商品

建议 v1 不支持自由文本临时商品：

~~~text
未建档商品
→ 先建 Product
→ 再卖货
~~~

如确有“一次性杂项商品”需求，应单独设计，而不是允许空 product_id。

## S-03 草稿默认可见 / 编辑范围

建议：

- STAFF 默认只自动恢复自己创建的 Draft；
- OWNER 或拥有专门权限的人是否可以查看、接管他人 Draft，在 07 / 09 统一确认。

不建议 Merchant 内所有 STAFF 默认互相编辑草稿。
