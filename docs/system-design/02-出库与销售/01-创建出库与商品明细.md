# 01 — 创建出库与商品明细

> 状态：第一轮详细设计完成（DESIGN BASELINE v1，部分产品语义待确认）
> 所属模块：02 出库 / 销售
> 当前边界：只定义“如何开始一笔销售出库、如何形成和维护商品明细”；价格、客户、收款、库存扣减的最终规则分别进入后续子模块。

---

# 1. 设计目标

本子模块回答以下问题：

1. 一次销售 / 出库从什么业务动作开始；
2. 谁可以发起；
3. 商品如何被搜索、扫码、选择并形成商品行；
4. 商品行如何新增、删除、修改；
5. 同一商品重复加入时如何处理；
6. 停用商品、跨 Merchant 商品、临时商品如何处理；
7. 用户中途退出后是否存在可恢复草稿；
8. 创建和编辑过程中失败后系统留下什么；
9. 哪些动作属于低风险草稿编辑，哪些必须推迟到“完成销售”时统一校验；
10. 创建阶段如何处理权限、幂等、并发和 Audit。

本文件不提前冻结：

- 数量精度、单位换算；
- 默认销售价、成交价修改；
- 客户是否必填；
- 欠款；
- 实收金额；
- 记账账户；
- 库存扣减；
- 完成后的更正、撤销、作废。

这些分别进入 02～10 子模块。

---

# 2. 继承的已冻结规则

以下不是本轮重新讨论的结论，而是直接继承上游正式需求与账户模块：

- 系统账号只有 SYSTEM_ADMIN、OWNER、STAFF；
- OWNER 是本 Merchant 的经营负责人；
- STAFF 采用“STAFF + 业务权限集合”；
- STAFF 是否可卖货必须由 OWNER 授权；
- Agent 不能绕过当前用户、Merchant、权限和业务规则，只能调用正常 Application Service；
- Merchant FROZEN 只能 READ_ONLY，禁止经营写入；
- Merchant CLOSED 不允许普通经营写入；
- master-goods 是经营记录 / 记账系统，不是实际支付清算系统；
- 客户不是系统账号；
- Permission Catalog 必须从真实销售用例反推，当前不提前把权限码写死成数据库常量；
- SYSTEM_ADMIN 的业务纠错必须走专用受控服务并写 Audit，不能伪装成普通 OWNER / STAFF 直接创建日常销售。

# 3. 业务动作定义

## 3.1 一次“创建销售”是什么

本模块把一次卖货设计为：

~~~text
创建一个 Merchant 范围内的可编辑销售草稿
→ 逐步加入商品明细
→ 后续补齐数量 / 单位 / 成交价 / 客户 / 收款等信息
→ 用户显式执行“完成销售”
→ 系统才形成正式、可追溯的销售 / 出库业务事实
~~~

因此：

- “创建草稿”不是“销售已经发生”；
- “加入商品”不是“库存已经扣减”；
- “修改商品行”不是“修改历史销售”；
- 只有后续 Complete Sale 成功，才允许正式业务事实生效。

这是为了避免多步骤录入过程中出现：

~~~text
商品行已保存
但金额未完成
或客户未完成
或库存只扣了一半
或收款记录已写而销售未完成
~~~

创建阶段必须保持“无正式经营副作用”。

## 3.2 SaleDraft 与正式销售记录

本子模块引入 SaleDraft 作为创建期业务聚合。

SaleDraft 的职责：

- 保存当前 Merchant；
- 保存创建人；
- 保存商品明细；
- 保存创建来源；
- 保存当前 revision；
- 承载后续子模块逐步补齐的字段；
- 在最终完成前保持可编辑。

SaleDraft 不是历史销售记录。

最终 Complete Sale 成功后：

- SaleDraft 不再可编辑；
- 后续由模块 10 决定是“同一聚合状态转为完成”还是“消费 Draft 形成正式 Sale / Outbound Record”；
- 无论最终实现形式如何，业务上都必须满足“完成后不可继续按草稿方式覆盖历史事实”。

Sale 与 Outbound 最终是否是一个领域实体或两个紧密关联概念，仍留到模块 10 收口，不在本文件提前锁死。

# 4. 角色与权限

## 4.1 OWNER

OWNER 在以下条件全部满足时可以创建和编辑本 Merchant 销售草稿：

- User 可用；
- Membership 可用；
- Merchant = ACTIVE；
- 当前 Session 允许经营写入。

OWNER 不需要额外 STAFF 业务授权。

## 4.2 STAFF

STAFF 需要同时满足：

- User 可用；
- Membership 可用；
- Merchant = ACTIVE；
- 当前 Session 允许经营写入；
- 拥有“创建 / 编辑销售”对应业务能力。

当前只冻结能力语义，不提前冻结最终 permission code 字符串。

例如后续 Permission Catalog 可能形成：

~~~text
销售创建
销售价格修改
赊销
收款账户修改
销售撤销
~~~

但具体 code 由模块 09 统一收口。

## 4.3 SYSTEM_ADMIN

SYSTEM_ADMIN：

- 可以查看和治理销售数据；
- 可以执行有原因、有 Audit 的纠错命令；
- 不通过普通“新建销售”入口替某 Merchant 日常记一单；
- 不因为拥有平台权限就绕过 Merchant 业务不变量。

## 4.4 Agent

Agent 可以：

- 在当前用户身份下创建 SaleDraft；
- 修改 SaleDraft；
- 解释当前草稿；
- 请求用户确认后执行后续高风险完成动作。

Agent 不可以：

- 直接写数据库；
- 绕过 STAFF 权限；
- 绕过 Merchant ACTIVE / FROZEN / CLOSED；
- 绕过商品有效性；
- 在用户未满足最终确认策略时直接把草稿变成正式销售。

# 5. SaleDraft 聚合

## 5.1 建议结构

概念结构：

~~~text
SaleDraft
├── draft_id
├── merchant_id
├── created_by_user_id
├── source
├── status
├── revision
├── created_at
├── updated_at
└── lines[]

SaleLineDraft
├── line_id
├── product_id
├── product_snapshot_ref
├── quantity-related fields      ← 由 02 子模块定义
├── unit-related fields          ← 由 02 子模块定义
├── price-related fields         ← 由 02 子模块定义
└── line_revision / ordering
~~~

这里的结构是领域概念，不是数据库 Schema。

## 5.2 Draft 状态

本子模块只需要三个创建期状态：

~~~text
ACTIVE
CANCELLED
CONSUMED
~~~

含义：

- ACTIVE：可继续编辑；
- CANCELLED：用户主动放弃，不再用于完成销售；
- CONSUMED：已经被成功的 Complete Sale 消费，不再允许草稿编辑。

最终正式销售自己的状态机由模块 10 决定。

~~~mermaid
stateDiagram-v2
    [*] --> ACTIVE: 创建销售草稿
    ACTIVE --> CANCELLED: 用户取消
    ACTIVE --> CONSUMED: 完成销售成功
    CANCELLED --> [*]
    CONSUMED --> [*]
~~~

规则：

- CANCELLED 不恢复为 ACTIVE；
- CONSUMED 不恢复为 ACTIVE；
- 用户需要继续业务时新建草稿；
- 不用“删除正式销售”来模拟取消草稿。

# 6. 商品选择与商品行

## 6.1 商品来源

商品可以通过以下入口被选择：

- 商品搜索；
- 商品列表；
- 条码 / 编码扫码；
- 最近使用 / 常用商品等 UI 快捷入口。

这些只是“如何找到 Product”的客户端方式。

进入 Domain / Application Service 后必须统一变成：

~~~text
SelectProduct(product_id)
~~~

或等价命令。

搜索和扫码不能形成两套业务规则。

## 6.2 商品合法性

加入 SaleDraft 前必须至少检查：

1. Product 存在；
2. Product 属于当前 Merchant；
3. Product 当前允许用于销售；
4. Product 没有被停用到“禁止新业务引用”的状态；
5. Draft 仍是 ACTIVE；
6. 当前操作者仍有编辑该 Draft 的权限。

跨 Merchant product_id 必须拒绝，不允许通过猜测 ID 访问。

## 6.3 停用商品

当前设计基线：

- 已停用商品不能新加入 SaleDraft；
- 商品加入 Draft 后、完成销售前如果被停用，最终 Complete Sale 必须重新校验；
- 不能因为“草稿里曾经选过”就永久绕过商品状态。

这样可以防止：

~~~text
A 设备打开旧草稿
→ 管理员停用商品
→ A 设备几小时后仍按旧状态完成销售
~~~

最终完成时必须以当时有效业务状态为准。

## 6.4 临时商品

v1 不引入“只存在于某一销售行、没有 Product 主数据”的临时商品。

如果现实中要卖未建档商品：

~~~text
先创建 Product
→ 再加入 SaleDraft
~~~

原因：

- 库存必须有稳定商品身份；
- 销售历史必须可按商品查询；
- 后续退货 / 更正 / 经营分析需要稳定引用；
- 临时自由文本商品会把商品主数据、库存和销售历史拆成两套模型。

如果后续真实业务证明必须支持临时商品，应作为明确产品能力单独设计，不通过允许 product_id = NULL 偷渡实现。

# 7. 同一商品重复添加

## 7.1 默认行为

同一商品重复选择时，系统不默认创建“完全相同的重复行”。

当前推荐算法：

~~~text
根据 LineIdentityKey 查找现有商品行
→ 如果是同一业务行：更新现有行
→ 如果因为单位 / 价格上下文不同而必须拆行：创建新行
~~~

在 01 子模块阶段：

~~~text
LineIdentityKey 至少包含 product_id
~~~

最终是否扩展为：

~~~text
product_id + unit + price_context
~~~

由 02 数量 / 单位 / 价格设计确定。

因此本文件冻结的是：

> 不允许产生语义完全相同、系统无法解释其差异原因的重复商品行。

不是冻结“一个商品在任何情况下永远只能一行”。

## 7.2 为什么不简单允许任意重复行

任意重复行会导致：

- 总数量计算复杂；
- 修改价格时不清楚改哪一行；
- 扫码连扫容易制造多行噪声；
- 用户容易误以为重复记账；
- Agent 修改草稿时难以稳定引用目标行。

所以重复行必须由明确业务差异产生，而不是由重复点击产生。

# 8. 商品行新增、修改、删除

## 8.1 新增

新增商品行：

~~~text
校验 Draft
→ 校验操作者
→ 校验 Product
→ 计算 LineIdentityKey
→ 新建或合并商品行
→ revision + 1
→ 返回最新 Draft
~~~

## 8.2 修改

当前子模块允许修改“商品行的可编辑属性”，但属性本身由后续模块定义。

任何修改都必须：

- 指定 draft_id；
- 指定 line_id；
- 携带预期 revision；
- 通过权限和 Draft 状态检查；
- 只作用于当前 Merchant。

## 8.3 删除

ACTIVE Draft 中可以删除商品行。

规则：

- 删除只是删除草稿中的意图；
- 不产生库存回补；
- 不产生资金冲销；
- 不产生客户欠款调整；
- 因为这些正式业务事实在草稿阶段根本还没有发生。

删除最后一个商品行后，Draft 可以暂时保持空草稿，但不能进入 Complete Sale。

# 9. 草稿保存、退出与恢复

## 9.1 推荐基线：服务端可恢复草稿

本轮建议采用服务端 SaleDraft，而不是仅客户端本地临时状态。

原因：

- 四个正式客户端共用同一后端契约；
- 移动端可能闪退、切后台、断网；
- Agent 需要创建和修改业务草稿；
- 同一个用户可能在不同设备继续；
- 不能把关键经营录入完全依赖单一客户端内存。

行为：

~~~text
用户创建 / 首次加入商品
→ 服务端持久化 ACTIVE Draft
→ 每次有效修改保存新 revision
→ 中途退出
→ 下次进入卖货入口时可查询自己的未完成草稿
~~~

## 9.2 草稿可见范围

默认业务基线：

- 普通 STAFF 自动恢复自己的草稿；
- 不自动把其他 STAFF 草稿塞给当前 STAFF；
- OWNER 是否可查看 / 接管其他人草稿，进入 07 查询历史与 09 权限审计统一设计；
- Agent 只能访问当前用户和权限允许的 Draft。

这里区分：

~~~text
“草稿属于 Merchant”
与
“谁默认可以继续编辑这个草稿”
~~~

不能因为 Merchant 相同就允许任何 STAFF 相互覆盖。

## 9.3 草稿保留与清理

~~~mermaid
flowchart TD
    A[草稿进入保留策略] --> B{当前状态}
    B -->|ACTIVE| C[禁止静默物理删除]
    C --> D{是否已正式定义过期语义?}
    D -->|否| E[继续保留 ACTIVE]
    D -->|是| F[按显式状态迁移处理]
    B -->|CANCELLED| G[按终态保留周期归档 / 清理]
    B -->|CONSUMED| H[正式销售已建立]
    H --> I[Draft 仅按技术留存策略处理]
~~~

**流程说明：**

- 现有 Draft 状态机只有 ACTIVE / CANCELLED / CONSUMED，因此不能一边没有 EXPIRED 状态，一边又让后台定时任务静默删除 ACTIVE Draft。
- 在产品没有确认“草稿过期”语义前，ACTIVE Draft 不做不可恢复的自动删除。
- CANCELLED / CONSUMED 属于终态，可以按审计、存储和运维要求设置归档 / 清理周期，但不能影响正式销售事实。
- 如果未来决定支持草稿过期，必须先新增明确的 EXPIRED（或等价）业务状态、恢复规则和用户提示，再实现后台清理。
- 该问题新增为 S-05，见本文待确认项。

# 10. 主流程

~~~mermaid
flowchart TD
    A[用户进入卖货入口] --> B[解析当前 User / Merchant / Role]
    B --> C{是否允许访问销售入口?}
    C -->|否| X[拒绝或按只读权限返回]
    C -->|是| D[查询当前用户可见的 ACTIVE Draft]

    D --> E{可恢复 Draft 数量}
    E -->|0| F[展示新建销售]
    E -->|1| G[展示继续该草稿或新建]
    E -->|多条| H[展示草稿列表并让用户选择]

    F --> I[用户显式选择新建]
    G -->|继续| J[读取最新 Draft revision]
    G -->|新建| I
    H -->|继续某条| J
    H -->|新建| I

    I --> K[CreateSaleDraft]
    K --> L[事务内再次校验 User / Membership / Merchant / Permission]
    L --> M{仍允许经营写入?}
    M -->|否| X
    M -->|是| N[创建 ACTIVE Draft 并返回 revision]

    J --> O[重新校验草稿可见 / 编辑权限]
    O --> P{允许编辑?}
    P -->|否| Q[只读展示或拒绝，取决于查询权限]
    P -->|是| R[进入草稿编辑]

    N --> R
    R --> S[搜索 / 扫码 / 列表选择商品]
    S --> T[解析为明确 product_id]
    T --> U[AddProductToSaleDraft]
    U --> V[事务内校验 Draft / 权限 / Product / expected_revision]
    V --> W{全部通过?}
    W -->|否| Y[返回稳定业务错误，Draft 不变化]
    W -->|是| Z[新增 / 合并商品行并 revision + 1]
    Z --> AA[返回最新 Draft]
~~~

**流程说明：**

- **打开卖货入口不是写操作。** 入口首先查询可恢复 Draft，不因为用户仅打开页面就创建一条持久化空草稿。
- 服务端 Draft 只有在用户明确选择“新建销售”、Agent 明确创建草稿，或等价的显式创建命令时产生。
- “恢复草稿”不是把客户端本地内容覆盖到服务端，而是重新读取服务端最新 revision。
- 创建和每一次编辑都重新检查权限与 Merchant 状态，不能把进入页面时的权限结果当成永久授权。
- 商品搜索、扫码、最近商品等只负责得到候选商品；真正写入 Draft 前必须统一解析为明确的 product_id，再走同一个 AddProduct 业务命令。
- 是否允许一个用户同时存在多条 ACTIVE Draft 属于 S-04 待确认；流程本身兼容 0 / 1 / 多条，不把这个产品决策硬编码到 Application Service。

# 11. 关键分支

## 11.1 Merchant 已被冻结

~~~text
用户打开旧页面
→ Merchant 后续变为 FROZEN
→ 用户尝试继续加商品
→ 服务端拒绝经营写入
→ 原 Draft 保留
~~~

FROZEN 不允许继续编辑销售草稿。

## 11.2 Product 已停用

~~~text
草稿中已有商品 A
→ 商品 A 被停用
→ 用户继续编辑其他行可以按策略继续
→ 最终完成前再次校验 A
→ 若 A 当前不允许销售，则 Complete Sale 拒绝
~~~

是否在商品被停用时立即把整张 Draft 标红属于 UI / 查询表现，不改变最终服务端校验。

## 11.3 网络重试

~~~text
客户端发送 AddProduct
→ 服务端已成功
→ 响应丢失
→ 客户端用同一 idempotency_key 重试
→ 服务端返回第一次结果
→ 不重复加行 / 不重复增加数量
~~~

## 11.4 并发编辑冲突

~~~text
设备 A revision = 8
设备 B revision = 8

A 修改成功
→ revision = 9

B 仍提交 expected_revision = 8
→ CAS 失败
→ 返回 VERSION_CONFLICT
→ 客户端拉取 revision = 9 后重新展示
~~~

禁止最后写入者无提示覆盖前一个修改。

# 12. 事务边界

## 12.1 Draft 编辑事务

每个 Draft 写命令至少包含：

~~~text
校验当前 Draft revision
→ 修改行
→ 更新 Draft revision
→ 写必要的 Draft Activity
~~~

这些必须作为单个本地事务完成。

失败时：

- Draft 保持调用前状态；
- 不留下半条商品行；
- 不递增成功 revision；
- 不产生正式库存 / 收款 / 欠款事实。

## 12.2 完成销售事务

本子模块冻结跨模块原则：

> 一笔销售只有在 Complete Sale 的全部正式业务事实能够一致提交时，才算完成。

因此后续 02～05 设计完成后，模块 10 必须把：

- 正式销售记录；
- 正式商品明细；
- 最终金额事实；
- 客户应收 / 欠款事实（如有）；
- 当次收款记账事实（如有）；
- 销售出库库存流水；

纳入明确的一致性边界。

如果最终都在同一 PostgreSQL 中，优先本地事务 / Unit of Work，不使用无必要的分布式 Saga。

事务提交后的外部通知、异步统计等通过 Outbox。

# 13. 幂等

需要幂等的命令至少包括：

- CreateSaleDraft；
- AddProduct；
- RemoveSaleLine；
- UpdateSaleLine；
- CancelSaleDraft；
- 后续 CompleteSale。

建议幂等作用域：

~~~text
merchant_id
+ actor_user_id
+ command_type
+ idempotency_key
~~~

幂等结果需要能返回：

- 已完成的 draft_id；
- 最新 revision；
- 对应 line_id / 删除结果；
- 原始业务结果。

不能只存“请求来过”，否则客户端重试后无法恢复 UI。

# 14. 并发控制

SaleDraft 使用乐观并发控制。

核心字段：

~~~text
revision: integer
~~~

更新形式：

~~~text
UPDATE draft
SET ..., revision = revision + 1
WHERE draft_id = ?
  AND revision = expected_revision
  AND status = ACTIVE
~~~

受影响行数为 0：

- Draft 不存在；
- Draft 已不是 ACTIVE；
- revision 冲突；

需要进一步读取并映射成不同失败语义。

不建议对用户编辑全过程持有数据库悲观锁。

# 15. Audit 与来源追踪

Draft 阶段不需要把每一次输入框敲字都写成高成本全局 Audit。

至少保留：

- created_by_user_id；
- last_modified_by_user_id；
- source（WEB / MINI_PROGRAM / ANDROID / IOS / AGENT 等来源语义）；
- created_at / updated_at；
- revision；
- Create / Cancel / Agent 自动修改等关键 Activity；
- SYSTEM_ADMIN 任何介入必须单独记录完整 Audit。

最终 Complete Sale 必须保存正式操作者和完成来源。

Agent 修改 Draft 时需要能区分：

~~~text
human initiated
agent proposed
human confirmed
agent executed
~~~

具体确认事件在 07 Agent / 09 权限风险 / 10 事务收口继续设计。

# 16. Risk

创建空 Draft、搜索商品、增加普通商品行本身属于低风险经营准备动作。

高风险判断后置到真实风险产生的子模块，例如：

- 修改成交价；
- 赊销；
- 超额收款；
- 负库存；
- 撤销 / 作废；
- SYSTEM_ADMIN 纠错。

因此本子模块不引入“每次加商品都 Step-up”的过度安全设计。

但以下是 Hard Reject，不属于 Risk Score：

- Merchant 非 ACTIVE；
- User / Membership 不可用；
- STAFF 无销售编辑能力；
- Draft 非 ACTIVE；
- Product 不属于当前 Merchant；
- Product 当前禁止用于新销售。

# 17. 设计模式

## 17.1 Aggregate

SaleDraft 作为创建期 Aggregate Root：

- 统一控制商品行；
- 统一维护 revision；
- 统一保证 Draft 状态；
- 不允许客户端直接独立写 SaleLineDraft。

## 17.2 Command

写操作使用显式命令：

~~~text
CreateSaleDraft
AddProductToSaleDraft
UpdateSaleLine
RemoveSaleLine
CancelSaleDraft
~~~

便于权限、幂等、Audit 和 Agent Tool 复用。

## 17.3 Policy / Specification

建议至少有：

~~~text
CanEditSaleDraftPolicy
ProductEligibleForSaleSpecification
SaleDraftStatePolicy
~~~

把“是否允许”集中表达，不散落在 Controller。

## 17.4 Optimistic Concurrency Control

revision + CAS 解决：

- 多设备编辑；
- Agent 与人工同时编辑；
- 网络延迟导致旧请求覆盖新请求。

## 17.5 Idempotency

防止移动网络重试和 Agent Tool Retry 重复新增商品。

# 18. 判断算法

## 18.1 CanEditSaleDraft

~~~text
if user unavailable:
    reject

if membership unavailable:
    reject

if merchant != draft.merchant:
    reject

if merchant.status != ACTIVE:
    reject

if role == OWNER:
    allow

if role == STAFF and has sale-edit capability:
    allow

otherwise:
    reject
~~~

## 18.2 AddProduct

~~~text
load ACTIVE Draft
check expected revision
authorize actor
load Product within same Merchant
check Product eligible for sale

key = LineIdentityKey(product, current unit/price context)

if existing line with same key:
    merge according to quantity policy
else:
    append new line

revision += 1
commit atomically
return latest Draft
~~~

02 子模块完成前，quantity policy 仍是接口，不在此处偷偷实现整数 +1 的永久规则。

# 19. 性能与索引原则

正式 Schema 后续再定，但实现时至少考虑以下查询路径：

- Merchant + Draft Status + Created By 查询未完成草稿；
- draft_id + merchant_id 精确读取；
- Product 按 Merchant + 状态 + 名称 / 编码 / 条码搜索；
- SaleLine 按 draft_id 排序读取；
- 幂等键按 Merchant + Actor + Command + Key 唯一查询。

条码搜索的唯一性规则属于商品模块，不在销售模块私自定义。

SaleDraft 不应无限累积；长期未完成 Draft 的清理策略进入配置与运维设计。

# 20. 失败语义

建议使用稳定业务错误，而不是把所有失败都映射成 500：

| 场景 | 语义 |
|---|---|
| Merchant 非 ACTIVE | MERCHANT_NOT_WRITABLE |
| STAFF 无销售能力 | SALE_PERMISSION_DENIED |
| Draft 不存在 / 跨 Merchant | SALE_DRAFT_NOT_FOUND |
| Draft 已取消 / 已消费 | SALE_DRAFT_NOT_EDITABLE |
| revision 冲突 | SALE_DRAFT_VERSION_CONFLICT |
| Product 不存在 / 跨 Merchant | PRODUCT_NOT_FOUND |
| Product 已停用 | PRODUCT_NOT_SALEABLE |
| 幂等请求已成功 | 返回原成功结果 |
| 数据库事务失败 | 本次命令失败，Draft 保持原状态 |

错误 code 最终命名可在 API 设计阶段统一规范，但业务语义必须保留。

# 21. 边界测试矩阵

| 场景 | 预期 |
|---|---|
| OWNER 在 ACTIVE Merchant 创建 Draft | 允许 |
| STAFF 有销售能力创建 Draft | 允许 |
| STAFF 无销售能力创建 Draft | 拒绝 |
| FROZEN Merchant 从旧页面继续加商品 | 拒绝写入 |
| CLOSED Merchant 创建 Draft | 拒绝 |
| 加入本 Merchant 正常商品 | 允许 |
| 加入其他 Merchant 商品 ID | 拒绝 |
| 加入已停用商品 | 拒绝 |
| 商品加入后再被停用 | Draft 可保留，完成时必须重新校验 |
| 同一商品重复扫码 | 命中 LineIdentityKey；不产生无法解释的完全重复行 |
| 删除最后一行 | Draft 可为空，但不能完成 |
| 两设备同 revision 修改 | 只有一个 CAS 成功，另一方冲突 |
| AddProduct 响应丢失后同 key 重试 | 返回原结果，不重复 |
| 用户取消 Draft | 进入 CANCELLED，不产生库存 / 金额影响 |
| Agent 创建 Draft | 继承当前用户权限 |
| SYSTEM_ADMIN 通过普通商户入口代创建销售 | 不作为标准流程 |

# 22. 本轮已冻结 / 继承冻结

以下可以直接作为 Coding Agent 的业务不变量：

1. 销售创建阶段与正式完成阶段分离；
2. 草稿阶段不产生正式库存、收款、欠款经营副作用；
3. OWNER 可在本 Merchant 正常经营状态下创建销售；
4. STAFF 必须有销售业务授权；
5. Merchant FROZEN / CLOSED 禁止销售写入；
6. Agent 只能复用正常销售 Application Service；
7. 商品必须属于同一 Merchant；
8. 当前禁止销售的商品不能新加入 Draft；
9. 完成销售时必须重新校验商品有效性；
10. 不允许无业务差异的完全重复商品行；
11. Draft 写入使用 revision 乐观并发控制；
12. 写命令必须支持幂等；
13. 删除 Draft 行不产生库存或资金冲销；
14. Complete Sale 成功前不允许出现“部分正式业务事实已生效”的半完成销售。

建议：

- STAFF 默认只自动恢复自己创建的 Draft；

不建议 Merchant 内所有 STAFF 默认互相编辑草稿。

~~~mermaid
flowchart TD

    A --> C[恢复与权限变化]
    A --> D[商品搜索 / 扫码解析]
    A --> E[商品状态变化]
~~~

**流程说明：**

1. **业务歧义风险**：例如多个未完成 Draft、扫码多个商品、商品在草稿期间发生变化；
2. **一致性风险**：例如重复网络请求、权限撤回、取消与完成同时发生、客户端离线后以为本地修改已经保存。

后续 Coding Agent 必须以这些流程为边界，不允许用“最后写入覆盖”“扫码随便选第一条”“后台删旧 ACTIVE Draft”等方式自行补语义。

# 25. 进入卖货入口：查询、恢复、新建必须分离

~~~mermaid
flowchart TD
    A[打开卖货入口] --> B[只读查询可恢复 Draft]
    B --> C{是否有可见 ACTIVE Draft}
    C -->|没有| D[显示新建销售]
    C -->|有一条| E[显示继续 / 新建]
    C -->|有多条| F[显示草稿列表 / 新建]

    D --> G{用户是否明确开始新销售?}
    E --> H{用户选择}
    F --> I{用户选择}

    G -->|否| J[不创建持久 Draft]
    G -->|是| K[CreateSaleDraft]
    H -->|继续| L[LoadLatestDraft]
    H -->|新建| K
    I -->|继续某条| L
    I -->|新建| K
~~~

**流程说明：**

- 第一轮文档中的“创建或恢复销售草稿”容易被实现成“只要打开卖货页面就 INSERT 一条空 Draft”，这会产生大量无意义空草稿。
- 本轮明确把入口拆成 ListResumableDrafts / CreateSaleDraft / LoadDraft 三种语义：查询不产生写副作用。
- 是否允许多个 ACTIVE Draft 是产品策略，不应该通过数据库偶然行为决定；见 S-04。
- 如果最终确认只允许一个 ACTIVE Draft，流程仍成立，只是“多条”分支不会出现在正常数据中。

# 26. 恢复旧草稿时重新判断权限与 Merchant 状态

~~~mermaid
flowchart TD
    A[用户选择恢复 Draft] --> B[按可信 Merchant Context 加载 Draft]
    B --> C{Draft 存在且属于当前 Merchant?}
    C -->|否| X[按 NOT FOUND 处理并记录异常访问]
    C -->|是| D[读取服务端最新 revision]

    D --> E[重新检查 User / Membership / Merchant / 销售权限]
    E --> F{当前可编辑?}
    F -->|是| G[返回最新可编辑 Draft]
    F -->|否，但有销售查询权限| H[只读展示，不允许写]
    F -->|否且无查询权限| I[拒绝访问]

    G --> J{草稿中是否存在失效商品行?}
    J -->|否| K[正常编辑]
    J -->|是| L[标记问题行并要求处理后才能完成]
~~~

**流程说明：**

- Draft 创建时的 OWNER / STAFF 身份不是永久授权快照。用户角色、Membership、Merchant 状态、业务权限都可能在草稿存续期间变化。
- OWNER 交接、STAFF 权限被撤回、Merchant 进入 FROZEN / CLOSED 后，旧 Draft 不应被自动删除；但新的写操作必须按当前状态重新判定。
- 如果后续权限恢复且 Draft 仍为 ACTIVE，可以重新按当前规则判断是否允许继续。
- 跨 Merchant 的 draft_id 不返回“你没有权限访问某商户 Draft”的可枚举信息，业务层按 NOT FOUND / 不可见处理，并可记录 Security Event。

# 27. 商品搜索与扫码：0、1、多匹配必须有明确分支

~~~mermaid
flowchart TD
    A[搜索 / 扫码 / 输入编码] --> B[限定当前 Merchant 查询销售可选商品]
    B --> C{候选结果数量}

    C -->|0| D[不加入 Draft]
    D --> E{用户是否有商品新增能力?}
    E -->|否| F[提示未找到商品]
    E -->|是| G[可跳转到正式商品创建流程]

    C -->|1| H[得到明确 product_id]
    C -->|多条| I[展示候选，让用户明确选择]
    I --> J{用户是否选择一条?}
    J -->|否| K[保持 Draft 不变]
    J -->|是| H

    H --> L[AddProductToSaleDraft]
~~~

**流程说明：**

- 搜索和扫码不能因为入口不同而走两套业务规则。
- 扫码得到多条候选时禁止“默认取第一条”，否则商品条码重复、历史脏数据或未来多包装规则会产生错误销售。
- 未找到商品时不会偷偷创建临时自由文本行。若用户有“新增商品”能力，可以进入正式 Product 创建流程；创建成功后再显式回到销售草稿添加。
- “新增商品”属于商品模块 Application Service，不由 Sales Service 直接 INSERT Product。
- S-02 仍决定 v1 是否完全禁止临时商品；在其确认前，任何实现都不能用 product_id = NULL 绕开商品主数据。

# 28. 销售商品选择器的数据范围必须最小化

~~~mermaid
flowchart TD
    A[销售用户搜索商品] --> B[Sales Product Projection]
    B --> C[商品名称 / 编码 / 条码]
    B --> D[销售所需单位信息]
    B --> E[默认销售价等销售字段]
    B --> F{字段是否属于销售流程必需?}

    F -->|是| G[按当前权限返回]
~~~

**流程说明：**

- “有卖货权限”意味着用户必须能够完成销售场景中的商品选择，但不等于自动获得商品管理、采购成本或利润查看权限。
- 销售商品搜索应该使用销售场景专用的 Read Model / Projection，只暴露完成卖货所需字段。

# 29. 搜索结果到真正加入 Draft 之间必须重新校验

~~~mermaid
flowchart TD
    A[客户端拿到商品搜索结果] --> B[用户稍后点击加入]
    B --> C[提交 product_id + draft_id + expected_revision]
    C --> D[服务端重新加载 Product 当前状态]
    D --> E{仍属于当前 Merchant?}
    E -->|否| X[拒绝 PRODUCT_NOT_FOUND]
    E -->|是| F{当前仍可用于销售?}
    F -->|否| Y[拒绝 PRODUCT_NOT_SALEABLE]
    F -->|是| G[校验 Draft ACTIVE / 权限 / revision]
    G --> H{全部通过?}
    H -->|否| Z[拒绝，Draft 不变化]
    H -->|是| I[执行商品行新增 / 合并]
~~~

**流程说明：**

- 搜索结果是读模型快照，不是写入授权。
- 商品可能在“搜索完成 → 用户点击加入”这几秒或几分钟内被停用、合并、修改或发生异常数据修复，因此 AddProduct 必须重新读取当前 Product。
- 客户端不能把搜索结果里的 saleable=true 当成服务端写入凭证。
- 同理，Merchant 状态和 STAFF 权限也必须在写事务中重新确认，防止 TOCTOU（检查时允许、执行时已不允许）。

# 30. 重复扫码必须区分“真实业务意图”与“技术重复请求”

~~~mermaid
flowchart TD
    A[收到一次 AddProduct 请求] --> B{幂等键是否已存在?}
    B -->|是| C{请求指纹是否相同?}
    C -->|是| D[返回原业务结果，不再次修改 Draft]
    C -->|否| E[拒绝 IDEMPOTENCY_KEY_REUSED]

    B -->|否| F[这是新的业务意图]
    F --> G{同商品是否已有候选行?}
    G -->|否| H[创建新行]
    G -->|是| I[交给 LineGrouping / Quantity Policy]
    I --> J[合并数量或按业务差异拆行]
    H --> K[revision + 1]
    J --> K
~~~

**流程说明：**

- **网络重试**与**用户真的又扫了一次商品**不是同一件事。
- 同一用户意图因为超时重发时，应复用同一个 idempotency_key，系统返回第一次成功结果。
- 用户确实再次扫码，应产生新的 idempotency_key，代表新的业务意图；随后由 02 子模块的数量 / 行分组规则决定是数量增加还是拆成新行。
- 同一个 idempotency_key 如果携带了不同 payload，不能静默返回第一次结果，否则客户端 bug 可能把完全不同的操作误判成功。
- 这一流程也解决扫码枪 / 手机相机回调重复与 HTTP Retry 混在一起的问题。

# 31. 商品加入草稿后发生变化：不静默删除、不静默替换

~~~mermaid
flowchart TD
    A[商品已经在 ACTIVE Draft 中] --> B[商品主数据发生变化]
    B --> C{变化类型}

    C -->|名称等展示字段变化| D[恢复 Draft 时重新解析当前展示信息]
    C -->|停售 / 停用| E[标记该行当前不可完成]
    C -->|商品无法解析 / 被合并 / 异常删除| F[保留草稿行痕迹并标记无效]
    C -->|单位 / 价格相关定义变化| G[交给 02 子模块判断是否需要重新确认]

    D --> H[继续编辑]
    E --> I[用户删除 / 替换问题行后才能完成]
    F --> I
    G --> J[按最新规则重新校验]
~~~

**流程说明：**

- Draft 是未完成业务意图，因此可以重新读取当前 Product 状态；但系统不能在后台把用户已经选过的商品行直接删掉。
- 如果 Product 失效，Draft 行需要可见地进入“需要处理”的状态，最终 Complete Sale 必须拒绝，直到用户删除或明确替换。
- 系统也不能因为商品被“合并到另一个 Product”就静默改写草稿里的 product_id；替换必须是显式业务动作，否则用户无法知道自己原来选的商品被改成了什么。
- 最终正式销售需要怎样保存不可变商品快照，由 02 / 06 / 10 继续收口。

# 32. 多端与 Agent 同时编辑：读取可以并行，写入必须 CAS

~~~mermaid
flowchart TD
    A[设备 A / 设备 B / Agent 都读取 revision=8] --> B1[设备 A 提交修改]
    A --> B2[设备 B 提交修改]
    A --> B3[Agent 提交修改]

    B1 --> C{第一个 CAS 命中 revision=8}
    B2 --> C
    B3 --> C

    C -->|成功者| D[保存修改并变成 revision=9]
    C -->|其余请求| E[CAS 失败]
    E --> F[返回 VERSION_CONFLICT]
    F --> G[重新读取 revision=9]
    G --> H[重新向用户 / Agent 展示最新 Draft]
    H --> I[用户重新决定是否提交]
~~~

**流程说明：**

- 不做字段级“聪明自动合并”作为默认行为，因为销售行、数量、价格之间存在业务关联，自动合并可能把两个不同意图拼成错误账单。
- Agent 与人工编辑的并发地位相同：Agent 不能因为是系统能力就绕过 revision。
- 冲突后必须重新基于最新 Draft 形成新的用户意图，再提交新的 idempotency_key。
- 以后如果某些字段证明可以安全做细粒度 merge，可以在对应子模块显式设计，不在这里默认开启。

# 33. 取消、完成、编辑同时发生：只能有一个合法状态变化

~~~mermaid
flowchart TD
    A[ACTIVE Draft revision=N] --> B1[编辑命令]
    A --> B2[CancelSaleDraft]
    A --> B3[CompleteSale]

    B1 --> C[CAS: status=ACTIVE 且 revision=N]
    B2 --> C
    B3 --> C

    C --> D{谁先成功提交?}
    D -->|编辑成功| E[revision=N+1, status 仍 ACTIVE]
    D -->|取消成功| F[status=CANCELLED]
    D -->|完成成功| G[status=CONSUMED / 正式销售建立]

    E --> H[其他旧 revision 请求全部冲突]
    F --> I[后续编辑 / 完成全部拒绝]
    G --> J[后续编辑 / 取消全部拒绝]
~~~

**流程说明：**

- Cancel、Complete、普通编辑都必须以 Draft 当前状态和 revision 为前置条件。
- 不能出现“销售已经完成，但稍后又收到取消请求把 Draft 改成 CANCELLED”的状态回退。
- 也不能出现“取消成功后晚到的 AddProduct 又把草稿复活”。
- 最终由数据库 CAS / 条件更新保证只有一个合法迁移生效，客户端提示只是体验层，不是正确性的唯一保障。

# 34. Session 过期、断网、闪退：以服务端已提交 revision 为唯一事实

~~~mermaid
flowchart TD
    A[用户编辑 Draft] --> B[客户端发送写命令]
    B --> C{服务端是否提交成功?}

    C -->|成功且客户端收到响应| D[客户端采用新 revision]
    C -->|成功但响应丢失| E[客户端保持同一 idempotency_key 重试]
    E --> F[服务端返回原成功结果]

    C -->|未提交 / 网络失败| G[服务端 Draft 不变化]
    G --> H[客户端标记未保存，不得假装成功]

    B --> I{Session 是否已失效?}
    I -->|是| J[返回认证失败]
    J --> K[用户重新登录]
    K --> L[重新读取服务端最新 Draft]
~~~

**流程说明：**

- v1 不把离线本地修改视为权威业务事实。客户端可以做 UI 缓存，但只有服务端事务成功后的 revision 才表示已保存。
- 请求超时不能简单生成一个新 idempotency_key 再提交，否则可能把一次业务意图执行两次。
- Session 失效不会删除 Draft；重新认证后，用户按当前权限重新读取。
- 如果未来要支持真正的离线销售，需要独立设计离线 Command Log、冲突解决和重新同步，不能由当前 Draft 模型顺手承担。

# 35. 幂等判定顺序必须先于版本冲突判定

~~~mermaid
flowchart TD
    A[收到写命令] --> B[计算 idempotency scope + request fingerprint]
    B --> C{是否已有幂等记录?}

    C -->|有，相同 fingerprint| D[直接返回第一次完成结果]
    C -->|有，不同 fingerprint| E[拒绝 key 重用]
    C -->|没有| F[加载 Draft 当前状态]

    F --> G{expected_revision 是否匹配?}
    G -->|否| H[VERSION_CONFLICT]
    G -->|是| I[执行 Domain Command]
    I --> J[同事务保存 Draft + 幂等结果]
    J --> K[提交]
~~~

**流程说明：**

- 如果第一次 AddProduct 已经成功但响应丢失，随后 Draft 又被别的设备改到更高 revision，原请求重试仍应返回“第一次已成功”的结果，而不是因为当前 revision 不同误报冲突。
- 因此幂等命中必须在正常业务版本检查前识别。
- “Draft 修改 + 幂等成功结果”需要保持一致，不能 Draft 提交了但幂等记录没写，导致下一次重试重复执行。
- 具体表结构和幂等记录保留周期留到 Schema / API 阶段，但行为顺序在业务设计阶段先固定。

# 36. ACTIVE Draft 的过期不能由后台任务擅自决定

~~~mermaid
flowchart TD
    A[后台清理任务扫描 Draft] --> B{Draft 状态}

    B -->|CANCELLED / CONSUMED| C[按终态保留策略处理]
    B -->|ACTIVE| D{产品是否已经确认 S-05?}

    D -->|否| E[跳过，不自动删除]
    D -->|是：支持过期| F[先按定义执行显式过期状态迁移]
    F --> G[用户后续进入时看到明确过期结果]
~~~

**流程说明：**

- ACTIVE Draft 是用户尚未完成的经营意图，静默物理删除会产生真实的工作丢失。
- 如果未来确实需要“30 天未编辑自动过期”，必须先定义：过期状态、能否恢复、谁能恢复、过期提示、Agent 如何处理、是否可以复制成新 Draft。
- 在这些语义确认前，只允许清理终态 Draft，不允许清理 ACTIVE。
- 本项新增为 S-05。

# 37. 大草稿与异常扫描需要技术保护，但不把技术阈值伪装成产品规则

~~~mermaid
flowchart TD
    A[持续向 Draft 加商品] --> B[检查当前商品行数量 / 请求频率]
    B --> C{是否触发技术安全阈值?}
    C -->|否| D[继续正常业务校验]
    C -->|是| E[拒绝本次新增并提示拆分 / 稍后重试]
    E --> F[记录异常指标]
    D --> G[正常保存]
~~~

**流程说明：**

- 需要防止脚本错误、扫码设备抖动或异常客户端把单个 Draft 扩大到不可控规模。
- max_draft_lines、搜索分页、扫码请求频率等属于技术 / 配置阈值，不应被写成“业务上一张销售永远最多 100 行”之类未经确认的产品规则。
- 如果真实商户存在超大批发单，需要通过压测和运营数据确定阈值。
- 达到技术阈值时不能部分写入或悄悄丢行。

# 38. 第二轮审查后的规则状态

~~~mermaid
flowchart TD
    A[第二轮审查结果] --> B[可直接作为一致性不变量]
    A --> C[仍需产品确认]

    B --> B1[入口查询与 Create Draft 分离]
    B --> B2[恢复时重新授权并读取最新 revision]
    B --> B3[扫码多匹配不得自动选第一条]
    B --> B4[写入前重新校验 Product / Merchant / Permission]
    B --> B5[失效商品行不得静默删除或替换]
    B --> B6[幂等命中先于 revision 冲突判断]
    B --> B7[Cancel / Complete / Edit 使用状态 + revision CAS]
    B --> B8[服务端已提交 revision 才是保存事实]
    B --> B9[销售选择器不得无授权泄露成本等敏感字段]

    C --> C1[S-01 服务端可恢复 SaleDraft]
    C --> C2[S-02 v1 是否禁止临时商品]
    C --> C3[S-03 他人 Draft 查看 / 接管范围]
    C --> C4[S-04 是否允许同一用户多条 ACTIVE Draft]
    C --> C5[S-05 ACTIVE Draft 是否存在自动过期]
~~~

**流程说明：**

- B 组规则主要是已有权限、幂等、并发和数据隔离原则在销售 Draft 上的具体落地，不需要重新发散。
- C 组是会影响真实产品体验或生命周期的语义，因此继续作为显式待确认项，不由 Coding Agent 选择。
- S-04 推荐允许同一用户存在多条 ACTIVE Draft，并在入口显式选择，以避免人工与 Agent、多个待处理客户之间互相覆盖；若产品更偏向极简模式，也可以确认“每用户只允许一条”。
- S-05 当前推荐 v1 不自动过期 ACTIVE Draft；如果后续运营数据表明长期垃圾 Draft 过多，再引入显式 EXPIRED 生命周期。
