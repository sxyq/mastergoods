# 1. 设计目标

回答：

```text
OWNER 怎样进入系统？
STAFF 怎样进入系统？
邀请码如何限制一个店的 OWNER / STAFF？
已有账号再次使用邀请码怎么办？
注册的事务一致性边界在哪里？
```

核心规则（已冻结）：

```text
SYSTEM_ADMIN 创建 MerchantInvitation，OWNER 使用未绑定的邀请码注册并创建 Merchant；
STAFF 使用 OWNER 所属 MerchantInvitation 注册，后端只在 STAFF 完成注册时创建 User 和 Membership。
```

一个邀请码包含两个配额：

```text
OWNER 可注册数量：当前主规则 = 1
STAFF 可注册数量：N，由 SYSTEM_ADMIN 配置
```

> 来源：对话第 32、35、36 轮

# 2. Merchant 注册资格与邀请码凭据分离

第 42 轮把共享注册资格与用户实际输入的邀请码拆开：

```text
MerchantRegistrationGrant = OWNER / STAFF 共享累计配额
InvitationCredential      = 某一串实际邀请码
```

一个 Grant 可以拥有多个 InvitationCredential；所有邀请码共享：

```text
owner_limit = 1
owner_used
staff_limit = N
staff_used = 累计成功注册 STAFF 数
```

STAFF 停用 / 离职不返还 `staff_used`。

## 2.1 刷新与新建

`RotateInvitationCredential`：刷新某邀请码，旧 code 立即失效，Grant / Merchant / 配额不变。

`CreateAdditionalInvitationCredential`：创建额外邀请码，原邀请码继续存在；新旧邀请码可同时有效，但共享同一 Grant 配额。

# 3. SYSTEM_ADMIN 邀请管理

SYSTEM_ADMIN 可创建初始 Grant、刷新邀请码、新建额外邀请码，并查看：Credential 状态、创建 / 刷新历史、绑定 Merchant、OWNER 使用、STAFF 累计使用和剩余额度。所有动作必须 Audit。

# 4. OWNER 先注册并创建 Merchant

当前基线：

```text
邀请码
→ OWNER 先注册
→ 创建 Merchant
→ 邀请码绑定 Merchant
→ STAFF 再使用同一邀请码加入
```

主流程时序：

```mermaid
sequenceDiagram
    actor O as OWNER
    participant C as Client
    participant INV as Invitation Service
    participant IAM as IAM Service
    participant M as Merchant Service
    participant DB as PostgreSQL

    O->>C: 使用邀请码注册
    C->>INV: Validate OWNER Invitation
    INV->>DB: 检查 OWNER 配额

    alt OWNER 配额已用完
        INV-->>C: 拒绝
    else 可用
        INV-->>IAM: Allowed
        IAM->>DB: BEGIN
        IAM->>DB: 创建 User
        IAM->>M: 创建 Merchant
        M->>DB: 创建 OWNER Membership
        INV->>DB: owner_used + 1
        INV->>DB: Invitation 绑定 Merchant
        IAM->>DB: COMMIT
        IAM-->>C: 注册成功
    end
```

系统原则：

```text
OWNER 注册
=
User + Merchant + OWNER Membership
```

三个必须一次事务成功。不能出现：

```text
有账号
但是没有 Merchant
```

这种脏状态。

关键约束：

- STAFF 必须等 OWNER 建店后才能注册（已冻结）；
- OWNER 不直接创建 STAFF User；OWNER 只负责提供已绑定的 MerchantInvitation，及注册后的员工管理、权限、停用和密码重置；
- STAFF 自己使用 MerchantInvitation 完成注册，注册事务内创建 User、STAFF Membership 并消耗配额。

# 6. 注册的事务一致性

"STAFF 单店判断"和"邀请码配额消耗"必须处在一个事务一致性边界，不能出现：

```text
STAFF 注册失败
但 staff_used 已经 +1
```

STAFF 注册最终判定（第 39 轮）：

```mermaid
sequenceDiagram
    participant REG as Registration
    participant INV as Invitation
    participant DB as PostgreSQL

    REG->>INV: 邀请码有效?
    INV-->>REG: Yes

    REG->>DB: STAFF 配额还有?
    DB-->>REG: Yes

    REG->>DB: 此 User 已经属于别的 Merchant 当 STAFF?

    alt Yes
        DB-->>REG: Reject
    else No
        REG->>DB: 同一事务创建 Membership + 消耗配额
    end
```

**图示说明（6. 注册的事务一致性）：** 这是服务调用时序图，参与者包括 Registration、Invitation、PostgreSQL。箭头表示一次调用或返回，alt/else 分支表示 Decision 的不同结果；事务提交前只做校验和状态准备，短信、邮件等外部副作用应在提交后通过 Outbox 执行。

配额消耗使用原子条件更新（禁止先 SELECT 再 UPDATE，防止并发超卖）：

```text
UPDATE invitations
SET staff_used = staff_used + 1
WHERE id = :id
  AND status = 'ACTIVE_BOUND'
  AND staff_used < staff_limit
RETURNING staff_used;
```

Membership 创建与配额消耗同事务。

> 来源：对话第 38、39 轮

# 7. 已有账号再次输入邀请码（关键边界）

当前规则要求一个 User 只能有一个有效 Merchant Membership。已有账号再次输入邀请码时，必须先证明本人身份，并在已经存在有效 Membership 时拒绝创建第二个 Membership：

```text
手机号 / 邮箱 / 登录账号已经存在
```

这时候不能创建重复 User，也不能仅凭邀请码就自动把别人账号加入新 Merchant。

```mermaid
sequenceDiagram
    actor U as Existing User
    participant INV as Invitation
    participant IAM as Identity
    participant DB as PostgreSQL

    U->>INV: 输入新邀请码
    INV-->>IAM: Merchant Admission

    IAM->>DB: 查询 Login Identifier
    DB-->>IAM: User 已存在

    IAM-->>U: 请先验证现有账号
    U->>IAM: 登录 / 验证身份

    IAM->>DB: 检查该 Merchant Membership

    alt 已有有效 Membership
        IAM-->>U: 拒绝创建第二个 Membership
    else 没有有效 Membership
        IAM->>DB: 创建唯一 STAFF Membership
        IAM-->>U: 完成注册
    end
```

**图示说明（7. 已有账号再次输入邀请码（关键边界））：** 这是服务调用时序图，参与者包括 Existing User、Invitation、Identity、PostgreSQL。箭头表示一次调用或返回，alt/else 分支表示 Decision 的不同结果；事务提交前只做校验和状态准备，短信、邮件等外部副作用应在提交后通过 Outbox 执行。

这能避免“知道某人的手机号 + 拿到邀请码”就把别人的账号直接挂进商户；已有有效 Membership 的 User 必须走店长交接或其他明确的业务流程，不能通过再次注册增加第二个 Merchant Membership。

> 来源：对话第 35、36 轮

# 8. STAFF 单店约束（已冻结收紧）

对话第 39 轮按用户要求收紧：

```text
一个 STAFF 账号
→ 只能对应一个 Merchant
```

```mermaid

    actor S as STAFF
    participant IAM as Membership Policy
    participant DB as PostgreSQL

    S->>IAM: 使用 STAFF MerchantInvitation
    IAM->>DB: 是否已有 ACTIVE STAFF Membership?

    alt 已有有效 STAFF Membership
        IAM-->>S: 拒绝创建第二个 Membership
    else 没有有效 STAFF Membership
        IAM-->>S: 可以继续注册
    end
```

**图示说明（8. STAFF 单店约束（已冻结收紧））：** 这是服务调用时序图，参与者包括 STAFF、Membership Policy、PostgreSQL。箭头表示一次调用或返回，alt/else 分支表示 Decision 的不同结果；事务提交前只做校验和状态准备，短信、邮件等外部副作用应在提交后通过 Outbox 执行。

不过 `User` 和 `Membership` 仍然保持分离（领域设计价值保留），只是增加强约束：

```text

```

# 9. Invitation Credential 生命周期与 Grant 可用性

配额耗尽不再作为 Credential 生命周期状态，由共享 Grant 计数派生。

Credential：

```text
CREATED
ACTIVE
DISABLED
EXPIRED
ROTATED
```

Grant 可用性由 `InvitationAvailabilityPolicy` 计算：

```text
OWNER_AVAILABLE / STAFF_AVAILABLE
OWNER_QUOTA_EXHAUSTED / STAFF_QUOTA_EXHAUSTED
MERCHANT_NOT_BOUND / MERCHANT_NOT_WRITABLE
```

SYSTEM_ADMIN 增加 staff_limit 后无需修改 Credential 状态，避免状态与计数漂移。

# 10. 注册决策（封口设计方向）

第 41 轮确定注册准入 Decision 的输入输出：

```text
输入：
Invitation
Role
User
Identifier
Merchant
Quota

输出：
RegistrationDecision
```

最终系统只认：

```text
ALLOW
或
DENY_INVITATION_INVALID
DENY_OWNER_ALREADY_EXISTS
DENY_STAFF_QUOTA_FULL
DENY_STAFF_ALREADY_HAS_MERCHANT
DENY_IDENTIFIER_CONFLICT
...
```

对应核心算法（第 36、39 轮综合）：

```text
InvitationValid
AND RoleQuotaAvailable
AND IdentifierOwnershipValid
AND StaffHasNoMerchant
AND MerchantStateAllowsRegistration
→ ALLOW
```

注册准入决策系统（08-01）完整时序（第 40 轮）：

```mermaid
sequenceDiagram
    actor U as User
    participant REG as Registration Service
    participant POLICY as Registration Policy
    participant INV as Invitation
    participant ID as Identity
    participant DB as PostgreSQL

    U->>REG: Register Command
    REG->>POLICY: Evaluate Registration

    POLICY->>INV: Check Invitation
    POLICY->>ID: Check Identifier
    POLICY->>DB: Check Merchant / STAFF Constraint

    POLICY-->>REG: Allow / Reject + Reason

    alt Reject
        REG-->>U: Registration Rejected
    else Allow
        REG->>DB: Atomic Registration Transaction
        REG-->>U: Registration Complete
    end
```

# 11. 注册风险与边界

注册相关风险信号（Risk Engine）：

```text
高频猜邀请码
同邀请码大量失败注册
STAFF 配额耗尽后继续大量尝试
已有账号反复绕过身份确认
```

边界条件（第 38 轮）：

```text
已有 User + 新邀请码必须重新证明本人身份
Merchant 被关闭后邀请码禁止新增
同一 User + Merchant 不允许重复 Membership
STAFF 配额不能超卖
```

> 来源：对话第 38 轮

# 12. 已冻结规则汇总

1. SYSTEM_ADMIN 创建 MerchantInvitation；OWNER 使用未绑定邀请码注册并创建 Merchant；STAFF 使用已绑定 MerchantInvitation 注册；
2. 一个邀请码 OWNER 固定最多 1；
3. STAFF 上限 N，由 SYSTEM_ADMIN 设置；
4. STAFF 必须等 OWNER 建店后才能注册；
5. OWNER 注册 = User + Merchant + OWNER Membership（同一事务）；
6. 邀请码承担：注册资格 + 角色配额 + Merchant 归属；
7. 邀请码绑定 Merchant 后（ACTIVE_BOUND）STAFF 仍可继续注册；
8. 已有账号再次使用邀请码：必须验证本人身份，不重复创建 User；
9. 一个 STAFF User 生命周期只绑定一个 Merchant；Membership 停用后也不能加入其他 Merchant；
10. 一个 OWNER User 生命周期只绑定一个 Merchant；
11. 配额消耗与 Membership 创建必须同事务，不能超卖；STAFF 停用 / 离职不返还累计注册配额。

# 14. 第 42 轮新增注册边界

1. Merchant-side User 不允许历史换店。
2. 一个 Registration Grant 可以有多个 Invitation Credential；新建 Credential 不改变总配额。
3. Rotate 会让被刷新的旧 code 立即失效，不影响同 Grant 的其他邀请码。
4. STAFF 配额是累计成功注册人数，只增不减。
5. 邀请码创建、刷新、停用、过期和使用必须可查询并写 Audit。
