## 二、四级目录规则

项目采用下面的通用层级：

| 层级 | 作用 | 当前示例 |
|---|---|---|
| 一级 | 资产类别或运行边界 | `Code/`、`data/`、`docs/`、`testing/`、`tmp/` |
| 二级 | 平台、工程或生命周期 | `Code/backend/`、`Code/frontend/android/`、`testing/Agent/` |
| 三级 | 技术层、模块或测试类型 | `api/`、`application/`、`domain/`、`feature/`、`功能测试/` |
| 四级 | 具体业务责任 | `product/`、`agent/conversation/`、`sales/`、`result-block/` |

四级表示“这段代码或这组测试解决哪项业务问题”。构建系统要求的目录继续保留，例如 `src/main/java/`、`src/test/`、Android 模块的 `src/main/`、Xcode 工程文件和 Vue 的 `src/`；它们负责让工程可构建，不替代业务分类。

### 后端四级业务索引

后端的三级技术层不强行改成业务目录；业务域通过同名的 Controller、DTO、Service、Entity、Repository 组来定位。已经存在的物理业务目录直接使用，尚未拆分的业务先按下表检索，避免为了目录好看破坏 package、Spring 扫描或迁移路径。

| 四级业务域 | Controller / DTO | Service | Entity | Repository / 基础设施 |
|---|---|---|---|---|
| `auth` 认证与租户 | `api/controller/v2/`、`api/dto/v2/auth/` | `application/service/`、`CurrentOwnerService` | `UserEntity`、`SessionEntity`、`UserCreditEntity` | `UserRepository`、`SessionRepository`、`infrastructure/security/` |
| `store` 门店与成员 | `V2StoreController`、`api/dto/v2/store/` | `V2StoreService` | `StoreEntity`、`StoreMembershipEntity` | Store 相关 Repository |
| `product` 商品目录 | `api/controller/v2/product/`、`api/dto/v2/product/` | `application/service/v2/product/` | `domain/entity/product/` | `infrastructure/repository/product/` |
| `partner` 客户与供应商 | `api/dto/v2/partner/`、客户/供应商 Controller | `V2CustomerService`、`V2SupplierService`、Partner Service | `CustomerEntity`、`SupplierEntity`、联系人和分组实体 | 客户、供应商和 Partner Repository |
| `sales` 销售与收款 | `api/dto/v2/sales/`、Pay DTO | Sale Order、Sales Return、Pay Order Service | 销售单、销售退货、支付实体 | 销售、退货和支付 Repository |
| `purchase` 采购与入库 | `api/dto/v2/purchase/` | Purchase Order、Receipt、Return Service | 采购单、收货、采购退货实体 | 采购和收货 Repository |
| `inventory` 库存 | `api/dto/v2/inventory/`、Inventory Controller | `V2InventoryService` | 调整、流水、快照和月统计实体 | `Inventory*Repository` |
| `finance` 财务与资金 | `api/dto/v2/finance/` | Account、Transfer、Cash、Finance Service | Account、Transfer、Cash、Finance、Credit 实体 | 账户、资金和财务 Repository |
| `agent` 对话与任务 | `api/dto/v2/agent/`、`V2AgentController` | `application/service/v2/agent/`、`V2AgentAiService` | Conversation、Message、Draft、Run Audit、Task、Notification | Agent Repository、`infrastructure/ai/`、工具组件 |
| `media-sync` 媒体、海报、导入与同步 | `api/dto/v2/media/`、poster、sync、Import Controller | Media、Poster、ImportJob、Sync Service | Media、Poster、ImportJob、Sync 实体 | `infrastructure/storage/`、媒体和同步 Repository |

## 八、按需求查找目录

| 需求 | 先看哪里 | 业务目录 |
|---|---|---|
| 修改后端接口 | `Code/backend/src/main/java/.../api/` | 对应 `auth`、`product`、`sales`、`agent` 等业务域 |
| 修改后端规则 | `Code/backend/src/main/java/.../application/service/` | 对应业务域 Service |
| 修改数据库实体或查询 | `domain/entity/`、`infrastructure/repository/` | 对应实体和 Repository |
| 修改数据库结构 | `Code/backend/src/main/resources/db/migration/` | 通过迁移文件名和业务说明定位 |
| 修改 Android 页面 | `Code/frontend/android/feature/` | `feature/<domain>/` |
| 修改 Android 网络或历史恢复 | `Code/frontend/android/data/`、`core/` | `agent`、`auth`、`sync` 等数据域 |
| 修改 Web 页面 | `Code/frontend/web/src/pages/`、`features/` | 页面业务子目录 |
| 修改 iOS 页面 | `Code/frontend/ios/ZhihuijiIOS/Features/` | 对应首字母大写业务目录 |
| 新增测试源码 | 所属工程的测试目录 | 与生产代码保持业务同名 |
| 新增测试计划或证据 | `testing/` | 主体 → 测试类型 → 业务域 |

## 九、目录整理的通用规则

1. 正式代码统一进入 `Code/`，按工程类型放入 `Code/backend/` 或 `Code/frontend/<platform>/`。
2. 代码内部先遵守技术栈构建约定，再在技术层下按业务域划分。
3. 共享能力放在 `core`、`shared`、`common` 或基础设施目录，不能复制到每个业务目录。
4. Agent 是业务域，不是独立的临时脚本；后端、Android、Web、iOS 和测试目录分别保留各自的 Agent 入口。
5. 测试源码与测试台账分离，运行证据与说明文件分离。
6. 构建缓存、依赖、APK、JAR、Web `dist` 和截图进入 `tmp/` 或 `testing/.artifacts/`，不放回 `Code/`。
7. 数据库、媒体、研究资料进入 `data/`，不与源码或测试证据混放。
8. 目录移动后先修正构建脚本、文档链接、测试脚本和 CI 入口，再执行构建验证。
9. 不为目录整齐改变 Java package、Flyway 扫描路径、Android module path、Xcode 工程引用或 Vite 资源路径。
10. 任何历史服务器资料都要单独标注历史属性，不能与当前运行目录混在一起。

这套规则可以直接迁移到其他 Gradle、Maven、npm、Python、Rust、CMake 或 Xcode 项目：把“工程类型”放到 `Code/` 下，把“业务域”放在技术层之后，把测试源码、测试证据、数据和生成物维持独立边界即可。
