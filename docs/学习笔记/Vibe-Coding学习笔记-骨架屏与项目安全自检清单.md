## 第一部分　骨架屏（Skeleton Screen）

### 1.1 一句话总结

> 骨架屏是**页面内容加载前的占位符**——用与最终内容相同结构、尺寸的灰色块先摆出"骨架"，等数据回来再原地替换。它不表示加载进度，只表示"内容正在路上"。

### 1.3 完整 AI 章节摘要

> 骨架屏是前端开发中的一种技术，用于在页面内容加载前显示占位符，以提高用户体验。骨架屏的设计应与最终内容的结构和尺寸相匹配，避免页面跳动。动效不表示完成进度，而是等待反馈。骨架屏适用于数据加载过程，但不适用于操作反馈和内容几乎同时出现的情况。

### 1.5 关键判断标准（视频核心观点）

| 应该用 | 不应该用 |
|---|---|
| 数据加载 > ~200–300ms | 操作反馈（按钮点击、删除确认等） |
| 内容结构相对固定（列表/详情/卡片） | 内容几乎同时出现（接口 < 100ms） |
| 期望用户**先看到结构** | 需要展示**加载百分比**的场景（用进度条） |

### 2.2 21 项完整清单

#### 01　先要一张「安全边界表」

- **核心**：后端安全不是开关，是请求进来要过的一道道关卡；先让 AI 把关卡摊开，别信"我做了安全处理"一句带过。
- **要点**：关卡包括登录状态、系统权限、输入校验、数据归属、注入……少一道就是一个口子；先有全景，再逐项深挖，你才不会被 AI 一句话糊弄过去。
- **对 AI 说**：请根据项目架构设计文档和当前业务功能，输出后端安全边界表。不要只说已做安全处理。请按接口输入、登录状态、系统权限设计、密码规则、数据归属、注入风险分别说明：风险是什么，当前在哪里处理，处理规则是什么，如何验证，哪些还没有验证。
- **你看什么**：每条防线有没有落到具体位置。这张表都说不清，就别急着问"能不能上线"。

#### 02　接口输入（前端传来的都默认不可信）

- **核心**：后端接口是公开的。真想钻空子的人用工具就能绕开整个前端，直接对着后端发请求。
- **要点**：你在页面上做的格式校验、按钮置灰、字段隐藏，对他们一点用没有；价格、数量、角色、用户 ID、订单归属这些影响结果的东西，**后端必须重新判断一遍**，不能前端传了就当真。
- **对 AI 说**：请审查当前后端接口的输入安全。不要只说已做参数校验。请按接口说明：哪些参数来自前端，哪些参数会影响身份、系统权限、金额、库存、数据归属或数据库写入；每个关键参数在哪里校验；校验失败返回什么；是否有示例请求证明。
- **你看什么**：它有没有把"关键输入"和"普通输入"分开。关键输入错了，就是越权、改错数据、金额或库存出错。

#### 03　登录与权限（登录 ≠ 什么都能做）

- **核心**：登录是确认"你是谁"，权限是确认"你能做什么"。登录通过，不代表这条数据你就能动。
- **要点**：
  - **垂直越权**：普通用户调用了本该只有管理员能用的接口（改别人角色、删后台数据）。
  - **水平越权**：人登录合法，却把链接里的订单号一改，就看到了别人的订单。
  - 很多项目只做了"要不要登录"，漏掉"登录之后能不能动这条数据"——水平越权大多这么来的。
- **对 AI 说**：请根据项目功能设计文档，输出系统权限设计表。每个接口都要说明：是否需要登录、允许哪些角色访问、是否只能操作自己的数据、管理员是否可以访问、权限判断在哪个文件或中间件处理、无权限时返回什么、有没有测试证明。
- **你看什么**：多角色项目（用户/商家/运营/管理员），权限要提前定清，别让 AI 每次现猜。

#### 04　会话与登录状态（那张「令牌」要管好）

- **核心**：登录之后，系统靠一张"令牌"认得你是谁。这张令牌要是管不好，等于钥匙配了一堆到处丢。
- **要点**：
  - **要有效期**：长期不失效，一次泄露就等于永久可用。
  - **退出登录、改密码后，旧令牌必须立刻失效**——这条最常被漏掉。
  - **别放在容易被偷的地方**：用 cookie 存的话，要开 `HttpOnly`、`Secure`、`SameSite` 这三个开关。
  - **优先用成熟方案**：让 AI 用所选框架或成熟认证库的会话机制，别自己造一套。
- **对 AI 说**：请审查当前登录状态（会话/令牌）的安全：令牌怎么生成、存在哪里、有效期多长、退出登录和修改密码后旧令牌是否立即失效、cookie 是否设置了 HttpOnly/Secure/SameSite、是否使用了框架或成熟认证库而不是自己实现。逐项说明现状，没做的标为未验证。
- **你看什么**：用没用成熟认证方案，"退出/改密码后旧令牌失效"这条尤其别漏。

#### 05　密码与账号（哈希存储 + 拦住弱密码）

- **核心**：攻击者不是手动猜密码，而是拿几百万条常见密码让程序批量试（暴力破解），123456 几秒就被试出来。
- **要点**：
  - **怎么存**：密码绝不能明文进数据库，必须先经过哈希（一种不可逆的处理）再存。数据库一旦泄露，明文密码等于直接公开。
  - **管理员尤其严**：它出影响的不是一个用户，是整个系统。
- **对 AI 说**：请审查当前后端的账号和密码安全规则。请说明注册、登录、修改密码、重置密码、创建管理员账号分别在哪里校验密码强度。请检查是否包含密码长度、字符组合、常见弱密码拦截、密码是否哈希存储（禁止明文保存）、登录失败次数限制、管理员账号额外要求。没有实现的项目标记为未验证，不要默认安全。
- **你看什么**：至少确认三件——密码规则存在、管理员账号有更严要求、后端真会拦弱密码。

#### 06　接口限流与防刷（别让人无限次调用）

- **核心**：接口默认是"不限量"的。有人写个脚本反复调用，就能猜密码、把你短信费刷爆、把服务器压垮。
- **要点**：
  - 登录、注册、找回密码、发短信/邮件验证码这些接口，必须限制同一账号、同一 IP 的请求频率。
  - 登录多次失败要锁一会儿，或加验证码。
  - 花钱、耗资源的操作（发短信、导出大数据、调用付费 AI）尤其要防刷。
- **对 AI 说**：请检查当前项目对登录、注册、找回密码、发送短信/邮件验证码，以及花钱或耗资源的接口，有没有做频率限制和防刷：是否限制单账号/单 IP 的调用频率、登录失败是否有锁定或验证码、短信邮件是否防轰炸。没做的请标出并给出方案。
- **你看什么**：至少登录和"发短信/验证码"两处要有限制——这两处最常被刷、最烧钱。

#### 07　注入（用户填的内容，别被当成命令执行）

- **核心**：注入的原理一句话——用户输入本该只是"数据"，却被后端当成"指令"执行了。
- **要点**：
  - 最典型是 **SQL 注入**：后端把用户填的内容直接拼进数据库查询语句，别人就能在输入框里填一段精心构造的内容，让数据库绕过登录、甚至拖走整张用户表。
  - 数据库之外，**系统命令、HTML、模板拼接**也有同类问题。
- **对 AI 说**：请检查当前接口是否存在注入风险。重点检查 SQL 注入、数据库查询注入、命令注入、HTML 或模板内容注入。请说明哪些位置使用了框架 ORM、参数化查询、白名单校验、内容转义或内容清洗；如果存在字符串拼接用户输入的情况，请标记为风险并给出修复方案。
- **你看什么**：别接受"已经过滤"。只让它讲清一件事——用的是框架/数据库自带的成熟方案，还是它自己临时写的过滤代码。后者还拍胸脯说安全，要特别警惕。

#### 08　文件上传（能上传东西的地方最危险）

- **核心**：只要你的应用能上传东西（头像、图片、附件），就是攻击者最爱的入口。
- **要点**：
  - **别只看后缀名**：改个文件名就能骗过去，要按文件的真实内容校验类型。
  - **限制大小**：防止一个超大文件把硬盘或服务撑爆。
  - **存到不能被当网页执行的地方**：别让别人上传一个伪装成图片的脚本，再访问它，让服务器把它跑起来。
  - **重命名**：别拿用户的原始文件名直接落地。
- **对 AI 说**：请审查当前文件上传功能的安全：是否只按后缀名判断类型（应按文件真实内容校验）、有没有大小限制、上传文件存在哪里、是否可能被当作脚本执行、是否重命名、访问时有没有权限控制。逐项说明，给出风险和修复。
- **你看什么**：最要命的一条——上传的文件绝不能被服务器当成程序执行。项目没有上传功能，这张可跳过。

#### 09　跨站与安全响应头（浏览器侧的坑）

- **核心**：这几项是浏览器侧的坑，好在大多能靠框架自带能力或几行配置解决，关键是别关掉、别配错。
- **要点**：
  - **CSRF（跨站请求伪造）**：别人诱导你在已登录状态下，悄悄替你发一个操作请求。用 cookie 登录的网站要防，优先用框架自带的 CSRF 防护，配合 SameSite cookie。
  - **安全响应头**：一组告诉浏览器"怎么更安全地对待你网站"的开关（如 CSP、HSTS），开启成本低、收益高。
  - **CORS（跨域）**：控制"哪些外部网站能调用你的接口"，别图省事设成"谁都能调"。
- **对 AI 说**：请检查当前项目的 CSRF 防护（尤其用 cookie 登录时，是否启用框架自带的 CSRF 防护和 SameSite cookie）、是否配置了常见安全响应头（如 CSP、HSTS）、CORS 跨域是否被设成允许任意来源。逐项说明现状和建议，优先使用框架自带能力。
- **你看什么**：别接受"为了方便先允许所有跨域"这种设置；能用框架自带就别自己造。纯后端接口项目，CSRF 这条按登录方式判断是否适用。

#### 10　外部请求（SSRF）（拿用户给的网址去访问要当心）

- **核心**：如果你的功能会"拿一个网址，让服务器去访问它"（按链接抓图、回调 webhook、调用外部接口），就要防 SSRF。
- **要点**：
  - **现象**：攻击者填一个指向你内部系统的地址，借你的服务器去访问本不该被外部碰到的内网资源。
  - 用户能填网址的地方，后端要用**白名单**（只允许访问指定域名），而不是黑名单。
  - **禁止访问内网地址和云服务器的"元数据地址"**。
- **对 AI 说**：我的项目里有没有"根据用户提供的网址，由服务器去请求"的功能（如抓取链接、上传网络图片、webhook、调用外部 API）？如果有，请检查是否存在 SSRF 风险：是否用白名单限制了可访问的域名、是否禁止访问内网和云元数据地址。逐项说明并给出修复。
- **你看什么**：没有"服务器去请求用户给的网址"这类功能，这张可跳过；有就必须用白名单。

#### 11　数据库操作（重要数据不能随便查、改、删）

- **核心**：数据库安全不止"能不能连上"，更要紧的是谁能查、谁能改、谁能删。
- **要点**：
  - **删除要谨慎**：用户、订单、支付记录这类数据，别直接物理删（真抹掉）；更稳的是**软删除**（只标记"已删除"，需要时能找回，很多框架自带 `deleted_at`）。
  - **多张表一起变动，必须用事务**：比如下单同时动订单、库存、优惠券——要么全成功要么全不算，不然会出现"订单建了、库存没扣"的烂账。
  - **操作必须绑业务规则**：能查到一条数据，不代表这个人有权操作它。
- **对 AI 说**：请审查当前后端数据库操作安全。请按数据表或数据模型列出：哪些是重要数据，哪些接口会读取它，哪些接口会修改它，哪些接口会删除它；每个操作是否经过身份校验、权限校验、数据归属校验和业务规则校验；是否存在直接根据前端传入 ID 修改或删除数据的情况；是否有软删除、事务或审计日志要求。
- **你看什么**：有没有"直接拿前端传来的 ID 就改/删数据"的情况——这正是水平越权的温床。

#### 12　业务逻辑与并发（功能跑通，也可能被钻规则空子）

- **核心**：有些漏洞不是"技术漏洞"，是业务规则没兜住——功能都跑通了，却被人钻了规则的空子。
- **要点**：
  - **金额、数量、积分后端要按真实规则重算**：别信前端传来的（比如有人把价格改成 0.01）。
  - **防重复提交和并发**：同一个"下单""领券""提现"被同时点很多次，会不会超卖、超额、重复扣款？要用事务、库存校验、幂等（同一操作做多次结果一样）兜住。
  - **关键步骤不能跳**：比如没付款就变成"已发货"。
- **对 AI 说**：请审查当前核心业务流程（下单、支付、退款、领券、提现等）的业务逻辑安全：金额/数量/库存是否由后端按业务规则重新校验、是否防止重复提交和并发导致的超卖/超额/重复扣款（事务、库存校验、幂等）、关键步骤能否被跳过。逐项说明并举例风险。
- **你看什么**：重点看"能不能重复提交""金额是不是后端说了算"——电商、支付类项目最容易栽在这。

#### 13　敏感数据保护（不止密码）

- **核心**：密码要哈希（前面讲了），但敏感数据不止密码——手机号、身份证、银行卡、聊天内容，传输和存储都要保护。
- **要点**：
  - **传输**：全站走 HTTPS（加密通道），别用明文传密码和隐私（证书在部署时落地）。
  - **存储**：身份证、银行卡这类高敏感数据，要么加密存，要么**脱敏**（只存部分）。
  - **最小收集**：用不到的敏感信息就别收集、别存，也别在接口里返回给前端。
- **对 AI 说**：请审查当前项目对敏感数据（密码、手机号、身份证、银行卡、支付信息等）的保护：传输是否强制 HTTPS、哪些敏感数据在数据库里是明文、是否需要加密或脱敏、接口返回给前端时有没有把不该给的敏感字段也带出去、有没有收集了其实用不到的敏感信息。逐项说明。
- **你看什么**：特别看"接口有没有把不该给前端的敏感字段也返回了"——这是最常见的泄露。

#### 14　别过度防御（安全不是把代码堆复杂）

- **核心**：一听"安全"，有的 AI 会滑向反面——给根本不可能发生的情况也写判断。
- **要点**：
  - 前面已强制登录，后面又反复判断"如果没登录怎么办"；这类永远走不到的分支叫**死代码**。
  - 它不增加一分安全，只会让代码更乱、把真正的业务逻辑淹没。
- **对 AI 说**：请审查当前接口安全逻辑是否存在过度防御。请区分：必须校验的业务规则、框架已经处理的基础校验、可以由前端体验层处理的提示校验，以及永远不会触发的防御分支（死代码）。不要为了安全感断增加重复判断或不可能成立的条件。任何新增安全封装都必须说明解决什么真实风险。
- **你看什么**：该严的地方（是否登录、是否有权限、金额库存是否合规）必须严；不该复杂的地方别乱加。

#### 15　配置与密钥（秘密绝不能写死在代码里）

- **核心**：AI 图方便，常把数据库地址、各种密钥、管理员初始密码直接写死在代码里。本地跑没事，代码一旦被提交、分享、部署，秘密就跟着暴露。
- **要点**：别人拿到数据库密码就能连库导数据，拿到支付密钥就能冒用你扣钱，而你很可能毫不知情。
- **对 AI 说**：请检查当前后端项目是否存在敏感配置写死在代码里的情况。重点检查数据库地址、数据库密码、登录令牌密钥（如 JWT）、第三方接口密钥、管理员初始密码、支付或通知相关密钥。请输出：配置名称、当前所在位置、是否来自环境变量、是否出现在代码或仓库中、是否登记在对应的配置示例文件（如 `.env.example`，具体按所用框架而定）、是否需要更换。
- **你看什么**：
  1. 真密钥绝不**出现在代码里**；
  2. 示例文件只写**占位**、不写真值；
  3. 代码从**环境变量**读配置；
  4. 之前写死过的密钥，让它明确回答要不要换掉。

#### 16　日志（别把敏感信息原样记下来）

- **核心**：日志本来是排查问题用的，但密码、token、手机号、身份证号、支付内容不该原样写进去——日志一泄露，等于又开一个口子。
- **要点**：关键功能还要**主动埋日志**（登录、注册、下单、支付、任何增删改重要数据），方便上线后出事排查。
- **对 AI 说**（查日志有没有泄露）：请审查当前后端日志安全。请说明请求日志、错误日志、数据库日志分别记录哪些内容，是否会记录密码、token、密钥、手机号、身份证号、支付信息等敏感数据。如果会记录，请说明如何脱敏或移除。请给出一条正常请求日志和一条错误日志示例。
- **对 AI 说**（给关键功能埋日志）：请在我这些关键功能上，加上必要的运行日志——登录、注册、下单、支付，以及所有涉及金额和重要数据的操作。记录关键步骤、传入的关键信息和最终结果，方便我上线后排查问题。**注意：日志里绝对不要打印密码、密钥这类敏感信息**。
- **你看什么**：哪些能记、哪些不能记、敏感内容有没有脱敏（如手机号只留前三位）。

#### 17　依赖安全（你用的框架和 SDK 本身也会爆漏洞）

- **核心**：漏洞不一定是你写错了，也可能是你用的那个库出了问题连累你。
- **要点**：
  - 比如 Log4j 当年爆出严重漏洞，攻击者能直接在服务器上运行命令，没及时升级的项目就一直暴露着。
  - AI 写代码用的往往是它知道的某个版本，它不会主动帮你盯这个库后来有没有爆新漏洞。
- **对 AI 说**：请列出当前后端项目用到的所有框架、第三方库和 SDK，以及各自的版本。请逐项说明：有没有已知的安全漏洞或安全公告，当前版本是不是官方建议升级的版本，如果需要升级，会影响哪些现有功能。请重点标出那些负责网络请求、登录认证、加密、文件上传、数据库连接的依赖。
- **你看什么**：升级别让 AI 随便来。先让它说清这次升级解决什么、会不会影响现有功能，确认了再升。

#### 18　清掉「墓碑代码」（临时接口是明晃晃的窟窿）

- **核心**：AI 做功能时常顺手留下调试打印、假数据、临时测试接口，而且它不会自己删——你不提，它就永远留着。
- **要点**：
  - 最危险的是**没有权限校验的临时接口**（能跳过登录、直接改数据），一旦跟着上线，别人能直接拿来操作你的数据。
  - 时机：功能写完、测试通过、你自己也用过确认没问题，之后再清。
- **对 AI 说**：这个功能已经开发完成，测试也通过了。请列出本次开发过程中，你为了调试、测试、临时验证而新增的代码，包括临时测试文件、调试打印、临时测试接口、写死的假数据、一次性脚本等。请逐项说明：它在哪个文件、最初做什么用、现在还需不需要。可以删的请删掉；不确定的先列出来让我决定。不要动正式的业务代码、正式的回归测试，以及我有意留在关键功能上、用来上线后排查问题的运行日志。
- **你看什么**：删完再跑一遍正式测试。别让它把该留的一起删了——正式回归测试、关键功能上的运行日志，都得留着。

#### 19　验收（让 AI 切换角色，测「出错会不会被拦」）

- **核心**：安全不能靠一句"已经处理了"。它不能只站在写代码的角度说"我写了校验"，还要站在没权限的人、发异常请求的人角度去试。
- **要点**：一个接口只能证明"正常请求跑得通"、却证明不了"错误请求会被拦住"，就不算验收完成。
- **对 AI 说**：请对本次新增或修改的接口做安全和业务双重验收。请输出：正常请求示例、参数错误示例、未登录示例、无权限示例、访问他人数据示例、数据库写入或修改前后的证据、日志记录证据。请说明哪些测试是通过接口完成，哪些测试是通过数据库检查完成。没有实际验证的项目标记为未验证。
- **你看什么**：有没有覆盖这几类——正常能用、出错会拦、没权限过不去、数据不越界、数据库结果对得上、关键过程日志能查到。

#### 20　上线前总检（一张清单从头过一遍）

- **核心**：临上线是最后一道关，最该绷紧的一根弦是——开发和上线，必须是两套环境。
- **要点**：
  - 连的数据库不同、用的密钥不同、域名分开，**生产环境的"调试模式"必须关掉**（不然一报错就把内部细节、敏感信息显示给所有访问的人看）。
  - 再核一遍：密钥没写死、测试全通过、临时接口和垃圾代码清干净、上线数据库没有测试数据、越权和注入、关键功能日志。
- **对 AI 说**：我准备把这个项目部署上线。请根据项目实际情况，帮我列一份上线前检查清单，并逐项检查、告诉我结果。至少包括：开发环境和生产环境是不是彻底分开（数据库、密钥、域名各用各的，生产环境的调试模式有没有关）、密钥和敏感配置有没有写死在代码里、所有测试是否全部通过、调试用的临时接口和垃圾代码有没有清理、上线数据库里有没有残留测试数据、有没有越权和注入风险、关键功能有没有加好必要的运行日志（且日志里不含密码密钥）。如果是 web 项目，还要检查多浏览器兼容性和前端性能体验。
- **你看什么**：这根弦松了后面再小心都白搭——开发的归开发，上线的归上线，绝不拿开发那套直接顶上去。

#### 21　一页速查（封底 / 合集图）

> 唯一保底动作：**任何一条 AI 的回答你看不懂，就让它用大白话重讲。看不懂的验收，等于没验收。**

| 板块 | 速查要点 |
|---|---|
| 接口输入 | 关键数据后端重新判断一遍 |
| 登录权限 | 登录 ≠ 能动这条数据，防垂直/水平越权 |
| 会话令牌 | 有有效期，退出/改密后旧令牌失效 |
| 密码账号 | 哈希存储、拦弱密码，管理员更严 |
| 限流防刷 | 登录、发短信/验证码必须限频 |
| 注入 | 用框架/数据库成熟方案，别信自造过滤 |
| 文件上传 | 按真实内容校验，上传物绝不能被执行 |
| 跨站跨域 | CSRF 用框架自带，别允许任意跨域 |
| SSRF | 服务器去请求用户给的网址，要用白名单 |
| 数据库 | 查改删绑业务规则，多表变动用事务 |
| 业务并发 | 金额后端说了算，防重复提交/超卖 |
| 敏感数据 | 传输走 HTTPS，别把敏感字段返回前端 |
| 过度防御 | 该严的严，别堆死代码 |
| 配置密钥 | 绝不写死在代码里 |
| 日志 | 不记敏感信息，关键功能埋日志 |
| 依赖 | 定期查漏洞，升级先评估 |
| 墓碑代码 | 清临时接口/假数据，别删回归测试和关键日志 |
| 验收 | 切换角色测"出错会不会被拦" |
| 上线前 | 开发/生产两套环境，调试模式必须关 |

## 第三部分　对我们（master-goods / 智慧记）项目开发的帮助

> 我们的项目是**进销存 + 财务**系统，涵盖商品、客户、供应商、订单、采购、销售、支付、库存、报表等模块。下面把这两份内容落到我们项目的具体场景里。

### 3.1 骨架屏——直接受益的场景

| 场景 | 当前问题 | 应该做的 |
|---|---|---|
| **销售单列表 / 采购单列表 / 库存列表** | 数据量大、查询慢，列表卡几秒才出来 | 用骨架屏先摆出"行结构"，等接口返回再替换 |
| **报表页面**（日销售、库存周转、利润分析） | 后端聚合运算耗时 1–3 秒 | 报表容器先出"图表骨架 + 数字占位"，避免空白屏 |
| **客户/商品详情页** | 接口串行加载（基本信息 + 应收 + 近期订单） | 顶部信息先出骨架，关联数据陆续补全 |
| **新增订单的"选商品"弹窗** | 弹窗打开瞬间空白，扫码再渲染 | 弹窗骨架预先画好"搜索框 + 列表行" |
| **AI 智能录入/识别** | AI 返回慢（2–5 秒） | 进度感用骨架 + 阶段文案，而不是 spinner |

**实现建议（按现有技术栈对齐）**：
- **Web 端**（`Code/frontend/web`，Vue + Vite）：抽一个 `<Skeleton />` 通用组件，结合 `loading` 状态；行/卡片/图表三种 variant。
- **Android 端**（`Code/frontend/android`，Compose）：用 `Modifier.shimmer()` 或 `pulse()` 动画 + 占位 Composable。
- **iOS 端**（`Code/frontend/ios/ZhihuijiIOS`）：用 `shimmer` 修饰符 + 占位 View。
- **不要在以下场景用骨架屏**：登录按钮 loading、保存订单的按钮内联 spinner、删除确认、扫码反馈——这些是"操作反馈"，不是"内容加载"。

### 3.2 安全自检——按我们项目现状直接对照

| 项 | 对应到 master-goods 的检查点 | 现状参考 |
|---|---|---|
| **02 接口输入** | 所有 `*Controller` 入参是否经过校验？我们后端有 `GlobalExceptionHandler` 兜底，但每个 Service 是否独立校验？ | `Code/backend/src/main/java/com/zhihuiji/backend/api/common/` 有 `ApiResponse` / `BusinessException` / `GlobalExceptionHandler` / `ParseUtils` |
| **03 登录与权限** | 多角色（用户/商家/运营/管理员）；是否在每个接口做"操作自己数据"的归属校验？ | 检查所有 `*Controller` 是否在服务层做了 `userId == resource.userId` 校验 |
| **04 会话令牌** | 用 JWT？token 有效期、改密后旧 token 是否失效？cookie 是否 `HttpOnly/Secure/SameSite`？ | 需要审计登录模块的 `JwtUtil` / Spring Security 配置 |
| **05 密码** | 密码是否 bcrypt 哈希？管理员账号有更强要求？ | 检查 `UserService` 注册 / 重置密码逻辑 |
| **06 限流防刷** | 登录、找回密码、发短信接口是否限流？ | 需要加 Redis 限流（如 Bucket4j） |
| **07 注入** | 用了 MyBatis/JPA 吗？有没有字符串拼 SQL？ | `Code/backend` 是 Spring Boot，应使用 JPA/MyBatis-Plus，避免 `${}` 直接拼接 |
| **08 文件上传** | 商品图片、客户头像、附件上传；是否按真实类型校验？ | 检查 `FileUploadController`（如有） |
| **09 跨站 / 响应头** | CSRF（管理后台 cookie 登录）、CSP、HSTS、CORS | 需在 Spring Security 中配齐 |
| **10 SSRF** | 是否有"按 URL 抓图"或 webhook 回调？ | 我们的项目基本不需要；如果有就上白名单 |
| **11 数据库操作** | 订单、库存、客户删除用软删？多表变动用事务？金额/库存后端重算？ | 检查 `*Service` 的删除/写入路径；核对 `OrderStatus` / `PayOrderStatus` 状态流转 |
| **12 业务并发** | 下单同时改订单+库存+优惠券是否事务？重复点"保存订单"会重复扣库存吗？ | 这是**智慧记最容易出问题的地方**——必须强校验 |
| **13 敏感数据** | 客户手机号、身份证、银行卡是否加密？接口是否把密码字段也返回？ | 检查 DTO 是否 `@JsonIgnore` 了敏感字段；DB 字段是否加密 |
| **15 配置密钥** | DB 密码、支付密钥、第三方接口密钥是否走环境变量？`.env.example` 是否只有占位？ | 检查 `application.yml` / `application.properties` 是否含明文密钥 |
| **16 日志** | 登录、下单、支付、改价、删客户是否埋日志？日志里有没有把密码/手机号明文写入？ | 检查 `Logger` / `logback-spring.xml` 配置；手机号只留前 3 位 |
| **17 依赖** | 跑 `mvn dependency-check:check` 或 OWASP Dependency-Check；Spring Boot / MyBatis / Jackson 等是否最新 | `Code/backend/gradlew` / `pom.xml` |
| **18 墓碑代码** | 上线前 grep `TODO` / `FIXME` / `System.out.println` / `@Test` 注释掉的代码 / 假数据 | 写一个 PR 检查脚本 |
| **19 验收** | 每个新接口要有：正常 / 参数错 / 未登录 / 无权限 / 越权访问他人数据 五种用例 | 已有 `Code/backend/src/test`，但需补充安全场景 |
| **20 上线前总检** | 开发和生产是两套环境、数据库/密钥/域名分开、生产 debug 模式关掉 | 检查 `application-prod.yml` / 部署脚本 |

### 3.3 立刻可落地的 3 件事

1. **骨架屏组件统一化（Web + Android + iOS 三端对齐）**  
   - 抽出 `<Skeleton variant="row|card|chart|avatar|text" />` 通用组件
   - 在 `loading` 状态时自动渲染；无数据时不要渲染骨架（避免和"空状态"混淆）
   - 列表/详情/报表三大场景优先

2. **把 21 项安全自检做成 PR 检查清单**  
   - 在 `Code/backend` 加一个 `docs/security-checklist.md`
   - 每个 PR 模板加上"安全自检 21 项"勾选
   - 关键项（02/03/04/05/07/11/12/15/16/20）设为必填

3. **登录与权限做一次专项审查**（最高 ROI）  
   - 智慧记多角色 + 多租户，最容易出水平越权
   - 用 03 项的"对 AI 说"提示词直接发给 AI，输出一份权限表
   - 重点核对：客户能不能改别人的客户、销售单能不能改别人的单、库存调整有没有归属校验

### 3.4 心智模型升级

| 之前 | 之后 |
|---|---|
| AI 默认给 spinner，我也跟着用 | 区分 spinner / 骨架屏 / 进度条 / 按钮 loader |
| 安全 = 框架能拦住就行 | 安全 = 21 项按清单逐项验证 |
| 后端靠 Spring Security 兜底 | 后端 = 入参校验 + 权限校验 + 业务规则校验 三层各自独立 |
| 日志 = 出错时打一下 | 日志 = 关键功能主动埋 + 敏感信息脱敏 |
| 上线 = 测试通过 + 部署 | 上线 = 20 项总检 + 开发/生产两套环境独立 |
