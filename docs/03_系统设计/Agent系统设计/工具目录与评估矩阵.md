这份文档对应服务器端 Agent 评测脚本
`testing/scripts/run_server_agent_all_tools.py`。当前源码注册 61 个 Agent 工具：46 个 `READ_ONLY`、15 个 `CREATE_ONLY`。数量只表示源码注册事实，尚未执行的评测不能写成通过。

评测时发送给模型的 `message` 只有表格里的用户问题，不附加测试编号、工具名或“请调用某工具”等指令。期望工具只存在于评测元数据和证据 JSON 的 `expected_tools` 字段中。一次问题允许调用多个工具；服务端会把它们放进同一个 `run_id`，按 `tool_sequence` 和 `tool_call_id` 保留顺序。

## 多工具问题

| 用户会怎么问 | 预计工具调用顺序 | 是否允许结构化展示 |
|---|---|---|
| 最近一周销售和回款帮我看一下，合适的话用图表示。 | `sales_overview_lookup` -> `result_visualization` | 是，模型主动选择后才展示 |
| 最近一周销售和现金流放在一起看下，合适的话用图展示。 | `sales_overview_lookup` -> `cashflow_summary_lookup` -> `result_visualization` | 是，模型主动选择后才展示 |
| 库存和补货一起帮我看，哪些要马上补？用合适的方式展示。 | `inventory_panorama_lookup` -> `smart_restock_lookup` -> `result_visualization` | 是，模型主动选择后才展示 |
| 客户欠款和供应商应付款一起算一下，重点对象用表格列出来。 | `customer_receivable_lookup` -> `supplier_payable_lookup` -> `result_visualization` | 是，模型主动选择后才展示 |

“预计顺序”是评测目标，不是强制脚本。模型可以调整同类只读查询的顺序，但必须选中所有与问题直接相关的工具，工具结果必须来自当前 owner 的真实数据库；没有真实数据时要如实返回空结果。普通文字问题不应调用 `result_visualization`。

### `image_generate` 工具契约

| 项目 | 约束 |
|---|---|
| 正式工具名/类型 | `image_generate` / `CREATE_ONLY` |
| 权限 | `agent:write`；由真实调用者和当前 owner/store 上下文计算 |
| 输入 | `prompt` 必填字符串，长度 1 至 2000；`reference_asset_ids` 可选正整数数组，最多 1 个；Schema `additionalProperties=false` |
| 工具阶段输出 | 创建 `agent_drafts(status=active)`，返回 `draft_card`、`draft_id`、`draft_type=image_generate`；不调用 Provider，不写正式业务表 |
| 确认输出 | `AgentDraftConfirmService` 路由至 `AgentImageService`；成功返回 `image_url` 与可选 `revised_prompt`，草稿置 `confirmed` |
| 拒绝/失败 | 拒绝置 `cancelled` 且正式业务表不变；Provider 未配置、错误、超时、取消或结果无效时不宣称成功，草稿保持可重试并记录安全错误 |
| 参考图 | 确认时按当前 owner 查询 `media_assets`，只接受 `image/*`；store 不能改变 owner 作用域 |
| 结果安全 | Provider `url`/`b64_json` 只进入受控响应；`b64_json`、完整 URL、提示词原文不进通用日志或审计摘要，不主动抓取不可信结果 URL |

`image_generate` 与 `POST /v2/agent/images/generate` 是两个调用面。前者由 `ToolPlanner`/`ToolExecutor` 选择并先落草稿；后者直接调用 `AgentImageService.generate`，受 `agent:write` 保护且不等于 AgentTool 已执行。REST 接口存在不能替代 Agent 工具注册、工具选择和草稿确认证据。

## 当前系统提示词

### 工具规划器：原生工具调用路径

当前 `ToolPlanner` 发给模型的核心系统提示词为：

```text
你是智慧记的工具规划器。根据用户问题选择最相关的只读查询工具或创建类工具。
只读工具直接返回查询结果；创建类工具生成草稿，需用户确认后才执行写入。
不允许生成 SQL，不允许访问其他账号数据。最多选择 6 个工具。当前是初始查询阶段，不要调用 result_visualization；查询结果返回后由下一轮模型根据真实事实决定是否调用。
```

可用工具定义由 `ToolRegistry` 动态生成，每个工具包含名称、描述和严格参数 Schema。若 provider 不支持原生工具调用，系统会使用同一规则的 JSON 规划路径：

```text
你是智慧记的工具规划器。你可以选择以下只读查询工具和创建类工具。
只读工具直接返回查询结果；创建类工具会生成草稿，需用户确认后才执行写入，不会直接修改数据。
不允许生成 SQL，不允许访问其他账号数据。
只输出 JSON，不要输出 Markdown。
tools 最多 6 个，必须来自可选工具。params 为该工具的查询参数，根据用户问题提取，无参数时省略 params 字段。
初始阶段不要调用 result_visualization；查询结果返回后，下一轮模型会根据真实事实决定是否调用它。
```

### 补充查询路径

```text
你是智慧记的工具规划器。根据用户问题与已查询结果，判断是否需要补充查询其他工具。
可选工具：<动态工具清单>
若已收集到足够信息回答用户问题，输出 {"tools":[]}。
只有已经执行过真实数据查询并且用户需要结构化展示时，才可以调用 result_visualization；它必须在真实查询之后执行，不能自己生成数据。
若需要补充查询，输出 {"tools":[{"name":"...","params":{...}}],"rationale":"..."}，最多 2 个补充工具。
只输出 JSON，不要输出 Markdown。
```

### 正式回答生成器

当前 `AnswerSynthesizer` 的正式回答提示词为：

```text
你是智慧记的正式回答生成器。请直接返回面向用户的自然语言正文，不要返回 JSON 信封、固定模板、占位符、内部字段或工具调用说明。
本轮工具结果是业务事实的唯一数据来源。只能根据这些结果回答；不得编造、估算、补全、重算或推测任何业务数据。
可以按用户问题组织简短解释、结论和建议，但建议不能伪装成工具查询结果；没有数据时要如实说明没有数据。
如果本轮已有独立的表格或图表结果块，正文只解释结果，不复制或重新设计表格、图表和数据块。
```

正式回答之后，服务端事实校验会拒绝空回答、JSON 信封、占位符、无工具事实支撑的数字，以及把结构化数据重新写进正文的内容。模型失败时保持失败状态，不能用服务端固定模板冒充模型回答。

## 证据要求

每个用例 JSON 至少保留：原始 `prompt`、`run_id`、`expected_tools`、实际 `tool_calls`、每次调用的 `tool_call_id`、`sequence`、参数摘要、结果摘要、耗时、正式回答、数据库前后计数和清理结果。`result_visualization` 只能在同一次 run 已经有真实业务查询成功后生效。
